# 10 프로세스 vs 스레드 · 동시성

[01](01-process-signal.md)이 "프로세스를 어떻게 다루나"였다면, 여기는 **"프로세스와 스레드가 뭐가 다르고, 동시에 여러 일을 하면 무슨 문제가 생기나"** 다.
CS 면접 1순위 질문이고, 실무로는 **"웹서버가 요청을 어떻게 동시에 처리하나"**, **"CPU는 한가한데 왜 느리지?"** 로 이어진다.

---

## 프로세스 vs 스레드

| | 프로세스 | 스레드 |
|---|---|---|
| 정의 | 실행 중인 프로그램 | 프로세스 **안에서** 실제로 일하는 실행 흐름 |
| 메모리 | **각자 독립된** 메모리 공간 | 같은 프로세스의 스레드끼리 **메모리(코드·데이터·힙)를 공유** |
| 각자 가진 것 | 메모리 전체, 파일 디스크립터 등 | **스택**, 레지스터(= 지금 어디까지 실행했나) |
| 만들기 · 전환 비용 | 무겁다 | 가볍다 |
| 통신 | 어렵다 (IPC: 파이프, 소켓, 공유메모리) | 쉽다 (그냥 같은 변수를 읽고 씀) |
| 하나가 죽으면 | **다른 프로세스는 멀쩡** | **프로세스 전체가 같이 죽음** |

> 비유: **프로세스 = 식당**, **스레드 = 그 식당의 요리사들.**
> 요리사들은 **주방(메모리)을 같이 쓴다** → 협업이 빠르지만 **같은 냄비를 동시에 잡으면 사고**가 난다.
> 식당끼리는 주방이 따로라 안전하지만, 재료를 주고받으려면 배달(IPC)을 해야 한다.

### 그래서 뭘 쓰나 — 실제 사례

| | 방식 | 이유 |
|---|---|---|
| **Chrome** | 탭마다 **프로세스** | 탭 하나가 죽어도 브라우저 전체는 안 죽게 (격리) |
| **nginx** | 소수의 워커 **프로세스** + 이벤트 루프 | CPU 코어 수만큼 워커, 각 워커가 수천 연결을 비동기로 |
| **Apache prefork / Gunicorn sync** | 요청마다 워커 **프로세스** | 격리는 좋지만 동시 처리 수 = 워커 수 |
| **Tomcat (Java)** | 요청마다 **스레드** (스레드 풀) | 가볍게 많이 처리, 대신 스레드 안전성을 챙겨야 함 |

> 리눅스 커널 입장에서는 스레드도 **"메모리를 공유하는 프로세스"** 일 뿐이다(둘 다 `task`). `ps -eLf`나 `top -H`로 스레드까지 볼 수 있다.

## 컨텍스트 스위칭

CPU 코어 하나는 **한 순간에 하나만** 실행한다. 여러 개가 동시에 도는 것처럼 보이는 건 **아주 빠르게 번갈아** 실행하기 때문이다.

**컨텍스트 스위칭** = 지금 실행 중인 것의 상태(레지스터, 어디까지 했나)를 **저장**하고, 다음 것의 상태를 **불러오는** 작업.

- 이 전환 자체는 **아무 일도 안 하는 순수 비용**이다.
- **스레드 전환이 프로세스 전환보다 싸다** — 같은 메모리를 쓰니까 메모리 주소 변환 정보(페이지 테이블)를 안 바꿔도 되고, 캐시(TLB)도 덜 날아간다. → [11](11-memory.md)

> 스레드를 **너무 많이** 만들면? CPU가 일보다 **전환에 시간을 더 쓴다.** 그래서 스레드를 요청마다 새로 만들지 않고 **스레드 풀**로 개수를 제한한다.

```bash
vmstat 1          # cs 열 = 초당 컨텍스트 스위칭 수, r 열 = CPU를 기다리는 작업 수
pidstat -w 1      # 프로세스별 스위칭 (cswch 자발적 / nvcswch 비자발적)
```

---

## 동시성 vs 병렬성

- **동시성 (Concurrency)**: 여러 일을 **번갈아 가며** 진행한다. 코어 1개로도 가능. → *"요리사 한 명이 라면 물 끓는 동안 김밥을 싼다"*
- **병렬성 (Parallelism)**: 여러 일을 **진짜 같은 순간에** 한다. 코어가 여러 개 필요. → *"요리사 두 명이 각자 요리한다"*

---

## CPU 바운드 vs I/O 바운드

| | CPU 바운드 | I/O 바운드 |
|---|---|---|
| 시간을 어디에 쓰나 | **계산** (암호화, 이미지 처리, 압축) | **기다리기** (DB 응답, 외부 API, 디스크) |
| 대부분의 웹 서버는? | | **여기** |
| 늘리면 좋은 것 | 코어 수만큼 프로세스/스레드 | **동시 처리 수** (스레드 풀 크기, 비동기) |

> **"CPU는 20%인데 응답이 느려요"** → 전형적인 I/O 바운드. CPU가 아니라 **무엇을 기다리는지**(DB 쿼리, 외부 호출, 커넥션 풀 대기)를 봐야 한다.

---

## 동기/비동기, 블로킹/논블로킹

- **블로킹**: 결과가 올 때까지 **그 자리에서 멈춰** 기다린다.
- **논블로킹 / 비동기**: 요청만 걸어두고 **다른 일을 하다가**, 결과가 오면 알림을 받아 처리한다.

nginx·Node.js는 **이벤트 루프** 방식이다. 스레드 하나가 수천 개 연결을 들고 있다가, **준비된 것만 골라서**(`epoll`) 처리한다. 기다리는 동안 스레드가 놀지 않으니 연결이 많아도 스레드를 많이 안 만든다.

> 대신 이벤트 루프 안에서 **CPU를 오래 쓰는 작업을 하면 전체가 멈춘다.** (한 명뿐인 요리사가 30분짜리 요리를 붙잡으면 모든 손님이 기다림)

## 동기화 문제 — 공유하면 생기는 사고

### 경쟁 상태 (Race Condition)

두 스레드가 `count = count + 1`을 동시에 하면:

```
스레드 A: count 읽음 (10)
스레드 B: count 읽음 (10)
스레드 A: 11 저장
스레드 B: 11 저장      ← 두 번 더했는데 11. 하나가 사라졌다
```

`count + 1`은 한 줄이지만 실제로는 **읽기 → 더하기 → 쓰기** 세 단계라서, 그 사이에 끼어들 틈이 있다.

→ 해결: **임계 구역(Critical Section)** 을 **한 번에 하나만** 들어가게 막는다.
- **뮤텍스 (Mutex)**: 열쇠가 **하나**. 들어간 사람만 연다. → *화장실 열쇠*
- **세마포어 (Semaphore)**: 열쇠가 **N개**. 동시에 N명까지. → *좌석 N개짜리 대기실*, **커넥션 풀**이 바로 이 개념

> 같은 문제가 **DB**에서도 똑같이 생긴다. "재고 1개 남았는데 두 명이 동시에 주문" → 트랜잭션 격리 수준과 락으로 푼다. → [12](12-database.md)

### 데드락 (Deadlock)

A는 자원1을 잡고 자원2를 기다리고, B는 자원2를 잡고 자원1을 기다린다 → **둘 다 영원히 대기.**

4가지 조건이 **모두** 성립할 때만 생긴다 → **하나만 깨면 막을 수 있다.**

| 조건 | 뜻 | 깨는 방법 |
|---|---|---|
| 상호 배제 | 자원을 한 번에 하나만 쓸 수 있다 | (보통 못 깸) |
| 점유 대기 | 하나 잡은 채로 다른 걸 기다린다 | 필요한 걸 **한 번에 다** 잡는다 |
| 비선점 | 남이 잡은 걸 뺏을 수 없다 | **타임아웃** 걸고 포기 |
| 순환 대기 | 서로 꼬리를 물고 기다린다 | **자원을 잡는 순서를 통일** ← 실무에서 제일 많이 씀 |

## 면접에서 이렇게 말한다

**Q. 프로세스와 스레드의 차이는?**
> 프로세스는 실행 중인 프로그램으로 각자 독립된 메모리 공간을 갖고, 스레드는 프로세스 안의 실행 흐름으로 같은 프로세스의 메모리를 공유하고 스택만 따로 가집니다. 그래서 스레드는 생성과 전환이 가볍고 데이터 공유가 쉽지만 동기화 문제가 생기고, 하나가 잘못되면 프로세스 전체가 죽습니다. 프로세스는 무겁지만 격리돼 있어서 Chrome이 탭마다 프로세스를 쓰는 이유가 그겁니다.

**Q. 컨텍스트 스위칭이 뭔가요?**
> CPU가 실행 중인 작업의 상태를 저장하고 다른 작업의 상태를 불러와 전환하는 과정입니다. 전환 자체는 실제 일을 하지 않는 오버헤드라서 스레드가 너무 많으면 전환 비용이 커집니다. 스레드끼리는 메모리를 공유해서 프로세스 전환보다 비용이 적습니다.

**Q. 멀티스레드에서 생기는 문제와 해결 방법은?**
> 여러 스레드가 공유 자원을 동시에 수정하면 경쟁 상태로 값이 꼬일 수 있습니다. 뮤텍스나 세마포어로 임계 구역에 한 번에 하나, 또는 N개만 들어가게 해서 해결합니다. 락을 잘못 쓰면 서로의 락을 기다리는 데드락이 생길 수 있어서, 락을 잡는 순서를 통일하거나 타임아웃을 거는 식으로 예방합니다.

**Q. 데드락 발생 조건은?**
> 상호 배제, 점유 대기, 비선점, 순환 대기 네 가지가 모두 성립해야 합니다. 하나만 깨면 되기 때문에 실무에서는 자원 획득 순서를 통일해서 순환 대기를 없애거나, 타임아웃으로 비선점을 깨는 방법을 주로 씁니다.

**Q. 서버 CPU는 낮은데 응답이 느립니다.**
> CPU를 쓰지 않고 뭔가를 기다리는 I/O 바운드 상황입니다. vmstat에서 wa(I/O 대기)가 높은지, D 상태 프로세스가 있는지 보고, 앱 쪽에서는 DB 슬로우 쿼리, 외부 API 응답 시간, 커넥션 풀이나 스레드 풀이 고갈돼서 요청이 대기 중인지를 확인합니다.
