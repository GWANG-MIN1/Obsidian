# 06 서브넷 · 라우팅 · NAT

**서브넷**은 IP 주소를 동네 단위로 나눈 것, **라우팅**은 "이 주소로 가려면 어느 문으로 나가야 하나"를 정하는 것, **NAT**은 문을 나갈 때 주소를 바꿔 쓰는 것이다.
MSP 면접에서는 거의 항상 **AWS VPC 설계**로 이어진다. "프라이빗 서브넷 EC2가 인터넷이 안 돼요"가 대표 질문.

---

## IP 주소와 서브넷 마스크

IPv4 주소는 **32비트**를 8비트씩 4칸으로 쓴 것이다. `10.0.1.25` = `00001010.00000000.00000001.00011001`

주소는 두 부분으로 나뉜다.
- **네트워크 부분** — "어느 동네"
- **호스트 부분** — "그 동네의 몇 번지"

어디까지가 동네인지 알려주는 게 **서브넷 마스크**이고, 그걸 짧게 쓴 게 **CIDR 표기(`/숫자`)** 다.

```
10.0.1.0/24   →  앞 24비트가 네트워크, 뒤 8비트가 호스트
마스크로 쓰면  →  255.255.255.0
```

---

## CIDR 계산 — 손으로 할 수 있어야 한다

**공식: 주소 개수 = 2^(32 − 프리픽스)**

| CIDR | 주소 개수 | 외우는 법 |
|---|---|---|
| `/16` | 65,536 | VPC 기본 크기로 자주 씀 |
| `/20` | 4,096 | |
| `/24` | 256 | 가장 흔한 서브넷. 세 번째 칸까지 고정 |
| `/26` | 64 | /24를 4등분 |
| `/28` | 16 | AWS 서브넷 최소 크기 |
| `/32` | 1 | **딱 그 IP 하나** (보안그룹에서 "내 IP만" 허용할 때) |

> 프리픽스가 **1 커지면 절반**, **1 작아지면 두 배**. /24=256 → /25=128 → /26=64 …

### 예제: `10.0.1.64/26`

- 주소 개수 = 2^(32−26) = **64개**
- 범위 = `10.0.1.64` ~ `10.0.1.127`
- 네트워크 주소 `.64`, 브로드캐스트 `.127` → 일반 네트워크에서 쓸 수 있는 호스트는 **62개**

### AWS는 서브넷마다 5개를 예약한다

| 주소 | 용도 |
|---|---|
| 첫 번째 (`.0`) | 네트워크 주소 |
| `.1` | VPC 라우터 |
| `.2` | DNS 서버 (AmazonProvidedDNS) |
| `.3` | 예비 |
| 마지막 (`.255`) | 브로드캐스트 (VPC는 브로드캐스트를 지원 안 하지만 예약) |

→ `/24` 서브넷에서 실제 쓸 수 있는 IP는 **256 − 5 = 251개**. 면접 단골 숫자다.

> EKS처럼 **Pod마다 VPC IP를 하나씩 쓰는** 환경에서는 서브넷을 작게 잡았다가 IP가 고갈되는 일이 흔하다. 그래서 서브넷 크기 계산이 실무에서 중요하다.

### 사설 IP 대역 (RFC 1918)

인터넷에서 직접 쓰이지 않는, 내부용으로 약속된 대역:

| 대역 | 범위 |
|---|---|
| `10.0.0.0/8` | 10.0.0.0 ~ 10.255.255.255 |
| `172.16.0.0/12` | 172.16.0.0 ~ 172.31.255.255 |
| `192.168.0.0/16` | 192.168.0.0 ~ 192.168.255.255 (집 공유기) |

> VPC 피어링·VPN·Transit Gateway로 네트워크를 연결하려면 **CIDR이 겹치면 안 된다.** 처음 VPC를 만들 때 회사 전체 대역 계획이 필요한 이유.

## 라우팅 — 어느 문으로 나갈까

패킷을 보낼 때 OS는 먼저 **"목적지가 내 서브넷 안인가?"** 를 본다.

- **같은 서브넷** → 게이트웨이 없이 **직접** 보낸다 (ARP로 상대 MAC 주소를 알아내서)
- **다른 서브넷** → **라우팅 테이블**을 보고 해당하는 게이트웨이로 보낸다. 해당 항목이 없으면 **기본 게이트웨이(`default`, `0.0.0.0/0`)** 로

```bash
$ ip route
default via 10.0.1.1 dev eth0          # 나머지는 전부 10.0.1.1로
10.0.1.0/24 dev eth0 proto kernel      # 내 서브넷은 직접
```

### Longest Prefix Match — 여러 개가 맞으면?

목적지가 여러 규칙에 해당하면 **가장 구체적인(프리픽스가 긴) 규칙**이 이긴다.

```
10.0.0.0/16   → local
10.0.5.0/24   → VPN 게이트웨이
0.0.0.0/0     → 인터넷
```

`10.0.5.9`로 가는 패킷은 세 규칙 모두 해당하지만 **/24가 가장 길어서 VPN으로** 간다. `0.0.0.0/0`은 길이 0이라 항상 **최후의 수단**이다.

## NAT — 주소를 바꿔 쓰기

사설 IP는 인터넷에서 통하지 않는다. 그래서 문을 나갈 때 누군가 **공인 IP로 바꿔줘야** 한다.

| | SNAT (Source NAT) | DNAT (Destination NAT) |
|---|---|---|
| 뭘 바꾸나 | **출발지** 주소 | **목적지** 주소 |
| 방향 | 안 → 밖 (**나가는** 연결) | 밖 → 안 (**들어오는** 연결) |
| 예 | 집 공유기, **AWS NAT Gateway** | 공유기 포트포워딩, **`docker run -p 8080:80`**, 로드밸런서, 쿠버네티스 Service |

**SNAT 동작 예** (집 공유기):
```
내 PC 192.168.0.10:51000 → 공유기가 출발지를 공인IP 1.2.3.4:40001 로 바꿔서 → 서버
서버 응답 → 1.2.3.4:40001 로 옴 → 공유기가 기록(NAT 테이블)을 보고 192.168.0.10:51000 으로 돌려줌
```

> 핵심: SNAT은 **안에서 먼저 시작한 연결의 응답만** 돌려보낼 수 있다. 밖에서 먼저 들어오는 연결은 공유기가 누구에게 줄지 모르니 버린다.
> → 이게 **"NAT Gateway 뒤의 서버는 밖에서 접속할 수 없다"** 의 원리다.

> 리눅스에서는 이걸 **iptables(netfilter)** 가 한다. Docker의 `-p` 옵션도, 쿠버네티스 kube-proxy도 결국 iptables DNAT 규칙을 만든다. (`sudo iptables -t nat -L -n`)

## AWS VPC로 옮기면

```
                    인터넷
                      │
              [Internet Gateway]
                      │
 ┌─ VPC 10.0.0.0/16 ──┼───────────────────────────────┐
 │  ┌ 퍼블릭 서브넷 10.0.1.0/24 ┐                        │
 │  │  ALB, Bastion, [NAT GW + EIP]                     │
 │  └───────────────────┬──────┘                        │
 │                      │ (나가는 트래픽만)               │
 │  ┌ 프라이빗 서브넷 10.0.2.0/24 ┐                      │
 │  │  앱 서버, DB                 │                      │
 │  └──────────────────────────────┘                      │
 └────────────────────────────────────────────────────────┘
```

| 서브넷 | 라우트 테이블 |
|---|---|
| 퍼블릭 | `10.0.0.0/16 → local`, **`0.0.0.0/0 → igw-xxx`** |
| 프라이빗 | `10.0.0.0/16 → local`, **`0.0.0.0/0 → nat-xxx`** |

> **"퍼블릭 서브넷"이라는 속성은 따로 없다.** 라우트 테이블에 **IGW로 가는 경로가 있으면 퍼블릭**, 없으면 프라이빗이다. 이 한 문장이 면접에서 강하다.

### IGW vs NAT Gateway

| | Internet Gateway | NAT Gateway |
|---|---|---|
| 역할 | VPC와 인터넷을 잇는 **문** | 프라이빗 서브넷의 **나가는 전용** 출구 |
| 방향 | **양방향** (공인 IP 가진 인스턴스는 밖에서 접속 가능) | **안 → 밖만** (SNAT) |
| 위치 | VPC에 1개 붙임 | **퍼블릭 서브넷**에 만들고 EIP를 붙임 |
| 비용 | 무료 | **시간당 + 처리 데이터(GB)당 과금** — 비용 질문 단골 |
| 가용성 | AWS가 알아서 | **AZ 단위** 리소스 → AZ마다 하나씩 두는 게 권장 |

> IGW도 사실 NAT을 한다. 인스턴스에 붙은 공인 IP는 OS 안에서는 안 보이고(`ip a`에는 사설 IP만), **IGW가 사설↔공인을 1:1로 바꿔준다.**

> 비용 팁: 프라이빗 서브넷에서 S3·DynamoDB로 가는 트래픽은 **Gateway VPC Endpoint**(무료)로 보내면 NAT GW 데이터 요금을 아낄 수 있다.

## "프라이빗 서브넷 EC2가 인터넷이 안 돼요" 확인 순서

`yum update`나 `curl https://...`가 **timeout** 난다면 ([05](05-tcp-handshake.md)의 timeout = 경로 문제):

1. **프라이빗 서브넷의 라우트 테이블**에 `0.0.0.0/0 → nat-xxx`가 있나?
2. **NAT GW가 퍼블릭 서브넷에** 있나? (프라이빗에 만들면 NAT GW 자신이 못 나감)
3. **NAT GW가 있는 서브넷의 라우트 테이블**에 `0.0.0.0/0 → igw-xxx`가 있나?
4. **보안그룹 아웃바운드**가 막혀 있지 않나? (기본값은 전체 허용)
5. **NACL** — NACL은 **stateless**라서 응답 트래픽도 따로 허용해야 한다. 아웃바운드 443만 열고 **인바운드 임시 포트(1024–65535)** 를 안 열면 응답이 못 돌아온다.
6. DNS 문제는 아닌가? `dig`로 이름이 풀리는지 → [07](07-dns.md)

> **보안그룹 vs NACL 한 줄**: 보안그룹은 **인스턴스 단위, stateful**(나간 요청의 응답은 자동 허용), NACL은 **서브넷 단위, stateless**(양방향 다 규칙 필요), 허용+거부 규칙 모두 가능.

## 면접에서 이렇게 말한다

**Q. `/24` 서브넷에서 쓸 수 있는 IP는 몇 개인가요? AWS에서는?**
> 2의 8승이라 256개이고, 일반 네트워크에서는 네트워크 주소와 브로드캐스트를 빼서 254개입니다. AWS는 서브넷마다 네트워크 주소, VPC 라우터, DNS, 예비, 브로드캐스트까지 5개를 예약해서 251개를 쓸 수 있습니다.

**Q. 퍼블릭 서브넷과 프라이빗 서브넷의 차이는?**
> 서브넷 자체의 속성이 아니라 라우트 테이블로 결정됩니다. 0.0.0.0/0이 Internet Gateway로 가면 퍼블릭, 그렇지 않으면 프라이빗입니다. 프라이빗 서브넷이 인터넷으로 나가야 하면 퍼블릭 서브넷에 둔 NAT Gateway로 기본 경로를 보냅니다.

**Q. NAT이 뭔가요? SNAT과 DNAT의 차이는?**
> 패킷의 IP 주소를 바꿔주는 기술입니다. SNAT은 출발지를 바꾸는 것으로, 사설 IP 서버가 공인 IP로 인터넷에 나갈 때 씁니다. DNAT은 목적지를 바꾸는 것으로, 공인 주소로 들어온 요청을 내부 서버로 전달하는 포트포워딩이나 로드밸런서, docker -p가 이 방식입니다.

**Q. Internet Gateway와 NAT Gateway의 차이는?**
> IGW는 VPC와 인터넷을 양방향으로 연결하는 관문이라, 공인 IP가 있는 인스턴스는 밖에서도 접속할 수 있습니다. NAT Gateway는 프라이빗 서브넷 인스턴스가 밖으로 나가는 것만 허용하고 밖에서 먼저 들어오는 연결은 받지 않습니다. NAT GW는 퍼블릭 서브넷에 두고, AZ 단위라 가용성을 위해 AZ마다 두며, 데이터 처리량만큼 비용이 나옵니다.

**Q. 프라이빗 서브넷의 EC2가 패키지 설치를 못 합니다.**
> 먼저 프라이빗 서브넷 라우트 테이블에 NAT Gateway로 가는 기본 경로가 있는지 보고, NAT GW가 퍼블릭 서브넷에 있고 그 서브넷이 IGW로 라우팅되는지 확인합니다. 그다음 보안그룹 아웃바운드와, stateless인 NACL에서 응답용 임시 포트가 인바운드로 열려 있는지 봅니다. 마지막으로 DNS 해석이 되는지도 확인합니다.

**Q. VPC CIDR은 어떻게 정하나요?**
> 나중에 피어링이나 VPN, Transit Gateway로 다른 VPC나 온프레미스와 연결할 수 있어서 대역이 겹치지 않게 계획합니다. 그리고 EKS처럼 Pod가 VPC IP를 쓰는 환경을 고려해 서브넷을 넉넉하게, AZ별로 퍼블릭과 프라이빗을 나눠서 잡습니다.
