# 13 가상화와 컨테이너

**VM은 컴퓨터를 통째로 흉내 내는 것**이고, **컨테이너는 컴퓨터 하나를 나눠 쓰면서 "나 혼자 쓴다"고 믿게 만드는 것**이다.
면접에서는 "VM과 컨테이너 차이"가 거의 무조건 나오고, 한 단계 더 들어가면 **"컨테이너는 리눅스의 무엇으로 만들어지나"** (namespace, cgroup)를 묻는다.

---

## 가상화 — 하이퍼바이저

**하이퍼바이저** = 물리 서버 하나 위에서 **여러 개의 가상 컴퓨터(VM)** 를 돌리게 해주는 소프트웨어. 각 VM은 **자기만의 OS(커널)** 를 가진다.

| | Type 1 (베어메탈) | Type 2 (호스트형) |
|---|---|---|
| 어디에 설치 | **하드웨어 바로 위** | 기존 OS(Windows, macOS) **위의 프로그램** |
| 성능 | 좋음 | 한 겹 더 거쳐서 느림 |
| 예 | **KVM, Xen, VMware ESXi, AWS Nitro** | VirtualBox, VMware Workstation |
| 용도 | 데이터센터, 클라우드 | 개발자 PC |

> **EC2 인스턴스 = AWS 하이퍼바이저(Nitro, KVM 기반) 위의 VM.** Nitro는 네트워크·스토리지 처리를 **전용 하드웨어 카드로 떼어내서** 하이퍼바이저 부담을 거의 없앴다. 그래서 VM인데도 베어메탈에 가까운 성능이 나온다.

---

## VM vs 컨테이너

```
VM                                       컨테이너
─────────────────────────────            ─────────────────────────────
App A    | App B    | App C              App A    | App B    | App C
Libs     | Libs     | Libs               Libs     | Libs     | Libs
게스트 OS | 게스트 OS | 게스트 OS            (게스트 OS 없음)
하이퍼바이저 (KVM, Nitro)                   컨테이너 런타임 (containerd)
                                         호스트 OS — 커널 하나를 모두가 공유
물리 하드웨어                               물리 하드웨어
```

| | VM | 컨테이너 |
|---|---|---|
| 커널 | **각자 따로** (게스트 OS) | **호스트 커널 하나를 공유** |
| 크기 | GB 단위 | MB 단위 |
| 시작 시간 | 분 단위 (OS 부팅) | **초 단위** (그냥 프로세스 시작) |
| 격리 강도 | **강함** (하드웨어 수준) | 상대적으로 약함 (커널을 같이 씀) |
| 다른 OS | 리눅스 서버 위에 **윈도우 VM 가능** | 리눅스 호스트 위엔 **리눅스 컨테이너만** |

> 핵심 문장: **"컨테이너는 가벼운 VM이 아니라, 격리된 프로세스다."**
> 호스트에서 `ps aux`를 치면 컨테이너 안 프로세스가 **그대로 보인다.** 그냥 리눅스 프로세스인데, 자기가 보는 세상이 좁혀져 있을 뿐이다.

> 커널을 공유하니까: 컨테이너 안에서 커널 취약점이 터지면 **호스트까지 위험하다.** 그래서 컨테이너를 **root로 돌리지 말고**, 권한을 최소로 준다. 강한 격리가 필요하면 **Firecracker**(Lambda, Fargate가 쓰는 초경량 VM) 같은 방식을 쓴다.

## 컨테이너를 만드는 리눅스 기능 3가지

### 1. Namespace — **무엇을 볼 수 있나** (시야 가리기)

프로세스에게 **자기만의 좁은 세상**을 보여준다.

| Namespace | 격리하는 것 | 그래서 컨테이너 안에서는 |
|---|---|---|
| **PID** | 프로세스 번호 | 내 앱이 **PID 1**로 보인다 → [01](01-process-signal.md) |
| **NET** | 네트워크 (인터페이스, IP, 포트, 라우팅) | 자기만의 `eth0`, IP, 포트 공간 → [06](06-subnet-routing-nat.md) |
| **MNT** | 파일시스템 마운트 | 이미지 내용이 `/`로 보인다 |
| **UTS** | 호스트 이름 | 자기만의 hostname |
| **IPC** | 프로세스 간 통신 | |
| **USER** | 사용자 ID | 안에서는 root(0)인데 밖에서는 일반 사용자로 매핑 가능 |

> 쿠버네티스 **파드 안의 컨테이너들은 NET namespace를 공유**한다. 그래서 같은 파드의 컨테이너끼리 `localhost`로 통신할 수 있다(사이드카 패턴).

### 2. cgroup — **얼마나 쓸 수 있나** (자원 제한)

프로세스 묶음이 쓸 수 있는 **CPU·메모리·I/O 양을 제한**한다.

- **메모리 limit**: 넘으면 **OOM Killer**가 컨테이너 안 프로세스를 죽인다 → `OOMKilled`, Exit 137 → [11](11-memory.md#컨테이너의-oomkilled)
- **CPU limit**: 넘으면 죽이지는 않고 **느리게 만든다(스로틀링).** "CPU 사용률은 낮아 보이는데 응답이 느린" 원인이 되기도 한다.

> 한 줄: **"namespace는 보이는 것을 제한하고, cgroup은 쓰는 양을 제한한다."**

```bash
docker run -m 512m --cpus 1 nginx          # cgroup으로 메모리 512MB, CPU 1개
docker stats                               # 컨테이너별 사용량
lsns                                       # 호스트의 namespace 목록
```

### 3. Union 파일시스템 (OverlayFS) — **이미지를 레이어로 쌓기**

```
[ 컨테이너 쓰기 레이어 ]   ← 실행 중 바뀌는 것 (컨테이너 지우면 사라짐)
[ COPY app.jar       ]   ← 읽기 전용
[ RUN apt install ... ]  ← 읽기 전용
[ FROM ubuntu        ]   ← 읽기 전용 (여러 이미지가 공유)
```

- Dockerfile **명령 한 줄 = 레이어 하나.** 같은 베이스 레이어는 디스크에 **한 번만** 저장하고 여러 이미지가 공유한다.
- **바뀌지 않은 레이어는 캐시**를 재사용한다 → Dockerfile에서 **자주 안 바뀌는 것(의존성 설치)을 위에, 자주 바뀌는 것(소스 코드)을 아래에** 둬야 빌드가 빠르다.
- 컨테이너 안에서 쓴 파일은 **맨 위 쓰기 레이어**에만 있어서, **컨테이너를 지우면 사라진다** → 남겨야 하는 데이터는 **볼륨**으로.

---

## 이미지 vs 컨테이너

- **이미지** = 읽기 전용 **설계도** (클래스)
- **컨테이너** = 그 이미지로 **실행한 것** (인스턴스). 이미지 하나로 컨테이너 여러 개.

---

## 컨테이너 운영에서 자주 나오는 것

| 상황 | 원인 | → |
|---|---|---|
| `docker stop`이 10초 걸리고 강제 종료됨 | 앱이 PID 1이라 SIGTERM 기본 동작이 없음, 또는 셸 형식 `CMD`로 셸이 시그널을 안 넘김 | [01](01-process-signal.md) |
| 컨테이너 앱에 밖에서 접속이 안 됨 | 앱이 `127.0.0.1`에 바인딩, 또는 `-p` 포트 매핑 누락 | [05](05-tcp-handshake.md) |
| `Exit Code 137` / `OOMKilled` | cgroup 메모리 limit 초과 | [11](11-memory.md) |
| 컨테이너 재시작하니 데이터가 사라짐 | 쓰기 레이어에 저장 → 볼륨 사용 | |
| 이미지가 1GB가 넘음 | 빌드 도구까지 포함 → **멀티스테이지 빌드**로 실행에 필요한 것만 | |

## 면접에서 이렇게 말한다

**Q. VM과 컨테이너의 차이는?**
> VM은 하이퍼바이저 위에서 각자 게스트 OS와 커널을 가지고 하드웨어 수준으로 격리됩니다. 컨테이너는 호스트 커널을 공유하고 namespace와 cgroup으로 격리된 프로세스라서, 훨씬 가볍고 초 단위로 시작됩니다. 대신 커널을 공유하기 때문에 격리 강도는 VM보다 약하고, 호스트와 다른 종류의 OS 커널은 쓸 수 없습니다.

**Q. 컨테이너는 어떻게 격리되나요?**
> 리눅스 커널 기능 두 가지로 만들어집니다. namespace로 프로세스가 볼 수 있는 범위를 제한해서 PID, 네트워크, 파일시스템, 호스트 이름 등을 독립적으로 보이게 하고, cgroup으로 CPU와 메모리 같은 자원 사용량을 제한합니다. 여기에 OverlayFS 같은 유니온 파일시스템으로 이미지를 레이어로 쌓아서 씁니다.

**Q. 하이퍼바이저 Type 1과 Type 2의 차이는?**
> Type 1은 하드웨어 위에 직접 설치되는 베어메탈 방식으로 KVM, ESXi, AWS Nitro 같은 게 있고 클라우드와 데이터센터에서 씁니다. Type 2는 기존 OS 위에 프로그램으로 설치되는 방식으로 VirtualBox 같은 게 있고, 한 겹을 더 거쳐서 성능이 떨어져 주로 개발용으로 씁니다.

**Q. 컨테이너에서 root로 실행하면 왜 위험한가요?**
> 컨테이너는 호스트 커널을 공유하기 때문에, 컨테이너 탈출 취약점이 있으면 컨테이너 안의 root가 호스트의 root가 될 수 있습니다. 그래서 Dockerfile에서 USER로 일반 사용자를 지정하고, 불필요한 capability를 제거하고, 파일시스템을 읽기 전용으로 두는 식으로 권한을 최소화합니다.

**Q. Dockerfile 빌드가 매번 오래 걸립니다.**
> 레이어 캐시가 깨지고 있을 가능성이 큽니다. 소스 코드를 복사한 뒤에 의존성을 설치하면 코드 한 줄만 바뀌어도 의존성 설치부터 다시 합니다. 의존성 정의 파일만 먼저 복사해서 설치하고, 소스 코드는 그 뒤에 복사하도록 순서를 바꾸면 의존성 레이어는 캐시를 재사용합니다. 이미지 크기는 멀티스테이지 빌드로 줄입니다.
