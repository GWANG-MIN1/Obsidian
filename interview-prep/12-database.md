# 12 데이터베이스 — 인덱스 · 트랜잭션 · 복제

DB 면접 질문은 세 덩어리다. **"왜 빠른가(인덱스)"**, **"왜 안 꼬이나(트랜잭션)"**, **"어떻게 안 죽나(복제)"**.
MSP에서는 DB를 직접 튜닝하기보다 **RDS를 어떻게 구성하고, 느려졌을 때 어디를 보나**를 묻는 경우가 많다.

---

## 인덱스 — 책 뒤의 "찾아보기"

인덱스가 없으면 `WHERE email = 'a@b.com'`을 찾으려고 **테이블 전체를 처음부터 끝까지** 읽는다(Full Table Scan).
인덱스는 **"email 값 → 그 행의 위치"** 를 **정렬해서** 따로 저장해 둔 것이다. 책 뒤의 찾아보기처럼 바로 해당 페이지로 간다.

### 왜 B-Tree인가

대부분의 DB 인덱스는 **B-Tree(B+Tree)** 다.

```
             [  50  ]
           /         \
    [ 20 | 35 ]    [ 70 | 90 ]
    /   |   \       /   |   \
  (..) (..) (..)  (..) (..) (..)   ← 리프: 정렬된 값 + 행 위치, 옆으로 연결돼 있음
```

- **정렬돼 있어서** `=` 뿐 아니라 **범위 검색**(`BETWEEN`, `>`, `ORDER BY`)에도 쓸 수 있다.
- 트리가 **낮고 넓어서** 수억 건이어도 **3~4번만 내려가면** 찾는다. (디스크를 읽는 횟수 = 트리 높이)
- 해시 인덱스는 `=`는 더 빠르지만 **범위 검색을 못 한다.** 그래서 기본이 B-Tree.

### 인덱스는 공짜가 아니다

- **쓰기가 느려진다**: INSERT/UPDATE/DELETE 할 때마다 인덱스도 같이 고쳐야 한다.
- **공간을 먹는다.**
- 그래서 **"모든 컬럼에 인덱스"는 답이 아니다.** 자주 검색·조인·정렬하는 컬럼에, **값이 다양한(카디널리티 높은)** 컬럼에 건다. (성별처럼 값이 2~3개뿐인 컬럼은 효과가 적다)

### 인덱스가 있는데도 안 타는 경우

| 쿼리 | 왜 안 타나 |
|---|---|
| `WHERE LOWER(email) = ...` | 컬럼을 **함수로 가공**하면 정렬 순서가 깨진다 |
| `WHERE name LIKE '%민'` | **앞이 와일드카드**면 어디서부터 찾을지 모른다 (`'김%'`는 됨) |
| `WHERE phone = 01012345678` (컬럼은 문자열) | **타입이 달라서** 내부 형변환 |
| 복합 인덱스 `(a, b)`인데 `WHERE b = ...`만 | 복합 인덱스는 **앞 컬럼부터** 써야 한다 (전화번호부는 성으로 정렬 후 이름으로 정렬) |

```sql
EXPLAIN ANALYZE SELECT * FROM members WHERE email = 'a@b.com';
-- Seq Scan이면 전체 스캔, Index Scan이면 인덱스 사용
```

## 트랜잭션과 ACID

**트랜잭션** = **"전부 되거나, 전부 안 되거나"** 로 묶인 작업 단위.
계좌이체: A에서 만 원 빼기 + B에 만 원 넣기. 중간에 서버가 죽으면? **둘 다 없던 일**이 되어야 한다.

| | 뜻 | 쉬운 말 |
|---|---|---|
| **A**tomicity 원자성 | 전부 성공 or 전부 취소 (ROLLBACK) | 반쯤 된 상태는 없다 |
| **C**onsistency 일관성 | 규칙(제약조건)을 항상 지킨다 | 잔고가 음수가 되는 일은 없다 |
| **I**solation 격리성 | 동시에 도는 트랜잭션끼리 간섭하지 않는다 | 남이 하다 만 걸 보지 않는다 |
| **D**urability 지속성 | COMMIT된 건 서버가 죽어도 남는다 | 디스크의 로그(WAL)에 먼저 쓰고 성공 응답 |

### 격리 수준 — 얼마나 철저하게 떼어놓나

완벽하게 격리하면 **느리다** (다 줄 세워야 하니까). 그래서 **어느 정도까지 허용할지** 단계를 고른다.

| 격리 수준 | Dirty Read | Non-Repeatable Read | Phantom Read | 비고 |
|---|---|---|---|---|
| Read Uncommitted | 생김 | 생김 | 생김 | 거의 안 씀 |
| **Read Committed** | - | 생김 | 생김 | **PostgreSQL, Oracle 기본** |
| **Repeatable Read** | - | - | (생길 수 있음) | **MySQL InnoDB 기본** |
| Serializable | - | - | - | 가장 안전, 가장 느림 |

- **Dirty Read**: 남이 **아직 COMMIT 안 한** 값을 읽음 → 그쪽이 ROLLBACK하면 **없던 값**을 본 셈
- **Non-Repeatable Read**: 같은 행을 두 번 읽었는데 **그 사이 남이 수정·커밋**해서 값이 다름
- **Phantom Read**: 같은 조건으로 두 번 조회했는데 **그 사이 남이 행을 추가**해서 행 수가 다름

### 동시성 사고 막기 — 락

"재고 1개인데 두 명이 동시에 주문" 같은 경쟁 상태는 DB에서도 똑같다. → [10](10-process-thread.md#동기화-문제--공유하면-생기는-사고)

```sql
-- 비관적 락: 읽을 때부터 잠가서 남이 못 건드리게
SELECT stock FROM products WHERE id = 1 FOR UPDATE;
UPDATE products SET stock = stock - 1 WHERE id = 1;

-- 원자적 조건부 갱신: 조건 확인과 차감을 한 문장으로
UPDATE products SET stock = stock - 1 WHERE id = 1 AND stock > 0;   -- 영향받은 행이 0이면 품절
```

> 락을 서로 다른 순서로 잡으면 **데드락**이 난다. DB는 이걸 감지해서 한쪽을 강제로 ROLLBACK 시킨다 → 앱은 **재시도**할 수 있어야 한다.

## 정규화 vs 반정규화

- **정규화**: 같은 정보를 **한 곳에만** 저장하도록 테이블을 쪼갠다. 수정할 때 한 곳만 고치면 된다 (이상 현상 방지). 대신 조회할 때 **JOIN이 많아진다.**
- **반정규화**: 조회 성능을 위해 **일부러 중복 저장**한다. 읽기는 빨라지지만 **여러 곳을 같이 고쳐야** 한다.

> 기본은 정규화, **실제로 느린 조회가 확인되면** 그 부분만 반정규화. (NoSQL인 DynamoDB는 처음부터 **조회 패턴에 맞춰** 중복 저장하는 설계를 한다)

## RDB vs NoSQL

| | RDB (MySQL, PostgreSQL) | NoSQL (DynamoDB, MongoDB, Redis) |
|---|---|---|
| 스키마 | **고정** (테이블, 컬럼) | 유연 |
| 관계 · JOIN | 강력 | 약하거나 없음 |
| 트랜잭션 | 강력 (ACID) | 제한적인 경우가 많음 |
| 확장 | 주로 **수직 확장**(더 큰 서버), 읽기는 리플리카로 | **수평 확장**(서버 추가)이 쉬움 |
| 잘 맞는 곳 | 결제, 주문, 회원 — **정합성이 중요** | 세션, 캐시, 로그, 대량 트래픽의 단순 조회 |

## 복제와 고가용성 — AWS RDS로 말하기

| | **Multi-AZ** | **Read Replica** |
|---|---|---|
| 목적 | **고가용성** (안 죽게) | **읽기 성능** (부하 분산) |
| 복제 방식 | **동기** — 대기 DB에도 써져야 커밋 완료 | **비동기** — 약간 늦게 따라감 (**복제 지연**) |
| 대기 DB로 읽기? | **불가** (그냥 대기만) | **가능** (그게 목적) |
| 장애 시 | **자동 페일오버** (DNS 엔드포인트가 대기 DB로 바뀜, 보통 1~2분) | 자동 전환 안 됨 (수동 승격) |

> 한 줄: **"Multi-AZ는 보험, Read Replica는 분점."**

> **복제 지연 함정**: 쓰기는 Primary에, 읽기는 Replica로 보내면 **"방금 저장했는데 목록에 안 보여요"** 가 생긴다. 쓴 직후 바로 읽어야 하는 조회는 Primary에서 읽는다.

> 페일오버는 **DNS가 바뀌는 것**이라, 앱이 IP를 캐싱하거나 오래된 커넥션을 붙잡고 있으면 복구가 늦다. → [07](07-dns.md)

### 커넥션 풀

DB 연결을 맺는 건 비싸다 (TCP 핸드셰이크 + 인증). 그래서 **미리 연결을 몇 개 만들어 두고 돌려 쓴다.** → [05](05-tcp-handshake.md)
- 풀이 **너무 작으면**: 요청이 연결을 기다리며 줄 선다 → CPU는 낮은데 느림
- 풀이 **너무 크면**: 서버 대수 × 풀 크기가 DB의 `max_connections`를 넘어서 **`too many connections`**. 오토스케일링으로 서버가 늘 때 특히. (Lambda처럼 수가 확 늘어나는 경우엔 **RDS Proxy**)

## "DB가 느려요" 볼 순서

1. **슬로우 쿼리 로그** / RDS **Performance Insights** — 어떤 쿼리가 시간을 먹나
2. 그 쿼리를 **`EXPLAIN`** — 인덱스를 타나, 전체 스캔인가
3. **락 대기** — 누가 누구를 막고 있나 (`pg_stat_activity`, `SHOW PROCESSLIST`)
4. **커넥션 수** — 풀 고갈 or `max_connections` 도달
5. **리소스** — CPU, 메모리(버퍼 캐시 적중률), 디스크 IOPS (gp2의 버스트 크레딧 소진 등)

## 면접에서 이렇게 말한다

**Q. 인덱스가 뭐고 왜 빠른가요?**
> 특정 컬럼 값과 행 위치를 정렬해서 따로 저장한 자료구조입니다. 대부분 B-Tree로 구현되는데, 트리가 낮고 넓어서 몇 번의 탐색만으로 원하는 값을 찾을 수 있고, 정렬돼 있어서 범위 검색이나 정렬에도 쓸 수 있습니다. 다만 쓰기 때마다 인덱스도 갱신해야 해서 쓰기 성능과 공간을 희생하기 때문에, 자주 조회하고 카디널리티가 높은 컬럼에 선택적으로 겁니다.

**Q. 인덱스를 걸었는데 안 탑니다.**
> EXPLAIN으로 실행 계획을 먼저 봅니다. 흔한 원인은 컬럼에 함수를 씌웠거나, LIKE에서 앞에 와일드카드를 썼거나, 타입이 달라 형변환이 일어났거나, 복합 인덱스의 첫 번째 컬럼을 조건에 안 쓴 경우입니다. 조회 대상이 테이블 대부분이면 옵티마이저가 일부러 전체 스캔을 고르기도 합니다.

**Q. 트랜잭션과 ACID를 설명해주세요.**
> 트랜잭션은 전부 성공하거나 전부 취소되는 작업 단위입니다. 원자성은 중간 상태가 없다는 것, 일관성은 제약조건이 항상 지켜진다는 것, 격리성은 동시에 실행되는 트랜잭션끼리 간섭하지 않는다는 것, 지속성은 커밋된 데이터는 장애가 나도 남는다는 것입니다.

**Q. 트랜잭션 격리 수준에 대해 설명해주세요.**
> 동시에 실행되는 트랜잭션을 얼마나 격리할지의 단계입니다. Read Uncommitted, Read Committed, Repeatable Read, Serializable 순으로 격리가 강해지고 성능은 떨어집니다. 커밋 안 된 데이터를 읽는 Dirty Read, 같은 행을 다시 읽었을 때 값이 바뀌는 Non-Repeatable Read, 행 수가 바뀌는 Phantom Read를 단계별로 막습니다. PostgreSQL은 Read Committed, MySQL InnoDB는 Repeatable Read가 기본입니다.

**Q. RDS Multi-AZ와 Read Replica의 차이는?**
> Multi-AZ는 고가용성 목적으로, 다른 AZ의 대기 인스턴스에 동기 복제하고 장애 시 자동으로 페일오버합니다. 대기 인스턴스는 읽기에 쓸 수 없습니다. Read Replica는 읽기 성능 확장 목적으로 비동기 복제라 약간의 지연이 있고, 읽기 트래픽을 분산하는 데 씁니다. 그래서 쓰고 바로 읽어야 하는 조회는 Primary에서 읽어야 합니다.

**Q. 갑자기 `too many connections` 에러가 납니다.**
> DB의 max_connections에 도달한 겁니다. 오토스케일링으로 앱 서버가 늘면서 서버 수 곱하기 커넥션 풀 크기가 한도를 넘었거나, 앱이 커넥션을 반납하지 않는 누수일 수 있습니다. 현재 연결을 어느 호스트가 몇 개 잡고 있는지 확인하고, 풀 크기를 조정하거나 RDS Proxy 같은 커넥션 풀러를 앞에 둡니다.
