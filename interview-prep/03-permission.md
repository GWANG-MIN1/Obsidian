# 03 퍼미션

리눅스는 여러 사람이 한 서버를 같이 쓰는 걸 전제로 만들어졌다. 그래서 모든 파일에
**"누가(소유자·그룹·나머지) 무엇을(읽기·쓰기·실행) 할 수 있는가"** 가 적혀 있다.
"Permission denied" 장애를 스스로 풀 수 있느냐가 면접에서 보는 포인트다.

---

## ls -l 한 줄 읽기

```
-rwxr-xr--  1  gwangmin  dev  4096  Sep 22 10:00  deploy.sh
│└┬┘└┬┘└┬┘     └──┬───┘ └┬┘
│ │  │  │         소유자   그룹
│ │  │  └ 나머지(others) 권한: r--
│ │  └─── 그룹(group) 권한:    r-x
│ └────── 소유자(user) 권한:   rwx
└──────── 파일 종류: - 일반파일, d 디렉토리, l 심볼릭링크
```

권한은 **세 칸 × 세 글자**다.

- **누구에게?** 소유자(**u**ser) / 그룹(**g**roup) / 나머지(**o**thers)
- **무엇을?** 읽기(**r**ead) / 쓰기(**w**rite) / 실행(e**x**ecute)

> 판정 순서: 내가 소유자면 **소유자 칸만** 본다. 소유자가 아니고 그룹에 속하면 **그룹 칸만**, 둘 다 아니면 **나머지 칸**.
> "소유자 칸은 막혀 있지만 나머지 칸은 열려 있으니 되겠지"가 **안 된다**는 점이 헷갈리기 쉽다.

---

## 파일 vs 디렉토리 — rwx의 뜻이 다르다 (면접 포인트)

| 권한 | 파일에서 | 디렉토리에서 |
|---|---|---|
| `r` | 내용 읽기 | 안에 **어떤 이름이 있는지 목록 보기** (`ls`) |
| `w` | 내용 수정 | 안에 파일 **만들기, 지우기, 이름 바꾸기** |
| `x` | 프로그램으로 실행 | **안으로 들어가기/통과하기** (`cd`, 경로 지나가기) |

디렉토리는 결국 **"이름 → inode" 목록표**라는 걸 떠올리면 이해된다 ([02 파일시스템](02-filesystem.md)).
- `r` = 목록표를 **읽을** 수 있음
- `w` = 목록표를 **고칠** 수 있음 (= 파일 추가·삭제)
- `x` = 목록표를 **이용해서 안의 파일을 찾아갈** 수 있음

여기서 나오는 반직관적인 사실 두 개:

> **1. 파일을 지우는 권한은 파일이 아니라 "디렉토리"에 있다.**
> 파일 권한이 `r--`(읽기 전용)여도, 그 파일이 있는 **디렉토리에 `w`와 `x`가 있으면 지울 수 있다.**
> 삭제는 "목록표에서 이름을 지우는 것"이니까.
>
> **2. 경로 중간 디렉토리 하나라도 `x`가 없으면 그 안의 파일은 못 연다.**
> `/home/app/config/db.conf`를 열려면 `/`, `/home`, `/home/app`, `/home/app/config` **전부에 `x`** 가 있어야 한다.
> 파일 권한이 `777`이어도 중간이 막히면 Permission denied다.

```bash
namei -l /home/app/config/db.conf   # 경로의 모든 단계 권한을 한 번에 보기 (범인 찾기 좋음)
```

## 숫자로 쓰기 (8진수)

각 글자에 점수를 매겨서 더한다.

| r | w | x |
|---|---|---|
| 4 | 2 | 1 |

| 숫자 | 글자 | 뜻 |
|---|---|---|
| 7 | `rwx` | 전부 |
| 6 | `rw-` | 읽기+쓰기 |
| 5 | `r-x` | 읽기+실행 |
| 4 | `r--` | 읽기만 |
| 0 | `---` | 아무것도 못 함 |

자주 쓰는 조합은 외워두자.

| 값 | 의미 | 어디에 |
|---|---|---|
| `755` | 나는 전부, 남들은 읽고 실행만 | 디렉토리, 실행 스크립트 |
| `644` | 나는 읽고 쓰기, 남들은 읽기만 | 일반 파일 |
| `700` | 나만 전부 | `~/.ssh` 디렉토리 |
| `600` | 나만 읽고 쓰기 | SSH 개인키, 비밀번호 담긴 설정 |
| `400` | 나만 읽기 | AWS에서 받은 `.pem` 키 |

```bash
chmod 755 deploy.sh        # 숫자로
chmod u+x deploy.sh        # 글자로: 소유자에게 실행 권한 추가
chmod go-w config.conf     # 그룹·나머지에서 쓰기 권한 제거
chown app:app /data        # 소유자:그룹 바꾸기
chown -R app:app /data     # 하위 전부
```

> **`chmod 777`은 해결책이 아니다.** 아무나 수정·실행할 수 있게 되는 거라 보안 사고의 원인이 된다.
> 면접에서 "안 되면 777 줍니다"라고 하면 감점이다. **누가(어떤 사용자로 실행되는 프로세스가) 접근하는지** 확인하고 그 사용자에게 필요한 만큼만 준다.

## SSH 키 퍼미션 (실무 단골)

EC2 접속할 때 이런 에러를 본 적 있을 것이다.

```
WARNING: UNPROTECTED PRIVATE KEY FILE!
Permissions 0644 for 'my-key.pem' are too open.
```

SSH는 **개인키가 남에게도 읽히는 상태면 일부러 사용을 거부**한다. "이미 새어 나갔을 수도 있는 키"로 보기 때문.

```bash
chmod 400 my-key.pem       # 나만 읽기
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
```

서버 쪽 `~/.ssh`나 `authorized_keys` 권한이 너무 열려 있어도 키 로그인이 거부될 수 있다.

## umask — 새 파일의 기본 권한

새 파일을 만들 때 권한이 자동으로 정해지는 규칙이다.

- 시작값: 파일 `666`, 디렉토리 `777` (파일은 보안상 처음부터 실행 권한을 안 줌)
- 여기서 **umask에 적힌 권한을 가린다(뺀다)**
- 보통 umask는 `022` → "그룹과 나머지에게서 쓰기(2)를 빼라"

```
파일:     666 - 022 = 644  (rw-r--r--)
디렉토리: 777 - 022 = 755  (rwxr-xr-x)
```

```bash
umask        # 현재 값 확인
```

> 정확히는 빼기가 아니라 **"해당 비트를 꺼버리는 것"** 이다. 022처럼 흔한 값에서는 결과가 같아서 빼기로 기억해도 된다.
> (예: umask `033`이면 파일은 `644`가 된다. 666-033=633이 아니다 — 원래 없던 실행 비트는 뺄 게 없으니까.)

## 특수 권한 3종

| 이름 | 숫자 | 표시 | 쉬운 뜻 | 대표 예 |
|---|---|---|---|---|
| **setuid** | 4 | 소유자 x 자리에 `s` | 실행하는 동안 **파일 주인의 권한으로** 실행된다 | `/usr/bin/passwd` |
| **setgid** | 2 | 그룹 x 자리에 `s` | 디렉토리에 걸면, 안에 만든 파일이 **디렉토리의 그룹을 물려받는다** | 팀 공유 폴더 |
| **sticky bit** | 1 | 나머지 x 자리에 `t` | 디렉토리 안에서 **자기 파일만 지울 수 있다** | `/tmp` |

```bash
ls -ld /tmp              # drwxrwxrwt  ← 끝의 t
ls -l /usr/bin/passwd    # -rwsr-xr-x  ← 소유자 칸의 s
chmod 1777 /shared       # sticky 걸기
chmod 2775 /team         # setgid 걸기
```

**왜 passwd에 setuid가?**
비밀번호는 `/etc/shadow`에 저장되고, 이 파일은 root만 쓸 수 있다. 그런데 일반 사용자도 자기 비밀번호는 바꿀 수 있어야 한다.
→ `passwd`에 setuid를 걸어두면, 누가 실행하든 **실행하는 동안만 root 권한**으로 돌아서 `/etc/shadow`를 수정할 수 있다.

**왜 /tmp에 sticky bit가?**
`/tmp`는 누구나 파일을 만들어야 하니까 `777`이다. 그런데 그러면 **남의 파일도 지울 수 있게 된다**(삭제 권한은 디렉토리 `w`에 있으니까).
→ sticky bit를 걸면 "쓰기는 누구나, **지우기는 자기 파일만**"이 된다.

> setuid는 편리하지만 위험하다. setuid가 걸린 프로그램에 버그가 있으면 **일반 사용자가 root 권한을 얻는 통로**가 된다.
> 보안 점검 때 `find / -perm -4000 2>/dev/null`로 setuid 파일 목록을 확인하는 이유다.

## root와 sudo

- **root(UID 0)** 는 파일 권한 검사를 대부분 **무시**한다. 그래서 root로 작업하다 실수하면 막아줄 게 없다.
- 그래서 평소에는 일반 계정으로 일하고, 필요할 때만 **`sudo`** 로 잠깐 root 권한을 빌린다.
  - 누가 언제 뭘 했는지 **로그가 남고** (`/var/log/secure` 또는 `/var/log/auth.log`)
  - `/etc/sudoers`로 **사람마다 허용 명령을 제한**할 수 있다 (편집은 반드시 `visudo`로)

## 면접에서 이렇게 말한다

**Q. 755와 644의 의미는?**
> 세 자리가 각각 소유자, 그룹, 나머지 권한이고 r=4, w=2, x=1을 더한 값입니다. 755는 소유자는 읽기·쓰기·실행, 나머지는 읽기·실행이라 디렉토리나 실행 파일에 쓰고, 644는 소유자만 읽기·쓰기, 나머지는 읽기만이라 일반 파일에 씁니다.

**Q. 디렉토리의 x 권한은 무슨 의미인가요?**
> 디렉토리 안으로 들어가거나 그 디렉토리를 경로로 통과할 수 있는 권한입니다. r은 목록을 보는 권한, w는 안에 파일을 만들거나 지우는 권한입니다. 그래서 파일 삭제 권한은 파일이 아니라 상위 디렉토리의 w와 x로 결정되고, 경로 중간 디렉토리에 x가 없으면 파일 권한이 열려 있어도 접근할 수 없습니다.

**Q. 웹서버가 파일을 못 읽는다고 Permission denied가 납니다. 어떻게 확인하나요?**
> 먼저 웹서버 프로세스가 어떤 사용자로 실행 중인지 ps로 확인합니다. 그다음 namei -l로 파일까지 가는 경로의 모든 디렉토리 권한을 보고, 중간에 x가 빠진 곳이 없는지, 파일 자체의 r 권한이 그 사용자에게 있는지 봅니다. 그래도 문제가 없다면 SELinux 같은 추가 보안 정책을 확인합니다. 777을 주는 건 해결이 아니라 보안 구멍을 만드는 거라 쓰지 않습니다.

**Q. /tmp는 777인데 왜 남의 파일을 못 지우나요?**
> sticky bit가 걸려 있기 때문입니다. 원래는 디렉토리 쓰기 권한만 있으면 안의 파일을 누구 것이든 지울 수 있는데, sticky bit가 있으면 파일 소유자와 디렉토리 소유자, root만 지울 수 있습니다.

**Q. setuid가 뭔가요?**
> 실행 파일에 걸면, 누가 실행하든 그 파일 소유자의 권한으로 실행되게 하는 특수 권한입니다. passwd가 대표적인데, 일반 사용자가 root만 쓸 수 있는 /etc/shadow를 수정해야 하기 때문입니다. 대신 버그가 있으면 권한 상승 통로가 되기 때문에 보안 점검 대상입니다.
