# 09 OSI 7계층과 로드밸런서

**OSI 7계층**은 네트워크 통신을 "누가 무슨 일을 맡는지" 7칸으로 나눠 놓은 **지도**다. 외우라고 있는 게 아니라, 장애가 났을 때 **"몇 층 문제인지"로 범위를 좁히려고** 쓴다.
면접에서는 거의 항상 **"L4 로드밸런서와 L7 로드밸런서의 차이"** 로 이어진다. AWS로 치면 NLB vs ALB.

---

## 7계층 한눈에

| 계층 | 이름 | 하는 일 | 다루는 단위 · 주소 | 예 |
|---|---|---|---|---|
| **7** | 응용 (Application) | 사용자가 쓰는 프로토콜 | 메시지 | **HTTP**, DNS, SSH |
| 6 | 표현 (Presentation) | 인코딩, 암호화 | | TLS(애매하게 걸침), JSON |
| 5 | 세션 (Session) | 대화 유지 | | |
| **4** | 전송 (Transport) | **어느 프로그램에게**, 신뢰성 | 세그먼트 · **포트** | **TCP, UDP** |
| **3** | 네트워크 (Network) | **어느 컴퓨터에게** (경로 찾기) | 패킷 · **IP 주소** | **IP**, ICMP, 라우터 |
| **2** | 데이터링크 (Data Link) | **같은 동네 안에서** 옆 장비에게 | 프레임 · **MAC 주소** | 이더넷, 스위치, ARP |
| 1 | 물리 (Physical) | 전기·빛 신호 | 비트 | 케이블, 랜카드 |

> 실무에서는 5·6·7을 뭉뚱그려 **"응용 계층"** 하나로 보는 **TCP/IP 4계층**(링크 · 인터넷 · 전송 · 응용)을 더 많이 쓴다.
> 면접에서 **"L2, L3, L4, L7"** 이 나오면 위 표의 굵은 줄 네 개만 확실하면 된다.

### 택배로 비유하면

- **L3 (IP)** = 받는 **건물 주소**. 라우터가 이 주소를 보고 다음 경유지를 정한다.
- **L4 (포트)** = 그 건물의 **몇 호실**. 같은 서버 안에서도 nginx(443)냐 DB(5432)냐.
- **L2 (MAC)** = 지금 **바로 옆 경유지**의 주소. 경유지를 지날 때마다 바뀐다. (IP는 끝까지 그대로 — NAT만 빼고 → [06](06-subnet-routing-nat.md))
- **L7 (HTTP)** = 상자 안에 든 **편지 내용**.

### 캡슐화 — 내려갈 때 봉투를 씌우고, 올라갈 때 벗긴다

```
[HTTP 요청]                                   ← L7
[TCP 헤더 | HTTP 요청]                         ← L4: 포트 번호 붙임
[IP 헤더 | TCP 헤더 | HTTP 요청]                ← L3: IP 주소 붙임
[이더넷 헤더 | IP 헤더 | TCP 헤더 | HTTP 요청]    ← L2: MAC 주소 붙임 → 선으로 나감
```

## 계층별 장비와 "몇 층까지 보나"

| 장비 | 보는 정보 | 계층 |
|---|---|---|
| 스위치 | MAC 주소 | L2 |
| 라우터 | IP 주소 | L3 |
| 방화벽 · **보안그룹 · NACL** | IP + **포트** | L3~L4 |
| **NLB** | IP + 포트 | **L4** |
| **ALB**, nginx, **WAF** | **HTTP 내용** (경로, 헤더, 쿠키) | **L7** |

> 보안그룹이 "`/admin` 경로만 막기"를 못 하는 이유가 이것이다. SG는 L4까지만 보니까 **HTTP 경로를 모른다.** 그건 L7인 WAF나 ALB 규칙의 일이다.

## 장애를 계층으로 좁히기

"접속이 안 돼요"를 **아래층부터** 확인한다. → 자세한 순서는 [05](05-tcp-handshake.md#접속이-안-돼요-좁혀가는-순서)

| 계층 | 질문 | 확인 |
|---|---|---|
| L3 | 그 IP까지 **길이 있나?** | `ping`, `traceroute`, 라우트 테이블 |
| L4 | 그 **포트가 열려 있나?** | `nc -zv IP 포트`, 보안그룹, `ss -tlnp` |
| L7 | 열렸는데 **응답이 이상한가?** | `curl -v`, 상태 코드, 앱 로그 → [08](08-http-https.md) |

> `ping`이 안 된다고 서버가 죽은 건 아니다. **ICMP(L3)만 막혀 있고 TCP 443(L4)은 열려 있을 수** 있다. AWS 보안그룹은 ICMP를 따로 허용해야 한다.

## 로드밸런서 — L4 vs L7

로드밸런서는 **여러 서버 앞에 서서 요청을 나눠주는** 장비다. 한 대가 죽어도 서비스가 유지되고(가용성), 서버를 늘려 처리량을 키울 수 있다(확장성).

| | **L4 로드밸런서** (AWS **NLB**) | **L7 로드밸런서** (AWS **ALB**) |
|---|---|---|
| 보고 판단하는 것 | **IP + 포트**만 | **HTTP 내용** (경로, 호스트, 헤더, 쿠키) |
| 라우팅 예 | "443으로 온 건 이 서버들로" | "`/api/*`는 API 서버로, `/static/*`은 다른 곳으로", "`admin.example.com`은 관리 서버로" |
| 속도 · 부하 | **매우 빠름**, 초당 수백만 연결 | 내용을 풀어봐야 해서 상대적으로 무거움 |
| 프로토콜 | TCP, UDP, TLS 무엇이든 | HTTP / HTTPS / gRPC |
| TLS 처리 | 그대로 넘기거나 종료 가능 | 종료해서 내용을 봄 (ACM 인증서) |
| 고정 IP | **가능** (AZ당 고정 IP, Elastic IP) | **불가** (IP가 바뀜 → DNS 이름으로 접근) |
| 원래 클라이언트 IP | **그대로 보임** (기본) | 바뀜 → `X-Forwarded-For` 헤더로 전달 |
| 언제 쓰나 | 게임·IoT 같은 비 HTTP, **고정 IP가 필요할 때** (고객사 방화벽 화이트리스트), 초고성능 | **일반 웹 서비스, MSA 경로 라우팅** — 대부분의 경우 |

> 한 줄: **"L4는 봉투의 주소만 보고 나눠주고, L7은 편지를 열어서 내용을 보고 나눠준다."**

### 분산 알고리즘

| 방식 | 설명 |
|---|---|
| 라운드 로빈 | 순서대로 돌아가며 (ALB 기본) |
| 최소 연결 / 최소 미처리 요청 | 지금 제일 한가한 서버에게 |
| 해시 | 클라이언트 IP 등으로 해시 → **항상 같은 서버**로 (NLB는 연결 단위 해시) |

### 헬스체크

로드밸런서는 주기적으로 각 서버에 "살아있니?"를 물어 **죽은 서버를 빼고** 보낸다.
- **헬스체크 경로가 무거우면** (예: DB까지 조회) DB가 잠깐 느려질 때 **모든 서버가 동시에 Unhealthy** → 503 폭탄. 헬스체크는 가볍게, 의존성 확인은 따로.
- 헬스체크가 실패하는 흔한 이유: **서버 보안그룹이 LB 보안그룹을 허용 안 함**, 경로가 404/리다이렉트(301)를 반환 (기본 성공 코드는 200)

### 스티키 세션

같은 사용자를 **계속 같은 서버로** 보내는 기능 (ALB는 쿠키로 구현).
- 세션을 서버 메모리에 저장하는 앱을 살리려고 쓴다.
- 단점: 부하가 **한쪽으로 쏠리고**, 그 서버가 죽으면 **세션이 날아간다.**
- 근본 해결은 세션을 Redis 같은 **외부 저장소로 빼서 서버를 무상태로** 만드는 것. → [08](08-http-https.md#http의-기본-성질)

## 면접에서 이렇게 말한다

**Q. OSI 7계층을 설명해주세요.**
> 네트워크 통신을 역할별로 7단계로 나눈 모델입니다. 실무에서 중요한 건 L2는 MAC 주소로 같은 네트워크 안의 전달, L3는 IP 주소로 경로를 찾는 라우팅, L4는 포트 번호와 TCP/UDP로 어느 프로세스에게 어떻게 전달할지, L7은 HTTP 같은 애플리케이션 프로토콜입니다. 장애가 났을 때 몇 계층 문제인지로 범위를 좁힐 수 있어서 유용합니다.

**Q. L4 로드밸런서와 L7 로드밸런서의 차이는?**
> L4는 IP와 포트만 보고 트래픽을 분산해서 빠르고 TCP, UDP 무엇이든 처리할 수 있습니다. L7은 HTTP 내용을 보기 때문에 경로나 호스트 헤더 기반 라우팅이 가능합니다. AWS에서는 NLB가 L4, ALB가 L7이고, 일반 웹 서비스나 MSA는 ALB를, 고정 IP가 필요하거나 HTTP가 아닌 트래픽, 초고성능이 필요하면 NLB를 씁니다.

**Q. ALB 뒤의 서버에서 클라이언트 IP가 전부 ALB IP로 찍힙니다.**
> ALB는 L7 프록시라서 연결을 새로 맺기 때문에 서버 입장에서 출발지가 ALB가 됩니다. 원래 클라이언트 IP는 X-Forwarded-For 헤더에 담겨 오니까, 웹서버나 앱의 로그 포맷에서 그 헤더를 기록하도록 설정합니다.

**Q. ALB 타깃이 계속 Unhealthy입니다.**
> 먼저 타깃의 보안그룹이 ALB 보안그룹에서 오는 헬스체크 포트를 허용하는지 봅니다. 그다음 헬스체크 경로를 서버에서 직접 curl 해서 200이 나오는지 확인합니다. 로그인 페이지로 리다이렉트되는 301/302나 404가 나오면 실패로 처리되기 때문입니다. 앱이 127.0.0.1에만 바인딩돼 있지 않은지도 확인합니다.

**Q. 스티키 세션의 단점은?**
> 특정 서버로 부하가 쏠릴 수 있고, 그 서버가 죽으면 세션이 사라집니다. 오토스케일링으로 서버가 빠질 때도 마찬가지입니다. 그래서 세션을 Redis 같은 외부 저장소로 빼서 서버를 무상태로 만드는 게 더 나은 방법입니다.
