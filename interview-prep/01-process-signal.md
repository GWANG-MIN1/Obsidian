# 01 프로세스와 시그널

**프로세스는 "실행 중인 프로그램"** 이고, **시그널은 프로세스에게 보내는 짧은 쪽지**다.
서버에서 "뭐가 CPU를 먹고 있지?", "이거 안전하게 끄려면?" 같은 질문은 전부 이 두 개념으로 답한다.

---

## 프로그램 vs 프로세스

- **프로그램**: 디스크에 저장된 실행 파일. 책장에 꽂힌 **레시피**.
- **프로세스**: 그 프로그램을 메모리에 올려서 실제로 돌리고 있는 것. 레시피를 보고 **요리하고 있는 요리사**.

같은 레시피로 요리사 3명이 동시에 요리할 수 있듯이, `bash`를 3번 실행하면 **프로그램은 1개, 프로세스는 3개**다.

---

## PID와 부모-자식 관계

- 모든 프로세스는 번호를 가진다 → **PID** (Process ID)
- 나를 만든 프로세스의 번호 → **PPID** (Parent PID)
- 리눅스의 모든 프로세스는 결국 **PID 1**(요즘은 거의 `systemd`)에서 뻗어 나온 **가계도**를 이룬다.

```bash
ps -ef        # PID, PPID 같이 보기
pstree -p     # 가계도 모양으로 보기
```

---

## 프로세스는 어떻게 태어나나 — fork + exec

새 프로세스는 두 단계로 만들어진다.

1. **fork()** — 부모가 **자기 자신을 복사**해서 자식을 만든다. 막 태어난 자식은 부모와 내용이 똑같다.
2. **exec()** — 자식이 자기 내용을 **새 프로그램으로 갈아끼운다**.

터미널에서 `ls`를 치면 실제로는 이렇게 된다.

```
bash (부모)
  └─ fork → bash 복사본 (자식)
               └─ exec → ls 로 변신 → 실행 → 종료
  bash가 자식의 종료 결과를 회수(wait)하고 다음 프롬프트를 띄움
```

> 왜 굳이 복사 후 변신? 복사한 직후, 변신하기 전에 **입출력 방향(리다이렉션)이나 환경변수를 바꿔 끼울 틈**이 생기기 때문이다.
> `ls > out.txt`가 가능한 이유가 이것이다.

---

## 프로세스 상태

`ps aux`의 `STAT` 칸에 나온다.

| 상태 | 이름 | 쉬운 말 |
|---|---|---|
| `R` | Running | 지금 CPU를 쓰고 있거나, 쓸 차례를 기다리는 중 |
| `S` | Sleeping | 뭔가(입력, 네트워크 응답)를 기다리며 쉬는 중. **대부분 프로세스가 이 상태** |
| `D` | Uninterruptible sleep | 디스크 I/O 같은 걸 기다리는 중. **이때는 시그널로도 못 깨운다** |
| `T` | Stopped | 일시정지 (Ctrl+Z 등) |
| `Z` | Zombie | 죽었는데 부모가 아직 뒷정리를 안 해준 상태 |

> **`D` 상태 프로세스가 잔뜩 쌓여 있다면** → 디스크나 NFS 같은 스토리지가 느리거나 멈췄다는 신호.
> `kill -9`로도 안 죽는다. 프로세스를 볼 게 아니라 **스토리지 쪽**을 봐야 한다.

---

## 좀비 vs 고아 (단골 질문)

### 좀비 (Zombie)

- 자식이 종료되면 "나 이렇게 끝났어요"라는 **종료 기록**을 남긴다.
- 부모는 `wait()`로 그 기록을 읽어가야 한다. 이걸 안 하면 자식은 **이름만 남은 채** 프로세스 목록에 계속 떠 있다. 이게 좀비다.
- 메모리·CPU는 거의 안 쓰지만 **PID 번호 하나를 계속 차지**한다. 수만 개 쌓이면 새 프로세스를 못 만든다.
- **이미 죽어 있어서 kill로 못 죽인다.** 해결 방법은:
  - 부모 프로그램이 `wait()`를 제대로 하도록 고치거나
  - **부모를 종료**한다 → 좀비가 PID 1에게 입양되고, PID 1이 알아서 정리해준다.

### 고아 (Orphan)

- **부모가 먼저 죽고 자식만 살아 있는** 상태.
- 고아는 PID 1(또는 지정된 대리 부모)이 입양한다. 그래서 보통은 문제가 안 된다.

> 한 줄 비교
> - 좀비 = **자식은 죽었는데** 부모가 안 챙겨감
> - 고아 = **부모가 죽고** 자식만 남음

## 시그널 — 프로세스에게 보내는 쪽지

시그널은 "멈춰", "끝내", "설정 다시 읽어" 같은 **아주 짧은 신호**다. 대부분의 시그널은 프로세스가 받아서 **어떻게 반응할지 직접 정할 수 있다**(무시하거나, 정리 작업 후 종료하거나). 딱 두 개만 예외다.

| 번호 | 이름 | 언제 쓰나 | 프로세스가 막을 수 있나? |
|---|---|---|---|
| 1 | `SIGHUP` | 터미널이 끊김. 데몬에게는 관례적으로 "**설정 다시 읽어**" | 가능 |
| 2 | `SIGINT` | Ctrl+C | 가능 |
| 9 | `SIGKILL` | 무조건 강제 종료 | **불가능** |
| 15 | `SIGTERM` | "정리하고 끝내줘" (`kill`의 기본값) | 가능 |
| 17 | `SIGCHLD` | "자식이 끝났어요" 하고 부모에게 알려줌 | 가능 |
| 19 | `SIGSTOP` | 강제 일시정지 | **불가능** |
| 20 | `SIGTSTP` | Ctrl+Z | 가능 |

(번호는 x86 리눅스 기준. `kill -l`로 전체 목록 확인)

```bash
kill 1234           # SIGTERM(15) 보내기
kill -9 1234        # SIGKILL 강제 종료
kill -HUP 1234      # nginx 등에게 설정 리로드 요청
```

---

## SIGTERM vs SIGKILL — 가장 많이 나오는 질문

비유하면:
- **SIGTERM** = "퇴근 시간이에요. 하던 거 저장하고 정리하고 나가주세요."
- **SIGKILL** = 경비원이 와서 **그 자리에서 끌고 나감**. 저장이고 뭐고 없다.

SIGKILL은 프로세스가 **받지도 못한다**. 커널이 직접 없애버리기 때문에 프로세스 입장에서는 그냥 갑자기 사라지는 것이다.

그래서 SIGKILL을 바로 쓰면:
- 쓰던 파일이 반쯤 저장된 채로 깨질 수 있고
- 락 파일(`*.pid`, `*.lock`)이 안 지워져서 **다음 실행이 안 될 수 있고**
- 클라이언트 연결이 정상적으로 안 닫힌다

**원칙: 항상 SIGTERM 먼저 → 일정 시간 기다려도 안 죽으면 SIGKILL.**

> 실무 연결: `docker stop`, `systemctl stop`, 쿠버네티스 Pod 종료 전부 **SIGTERM → 유예시간 → SIGKILL** 순서로 동작한다.
> (docker는 기본 10초, 쿠버네티스는 `terminationGracePeriodSeconds` 기본 30초)

---

## 보너스 — 컨테이너에서 "docker stop이 10초 걸려요"

컨테이너 안에서 내 앱이 **PID 1**이 되는 경우가 많다. 그런데 리눅스는 PID 1을 특별 대우한다.

- 일반 프로세스는 SIGTERM을 받았을 때 **따로 처리 코드가 없으면 기본 동작(= 종료)** 을 한다.
- 그런데 **PID 1은 처리 코드가 없으면 SIGTERM을 그냥 무시**한다. (init이 실수로 죽으면 시스템 전체가 죽으니까 생긴 보호장치)

그래서 앱이 SIGTERM을 처리하지 않으면 → 무시됨 → 10초 기다림 → SIGKILL로 강제 종료. 정상 종료가 안 된다.

해결:
- Dockerfile에서 `CMD ["node", "app.js"]`처럼 **exec 형식**을 써서 셸이 끼지 않게 하고
- 앱에서 SIGTERM 처리 코드를 넣거나
- `docker run --init` / `tini` 같은 작은 init을 PID 1로 둔다

> 컨테이너 런타임을 다뤄봤다면 여기까지 말할 수 있으면 확실히 차별화된다.

## 면접에서 이렇게 말한다

**Q. 프로세스와 스레드 차이는?**
> 프로세스는 각자 독립된 메모리 공간을 가진 실행 단위이고, 스레드는 한 프로세스 안에서 메모리를 공유하면서 실행되는 흐름입니다. 그래서 스레드는 만들고 전환하는 비용이 싸지만, 한 스레드가 메모리를 망가뜨리면 같은 프로세스 전체가 영향을 받습니다.

**Q. 좀비 프로세스가 뭐고 어떻게 없애나요?**
> 자식 프로세스가 종료됐는데 부모가 wait으로 종료 상태를 회수하지 않아서 프로세스 테이블에 흔적만 남은 상태입니다. 이미 죽어 있기 때문에 kill로는 안 없어지고, 부모가 회수하도록 고치거나 부모를 종료하면 PID 1이 입양해서 정리합니다. 자원은 거의 안 쓰지만 PID를 차지하기 때문에 많이 쌓이면 문제가 됩니다.

**Q. kill -9와 kill -15 차이는?**
> 15번 SIGTERM은 종료를 요청하는 신호라서 프로세스가 받아서 파일 저장이나 연결 정리를 하고 끝낼 수 있습니다. 9번 SIGKILL은 프로세스가 받지도 못하고 커널이 즉시 종료시키기 때문에 정리할 기회가 없습니다. 그래서 15번을 먼저 보내고, 반응이 없을 때만 9번을 씁니다. docker stop이나 쿠버네티스 Pod 종료도 같은 순서로 동작합니다.

**Q. 서버에서 어떤 프로세스가 CPU를 100% 쓰고 있다면?**
> top이나 htop으로 PID와 실행 사용자를 확인하고, ps로 어떤 명령으로 실행됐는지 봅니다. 바로 죽이기보다 로그를 먼저 확인해서 무한루프인지, 트래픽 증가 때문인지 원인을 봅니다. 서비스라면 systemctl로 재시작하고, 단독 프로세스라면 SIGTERM으로 정상 종료를 시도한 뒤 안 되면 SIGKILL을 씁니다.

**Q. `kill -9`로도 안 죽는 프로세스는?**
> 두 가지 경우가 있습니다. 좀비라면 이미 죽은 상태라 부모 쪽을 처리해야 하고, D 상태라면 디스크나 NFS I/O를 기다리는 중이라 시그널이 전달되지 않습니다. 이 경우 스토리지 쪽 문제를 먼저 확인해야 합니다.
