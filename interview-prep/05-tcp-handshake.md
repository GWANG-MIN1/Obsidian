# 05 TCP 핸드셰이크

TCP는 **"받았는지 확인하면서 순서대로 보내는" 통신 규칙**이다. 그 확인 절차의 시작이 3-way 핸드셰이크, 끝이 4-way 핸드셰이크다.
"접속이 안 돼요"라는 장애의 절반은 **연결이 어느 단계에서 멈췄는지**로 원인이 갈린다.

---

## TCP vs UDP

| | TCP | UDP |
|---|---|---|
| 연결 | 먼저 **연결을 맺고** 보낸다 | 그냥 던진다 |
| 신뢰성 | 못 받으면 **재전송**, **순서 보장** | 보장 없음 (잃어버려도 모름) |
| 속도 | 확인 절차만큼 느림 | 빠르고 가벼움 |
| 비유 | **등기우편** (수령 확인) | **전단지** (뿌리고 끝) |
| 예 | HTTP(S), SSH, DB 접속 | DNS 조회, 스트리밍, 게임, (HTTP/3의 QUIC) |

> DNS는 기본이 UDP 53이지만, 응답이 크거나 존 전송(zone transfer)을 할 때는 **TCP 53**도 쓴다. 방화벽에서 둘 다 열어야 하는 이유. → [07 DNS](07-dns.md)

## 3-way 핸드셰이크 — 연결 맺기

```
클라이언트                          서버 (LISTEN)
    │ ── SYN (seq=x) ──────────────▶ │   "연결하고 싶어요. 내 번호는 x부터"
    │ ◀──── SYN+ACK (seq=y, ack=x+1) │   "좋아요. x 받았고, 내 번호는 y부터"
    │ ── ACK (ack=y+1) ────────────▶ │   "y 받았어요"
 ESTABLISHED                    ESTABLISHED
```

- **SYN** = 동기화(synchronize). "내 순서번호(seq) 시작값은 이거야"
- **ACK** = 확인(acknowledge). "네가 보낸 거 여기까지 받았어"

### 왜 2번이 아니라 3번인가?

양쪽 다 **"내 번호를 상대가 제대로 받았다"** 는 걸 확인해야 하기 때문이다.
- 2번째(SYN+ACK)에서 클라이언트는 "서버가 내 번호를 받았구나"를 안다.
- 3번째(ACK)가 있어야 **서버도** "클라이언트가 내 번호를 받았구나"를 안다.
- 2번으로 끝내면, 네트워크에 떠돌던 **옛날 SYN 하나**만으로도 서버가 연결을 열어버릴 수 있다.

> 핵심 문장: **"양방향 모두 시작 순서번호를 주고받고 확인하려면 최소 3번이 필요하다."**

## 4-way 핸드셰이크 — 연결 끊기

TCP 연결은 **양방향 통로 두 개**라서, 각 방향을 따로 닫는다.

```
먼저 끊는 쪽 (보통 클라이언트)            상대방
    │ ── FIN ─────────────────────▶ │   "나 보낼 거 다 보냈어"
FIN_WAIT_1                              CLOSE_WAIT
    │ ◀──────────────────────── ACK │   "알았어" (근데 나는 아직 보낼 게 남았을 수 있음)
FIN_WAIT_2                                   … 남은 데이터 전송 …
    │ ◀──────────────────────── FIN │   "나도 다 보냈어"
TIME_WAIT                               LAST_ACK
    │ ── ACK ─────────────────────▶ │
 (잠깐 대기 후) CLOSED                  CLOSED
```

> **왜 3번이 아니라 4번?** 상대는 FIN을 받아도 **아직 보낼 데이터가 남아 있을 수 있어서** ACK와 FIN을 한 번에 못 보낸다. (보낼 게 없으면 합쳐서 3번에 끝나기도 한다)

---

## TIME_WAIT와 CLOSE_WAIT — 운영에서 만나는 두 상태

### TIME_WAIT — **먼저 끊은 쪽**에 남는다

마지막 ACK를 보낸 뒤 바로 닫지 않고 **잠깐 기다리는** 상태. 리눅스는 **60초** 고정이다 (이론상 2×MSL).

기다리는 이유:
1. 내 마지막 ACK가 유실되면 상대가 FIN을 **다시 보낸다** → 그걸 받아서 다시 ACK 해줘야 함
2. 늦게 도착한 옛 패킷이 **같은 포트 번호로 새로 연 연결**에 섞여 들어가는 걸 막음

**문제가 되는 경우**: 서버가 다른 서버(DB, 외부 API)에 **짧은 연결을 엄청 많이** 열고 닫으면, TIME_WAIT가 수만 개 쌓여서 **로컬 포트(ephemeral port)가 고갈**된다 → `Cannot assign requested address`

해결: **커넥션 풀 / Keep-Alive로 연결을 재사용**하는 게 정석. (커널 튜닝 `net.ipv4.tcp_tw_reuse`는 보조 수단)

### CLOSE_WAIT — **상대가 끊었는데 내가 안 닫은** 상태

상대의 FIN은 받았는데, **내 앱이 `close()`를 안 부르고 있다**는 뜻이다. 이건 커널이 아니라 **앱 버그**(커넥션 반납 누락)다.
CLOSE_WAIT가 계속 늘어나면 → 파일 디스크립터 고갈 → `Too many open files` → 새 요청을 못 받는다.

> 한 줄 비교
> - TIME_WAIT 많음 = **정상 동작의 부산물**. 연결을 너무 자주 새로 열고 있다 → 재사용하라
> - CLOSE_WAIT 많음 = **앱이 연결을 안 닫는 버그** → 코드를 고쳐라

```bash
ss -tan state time-wait | wc -l     # TIME_WAIT 개수
ss -tan state close-wait            # CLOSE_WAIT 목록 (어느 프로세스인지는 -p)
ss -s                               # 상태별 요약
```

## Connection refused vs Connection timed out — 가장 실무적인 질문

둘 다 "접속 안 됨"이지만 **뜻이 완전히 다르다.**

| | refused (거부) | timed out (시간 초과) |
|---|---|---|
| 무슨 일이? | SYN을 보냈더니 **RST(거절)가 즉시 돌아옴** | SYN을 보냈는데 **아무 응답이 없음** |
| 의미 | 서버(호스트)까지는 **도달했다** | 중간 어딘가에서 **패킷이 사라졌다** |
| 흔한 원인 | 그 포트에 **LISTEN 중인 프로세스가 없음** (서비스 죽음, 포트 틀림, `127.0.0.1`에만 바인딩) | **방화벽·보안그룹이 조용히 버림(DROP)**, 라우팅 문제, 서버 자체가 꺼짐 |
| 걸리는 시간 | 즉시 | 수십 초 기다림 |
| 볼 곳 | **서버 안** — 프로세스, 포트, 바인딩 주소 | **네트워크 경로** — SG, NACL, 라우트 테이블, 방화벽 |

> **AWS 연결**: 보안그룹은 허용 안 된 트래픽을 **거절하지 않고 조용히 버린다.** 그래서 SG를 안 열었으면 refused가 아니라 **timeout**이 난다.
> "timeout이네 → 보안그룹부터 보자"가 바로 나오면 좋다.

> **`127.0.0.1` 바인딩 함정**: 앱이 `127.0.0.1:8080`에만 떠 있으면 서버 안에서 `curl localhost:8080`은 되는데 밖에서는 refused가 난다. `ss -tlnp`에서 주소가 `0.0.0.0`(모든 인터페이스)인지 확인. 컨테이너 안 앱도 같은 이유로 `0.0.0.0`에 바인딩해야 한다.

### 확인 명령어

```bash
nc -zv 10.0.1.20 5432          # 포트 열렸는지 (succeeded / refused / timeout)
curl -v http://10.0.1.20:8080  # 어느 단계에서 멈추는지 자세히
ss -tlnp | grep :8080          # (서버에서) 누가 어떤 주소로 LISTEN 중인지
sudo tcpdump -i any port 8080  # SYN이 서버까지 오긴 하는지 직접 보기
```

## "접속이 안 돼요" 좁혀가는 순서

1. **DNS** — 이름이 올바른 IP로 바뀌나? `dig +short 도메인` → [07](07-dns.md)
2. **경로** — 그 IP까지 갈 수 있나? `ping`(ICMP는 막혀 있을 수 있으니 참고만), `traceroute` → [06](06-subnet-routing-nat.md)
3. **포트** — `nc -zv IP 포트`
   - **timeout** → SG / NACL / 방화벽 / 라우팅
   - **refused** → 서버에서 프로세스가 떠 있는지, 바인딩 주소가 맞는지 (`systemctl status`, `ss -tlnp`) → [04](04-systemd.md)
4. **애플리케이션** — 포트는 열렸는데 응답이 이상하면 `curl -v`, 앱 로그(`journalctl -u`)

> 면접관이 보고 싶은 건 **"아래 계층부터 하나씩 잘라서 본다"** 는 사고방식이다.

## 면접에서 이렇게 말한다

**Q. TCP 3-way 핸드셰이크를 설명해주세요.**
> 클라이언트가 SYN으로 자기 시작 순서번호를 보내고, 서버가 SYN+ACK로 그걸 받았다는 확인과 자기 순서번호를 보내고, 클라이언트가 ACK로 서버 번호를 확인하면 연결이 맺어집니다. 3번인 이유는 양쪽 모두 자기 순서번호가 상대에게 전달됐는지 확인해야 하기 때문입니다.

**Q. TCP와 UDP의 차이는?**
> TCP는 연결을 맺고, 재전송과 순서 보장으로 신뢰성을 제공합니다. UDP는 연결 없이 바로 보내서 빠르지만 유실이나 순서를 보장하지 않습니다. 그래서 웹이나 DB 접속은 TCP, DNS 조회나 스트리밍처럼 빠른 게 중요한 곳은 UDP를 씁니다.

**Q. TIME_WAIT가 뭔가요? 많으면 문제인가요?**
> 연결을 먼저 끊은 쪽이 마지막 ACK를 보낸 뒤 일정 시간 기다리는 상태입니다. ACK가 유실됐을 때 재전송된 FIN에 응답하고, 늦게 온 옛 패킷이 새 연결에 섞이지 않게 하려는 목적입니다. 자체는 정상이지만 짧은 연결을 너무 많이 만들면 로컬 포트가 고갈될 수 있어서, 커넥션 풀이나 Keep-Alive로 연결을 재사용하는 게 해결책입니다.

**Q. CLOSE_WAIT가 계속 쌓이고 있습니다.**
> 상대가 연결을 끊었는데 우리 애플리케이션이 소켓을 닫지 않고 있다는 뜻입니다. 커널 설정 문제가 아니라 커넥션을 반납하지 않는 코드 문제라서, ss -tanp로 어느 프로세스인지 찾고 해당 코드의 연결 종료 처리를 확인합니다. 방치하면 파일 디스크립터가 고갈됩니다.

**Q. Connection refused와 timeout의 차이는?**
> refused는 서버까지 도달했지만 해당 포트에 듣고 있는 프로세스가 없어서 RST로 거절된 것이고, timeout은 SYN에 아무 응답이 없어서 중간에 패킷이 버려진 것입니다. 그래서 refused면 서버 안에서 서비스 상태와 바인딩 주소를 보고, timeout이면 보안그룹이나 NACL, 방화벽, 라우팅 같은 네트워크 경로를 봅니다. AWS 보안그룹은 거절 없이 버리기 때문에 timeout으로 나타납니다.
