# 02 파일시스템

리눅스는 **모든 것을 파일로 다루고**, 모든 파일이 **`/` 하나에서 시작하는 나무 구조**에 매달려 있다.
그리고 파일의 진짜 정보는 파일 이름이 아니라 **inode**라는 곳에 들어 있다. 이 세 가지가 면접의 핵심이다.

---

## "모든 것은 파일이다"

일반 문서뿐 아니라 이런 것들도 **파일처럼 열고, 읽고, 쓴다.**

- 디렉토리
- 디스크 장치 (`/dev/sda`, `/dev/nvme0n1`)
- 터미널, 키보드
- 실행 중인 프로세스 정보 (`/proc/1234/`)
- 커널 설정값 (`/proc/sys/...`)

그래서 `cat`, `echo`, `>` 같은 **똑같은 도구로 여러 가지를 다룰 수 있다.** 예를 들어:

```bash
cat /proc/cpuinfo                     # CPU 정보 보기
cat /proc/meminfo                     # 메모리 정보 보기
echo 1 > /proc/sys/net/ipv4/ip_forward   # 패킷 포워딩 켜기 (NAT에 필요 → 06 참고)
```

## 디렉토리 구조 (FHS)

윈도우는 `C:`, `D:`처럼 드라이브가 따로따로지만, 리눅스는 **`/` 하나에 전부 매달린다.** 두 번째 디스크도 `/data` 같은 폴더에 "붙여서(mount)" 쓴다.

| 경로 | 뭐가 있나 | 외우는 법 |
|---|---|---|
| `/etc` | **설정 파일** (nginx.conf, passwd, fstab) | "et cetera" → 설정 모음 |
| `/var` | **자주 바뀌는 것** — 로그(`/var/log`), 캐시, 스풀 | **var**iable |
| `/home` | 일반 사용자 홈 | |
| `/root` | root 사용자 홈 | `/`(루트 디렉토리)와 헷갈리지 말 것 |
| `/tmp` | 임시 파일. 재부팅 시 지워질 수 있음 | |
| `/bin`, `/usr/bin` | 일반 명령어 | **bin**ary |
| `/sbin`, `/usr/sbin` | 관리자용 명령어 | **s**ystem bin |
| `/dev` | 장치 파일 | **dev**ice |
| `/proc` | 커널·프로세스 정보. **디스크에 실제로 없는 가상 파일** | **proc**ess |
| `/boot` | 커널, 부트로더 | |
| `/opt` | 따로 설치한 소프트웨어 | **opt**ional |
| `/mnt`, `/media` | 임시로 붙이는 디스크 | **m**ou**nt** |

> 실무 감각: **"설정은 `/etc`, 로그는 `/var/log`"** 이 두 개만 몸에 붙어 있어도 장애 대응의 절반은 시작할 수 있다.

## inode — 파일의 진짜 정체

파일은 사실 **두 조각**으로 나뉘어 있다.

| 조각 | 들어 있는 것 |
|---|---|
| **inode** | 파일의 **모든 정보**: 크기, 소유자, 권한, 수정 시간, 그리고 **실제 데이터가 디스크 어디에 있는지** |
| **디렉토리 엔트리** | "**이름 → inode 번호**" 연결표 |

> **핵심: 파일 이름은 inode 안에 없다.** 이름은 디렉토리가 갖고 있다.
>
> 비유: inode는 **사람(주민번호)**, 파일 이름은 **전화번호부에 적힌 이름**.
> 전화번호부에 같은 사람을 두 이름으로 적을 수도 있고(하드링크), 이름을 지워도 사람이 바로 사라지진 않는다.

```bash
ls -i file.txt    # inode 번호 보기
stat file.txt     # inode에 들어 있는 정보 전부 보기
df -i             # 파일시스템별 inode 사용량
```

### inode는 개수가 정해져 있다

대부분의 파일시스템(ext4 등)은 **만들 때 inode 개수가 정해진다.** 그래서 이런 일이 생긴다.

> **"디스크 용량은 남았는데 파일을 못 만들어요 (No space left on device)"**
> → 작은 파일(세션 파일, 캐시, 메일 큐 등)이 수백만 개 쌓여서 **inode가 먼저 바닥난 것**.
> `df -h`로는 여유 있어 보이는데 `df -i`를 보면 100%다.

## 하드링크 vs 심볼릭링크

inode를 이해하면 둘 차이가 바로 보인다.

### 하드링크 — 같은 사람에게 이름을 하나 더

```bash
ln original.txt hard.txt
```

- `hard.txt`는 `original.txt`와 **같은 inode**를 가리킨다. 복사본이 아니라 **같은 파일에 이름이 두 개**인 것.
- `original.txt`를 지워도 `hard.txt`로 여전히 내용이 보인다. inode는 **자기를 가리키는 이름이 0개가 될 때** 비로소 삭제된다.
- 제약: **다른 파일시스템(다른 디스크)으로는 못 건다**(inode 번호는 파일시스템 안에서만 의미가 있으니까). 디렉토리에도 일반적으로 못 건다.

### 심볼릭링크 — "저기 가보세요" 메모

```bash
ln -s /etc/nginx/nginx.conf mylink
```

- 윈도우 **바로가기**와 같다. 자기만의 inode를 갖고, 안에는 **"원본 경로"라는 글자**만 들어 있다.
- 원본을 지우면 링크가 **깨진다**(dangling link).
- 다른 디스크, 디렉토리 어디든 걸 수 있다.

| | 하드링크 | 심볼릭링크 |
|---|---|---|
| inode | 원본과 **같음** | **별도** |
| 원본 삭제 시 | 계속 사용 가능 | **깨짐** |
| 다른 파일시스템 | 불가 | 가능 |
| 디렉토리 | 일반적으로 불가 | 가능 |

## 파일을 지웠는데 용량이 안 줄어요 (장애 단골)

`rm`은 사실 **"이름표를 떼는 것"** 이다. 데이터가 진짜 지워지는 조건은 두 가지가 모두 맞을 때다.

1. 그 inode를 가리키는 이름이 **0개**
2. 그 파일을 **열어두고 있는 프로세스가 0개**

그래서 이런 상황이 생긴다.

> nginx가 10GB짜리 로그 파일에 계속 쓰고 있는데, 용량이 부족해서 `rm access.log`를 했다.
> → 이름은 사라졌지만 **nginx가 파일을 계속 열고 있어서** 공간이 안 돌아온다.
> → `du`로 폴더를 합산해보면 작은데, `df`로 보면 여전히 꽉 차 있다.

해결:

```bash
lsof +L1                 # 지워졌지만 아직 열려 있는 파일 찾기
systemctl restart nginx  # 프로세스를 재시작하면 공간이 돌아온다
```

> **예방법**: 큰 로그를 비울 땐 `rm` 대신 **`> access.log`(내용만 비우기)** 를 쓰고,
> 평소에는 `logrotate`로 로그를 자동 교체·압축한다.

### df vs du

| | 무엇을 보나 | 비유 |
|---|---|---|
| `df -h` | **파일시스템 입장**에서 사용 중인 공간 (디스크 전체) | 창고 관리인의 장부 |
| `du -sh 폴더` | **파일을 하나씩 세서 더한** 크기 | 직접 상자를 세어본 결과 |

둘이 크게 다르면 → 위처럼 **지워졌지만 열려 있는 파일**이 있다는 뜻.

## 마운트 — 디스크를 폴더에 붙이기

새 디스크는 그냥 꽂는다고 바로 쓸 수 없다. **포맷 → 폴더에 붙이기** 과정이 필요하다.
EC2에 EBS 볼륨을 추가로 붙일 때 실제로 하는 작업이다.

```bash
lsblk                         # 붙어 있는 디스크 목록 (새 디스크 확인)
sudo mkfs -t xfs /dev/nvme1n1 # 포맷 (파일시스템 만들기) — 기존 데이터 전부 날아감!
sudo mkdir /data
sudo mount /dev/nvme1n1 /data # /data 폴더에 붙이기
df -h                         # 붙었는지 확인
```

재부팅 후에도 자동으로 붙게 하려면 `/etc/fstab`에 적는다.

```
UUID=xxxx-xxxx  /data  xfs  defaults,nofail  0  2
```

> **주의**: `/etc/fstab`을 잘못 쓰면 **부팅 자체가 안 될 수 있다.** EC2는 콘솔 접속이 까다로워서 치명적이다.
> - 장치 이름(`/dev/nvme1n1`) 대신 **UUID**를 쓴다 (재부팅 시 이름이 바뀔 수 있음, `blkid`로 확인)
> - `nofail` 옵션을 넣어서 디스크가 없어도 부팅은 되게 한다
> - 적은 뒤 **`sudo mount -a`로 먼저 테스트**한다

## 면접에서 이렇게 말한다

**Q. inode가 뭔가요?**
> 파일의 메타데이터를 저장하는 구조입니다. 크기, 소유자, 권한, 시간 정보와 실제 데이터 블록의 위치가 들어 있고, 파일 이름은 inode가 아니라 디렉토리 엔트리에 저장됩니다. 디렉토리는 결국 이름과 inode 번호를 연결한 표입니다.

**Q. 하드링크와 심볼릭링크 차이는?**
> 하드링크는 같은 inode를 가리키는 또 하나의 이름이라서 원본을 지워도 데이터가 남아 있고, 같은 파일시스템 안에서만 만들 수 있습니다. 심볼릭링크는 원본 경로를 담은 별도 파일이라 원본이 지워지면 깨지지만, 다른 파일시스템이나 디렉토리에도 걸 수 있습니다.

**Q. 디스크가 꽉 찼다는 알람이 왔습니다. 어떻게 하나요?**
> 먼저 df -h로 어느 파일시스템이 찼는지 보고, du로 어느 디렉토리가 큰지 좁혀갑니다. 보통 /var/log의 로그가 원인인 경우가 많습니다. 만약 df는 꽉 찼는데 du 합계가 훨씬 작다면, 삭제됐지만 프로세스가 아직 열고 있는 파일이 있다는 뜻이라 lsof +L1로 찾아서 해당 프로세스를 재시작합니다. 용량은 남았는데 파일 생성이 안 되면 df -i로 inode 고갈을 확인합니다. 재발 방지로는 logrotate 설정을 확인합니다.

**Q. EC2에 EBS를 새로 붙였는데 안 보여요.**
> 콘솔에서 연결(attach)만 하면 블록 장치로만 보이고, 파일시스템이 없어서 바로 쓸 수 없습니다. lsblk로 장치를 확인하고, 새 볼륨이면 mkfs로 포맷한 뒤 mount로 디렉토리에 붙입니다. 재부팅 후에도 유지하려면 fstab에 UUID와 nofail 옵션으로 등록하고 mount -a로 검증합니다.
