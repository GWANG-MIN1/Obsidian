# 11 메모리 — 가상 메모리 · 페이지 캐시 · OOM

**"메모리가 부족해요"** 는 서버 장애의 단골인데, 리눅스에서는 `free`의 숫자를 **잘못 읽어서** 생기는 오해가 절반이다.
면접에서는 가상 메모리가 왜 필요한지, `free`를 어떻게 읽는지, OOM Killer가 뭔지를 본다. 컨테이너의 `OOMKilled`로 바로 이어진다.

---

## 가상 메모리 — 모든 프로세스는 "나 혼자 쓴다"고 착각한다

각 프로세스는 **자기만의 가짜 주소 공간(가상 주소)** 을 받는다. 실제 RAM 위치(물리 주소)는 OS가 뒤에서 **연결(매핑)** 해준다.

```
프로세스 A의 0x1000 ──┐
                     ├──▶ (페이지 테이블) ──▶ 실제 RAM 어딘가
프로세스 B의 0x1000 ──┘                       (A와 B는 서로 다른 곳)
```

### 왜 이렇게 하나

1. **격리**: A가 B의 메모리를 건드릴 수 없다. 주소가 같아도 **가리키는 실제 위치가 다르다.** (잘못 건드리면 `Segmentation fault`)
2. **편의**: 프로그램은 실제 RAM이 어디 비었는지 몰라도 된다.
3. **RAM보다 크게 쓸 수 있다**: 당장 안 쓰는 부분은 디스크(스왑)에 내려둘 수 있다.
4. **공유**: 여러 프로세스가 쓰는 같은 라이브러리는 RAM에 **한 번만** 올리고 같이 가리킨다.

### 페이지와 페이지 폴트

- 메모리는 **4KB짜리 페이지** 단위로 관리한다.
- **페이지 테이블** = "가상 페이지 몇 번 → 물리 RAM 몇 번" 대응표. 프로세스마다 하나.
- **TLB** = 이 대응표의 **초고속 캐시**(CPU 안). 프로세스가 바뀌면 이 캐시가 쓸모없어져서 **컨텍스트 스위칭이 비싸진다.** → [10](10-process-thread.md#컨텍스트-스위칭)

**페이지 폴트** = 접근하려는 페이지가 **지금 RAM에 없을 때** 생기는 일. 에러가 아니라 **정상 동작**이다.
- **Minor**: RAM 어딘가엔 있음 → 연결만 해주면 끝 (빠름)
- **Major**: **디스크에서 읽어와야 함** (스왑 등) → 느림. 이게 많으면 문제

> 리눅스는 `malloc`으로 1GB를 달라고 해도 **바로 RAM을 주지 않는다.** 실제로 **처음 쓸 때** 페이지 폴트로 한 페이지씩 준다(지연 할당). 그래서 `VIRT`(달라고 한 양)는 크고 `RES`(실제 쓰는 양)는 작은 게 보통이다.

## `free` 읽는 법 — "free가 거의 0인데요?"

```
$ free -h
               total        used        free      shared  buff/cache   available
Mem:           7.6Gi       2.1Gi       210Mi        12Mi       5.3Gi       5.2Gi
Swap:             0B          0B          0B
```

| 칸 | 뜻 |
|---|---|
| `used` | 프로세스들이 실제로 쓰는 양 |
| `free` | **완전히 놀고 있는** 양 |
| `buff/cache` | 리눅스가 **디스크 내용을 RAM에 캐싱**해 둔 양 (페이지 캐시) |
| **`available`** | **새 프로그램이 지금 쓸 수 있는 양** ← **이걸 봐야 한다** |

> 리눅스 철학: **"노는 RAM은 낭비다."** 남는 RAM에 최근 읽은 파일을 캐싱해두고, 프로세스가 메모리를 달라고 하면 **캐시를 즉시 비우고 내준다.**
> 그래서 `free`가 210MB여도 `available`이 5.2GB면 **전혀 문제없다.** "메모리 부족"의 기준은 **`available`이 낮아지는 것**이다.

> `echo 3 > /proc/sys/vm/drop_caches`로 캐시를 비우면 `free`는 늘지만, 방금까지 RAM에서 읽던 걸 **디스크에서 다시 읽게 되니 오히려 느려진다.** 운영에서 습관적으로 할 일이 아니다.

## 스왑 (Swap)

RAM이 모자라면 **안 쓰는 페이지를 디스크로 내려보내는** 공간.

- 있으면: 갑자기 메모리가 튀어도 **바로 죽지 않고 버틴다.** 대신 **엄청 느려진다** (디스크는 RAM보다 수천 배 느림).
- **스래싱 (Thrashing)**: 메모리가 너무 부족해서 **내리고 올리기만 반복**하느라 실제 일을 못 하는 상태. `vmstat`의 `si`/`so`(swap in/out)가 계속 0이 아니면 의심.
- **쿠버네티스는 기본적으로 스왑을 끈다.** 스왑이 있으면 메모리 limit이 예측 불가능해지기 때문. EC2 AMI도 스왑이 없는 경우가 많다.

```bash
free -h                 # available 확인
vmstat 1                # si, so 열 = 스왑 in/out. 계속 0이 아니면 스래싱 의심
ps aux --sort=-rss | head   # 실제 메모리(RSS)를 많이 쓰는 프로세스
cat /proc/meminfo       # 더 자세히
```

## OOM Killer — 메모리가 정말 바닥나면

`available`이 바닥나고 스왑도 없거나 가득 차면, 커널은 **프로세스 하나를 골라 강제로 죽인다(SIGKILL).** 이게 **OOM(Out Of Memory) Killer**다.

- **누구를 죽이나**: 메모리를 **많이 쓰는** 프로세스일수록 점수(`oom_score`)가 높아 먼저 죽는다. 그래서 보통 **제일 중요한 프로세스(DB, 자바 앱)가 죽는다.**
- **SIGKILL이라서 앱 로그에 아무것도 안 남는다.** 앱은 그냥 "갑자기 사라진다." → 커널 로그를 봐야 한다.

```bash
dmesg -T | grep -i -E 'killed process|out of memory'
journalctl -k | grep -i oom
cat /proc/<PID>/oom_score          # 점수가 높을수록 먼저 죽음
```

> 특정 프로세스를 보호하려면 `oom_score_adj`를 음수로 (systemd 유닛에서 `OOMScoreAdjust=-500`). → [04](04-systemd.md)

### 컨테이너의 OOMKilled

컨테이너는 **cgroup으로 메모리 한도(limit)** 가 걸려 있다. 서버 전체 RAM이 남아 있어도 **컨테이너가 자기 한도를 넘으면** 그 안에서 OOM Killer가 돈다. → [13](13-virtualization-container.md)

```bash
kubectl describe pod <이름>    # Last State: Terminated, Reason: OOMKilled, Exit Code: 137
docker inspect <컨테이너> --format '{{.State.OOMKilled}}'
```

> **Exit Code 137 = 128 + 9 = SIGKILL로 죽었다.** 쿠버네티스에서 137을 보면 거의 OOMKilled다. → [01](01-process-signal.md)

**자바 앱이 자꾸 OOMKilled** 되는 고전적인 이유: JVM 힙(`-Xmx`)을 컨테이너 limit과 같게 잡으면, 힙 **바깥**(스레드 스택, 메타스페이스, 네이티브 메모리)까지 합쳐서 limit을 넘는다. 힙은 limit의 **70~75% 정도**로 (`-XX:MaxRAMPercentage=75`).

---

## 메모리 누수 vs 그냥 많이 쓰는 것

| | 누수 (Leak) | 그냥 많이 씀 |
|---|---|---|
| 그래프 모양 | **시간에 따라 계속 우상향**, 재시작하면 떨어졌다가 또 오름 | 부하에 따라 오르내리다 **일정 수준에서 평평** |
| 해결 | 코드 수정 (반납 안 하는 객체·커넥션) | 한도 상향, 인스턴스 크기 조정 |

> 임시방편으로 주기적 재시작을 걸 수는 있지만, "왜 재시작하면 괜찮아지는지"를 설명할 수 있어야 한다.

## 면접에서 이렇게 말한다

**Q. 가상 메모리가 뭔가요? 왜 쓰나요?**
> 각 프로세스에게 독립된 가상 주소 공간을 주고, OS가 페이지 테이블로 실제 물리 메모리에 매핑하는 방식입니다. 프로세스끼리 메모리가 격리되고, 프로그램은 실제 RAM 위치를 몰라도 되며, 공유 라이브러리를 한 번만 올려 공유할 수 있고, 스왑을 이용해 물리 메모리보다 큰 공간을 쓸 수도 있습니다.

**Q. `free`로 봤더니 free가 거의 0입니다. 메모리 증설해야 하나요?**
> 아닙니다. 리눅스는 남는 메모리를 페이지 캐시로 활용하기 때문에 free가 작은 건 정상입니다. 캐시는 프로세스가 필요하면 바로 반환되니까, 실제로 쓸 수 있는 양인 available 값을 봐야 합니다. available이 충분하면 문제없고, 그게 계속 낮고 스왑 in/out이 발생하면 그때 원인 프로세스를 찾고 증설을 검토합니다.

**Q. 어젯밤 앱이 로그도 없이 죽었습니다.**
> 로그 없이 사라졌다면 SIGKILL을 의심하고, 가장 흔한 원인이 OOM Killer입니다. dmesg나 journalctl -k에서 Out of memory, Killed process 메시지를 찾아서 어떤 프로세스가 언제 죽었는지 확인합니다. 그다음 메모리 사용량 그래프로 누수인지 일시적인 급증인지 구분해서, 코드 수정이나 메모리 한도 조정을 합니다.

**Q. 파드가 OOMKilled로 계속 재시작합니다.**
> 컨테이너가 cgroup 메모리 limit을 넘어서 커널이 죽인 겁니다. describe에서 Reason이 OOMKilled, Exit Code가 137인지 확인합니다. 실제 사용량이 limit에 비해 정상적으로 높은 거라면 limit을 올리고, 계속 증가하는 패턴이면 누수를 봅니다. 자바라면 힙을 limit과 같게 잡아서 힙 바깥 메모리로 넘치는 경우가 많아서 MaxRAMPercentage로 여유를 둡니다.

**Q. 스왑은 켜는 게 좋나요?**
> 장단점이 있습니다. 스왑이 있으면 순간적인 메모리 부족에 바로 죽지 않고 버티지만, 디스크를 쓰기 때문에 성능이 급격히 떨어지고 스래싱이 생길 수 있습니다. 응답 속도가 중요한 서버나 쿠버네티스 노드는 스왑을 끄고, 대신 메모리 모니터링과 한도 설정으로 관리하는 경우가 많습니다.
