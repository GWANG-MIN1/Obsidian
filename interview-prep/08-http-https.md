# 08 HTTP와 HTTPS

**HTTP**는 "요청 한 번, 응답 한 번"으로 주고받는 웹의 대화 규칙이고, **HTTPS**는 그 대화를 **TLS로 암호화한 통로 위에서** 하는 것이다.
면접에서는 상태 코드로 장애를 읽을 줄 아는지, TLS 핸드셰이크에서 "무엇을 왜 확인하는지"를 말할 수 있는지를 본다.

---

## HTTP의 기본 성질

- **요청-응답**: 클라이언트가 물어야 서버가 답한다. 서버가 먼저 말 걸 수 없다. (그래서 실시간 푸시는 WebSocket, SSE 같은 별도 방법을 쓴다)
- **무상태(Stateless)**: 서버는 **이전 요청을 기억하지 않는다.** 로그인 상태 같은 건 매 요청마다 쿠키·토큰으로 다시 알려줘야 한다.

> 무상태라서 좋은 점: **서버를 여러 대로 늘리기 쉽다.** 어느 서버가 요청을 받아도 똑같이 처리할 수 있으니까.
> 세션을 서버 메모리에 저장하면 이 장점이 깨진다 → 로드밸런서 **스티키 세션**이 필요해지거나, 세션을 Redis 같은 **외부 저장소**로 빼야 한다. → [09](09-osi-loadbalancer.md)

### 요청과 응답의 모양

```
GET /api/members?page=2 HTTP/1.1        ← 메서드, 경로, 버전
Host: api.example.com                   ← 헤더 (어느 사이트인지 — 한 IP에 여러 사이트가 있을 수 있어서 필수)
Authorization: Bearer eyJ...
                                        ← 빈 줄
(본문 — GET은 보통 없음)

HTTP/1.1 200 OK                         ← 버전, 상태 코드
Content-Type: application/json
Cache-Control: max-age=60

{"members": [...]}
```

## 메서드

| 메서드 | 용도 | 멱등? | 안전? |
|---|---|---|---|
| `GET` | 조회 | O | O (서버 상태 안 바꿈) |
| `POST` | 생성, 기타 처리 | **X** | X |
| `PUT` | 통째로 교체 | O | X |
| `PATCH` | 일부 수정 | (보장 안 됨) | X |
| `DELETE` | 삭제 | O | X |

**멱등(idempotent)** = **같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같다.**
- `DELETE /members/3`을 두 번 보내도 3번 회원은 "삭제된 상태" 그대로.
- `POST /orders`를 두 번 보내면 **주문이 두 개** 생긴다.

> 왜 중요한가? **타임아웃이 나서 재시도할 때.** 멱등한 요청은 그냥 다시 보내도 안전하지만, POST는 중복 결제·중복 주문이 생긴다.
> 그래서 결제 API는 `Idempotency-Key` 헤더로 "이 요청은 아까 그 요청이야"를 표시해 중복을 막는다.

## 상태 코드 — 장애 읽는 법

| 대역 | 뜻 | 누구 탓? |
|---|---|---|
| **2xx** | 성공 | — |
| **3xx** | 다른 데로 가라 (리다이렉트) | — |
| **4xx** | **요청이 잘못됨** | **클라이언트** |
| **5xx** | **서버가 처리 못 함** | **서버** |

### 꼭 구분해야 하는 것들

| 코드 | 뜻 | 실무에서 만나는 상황 |
|---|---|---|
| `301` / `302` | 영구 / 임시 이동 | HTTP → HTTPS 리다이렉트는 301 |
| `401` Unauthorized | **누군지 모름** (인증 실패) | 토큰 없음, 만료 |
| `403` Forbidden | **누군지 아는데 권한 없음** (인가 실패) | IAM 정책, S3 버킷 정책, WAF 차단 |
| `404` | 없음 | 경로 오타, ALB 리스너 규칙에 안 걸림 |
| `429` | 너무 많이 보냄 | Rate limit, API Gateway 스로틀링 |
| `500` | 서버 내부 오류 | **앱 코드 예외** → 앱 로그를 본다 |
| `502` Bad Gateway | **프록시가 뒤 서버에게서 이상한 응답을 받음** | 뒤 서버가 죽었거나 연결을 끊어버림 |
| `503` Service Unavailable | **보낼 곳이 없음** / 과부하 | ALB 타깃 그룹에 **Healthy 타깃이 0개** |
| `504` Gateway Timeout | **프록시가 뒤 서버를 기다리다 포기** | 뒤 서버가 너무 느림 (DB 쿼리가 오래 걸림 등) |

> **502 / 503 / 504는 "앞에 프록시(ALB, nginx)가 있다"는 뜻이다.** 에러를 만든 건 프록시고, 원인은 그 **뒤**에 있다.
> - 502 → 뒤 서버가 **이상하게 응답**했다 (죽음, 포트 틀림, 연결 리셋)
> - 503 → 보낼 **뒤 서버가 없다** (헬스체크 전부 실패)
> - 504 → 뒤 서버가 **너무 느리다** (타임아웃)

## HTTP 버전 — 무엇을 해결하려고 바뀌었나

| 버전 | 핵심 변화 | 남은 문제 |
|---|---|---|
| **1.0** | 요청마다 TCP 연결을 새로 맺음 | 매번 3-way 핸드셰이크 → 느림 |
| **1.1** | **Keep-Alive**로 연결 재사용 (기본값) | 한 연결에서 **앞 응답이 끝나야 다음 응답** (HOL 블로킹) → 브라우저가 연결을 6개씩 엶 |
| **2** | 한 연결 안에서 여러 요청을 **동시에** 주고받음 (멀티플렉싱), 헤더 압축 | TCP 자체는 순서를 지켜야 해서, 패킷 하나 잃으면 **전부 대기** |
| **3** | TCP 대신 **UDP 기반 QUIC** 위에서 동작 | (연결 수립도 더 빠름 — TLS를 합쳐서 한 번에) |

> 한 줄: **"1.1은 연결 재사용, 2는 한 연결에서 동시 전송, 3은 TCP의 순서 대기 문제까지 없애려고 UDP로 갔다."** → TCP/UDP는 [05](05-tcp-handshake.md)

## HTTPS — TLS가 해주는 세 가지

1. **암호화**: 중간에서 엿봐도 내용을 못 읽는다.
2. **무결성**: 중간에서 바꿔치기하면 티가 난다.
3. **인증**: 내가 접속한 서버가 **진짜 그 도메인의 주인**인지 확인한다. ← 제일 중요하고 제일 자주 까먹는 부분

> 암호화만 하고 인증을 안 하면? 가짜 서버와 **아주 안전하게 암호화된 대화**를 하게 된다. 그래서 인증서가 필요하다.

### 대칭키 vs 비대칭키 — 왜 둘 다 쓰나

| | 대칭키 | 비대칭키 (공개키) |
|---|---|---|
| 키 | 암호화·복호화 **같은 키 하나** | **공개키**로 잠그고 **개인키**로 연다 |
| 속도 | **빠름** | 느림 |
| 문제 | 그 키를 **어떻게 안전하게 나눠 갖나?** | 대량 데이터엔 너무 느림 |

→ TLS는 **처음에 비대칭 방식으로 대칭키를 안전하게 합의**하고, 이후 실제 데이터는 **빠른 대칭키로** 암호화한다. 둘의 장점만 쓴다.

### TLS 1.2 핸드셰이크 (흐름만)

```
클라이언트                                       서버
  │ ── ClientHello ─────────────────────────▶ │  "내가 쓸 수 있는 암호 방식 목록, 랜덤값"
  │ ◀──────────────────────────── ServerHello │  "이 방식으로 하자, 내 랜덤값"
  │ ◀─────────────────────────── Certificate  │  "내 인증서(공개키 포함)"
  │  (인증서 검증: 믿을 수 있는 CA가 서명했나? 도메인 맞나? 만료 안 됐나?)
  │ ◀─── 키 교환 ───────────────▶                (ECDHE로 양쪽이 같은 대칭키를 계산)
  │ ── Finished ────────────────────────────▶ │
  │ ◀──────────────────────────────── Finished │
  │ ═════════ 이후 대칭키로 암호화된 HTTP ═════════ │
```

- TLS 1.2는 이 과정에 **2번 왕복**, **TLS 1.3은 1번 왕복**으로 줄었다. (HTTPS 첫 연결이 느린 이유 = TCP 핸드셰이크 + TLS 핸드셰이크)

### 인증서 체인 — "누가 보증하나"

```
루트 CA (OS·브라우저에 미리 깔려 있음, 믿음의 출발점)
  └─ 중간 CA (루트가 서명)
       └─ www.example.com 인증서 (중간 CA가 서명)
```

> **자주 나는 장애**: 서버에 **내 인증서만 올리고 중간 인증서를 빼먹으면** → 브라우저는 캐시된 중간 인증서로 되는데, `curl`이나 앱(Java 등)에서는 `unable to get local issuer certificate`로 실패한다. "브라우저는 되는데 서버 간 호출만 안 돼요"의 단골 원인.

### TLS 종료 (TLS Termination)

AWS에서는 보통 **ALB나 CloudFront에서 TLS를 풀고**(ACM 인증서를 여기에 붙임), 뒤의 EC2·컨테이너는 **평문 HTTP**로 받는다.
- 장점: 인증서 관리를 한 곳에서, 앱 서버는 암호화 부담이 없음, ALB가 HTTP 내용을 볼 수 있어 **경로 기반 라우팅**이 가능 → [09](09-osi-loadbalancer.md)
- 앱이 "원래 HTTPS였는지" 알아야 하면 `X-Forwarded-Proto` 헤더를 본다. 이걸 안 보면 **리다이렉트 무한 루프**가 생기기도 한다 (앱: "HTTP네? HTTPS로 가" → ALB가 다시 HTTP로 넘김 → 반복)

```bash
curl -v https://example.com                       # TLS 협상 과정 + 응답 헤더
curl -I https://example.com                       # 헤더만
openssl s_client -connect example.com:443 -servername example.com   # 인증서 체인 직접 보기
echo | openssl s_client -connect example.com:443 2>/dev/null | openssl x509 -noout -dates   # 만료일
```

## 쿠키 · 세션 · 토큰

무상태인 HTTP에서 "로그인 상태"를 유지하는 방법들.

| | 세션 (서버 저장) | 토큰 (JWT 등) |
|---|---|---|
| 상태를 어디에? | **서버**(메모리·Redis)에 저장, 클라이언트는 세션 ID만 쿠키로 | **토큰 자체**에 정보가 들어있고 서버는 서명만 검증 |
| 서버 확장 | 세션 저장소를 공유해야 함 | 쉽다 (어느 서버든 서명만 확인) |
| 강제 로그아웃 | 쉽다 (서버에서 세션 삭제) | 어렵다 (만료 전까지 유효 → 만료를 짧게 + 리프레시 토큰) |

## 면접에서 이렇게 말한다

**Q. HTTP와 HTTPS의 차이는?**
> HTTPS는 HTTP를 TLS 위에서 주고받는 겁니다. TLS가 암호화, 무결성, 그리고 서버 인증을 제공합니다. 특히 인증서로 접속한 서버가 진짜 그 도메인의 주인인지 확인하는 게 핵심이고, 이게 없으면 가짜 서버와 암호화된 통신을 하는 셈이 됩니다.

**Q. TLS 핸드셰이크 과정을 설명해주세요.**
> 클라이언트가 지원하는 암호 방식을 보내면 서버가 하나를 고르고 인증서를 보냅니다. 클라이언트는 인증서가 신뢰하는 CA 체인으로 서명됐는지, 도메인과 유효기간이 맞는지 검증합니다. 그다음 ECDHE 같은 키 교환으로 양쪽이 같은 대칭키를 만들고, 이후 데이터는 그 대칭키로 암호화합니다. 비대칭키는 느리니까 키 합의에만 쓰고, 실제 데이터는 빠른 대칭키를 쓰는 구조입니다.

**Q. 401과 403의 차이는?**
> 401은 인증 실패, 즉 누군지 모르는 상태입니다. 토큰이 없거나 만료된 경우입니다. 403은 누군지는 알지만 권한이 없는 인가 실패입니다. AWS에서는 IAM 정책이나 S3 버킷 정책, WAF 차단에서 403을 자주 봅니다.

**Q. ALB에서 502, 503, 504가 나면 각각 어디를 보나요?**
> 셋 다 ALB가 만든 에러고 원인은 뒤쪽 타깃에 있습니다. 503은 타깃 그룹에 Healthy 타깃이 없는 경우가 많아서 헬스체크 경로와 보안그룹을 봅니다. 502는 타깃이 연결을 끊거나 잘못된 응답을 준 거라 앱이 죽었는지, 포트가 맞는지를 봅니다. 504는 타깃이 제한 시간 안에 응답을 못 한 거라 느린 쿼리나 외부 호출을 보고, 필요하면 ALB idle timeout과 앱 타임아웃을 맞춥니다.

**Q. 멱등성이 뭐고 왜 중요한가요?**
> 같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같은 성질입니다. GET, PUT, DELETE는 멱등이고 POST는 아닙니다. 네트워크 타임아웃으로 재시도할 때 멱등하지 않은 요청은 중복 처리가 생기기 때문에, 결제 같은 API는 멱등성 키로 중복을 막습니다.

**Q. HTTP/1.1, 2, 3의 차이는?**
> 1.1은 Keep-Alive로 연결을 재사용하지만 한 연결에서 응답이 순서대로만 와서 앞이 막히면 뒤도 기다립니다. 2는 한 연결 안에서 여러 요청을 동시에 주고받는 멀티플렉싱을 도입했지만, TCP 레벨에서 패킷 하나가 유실되면 전체가 기다립니다. 3은 이걸 없애려고 UDP 기반 QUIC을 쓰고 TLS까지 통합해서 연결 수립도 빨라졌습니다.
