# 04 컴퓨트 구매 옵션

같은 인스턴스를 **어떻게 사느냐**에 따라 단가가 최대 몇 배 차이 난다.  
기술적으로는 완전히 동일한 EC2인데 **약정·중단 감수 여부**만으로 가격이 결정된다.

---

## 네 가지 구매 방식

```
비쌈 ────────────────────────────────────────▶ 쌈
온디맨드    Savings Plans / RI          Spot
  기준       ~30~70% 절감           ~60~90% 절감
             (1~3년 약정)            (중단 가능)
```

| 방식 | 절감 | 약정 | 중단 | 적합 |
|---|---|---|---|---|
| **온디맨드** | 0% | 없음 | 없음 | 예측 불가·단기 |
| **Savings Plans** | ~30~70% | 1~3년 (금액) | 없음 | **꾸준한 기저 부하** |
| **Reserved Instances** | ~30~70% | 1~3년 (인스턴스) | 없음 | 변경 없는 특정 타입 |
| **Spot** | **~60~90%** | 없음 | **2분 예고 후 회수** | 중단 감내 가능한 워크로드 |

> 절감률·단가는 리전·타입·시점마다 다르다. **반드시 현재 가격 페이지에서 확인**한다. 여기 숫자는 크기 감각용이다.

---

## Savings Plans vs RI

```
Savings Plans   "시간당 $X 를 1~3년간 쓰겠다" 는 금액 약정
                → 인스턴스 타입·리전·OS 를 바꿔도 할인이 따라온다

Reserved        "이 타입 이 리전 이 개수를 쓰겠다" 는 인스턴스 약정
Instances       → 유연성이 낮지만 특정 조건에서 할인율이 더 높을 수 있다
```

| 종류 | 적용 범위 | 유연성 |
|---|---|---|
| **Compute Savings Plans** | EC2 + Fargate + Lambda, 리전·타입 무관 | **가장 유연** |
| EC2 Instance Savings Plans | 특정 리전·인스턴스 패밀리 | 중간 (할인율↑) |
| Standard RI | 특정 타입 고정 | 낮음 |
| Convertible RI | 타입 교환 가능 | 중간 |

> **대부분의 경우 Compute Savings Plans가 정답이다.** Kubernetes 환경에서는 인스턴스 타입이 자주 바뀌므로(Karpenter가 자동으로 고른다) 타입에 묶이는 RI는 위험하다. → `06-karpenter/`

### ⚠️ 사는 순서가 중요하다

```
❌ 낭비를 안 지운 채로 Savings Plans 구매
      → 낭비를 1~3년 약정으로 확정한다  💥

✅ ① 유휴 정리 → ② 라이트사이징 → ③ 안정화 → ④ 커밋 구매
```

> **커밋은 마지막에 산다.** 라이트사이징으로 사용량이 30% 줄어들 예정인데 지금 커밋을 사면, 남는 커밋만큼이 그냥 매몰 비용이 된다.  
> 반대로 **정리가 끝난 뒤에는 커밋을 미룰 이유가 없다** — 안 사는 동안은 매달 정가를 내고 있는 것이다.

### 얼마나 살 것인가

```
사용량 그래프
  ┌──────────────────────────── 피크 (온디맨드/Spot 로 흡수)
  │      ╱╲    ╱╲
  │  ╱╲╱  ╲╱╲╱  ╲
──┼─────────────────────────── 기저 부하 (여기까지만 커밋)
  └────────────────────────────
```

> **커밋은 "확실히 쓸 최소량"에만 건다.** 보통 최근 3개월 사용량의 **하위 60~80%** 선이다.  
> 남는 커밋은 환불되지 않는다. **부족한 건 정가를 내면 되지만, 남는 건 그냥 버린다.**

```bash
aws ce get-savings-plans-purchase-recommendation \
  --savings-plans-type COMPUTE_SP --term-in-years ONE_YEAR \
  --payment-option NO_UPFRONT --lookback-period-in-days SIXTY_DAYS
```

| 결제 옵션 | 할인 | 현금 부담 |
|---|---|---|
| No Upfront | 낮음 | 없음 |
| Partial Upfront | 중간 | 절반 |
| All Upfront | **가장 높음** | 전액 선결제 |

> 할인 차이가 크지 않다면 **No Upfront가 무난하다.** 현금 흐름을 묶지 않고, 판단이 틀렸을 때 손실도 작다.

## EKS 가격 구조

```
EKS 총비용
├── 컨트롤 플레인   클러스터당 시간당 고정 (약 $0.10/h ≈ 월 $72)
├── 워커 노드      EC2 요금 (여기가 대부분)
├── EBS 볼륨       노드 루트 + PVC
├── 데이터 전송     NAT, 크로스 AZ, 인터넷 아웃바운드 → 08-storage-network-cost/
└── 부가 서비스     ELB, ECR, CloudWatch
```

### ⚠️ 클러스터 개수가 곧 고정비다

```
클러스터 1개  → 컨트롤 플레인 월 ~$72
클러스터 10개 → 월 ~$720  (워커 노드 비용은 별개)
```

> **"팀마다 클러스터"는 고정비를 팀 수만큼 곱한다.** 네임스페이스로 나눌 수 있으면 나누는 게 싸다.  
> 반대로 **격리(보안·폭발 반경)를 위해 나누는 건 정당한 비용**이다. 이것도 명시적인 트레이드오프로 다룬다. → `../security-lab/05-rbac-least-privilege/`

### 비운영 클러스터는 끈다

```hcl
# dev 클러스터를 매일 파괴한다
#   → 컨트롤 플레인 + 노드 + NAT 비용이 사용한 시간만큼만
#   → Terraform 으로 만들었으니 다시 만들면 그만
```

```
주 168시간 중 실제 사용 40시간
  24시간 가동 → 100% 비용
  필요할 때만 → ~24% 비용
```

> **이게 가장 절감률이 높고 위험이 낮은 조치다.** IaC가 갖춰져 있으면 재생성 비용이 거의 0이기 때문에 가능하다. → `../terraform-lab/09-aws-vpc-eks/`  
> 매일 파괴하는 전제가 다른 결정에도 영향을 준다 — PVC를 안 붙이고, 관측성 보존을 짧게 잡고, Spot을 쓰는 것 전부 이 전제 위에서 정당해진다.

## Fargate와 비교

| | 관리형 노드 (EC2) | Fargate |
|---|---|---|
| 과금 | 노드 시간 (파드 유무 무관) | **파드 vCPU·메모리 시간** |
| 유휴 비용 | 있다 | **없다** |
| 단가 | 낮다 | **높다 (약 1.5~2배)** |
| DaemonSet | 가능 | ❌ 불가 |
| Spot | 가능 | ❌ (EKS Fargate) |
| 노드 관리 | 필요 | 불필요 |

```
파드가 드문드문·짧게 돈다        → Fargate 가 쌀 수 있다 (유휴 0)
파드가 항상 꽉 차 있다           → EC2 노드가 압도적으로 싸다
DaemonSet(로그·모니터링)이 필요   → EC2 노드 필수
```

> **Fargate의 비싼 단가는 "유휴가 없다"로 상쇄된다.** 노드 사용률이 30%대라면 Fargate가 더 쌀 수도 있다.  
> 다만 **DaemonSet을 못 쓰는 게 실무에서 큰 제약**이다 — promtail 같은 로그 수집기를 사이드카로 바꿔야 한다. → `../observability-lab/06-logging/`

## Graviton (ARM)

```
같은 성능 대비 약 20~40% 저렴 + 전력 효율
  → 멀티 아키텍처 이미지만 있으면 전환 비용이 낮다
```

```yaml
# 노드 그룹
ami_type       = "AL2023_ARM_64_STANDARD"
instance_types = ["m7g.large", "m6g.large"]
```

```yaml
# 파드가 아키텍처를 고르게
nodeSelector:
  kubernetes.io/arch: arm64
```

```bash
# 멀티 아키텍처 이미지 빌드 → ../cicd-lab/04-container-image-pipeline/
docker buildx build --platform linux/amd64,linux/arm64 -t myapp:1.0 --push .
```

> **가장 저평가된 절감 수단이다.** 대부분의 언어 런타임(Go·Java·Node·Python)은 ARM을 이미 지원한다.  
> 걸림돌은 보통 **네이티브 확장이 있는 의존성**과 **멀티아키 이미지 빌드 파이프라인**이다. 후자는 `buildx` 한 줄이면 되지만 빌드 시간이 늘어난다.

## 실제 조합 전략

```
prod
├── 기저 부하        Savings Plans (온디맨드 커밋)
├── 변동 부하        온디맨드
└── 배치·스테이트리스 Spot

dev / stg
└── 전부 Spot + 야간·주말 정지 (또는 매일 파괴)
```

```hcl
# dev — 이 프로젝트의 선택
node_capacity_type  = "SPOT"        # 싸고, 중단돼도 무관
node_instance_types = ["t3.medium"]
node_desired_size   = 2
node_min_size       = 1
node_max_size       = 3
```

> **환경별로 다른 전략을 쓰는 게 핵심이다.** dev에서 온디맨드를 쓰는 건 순수한 낭비이고, prod에서 전부 Spot을 쓰는 건 무모하다.  
> 관리형 노드 그룹은 `capacity_type` 한 줄로 바뀌지만, **혼합 구성이 필요하면 노드 그룹을 나누거나 Karpenter를 쓴다.** → `05-spot-instances/` `06-karpenter/`

## 배운 점

- 같은 EC2도 **약정·중단 감수 여부**로 단가가 몇 배 차이 난다
- **Savings Plans는 금액 약정, RI는 인스턴스 약정** — SP가 유연하다
- Kubernetes는 인스턴스 타입이 자주 바뀌므로 **Compute Savings Plans가 무난**
- ⚠️ **낭비를 안 지운 채 커밋을 사면 낭비를 1~3년 약정으로 확정**한다
- 순서: **정리 → 라이트사이징 → 안정화 → 커밋 구매**
- 정리가 끝났으면 **커밋을 미룰 이유도 없다** (안 사는 동안 정가를 낸다)
- 커밋은 **"확실히 쓸 최소량"** 에만 — 남는 커밋은 환불되지 않는다
- 할인 차이가 크지 않으면 **No Upfront**가 무난하다
- **EKS 컨트롤 플레인은 클러스터당 고정비** — 클러스터 개수가 곧 고정비
- 격리를 위한 클러스터 분리는 **정당한 비용**이지만 명시적 트레이드오프로 다룬다
- **비운영 환경을 끄는 것이 절감률 최고·위험 최저** — IaC가 있으면 재생성 비용이 0에 가깝다
- 매일 파괴하는 전제가 **PVC 미사용·짧은 보존·Spot 선택을 정당화**한다
- Fargate는 단가가 비싸지만 **유휴가 없다** — 사용률이 낮으면 유리할 수 있다
- ⚠️ **Fargate는 DaemonSet을 못 쓴다** (로그 수집기를 사이드카로 바꿔야 한다)
- **Graviton(ARM)은 가장 저평가된 절감 수단** — 멀티아키 이미지만 있으면 된다
- **환경별로 다른 구매 전략**을 쓴다 (dev 전부 Spot, prod는 혼합)
