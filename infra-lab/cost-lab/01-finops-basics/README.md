# 01 FinOps 기초

온프레미스에서 비용은 **연 1회 구매 결정**이었다. 클라우드에서는 **엔지니어가 매일 만드는 결과**다.  
`terraform apply` 한 번, 인스턴스 타입 한 줄, NAT 게이트웨이 개수 한 줄이 곧 청구서가 된다. FinOps는 그 사실을 조직 운영에 반영하는 방법론이다.

---

## 온프레미스와 무엇이 다른가

| | 온프레미스 | 클라우드 |
|---|---|---|
| 비용 발생 | 구매 시점 (CapEx) | **사용하는 매 순간 (OpEx)** |
| 결정 주체 | 인프라 팀·재무 | **코드를 쓰는 엔지니어** |
| 변경 속도 | 분기·연 단위 | 초 단위 |
| 낭비의 형태 | 놀고 있는 서버 | **잊혀진 리소스** |
| 가시성 | 자산 대장 | 청구서를 봐야 안다 |

```
클라우드 비용의 핵심 성질
  ① 쓰는 만큼 낸다        → 안 쓰면 안 낸다 (끄는 것이 최고의 최적화)
  ② 결정이 즉시 반영된다   → 실수도 즉시 반영된다
  ③ 아무도 안 보면 계속 는다 → 지우는 사람이 없다
```

> **클라우드에서 가장 큰 낭비는 비싼 리소스가 아니라 잊혀진 리소스다.** 실험용으로 띄운 클러스터, 지운 인스턴스의 EBS 볼륨, 연결 안 된 Elastic IP.  
> 그래서 FinOps의 절반은 협상이 아니라 **정리**다. → `10-cost-operations/`

## FinOps 3단계

```
   Inform  ──▶  Optimize  ──▶  Operate
   (보이게)      (줄이기)       (지속)
      │             │              │
   태그·배분     라이트사이징     예산·자동화
   대시보드      Spot·커밋       정책·문화
```

| 단계 | 질문 | 하는 일 |
|---|---|---|
| **Inform** | 누가 얼마를 쓰는가 | 태그, 비용 배분, 대시보드 |
| **Optimize** | 어디를 줄일 수 있는가 | 라이트사이징, 구매 옵션, 유휴 제거 |
| **Operate** | 어떻게 유지하는가 | 예산 알림, 이상 탐지, 정책 |

> **순서를 건너뛸 수 없다.** 누가 뭘 쓰는지 모르는 상태에서 "비용을 줄여라"고 하면 아무도 자기 몫을 모른다.  
> 관측성과 정확히 같은 구조다 — **계측 → 대시보드 → 알림 → 자동 조치**. → `../observability-lab/01-observability-basics/`

## 비용은 아키텍처 결정이다

```hcl
# 이 한 줄이 월 수십 달러 차이
single_nat_gateway = true    # dev: NAT 1개
                             # prod: AZ 마다 1개 (가용성 우선)

# 이 한 줄이 60~70% 차이
node_capacity_type = "SPOT"  # dev: 중단 감수하고 싸게
                             # prod: ON_DEMAND 또는 혼합

# 이 한 줄이 노드 수를 결정한다
node_instance_types = ["t3.medium"]
```

> **비용 최적화는 재무 활동이 아니라 설계 활동이다.** 위 세 줄은 전부 아키텍처 판단이고, 각각 가용성·안정성과의 트레이드오프를 담고 있다.  
> 그래서 **비용은 Terraform 코드 리뷰에서 논의돼야 한다.** 청구서를 보고 나서가 아니라.

### 트레이드오프를 명시한다

| 선택 | 얻는 것 | 잃는 것 |
|---|---|---|
| `single_nat_gateway = true` | NAT 비용 1/N | **AZ 장애 시 전체 아웃바운드 중단** |
| Spot 인스턴스 | 60~70% 절감 | 2분 예고 후 중단 |
| 작은 인스턴스 | 세밀한 조정 | 노드당 파드 수 한계, 오버헤드 비율↑ |
| 관측성 보존 7일 | 스토리지 비용↓ | 장기 추세 분석 불가 |

> **"싸게 했다"가 아니라 "이만큼의 위험을 대가로 이만큼 아꼈다"** 로 말할 수 있어야 한다.  
> 매일 파괴하는 dev 클러스터라면 Spot 중단은 사실상 비용이 0인 위험이다. 같은 선택이 prod에서는 전혀 다른 의미가 된다.

## 단위 경제성 (Unit Economics)

**총액은 거의 항상 는다.** 사업이 커지면 당연하다. 의미 있는 지표는 총액이 아니라 **단위당 비용**이다.

```
❌ "이번 달 클라우드 비용 20% 증가"       → 나쁜 건가? 모른다.
✅ "요청 100만 건당 비용 $12 → $9"        → 개선됐다.
✅ "활성 사용자당 월 $0.30 → $0.42"       → 악화됐다. 원인을 찾는다.
```

| 단위 후보 | 적합한 서비스 |
|---|---|
| 요청 100만 건당 비용 | API 서비스 |
| 활성 사용자(MAU)당 비용 | SaaS |
| 주문 1건당 인프라 비용 | 커머스 |
| 배포 1회당 CI 비용 | 플랫폼 팀 |

> **단위 비용이 일정하면 성장 중이고, 줄면 효율화 중이고, 늘면 어딘가 새고 있다.**  
> 총액만 보면 "성장했으니 어쩔 수 없다"와 "낭비가 늘었다"를 구분할 수 없다.

## 비용은 누구의 책임인가

```
[ 흔한 실패 ]
재무: "클라우드 비용이 너무 많다. 줄여라."
      ↓
플랫폼 팀: 어느 팀이 얼마 쓰는지 모른다
      ↓
전체에 일괄 압박 → 아무도 자기 일이라 생각 안 함 → 안 줄어듦
```

```
[ FinOps ]
비용을 팀별로 배분해 보이게 만든다
      ↓
각 팀이 자기 비용을 본다 (대시보드·주간 리포트)
      ↓
엔지니어가 설계 단계에서 비용을 고려한다
```

| 역할 | 책임 |
|---|---|
| **엔지니어** | 설계 시 비용 고려, 자기 팀 비용 인지 |
| **플랫폼 팀** | 가시성 제공, 기본값을 효율적으로, 가드레일 |
| **재무** | 예산, 커밋 구매 결정 |
| **경영** | 트레이드오프 승인 (비용 vs 성능·가용성) |

> **플랫폼 팀의 역할은 감시가 아니라 "기본값을 효율적으로 만드는 것"** 이다.  
> 템플릿의 기본 인스턴스 타입, 기본 보존 기간, 기본 레플리카 수가 조직 전체 비용의 상당 부분을 결정한다. 이건 Kyverno로 강제할 수도 있다. → `../security-lab/04-kyverno/`

## 최적화의 우선순위

```
1. 끄기 (Eliminate)      안 쓰는 걸 지운다              ← 절감률 100%, 위험 0
2. 줄이기 (Rightsize)     실사용에 맞게 조정              ← 큰 효과, 낮은 위험
3. 싸게 사기 (Purchase)   Spot·Savings Plans·RI          ← 큰 효과, 커밋 위험
4. 다시 짜기 (Rearchitect) 서버리스·관리형 전환            ← 효과 큼, 비용 큼
```

> **순서를 지키는 게 중요하다.** 낭비를 안 지운 채로 Savings Plans를 사면 **낭비를 3년 약정으로 확정**하는 셈이 된다.  
> 라이트사이징 전에 커밋을 사는 것도 같은 실수다. **먼저 정리하고, 줄이고, 그 다음에 산다.**

### 효과 대비 노력

| 조치 | 절감 | 노력 | 위험 |
|---|---|---|---|
| 유휴 EBS·EIP 정리 | 소~중 | **낮음** | 없음 |
| 비운영 환경 야간 정지 | **중~대** | 낮음 | 낮음 |
| gp2 → gp3 전환 | 소~중 | 낮음 | 낮음 |
| requests 라이트사이징 | **대** | 중간 | 중간 |
| Spot 전환 | **대** | 중간 | 중간 |
| Savings Plans | **대** | 낮음 | **커밋** |
| Karpenter 도입 | 대 | 중간 | 중간 |
| 아키텍처 재설계 | 대 | **높음** | 높음 |

> **가장 먼저 할 일은 "비운영 환경을 안 쓸 때 끄는 것"** 이다. dev/stg가 주 168시간 중 실제로 쓰이는 건 40~50시간뿐인데 대부분 24시간 켜져 있다.  
> 이 저장소의 dev 클러스터를 **매일 파괴하는 것**이 그 극단적인 형태다 — Terraform으로 만들었으니 다시 만들면 그만이다. → `../terraform-lab/09-aws-vpc-eks/`

## 흔한 함정

| 함정 | 왜 문제인가 |
|---|---|
| **총액만 본다** | 성장인지 낭비인지 구분 못 한다 |
| **정리 전에 커밋 구매** | 낭비를 약정으로 확정한다 |
| **가용성을 희생한 절감** | 장애 1회 비용 > 연간 절감액 |
| **엔지니어에게 안 보여준다** | 청구서를 못 보는 사람이 비용을 만든다 |
| **일회성 정리** | 3개월 뒤 원상복구 |
| **비용만 보고 시간을 안 본다** | 월 $50 아끼려고 엔지니어 주 8시간 |

> ⚠️ **가용성을 희생한 절감이 가장 비싼 실수다.** 운영 장애 1회로 잃는 매출·신뢰가 연간 절감액을 넘는 경우가 흔하다.  
> **"이 절감이 SLO를 위협하는가"** 를 먼저 묻는다. → `../observability-lab/01-observability-basics/`

## 배운 점

- 클라우드에서 **비용은 엔지니어가 매일 만드는 결과**다 (구매 결정이 아니라)
- 가장 큰 낭비는 비싼 리소스가 아니라 **잊혀진 리소스**
- FinOps 3단계 **Inform → Optimize → Operate** — 순서를 건너뛸 수 없다
- 관측성과 같은 구조다: **계측 → 대시보드 → 알림 → 자동 조치**
- **비용 최적화는 재무 활동이 아니라 설계 활동** — Terraform 코드 리뷰에서 논의돼야 한다
- 절감은 **"이만큼의 위험을 대가로 이만큼 아꼈다"** 로 표현한다
- 같은 선택(Spot·단일 NAT)이 dev와 prod에서 전혀 다른 의미를 갖는다
- **총액이 아니라 단위 경제성**을 본다 (요청 100만 건당, MAU당)
- 단위 비용이 일정=성장, 감소=효율화, 증가=어딘가 새는 중
- 팀별로 배분해 보이게 만들지 않으면 **아무도 자기 일이라 생각하지 않는다**
- 플랫폼 팀의 역할은 감시가 아니라 **기본값을 효율적으로 만드는 것**
- 최적화 순서: **끄기 → 줄이기 → 싸게 사기 → 다시 짜기**
- ⚠️ **정리 전에 Savings Plans를 사면 낭비를 약정으로 확정**한다
- 가장 효과 좋은 첫 조치는 **비운영 환경을 안 쓸 때 끄는 것**
- ⚠️ **가용성을 희생한 절감이 가장 비싼 실수** — 장애 1회 > 연간 절감액
- 월 $50 아끼려고 엔지니어 주 8시간을 쓰지 않는다
