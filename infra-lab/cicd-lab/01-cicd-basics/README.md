# 01 CI/CD 기초

배포가 무서운 조직은 배포를 미룬다. 미루면 한 번에 나가는 변경이 커지고, 커지면 더 무서워진다.  
**CI/CD의 목표는 자동화 자체가 아니라 이 악순환을 끊는 것** — 변경을 작게, 자주, 되돌릴 수 있게 만드는 일이다.

---

## CI · CD · CD

세 단어가 비슷해 헷갈리지만 경계가 명확하다.

```
Continuous Integration        Continuous Delivery        Continuous Deployment
   (지속적 통합)                 (지속적 제공)              (지속적 배포)
        │                            │                          │
  코드를 자주 합치고            언제든 배포 가능한          승인 없이 자동으로
  자동으로 검증한다             상태를 유지한다            운영에 나간다
        │                            │                          │
  빌드 + 테스트 + 린트         + 아티팩트 생성 + 스테이징     + 운영 자동 배포
                              (운영 배포는 '수동 승인')
```

| | 자동화 범위 | 운영 배포 |
|---|---|---|
| **CI** | 빌드·테스트·정적분석 | — |
| **CD (Delivery)** | + 아티팩트·스테이징 배포 | **사람이 버튼을 누른다** |
| **CD (Deployment)** | + 운영 배포 | **자동** |

> 대부분의 조직은 **Continuous Delivery**까지 간다. Deployment(완전 자동)는 자동 롤백·카나리 분석 같은 안전장치가 갖춰진 뒤의 이야기다. → `09-argo-rollouts/`  
> "우리는 CI/CD 한다"는 말 대부분은 실제로는 CI + 수동 배포다. 어디까지 자동인지를 정확히 아는 게 먼저다.

## 파이프라인 단계

```
커밋 ──▶ 빌드 ──▶ 테스트 ──▶ 정적분석 ──▶ 이미지 ──▶ 배포 ──▶ 검증
        │        │          │           │         │        │
      컴파일    단위/통합   린트·보안    태그·푸시  롤아웃   스모크·관측
```

| 단계 | 목적 | 실패 시 |
|---|---|---|
| **빌드** | 컴파일·의존성 해결 | 즉시 중단 |
| **테스트** | 회귀 방지 | 즉시 중단 |
| **정적분석** | 린트·타입·보안 스캔 | 정책에 따라 게이트 또는 리포트 |
| **이미지** | 컨테이너 빌드·푸시 | 중단 → `04-container-image-pipeline/` |
| **배포** | 클러스터에 반영 | 롤백 |
| **검증** | 스모크 테스트·메트릭 확인 | 자동 롤백 |

### 빠른 피드백이 전부다

```
❌ 파이프라인 40분  →  PR 올리고 다른 일 하러 감  →  실패해도 한참 뒤에 앎
✅ 파이프라인 5분   →  올리고 기다림  →  즉시 고침
```

| 목표 시간 | 단계 |
|---|---|
| ~2분 | 린트·타입·단위 테스트 |
| ~10분 | 통합 테스트·이미지 빌드 |
| 별도(야간·주간) | E2E, 전체 보안 스캔, 성능 테스트 |

> **PR 파이프라인에 모든 걸 넣지 않는다.** 느린 검사는 머지 후나 스케줄로 분리한다.  
> 실제로 이 저장소의 보안 스캔도 PR·push 외에 **매주 월요일 cron**으로 재실행한다 — 코드가 안 바뀌어도 새로 공개된 CVE는 잡아야 하기 때문이다.

## 게이팅 전략 — 무엇으로 빌드를 깨뜨릴 것인가

모든 발견을 실패로 만들면 `main`이 상시 빨갛게 되고, 그러면 아무도 안 본다. 관측성의 알림 피로와 같은 문제다. → `../observability-lab/05-alerting/`

```
[ 2단 구성 ]
  리포트  : HIGH + CRITICAL 전부 출력 (exit-code 0)   ← 보이게만 한다
  게이트  : 고칠 수 있는 CRITICAL 만 실패 (exit-code 1) ← 오늘 조치 가능한 것
```

| 판단 기준 | 게이트 | 리포트 |
|---|---|---|
| 지금 조치할 수 있는가 | ✅ | |
| 조치 방법이 없는가 (upstream 미수정) | | ✅ |
| 오탐이 잦은가 | | ✅ |
| 정책상 반드시 막아야 하는가 | ✅ | |

> `ignore-unfixed` 같은 옵션이 중요한 이유다. **패치가 없는 CVE로 빌드를 깨뜨리면 개발자는 스캔을 끄는 법을 배운다.**  
> 처음엔 리포트로 시작하고, 팀이 대응 가능해지면 게이트로 승격하는 순서가 현실적이다.

## Push 방식 vs Pull 방식 (GitOps)

배포를 **누가 실행하는가**의 차이다.

```
[ Push — 전통적 CI/CD ]
  CI 서버 ──kubectl apply / helm upgrade──▶ 클러스터
     └─ CI가 클러스터 자격증명을 갖고 있다

[ Pull — GitOps ]
  CI 서버 ──이미지 푸시 + 매니페스트 커밋──▶ Git
                                            │
                              클러스터 안 ArgoCD가 당겨간다
     └─ CI는 클러스터 자격증명이 필요 없다
```

| | Push | Pull (GitOps) |
|---|---|---|
| 배포 주체 | CI가 클러스터에 적용 | 클러스터 내 에이전트가 Git을 당김 |
| 자격증명 | **CI가 클러스터 관리자 권한 보유** | 클러스터 밖으로 안 나간다 |
| 진실의 원천 | 불명확 (CI 로그 + 수동 변경) | **Git** |
| 드리프트 | 감지 어려움 | 자동 감지·복구 (selfHeal) |
| 롤백 | 파이프라인 재실행 | `git revert` |
| 멀티 클러스터 | 클러스터마다 자격증명 | 각 클러스터가 알아서 당김 |

> **Pull 방식의 실질적 이점은 보안이다.** CI에 클러스터 admin 자격증명을 두지 않아도 된다. CI가 털려도 클러스터는 안전하다.  
> 다만 GitOps라고 CI가 필요 없는 게 아니다. **빌드·테스트·이미지 생성은 여전히 CI의 몫**이고, GitOps는 그 뒤의 배포만 담당한다.

### 실무 조합

```
GitHub Actions              ArgoCD
────────────────           ─────────────
빌드·테스트·스캔      →     Git 감시
이미지 빌드·푸시            매니페스트 적용
매니페스트 태그 갱신   →     드리프트 복구
     │                         │
     └────── Git ──────────────┘
          (인계점)
```

> 두 시스템의 인계점은 **Git 커밋**이다. CI는 "새 이미지 태그를 Git에 쓴다"까지, CD는 "Git을 보고 클러스터를 맞춘다"부터. → `07-gitops-repo-strategy/`

## DORA 4지표

DevOps 성과를 재는 표준 지표다. 파이프라인을 왜 개선하는지에 대한 답이기도 하다.

| 지표 | 뜻 | 엘리트 수준 |
|---|---|---|
| **배포 빈도** (Deployment Frequency) | 얼마나 자주 배포하나 | 하루 여러 번 |
| **변경 리드타임** (Lead Time for Changes) | 커밋 → 운영 반영까지 | 1시간 미만 |
| **변경 실패율** (Change Failure Rate) | 배포 중 장애를 낸 비율 | 5~15% |
| **복구 시간** (MTTR / Failed Deployment Recovery Time) | 장애에서 회복까지 | 1시간 미만 |

```
앞의 두 개 = 속도(throughput)
뒤의 두 개 = 안정성(stability)
```

> **속도와 안정성은 트레이드오프가 아니다.** DORA 연구의 핵심 발견이 이것이다 — 자주 배포하는 조직이 장애도 적고 복구도 빠르다.  
> 작게 자주 배포하면 한 번의 변경 범위가 작아서 원인을 즉시 알 수 있기 때문이다. **큰 배포가 위험한 것이지 잦은 배포가 위험한 게 아니다.**

### 지표별 개선 수단

| 지표 | 개선 방법 |
|---|---|
| 배포 빈도 ↑ | 자동화, 트렁크 기반 개발, 작은 PR |
| 리드타임 ↓ | 파이프라인 단축, 승인 단계 축소 |
| 실패율 ↓ | 테스트 커버리지, 카나리 배포, 정책 검사 |
| 복구 시간 ↓ | **자동 롤백**, GitOps(`git revert`), 관측성 |

> 복구 시간을 줄이는 가장 효과적인 방법은 **롤백을 쉽게 만드는 것**이지 장애를 없애는 게 아니다. → `10-pipeline-operations/`

## 브랜치 전략

| 전략 | 구조 | CI/CD 궁합 |
|---|---|---|
| **트렁크 기반** | main 하나 + 짧은 수명 브랜치 | ✅ 가장 좋다 |
| **GitHub Flow** | main + feature 브랜치 + PR | ✅ 좋다 |
| Git Flow | main/develop/release/hotfix | ❌ 브랜치가 오래 살아 통합이 늦다 |

```
트렁크 기반:  feature 브랜치 수명 < 1~2일
              → 충돌 적고, 통합이 늘 최신
              → 미완성 기능은 '피처 플래그'로 감춘다
```

> **Git Flow는 CI(지속적 통합)와 상충한다.** 브랜치가 몇 주 살아 있으면 "지속적으로 통합"하는 게 아니다.  
> 릴리스 주기가 긴 패키지 소프트웨어라면 여전히 유효하지만, 하루에 여러 번 배포하는 서비스에는 맞지 않는다.

## 배운 점

- CI/CD의 목적은 자동화가 아니라 **변경을 작게·자주·되돌릴 수 있게** 만드는 것
- CI(통합) / CD Delivery(배포 가능 상태 유지, 배포는 수동) / CD Deployment(자동 배포)는 다르다
- 대부분의 "CI/CD"는 실제로 **CI + 수동 배포** — 어디까지 자동인지 정확히 아는 게 먼저
- **파이프라인 속도가 곧 피드백 속도** — PR에는 빠른 검사만, 느린 건 머지 후·스케줄로
- 코드가 안 바뀌어도 **주기적 보안 재스캔**이 필요하다 (새 CVE는 계속 나온다)
- **모든 발견을 게이트로 만들면 main이 상시 빨개진다** — 알림 피로와 같은 실패
- 게이트는 **오늘 조치할 수 있는 것**에만 (`ignore-unfixed`), 나머지는 리포트
- Push는 CI가 클러스터에 적용, **Pull(GitOps)은 클러스터가 Git을 당긴다**
- Pull의 실질적 이점은 **CI에 클러스터 자격증명을 두지 않아도 되는 것**
- GitOps여도 CI는 필요하다 — **빌드·테스트·이미지는 CI, 배포는 CD**
- 두 시스템의 인계점은 **Git 커밋**
- DORA 4지표 = 배포 빈도·리드타임(속도) + 변경 실패율·복구 시간(안정성)
- **속도와 안정성은 트레이드오프가 아니다** — 작은 배포가 둘 다 개선한다
- 복구 시간을 줄이는 최선은 장애를 없애는 게 아니라 **롤백을 쉽게** 만드는 것
- 브랜치는 짧게 산다 — **Git Flow는 지속적 통합과 상충**한다
