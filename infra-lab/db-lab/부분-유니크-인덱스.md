# 부분 유니크 인덱스 (Partial Unique Index)

> 메모: WHERE 조건을 붙인 유니크 인덱스. '취소된 행은 중복 검사에서 빼기' 같은 규칙을 DB에서 표현할 수 있다

---

## 개념

일반 UNIQUE 제약은 **테이블의 모든 행**을 대상으로 유일성을 검사한다.
부분 유니크 인덱스는 `WHERE` 조건에 맞는 행만 검사한다.

```sql
-- 모든 행이 대상
ALTER TABLE pt_session ADD CONSTRAINT uq_slot UNIQUE (trainer_id, session_date, session_time);

-- 취소되지 않은 행만 대상
CREATE UNIQUE INDEX uq_slot ON pt_session (trainer_id, session_date, session_time)
WHERE status <> 'CANCELLED';
```

**언제 쓰나** — "어떤 상태의 행은 유일성 검사에서 빼야 한다"는 규칙이 있을 때.

| 상황 | 조건 |
|---|---|
| 취소된 예약은 슬롯을 비운다 | `WHERE status <> 'CANCELLED'` |
| 소프트 삭제된 행은 중복 검사 제외 | `WHERE deleted_at IS NULL` |
| 기본 배송지는 사용자당 하나 | `WHERE is_default` |

### 제약이 아니라 인덱스다

부분 유니크는 `ALTER TABLE ... ADD CONSTRAINT`로 만들 수 없다. `CREATE UNIQUE INDEX`만 가능하다.
그래서 `information_schema.table_constraints`에는 안 나오고 `pg_indexes`에 나온다.

실용적으로는 차이가 거의 없다. **위반하면 똑같이 23505를 내고, 오류에 인덱스 이름이 실린다.**

```python
except IntegrityError as exc:
    exc.orig.diag.constraint_name   # 'uq_trainer_slot' — 인덱스여도 여기 실린다
```

`ON CONFLICT` 절에서도 `ON CONFLICT (a, b) WHERE ...`로 쓸 수 있다.

## 실행

```sql
CREATE TABLE pt_session (
    session_id   INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    member_id    INTEGER NOT NULL,
    trainer_id   INTEGER NOT NULL,
    session_date DATE NOT NULL,
    session_time VARCHAR(5) NOT NULL,
    status       VARCHAR(20) NOT NULL DEFAULT 'SCHEDULED'
);

CREATE UNIQUE INDEX uq_trainer_slot
    ON pt_session (trainer_id, session_date, session_time)
    WHERE status <> 'CANCELLED';
```

동작 확인 — 취소한 슬롯은 다시 쓸 수 있고, 살아 있는 슬롯은 막힌다.

```
취소된 슬롯 재예약 -> 18          (성공)
중복 예약 -> 거부됨: uq_trainer_slot
```

SQLAlchemy에서는 `__table_args__`에 `Index(..., unique=True, postgresql_where=...)`로 쓴다.

```python
Index(
    "uq_trainer_slot", "trainer_id", "session_date", "session_time",
    unique=True,
    postgresql_where=text("status <> 'CANCELLED'"),
)
```

기존 UNIQUE 제약에서 갈아탈 때는 제약을 먼저 떼야 한다. 제약을 지우면 뒤에 있는 인덱스도 같이 사라진다.

```sql
ALTER TABLE pt_session DROP CONSTRAINT IF EXISTS uq_trainer_slot;
DROP INDEX IF EXISTS uq_trainer_slot;          -- 인덱스로 존재하는 경우까지
CREATE UNIQUE INDEX uq_trainer_slot ON ... WHERE status <> 'CANCELLED';
```

## 배운 점

**부분 유니크는 일반 UNIQUE보다 느슨하다.** 검사 대상이 줄어들 뿐이라
기존 데이터가 새 인덱스를 위반할 일이 없다. 방향이 반대(느슨 → 엄격)면 기존 행부터 확인해야 한다.

**업무 규칙을 애플리케이션이 아니라 DB에 두면 어느 경로로 들어와도 같게 적용된다.**
"조회해서 없으면 INSERT"는 동시 요청 두 개가 나란히 통과할 수 있다.
