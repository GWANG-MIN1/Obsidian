# 10 신뢰성 운영

앞의 9장은 각각의 기법이다. 이 장은 그것들을 **지속되는 운영 체계**로 묶는다.  
좋은 도구를 다 갖춰도 **온콜이 번아웃되고, 런북이 낡고, 액션 아이템이 방치되면** 신뢰성은 유지되지 않는다.

---

## 온콜 로테이션

```
지속 가능한 온콜의 조건
  □ 주기가 짧다 (1주 이하)
  □ 인원이 충분하다 (최소 4~6명, 그래야 6주에 1번)
  □ 1차·2차 백업이 있다
  □ 알림이 하루 5건 이하
  □ 보상이 있다 (수당 또는 대체 휴가)
  □ 온콜 중에는 다른 업무 부담을 줄인다
```

| 안티패턴 | 결과 |
|---|---|
| 한 사람이 상시 온콜 | 번아웃 → 퇴사 → 지식 소실 |
| 인원 2명 로테이션 | 격주 온콜 → 지속 불가 |
| 알림 하루 20건 | **무시하게 되고 진짜 장애를 놓친다** |
| 온콜에 조치 권한 없음 | 결국 다른 사람을 깨운다 |
| 신규 입사자 단독 온콜 | 섀도잉 없이는 위험 |
| 개발자와 운영자가 분리 | 만든 사람이 고통을 모른다 |

> ⭐ **"자기가 만든 것을 자기가 온콜한다"(you build it, you run it)** 가 신뢰성 개선의 가장 강력한 동기다.  
> 새벽에 깨워지는 사람이 코드를 고칠 수 있는 사람이면, 알림은 자연스럽게 줄어든다.

### 인수인계

```
온콜 교대 시 넘기는 것
  □ 진행 중인 이슈
  □ 알려진 문제 (알림이 울릴 수 있는 것)
  □ 예정된 배포·작업
  □ 걸려 있는 사일런스 (만료 시각 포함)
  □ 임시 조치 상태
```

> ⚠️ **걸려 있는 사일런스를 안 넘기면 다음 온콜은 알림이 꺼진 줄 모른다.** 사일런스에 만료 시간을 반드시 넣는 이유다. → `../observability-lab/05-alerting/`

## 런북

**알림 하나에 런북 하나.** 런북 없는 알림은 "뭔가 잘못됐다"만 알려주고 끝난다.

```markdown
# 런북: SampleAppDown

## 의미
sample-app 의 가용 레플리카가 0이다. 배포 경로 전체의 카나리이므로,
이게 죽었다면 GitOps 가 깨진 것이거나 노드가 사라진 것이다.

## 영향
데모 워크로드 불가. 실제 사용자 영향은 없으나 플랫폼 이상 신호.

## 확인
```bash
kubectl -n sample-app get pods
kubectl -n sample-app describe deploy sample-app
kubectl -n argocd get application sample-app
kubectl get nodes
```

## 흔한 원인과 조치
| 증상 | 원인 | 조치 |
|---|---|---|
| Pending | 노드 자원 부족·max-pods | 노드 확인, 필요 시 증설 |
| ImagePullBackOff | 이미지 태그 오류 | Git 이미지 태그 확인 |
| ArgoCD OutOfSync | 동기화 실패 | `argocd app sync` 로그 확인 |
| 노드 0대 | Spot 전량 회수 | 노드그룹·Karpenter 확인 |

## 에스컬레이션
30분 내 미해결 시 2차 온콜.

## 관련
- 대시보드: <링크>
- 포스트모템: <링크>
```

| 좋은 런북 | 나쁜 런북 |
|---|---|
| 복붙 가능한 명령 | "확인해보세요" |
| 증상 → 원인 → 조치 표 | 긴 산문 |
| 에스컬레이션 기준 명시 | 없음 |
| 최종 검증일 기록 | 언제 쓴 건지 모름 |

> ⚠️ **런북은 반드시 낡는다.** 명령이 안 먹고, 대시보드 링크가 죽고, 구성이 바뀐다.  
> **게임데이에서 런북을 실제로 따라가 보는 게 가장 좋은 갱신 방법**이다. → `09-chaos-engineering/`  
> 런북에 **"최종 검증일"** 을 적어두면 낡은 걸 알아챌 수 있다.

## 변경 관리

```
장애의 대부분은 변경에서 온다
      ↓
그렇다고 변경을 줄이면? → 변경이 커지고 위험해진다
      ↓
✅ 변경을 작게, 자주, 되돌릴 수 있게
```

| 장치 | 역할 |
|---|---|
| **작은 PR** | 문제 범위가 좁아진다 |
| **CI 게이트** | 자동 검증 → `../cicd-lab/03-github-actions-advanced/` |
| **점진 배포** | 카나리·블루그린 → `../cicd-lab/09-argo-rollouts/` |
| **자동 롤백** | MTTR 단축 |
| **변경 창(freeze)** | 위험한 시기에는 멈춘다 |
| **변경 기록** | 장애 시 "뭘 바꿨나"에 즉답 |

### 변경 동결

```
동결이 정당한 경우          동결이 해로운 경우
  블랙프라이데이 등 성수기      "장애가 났으니 당분간 배포 금지"
  대규모 이벤트 기간            → 변경이 쌓여 다음 배포가 더 위험해진다
  연말연시 (대응 인력 부족)
```

> ⚠️ **"장애가 났으니 배포를 멈추자"는 대개 역효과다.** 변경이 쌓이면 다음 배포의 크기와 위험이 커진다.  
> 대신 **에러 버짓 정책**으로 판단한다 — 버짓이 없으면 기능 배포를 멈추고 안정화에 집중하되, 안정화 변경은 계속 배포한다. → `02-slo-operations/`

### 변경 기록이 곧 진단 도구다

```bash
# 장애 시 "최근에 뭘 바꿨나"에 즉답할 수 있어야 한다
git log --oneline --since="2 hours ago"
kubectl -n argocd get applications -o wide
kubectl -n myapp rollout history deploy/myapp
```

> **GitOps의 숨은 이점이 이것이다.** 모든 변경이 커밋으로 남아 있어 타임라인 재구성이 쉽다. → `../cicd-lab/07-gitops-repo-strategy/`

## 토일(Toil) 줄이기

```
토일 = 반복적이고, 수동이고, 자동화 가능하고, 가치를 늘리지 않는 작업
```

| 토일의 예 | 자동화 |
|---|---|
| 매번 손으로 롤백 | 자동 롤백 (Argo Rollouts) |
| 인증서 수동 갱신 | cert-manager |
| 디스크 차면 수동 정리 | 로그 로테이션·보존 정책 |
| 매주 수동 백업 확인 | 백업 성공 알림 |
| 같은 알림에 같은 조치 반복 | 자동 복구 또는 알림 삭제 |
| 수동 스케일 조정 | HPA |

```
SRE 관행: 토일이 업무 시간의 50% 를 넘으면 개선 작업을 우선한다
```

> ⭐ **"이 알림에 매번 같은 조치를 한다"면 자동화하거나 알림을 없앨 후보다.**  
> 자동으로 복구되는 문제에 사람을 깨우는 건 순수한 토일이다. → `../observability-lab/05-alerting/`

## 신뢰성 리뷰 루틴

```
주간
  □ SLO 번레이트·에러 버짓 소진율
  □ 발생한 알림 목록 — 오탐은 없었나, 조치 가능했나
  □ 온콜 부담 (알림 건수·야간 호출 수)

월간
  □ SLO 달성 여부, 목표값 적정성
  □ 포스트모템 액션 아이템 완료율
  □ 반복되는 알림 상위 5개 → 근본 대응
  □ 용량 추세 → 08-capacity-planning/

분기
  □ 복구 리허설 (백업·DR) → 07-backup-dr/
  □ 게임데이 → 09-chaos-engineering/
  □ 런북 검증·갱신
  □ 온콜 로테이션·보상 점검
  □ SLI 정의 재검토
```

```promql
# 리뷰용 지표
sum(increase(kube_pod_container_status_restarts_total[7d]))       # 재시작 총량
count(kube_deployment_spec_replicas < 2)                          # 단일 레플리카
count(kube_poddisruptionbudget_status_pod_disruptions_allowed == 0) # 막힌 PDB
sum(increase(kube_pod_status_reason{reason="Evicted"}[7d]))       # 축출
```

## 신뢰성 성숙도

```
1단계 반응형    장애가 나면 대응한다. 알림도 부실.
2단계 관측      SLI·대시보드·알림이 있다. 원인을 안다.
3단계 예방      SLO·에러 버짓·포스트모템이 돈다. 재발이 준다.
4단계 검증      카오스·게임데이·복구 리허설로 가정을 확인한다.
5단계 자동      자동 롤백·자동 복구. 사람이 개입할 일이 준다.
```

> **단계를 건너뛸 수 없다.** 관측성 없이 카오스를 하면 장애이고, SLO 없이 자동화를 하면 무엇을 지키는지 모른다.  
> 이 트랙 전체가 그 순서로 배치돼 있다 — **관측(observability) → 정의(SLO) → 대응(incident) → 학습(postmortem) → 설계(patterns·k8s) → 대비(backup·capacity) → 검증(chaos) → 운영(여기)**.

## 신뢰성과 다른 목표의 충돌

| 충돌 | 조정 |
|---|---|
| **속도 vs 안정성** | 에러 버짓으로 판단 → `02-slo-operations/` |
| **비용 vs 여유** | 안전 여유는 비용이다. SLO를 근거로 정당화 → `../cost-lab/01-finops-basics/` |
| **보안 vs 가용성** | Enforce 정책이 배포를 막을 수 있다. Audit부터 → `../security-lab/01-security-basics/` |
| **기능 vs 신뢰성 부채** | 액션 아이템을 백로그에 정식 등록 |

> ⭐ **이 충돌들은 해결하는 게 아니라 명시적으로 조정하는 것이다.**  
> 암묵적으로 두면 항상 급한 쪽(기능·비용)이 이기고, 신뢰성 부채가 쌓인다. **에러 버짓이 그 조정을 숫자로 만든다.**

## 마지막 — 도구보다 습관

```
갖춰야 할 것보다 중요한 것은 '실제로 돌아가는가' 다

□ 알림이 오면 사람이 실제로 조치하는가
□ 포스트모템 액션 아이템이 실제로 완료되는가
□ 런북대로 하면 실제로 복구되는가
□ 백업에서 실제로 복구해봤는가
□ 롤백을 실제로 해봤는가
```

> ⭐ **이 트랙 전체를 관통하는 한 문장:**  
> **"선언한 것과 실제로 동작하는 것은 다르다."**  
> Kyverno 정책은 bad-pod로, NetworkPolicy는 차단 테스트로, Spot은 drain으로, 백업은 복구 리허설로, 복원력은 카오스 실험으로 확인한다.  
> **확인하지 않은 것은 갖춘 것이 아니다.**

## 배운 점

- 도구를 다 갖춰도 **온콜 번아웃·낡은 런북·방치된 액션 아이템**이면 유지되지 않는다
- 지속 가능한 온콜: **1주 이하 주기, 4~6명 이상, 하루 5건 이하 알림, 보상**
- ⭐ **"자기가 만든 것을 자기가 온콜한다"** 가 신뢰성 개선의 가장 강력한 동기
- ⚠️ 인수인계 시 **걸려 있는 사일런스**를 반드시 넘긴다
- **알림 하나에 런북 하나** — 런북 없는 알림은 "뭔가 잘못됐다"만 알려준다
- 좋은 런북은 **복붙 가능한 명령 + 증상/원인/조치 표 + 에스컬레이션 기준**
- ⚠️ **런북은 반드시 낡는다** — 게임데이에서 따라가 보는 게 최고의 갱신 방법
- 장애의 대부분은 변경에서 온다 — 그래서 **작게·자주·되돌릴 수 있게**
- ⚠️ **"장애가 났으니 배포 금지"는 역효과** — 변경이 쌓여 다음이 더 위험해진다
- 대신 **에러 버짓으로 판단**한다 (기능은 멈추되 안정화 변경은 계속)
- **GitOps의 숨은 이점은 변경 기록** — "뭘 바꿨나"에 즉답할 수 있다
- ⭐ **같은 알림에 매번 같은 조치를 한다면 자동화하거나 알림을 없앤다**
- 토일이 업무의 50%를 넘으면 개선 작업을 우선한다
- 성숙도: **반응형 → 관측 → 예방 → 검증 → 자동** (건너뛸 수 없다)
- ⭐ 속도·비용·보안과의 충돌은 **해결이 아니라 명시적 조정** — 에러 버짓이 그 수단
- 암묵적으로 두면 항상 급한 쪽이 이기고 **신뢰성 부채가 쌓인다**
- ⭐ **"선언한 것과 실제로 동작하는 것은 다르다"** — 확인하지 않은 것은 갖춘 것이 아니다
