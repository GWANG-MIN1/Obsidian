# 05 복원력 패턴

의존하는 서비스는 반드시 언젠가 느려지거나 죽는다. **그때 내 서비스가 어떻게 행동하는가**가 복원력이다.  
잘못 설계하면 의존성 하나의 지연이 전체 시스템을 무너뜨린다 — **연쇄 장애**다.

---

## 연쇄 장애가 일어나는 방식

```
서비스 A 응답이 느려짐 (5초)
      ↓
호출자 B: 타임아웃 없음 → 스레드가 5초씩 묶임
      ↓
B 의 스레드 풀 고갈 → B 도 응답 못 함
      ↓
B 의 호출자 C: 실패 → 즉시 재시도 → A 에 부하 2배
      ↓
A 완전히 죽음 → 전체 장애
```

| 증폭 요인 | 대응 패턴 |
|---|---|
| 타임아웃 없음 | **타임아웃** |
| 무제한 재시도 | **백오프 + 지터 + 재시도 예산** |
| 죽은 서비스를 계속 호출 | **서킷 브레이커** |
| 자원을 공유 | **벌크헤드** |
| 전부 아니면 전무 | **우아한 성능 저하** |

> ⭐ **재시도가 장애를 증폭시킨다는 게 핵심이다.** 선의로 넣은 재시도가 죽어가는 서비스에 마지막 일격을 가한다.

---

## 타임아웃 — 가장 기본이자 가장 자주 빠뜨리는 것

```
타임아웃이 없다 = 무한히 기다린다 = 스레드가 영원히 묶인다
```

```
타임아웃 예산 (상위가 하위보다 커야 한다)
  클라이언트    10s
    └─ API      8s
        └─ 서비스 B  5s
            └─ DB     2s
```

| 잘못된 설정 | 결과 |
|---|---|
| 하위가 상위보다 김 | 상위가 먼저 끊어 하위 작업이 낭비된다 |
| 전부 같은 값 | 어디서 끊겼는지 모른다 |
| 너무 짧음 | 정상 요청도 실패 |
| **없음** | **스레드 고갈 → 연쇄 장애** |

```yaml
# Kubernetes 쪽 타임아웃도 함께 본다
readinessProbe:
  timeoutSeconds: 3          # 기본값 1초는 너무 짧은 경우가 많다
  periodSeconds: 5
  failureThreshold: 3
```

> **타임아웃 값은 p99 지연 × 2~3 정도**에서 시작한다. 평균으로 잡으면 정상 요청의 상당수가 잘린다.  
> ⚠️ **타임아웃이 곧 실패는 아니다.** 서버 쪽은 이미 처리했는데 클라이언트만 끊긴 경우가 있다 — 그래서 재시도는 **멱등한 작업**에만 안전하다.

---

## 재시도 — 백오프와 지터

```
❌ 즉시 재시도 3회
   장애 중인 서비스에 순간 부하 3배

✅ 지수 백오프 + 지터
   1s → 2s → 4s (각각 ±무작위)
```

```
지수 백오프만 쓰면
  모든 클라이언트가 정확히 1s, 2s, 4s 후에 동시에 재시도
        ↓
  동기화된 파도 (thundering herd) → 회복 직후 다시 죽는다  💥

지터(무작위 지연)를 더하면
  재시도가 시간축에 흩어진다
```

```python
# 완전 지터 (full jitter) — 실무에서 가장 안전한 형태
delay = random.uniform(0, min(cap, base * 2 ** attempt))
```

| 재시도해도 되는 것 | 재시도하면 안 되는 것 |
|---|---|
| 5xx, 타임아웃, 연결 실패 | **4xx (클라이언트 잘못)** |
| 멱등한 작업 (GET, PUT) | **비멱등 작업 (POST 결제)** |
| 일시적 오류 | 영구적 오류 |

> ⚠️ **비멱등 요청의 재시도는 중복 처리를 만든다.** 결제가 두 번 되는 사고가 여기서 나온다.  
> 해법은 **멱등성 키(idempotency key)** — 같은 키의 요청은 한 번만 처리한다.

### 재시도 예산

```
전체 요청의 10% 까지만 재시도 허용
  → 대규모 장애 시 재시도가 부하를 증폭시키는 걸 막는다
```

> 개별 요청의 재시도 횟수만 제한하면, **요청이 많을 때 전체 재시도량은 여전히 폭발한다.** 시스템 전체 관점의 예산이 필요하다.

## 서킷 브레이커

```
Closed (정상)
   │  실패율이 임계 초과
   ▼
Open (차단)  ── 호출 자체를 안 한다. 즉시 실패 반환.
   │  일정 시간 후
   ▼
Half-Open (탐색) ── 소수 요청만 흘려보고 판단
   ├─ 성공 → Closed
   └─ 실패 → Open
```

| 상태 | 동작 |
|---|---|
| **Closed** | 정상 호출, 실패율 집계 |
| **Open** | 호출하지 않고 즉시 실패 (또는 폴백) |
| **Half-Open** | 소수 요청으로 회복 여부 탐색 |

```
서킷 브레이커가 주는 것
  ① 죽은 서비스를 계속 때리지 않는다  → 회복할 여유를 준다
  ② 호출자가 빨리 실패한다            → 스레드가 안 묶인다
  ③ 폴백으로 전환할 지점이 생긴다
```

> ⭐ **"빨리 실패하는 것"이 오래 기다리는 것보다 낫다.** 5초 기다렸다 실패하는 것보다 즉시 실패하고 캐시된 값을 주는 게 사용자 경험이 좋다.  
> 구현은 라이브러리(Resilience4j, Polly)나 **서비스 메시(Istio `outlierDetection`)** 로 한다. → `../security-lab/08-network-security/`

```yaml
# Istio — 이상 감지로 서킷 브레이커 효과
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: backend
spec:
  host: backend
  trafficPolicy:
    connectionPool:
      tcp: { maxConnections: 100 }
      http: { http2MaxRequests: 1000, maxRequestsPerConnection: 10 }
    outlierDetection:
      consecutive5xxErrors: 5
      interval: 10s
      baseEjectionTime: 30s        # 문제 있는 엔드포인트를 30초 제외
      maxEjectionPercent: 50       # 절반 이상은 빼지 않는다
```

> ⚠️ **`maxEjectionPercent`가 중요하다.** 전부 제외하면 트래픽 보낼 곳이 없어져 완전 장애가 된다.

## 벌크헤드 — 격벽

배의 격벽처럼 **한 구역의 침수가 전체로 번지지 않게** 자원을 나눈다.

```
[ 벌크헤드 없음 ]
공유 스레드 풀 (100)
  ├─ 느린 의존성 호출이 90개를 점유
  └─ 나머지 기능도 스레드가 없어 실패      ← 무관한 기능까지 죽는다

[ 벌크헤드 ]
결제용 풀 (40)  |  검색용 풀 (40)  |  기타 (20)
  느린 검색이 40개를 다 써도 결제는 정상
```

| Kubernetes에서의 벌크헤드 |
|---|
| **네임스페이스 분리** + ResourceQuota |
| 워크로드별 **노드 풀 분리** (taint/toleration) |
| **PriorityClass** — 중요한 파드가 먼저 스케줄·나중에 축출 |
| 커넥션 풀을 의존성별로 분리 |

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: critical
value: 1000000
globalDefault: false
description: "결제 등 핵심 워크로드"
```

> 자원 경합 시 **낮은 우선순위 파드가 먼저 축출**된다. 배치 잡 때문에 결제 서비스가 죽는 걸 막는다. → `06-kubernetes-resilience/`

## 우아한 성능 저하 (Graceful Degradation)

```
❌ 추천 서비스가 죽음 → 상품 페이지 전체가 500
✅ 추천 서비스가 죽음 → 추천 영역만 비우고 상품 페이지는 정상
```

| 의존성 유형 | 실패 시 |
|---|---|
| **필수(critical)** | 실패해야 한다 (결제 시 DB) |
| **선택(optional)** | **없이도 동작해야 한다** (추천, 배너, 통계) |

```
설계 시 질문
  "이 의존성이 죽으면 사용자가 아무것도 못 하는가,
   아니면 일부 기능만 못 하는가?"
      ↓
  후자라면 폴백을 준비한다
```

| 폴백 전략 | 예시 |
|---|---|
| 캐시된 값 | 마지막으로 성공한 응답 |
| 기본값 | 인기 상품 고정 목록 |
| 빈 결과 | 추천 영역을 숨긴다 |
| 큐잉 | 나중에 처리 (비동기 전환) |

> ⭐ **가용성의 곱셈을 끊는 유일한 방법이다.** 직렬 의존은 가용성을 곱하지만, **선택적 의존은 실패해도 내 가용성에 영향이 없다.** → `01-reliability-basics/`  
> 대부분의 서비스에서 진짜 필수 의존성은 생각보다 적다. 분류만 해도 설계가 달라진다.

## 부하 제어

```
과부하가 오면
  ❌ 전부 받아서 전부 느려진다 → 전부 타임아웃 → 전멸
  ✅ 일부를 거절해서 나머지를 살린다
```

| 패턴 | 동작 |
|---|---|
| **레이트 리밋** | 클라이언트별 요청 수 제한 |
| **로드 셰딩** | 과부하 시 낮은 우선순위 요청부터 거절 |
| **큐 제한** | 대기열 길이 제한 (무한 큐는 지연만 늘린다) |
| 백프레셔 | 처리 속도에 맞춰 상류에 신호 |

> **429를 반환하는 건 실패가 아니라 방어다.** 전부 받아서 전부 죽는 것보다 낫다.  
> ⚠️ 다만 **의도한 레이트 리밋인지 용량 부족인지에 따라 SLI 포함 여부가 달라진다.** → `02-slo-operations/`  
> **무한 큐가 함정이다.** 큐가 길어지면 처리될 때쯤 클라이언트는 이미 타임아웃됐다 — 아무도 쓰지 않을 응답을 만드느라 자원을 쓴다.

## 상태와 멱등성

```
재시도·중복 전달이 불가피한 환경에서는
  "정확히 한 번(exactly once)" 은 사실상 불가능하다
      ↓
  "최소 한 번(at least once)" + 멱등한 처리 가 현실적인 답
```

```
멱등성 키
  클라이언트가 요청마다 고유 키를 붙인다
  서버는 같은 키의 요청을 한 번만 처리하고 결과를 캐시
      ↓
  재시도해도 안전하다
```

> **결제·주문처럼 중복이 치명적인 곳에는 반드시 필요하다.** 네트워크는 신뢰할 수 없으므로 중복은 반드시 온다.

## 어디에 구현할 것인가

| 계층 | 할 수 있는 것 | 못 하는 것 |
|---|---|---|
| **애플리케이션** | 폴백, 멱등성, 비즈니스 로직 기반 판단 | 언어마다 재구현 |
| **서비스 메시** | 타임아웃·재시도·서킷 브레이커·mTLS | 폴백 로직 |
| **Kubernetes** | probe, PDB, 우선순위, 자원 격리 | 요청 단위 제어 |

```
현실적인 조합
  Kubernetes    기본 격리·재시작·분산       → 06-kubernetes-resilience/
  애플리케이션    타임아웃·폴백·멱등성        ← 가장 중요
  서비스 메시     공통 정책 (필요해지면)      → 도입 비용 있음
```

> **서비스 메시로 타임아웃·재시도를 통일하는 건 매력적이지만 공짜가 아니다.** 사이드카가 리소스·지연·복잡도를 늘린다.  
> **애플리케이션 레벨의 타임아웃과 폴백이 먼저다.** 메시는 그걸 대체하는 게 아니라 보완한다. → `../security-lab/08-network-security/`

## 배운 점

- 복원력은 **의존성이 죽었을 때 내 서비스가 어떻게 행동하는가**
- ⭐ **재시도가 연쇄 장애를 증폭시킨다** — 선의의 재시도가 마지막 일격이 된다
- **타임아웃이 없으면 스레드가 묶여 연쇄 장애로 간다** — 가장 기본이자 가장 자주 빠뜨린다
- 타임아웃은 **상위가 하위보다 커야** 한다 (예산 구조)
- 타임아웃 값은 **p99 × 2~3**에서 시작 (평균으로 잡으면 정상 요청이 잘린다)
- ⚠️ **타임아웃 ≠ 실패** — 서버는 처리했을 수 있다 → 재시도는 멱등한 작업만
- **지수 백오프만으로는 부족하다 — 지터가 필요**하다 (동기화된 재시도 파도)
- **4xx는 재시도하지 않는다**, 비멱등 요청은 **멱등성 키**로 보호
- 개별 재시도 제한만으로는 부족 — **재시도 예산**(전체의 N%)이 필요
- 서킷 브레이커: **Closed → Open → Half-Open** — 죽은 서비스에 회복할 여유를 준다
- ⭐ **빨리 실패하는 게 오래 기다리는 것보다 낫다**
- ⚠️ Istio `outlierDetection`의 **`maxEjectionPercent`** 를 반드시 제한한다
- **벌크헤드**로 자원을 격리 — K8s에서는 네임스페이스·노드 풀·PriorityClass
- ⭐ **선택적 의존성은 실패해도 동작하게** 만든다 — 가용성의 곱셈을 끊는 유일한 방법
- 의존성을 **필수/선택으로 분류**만 해도 설계가 달라진다
- **429를 반환하는 건 실패가 아니라 방어** — 전부 받아 전멸하는 것보다 낫다
- ⚠️ **무한 큐가 함정** — 처리될 때쯤 클라이언트는 이미 타임아웃됐다
- "정확히 한 번"은 사실상 불가능 — **"최소 한 번 + 멱등 처리"** 가 현실적
- **애플리케이션 레벨 타임아웃·폴백이 먼저**, 서비스 메시는 보완이지 대체가 아니다
