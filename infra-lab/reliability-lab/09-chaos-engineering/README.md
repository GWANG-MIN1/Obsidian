# 09 카오스 엔지니어링

카오스 엔지니어링은 **"장애를 일부러 일으키는 것"** 이 아니라 **"시스템이 우리 생각대로 동작하는지 실험으로 확인하는 것"** 이다.  
목표는 부수는 게 아니라 **가정이 틀렸다는 걸 통제된 환경에서 먼저 발견하는 것**이다.

---

## 왜 필요한가

```
"레플리카가 3개니까 노드 하나 죽어도 괜찮다"
        ↓ 실제로는
레플리카 3개가 전부 같은 노드에 있었다   → 노드 하나 = 전멸

"PDB 를 걸었으니 안전하다"
        ↓ 실제로는
minAvailable 이 레플리카 수와 같아 드레인이 멈춘다

"readiness probe 가 있으니 무중단이다"
        ↓ 실제로는
/healthz 가 항상 200 을 반환하는 껍데기였다
```

> ⭐ **설정을 선언한 것과 실제로 동작하는 것은 다르다.** 이건 이 저장소 전체를 관통하는 패턴이다 —  
> Kyverno 정책의 **bad-pod 대조 실험**, NetworkPolicy의 **차단 테스트**, Spot의 **drain 검증**, 백업의 **복구 리허설**.  
> 카오스 엔지니어링은 그 검증을 **체계화한 것**이다. → `../security-lab/04-kyverno/` `07-backup-dr/`

---

## 원칙

```
① 정상 상태(steady state)를 정의한다      SLI 로 측정 가능해야 한다
② 가설을 세운다                          "노드 하나가 죽어도 에러율은 1% 미만이다"
③ 현실적인 이벤트를 주입한다              노드 종료, 지연 추가, 파드 삭제
④ 가설을 검증한다                        실제 SLI 를 관찰
⑤ 폭발 반경을 최소화한다                 ⭐ 가장 중요
```

```
❌ "일단 프로덕션에서 뭔가 부숴보자"        → 그냥 장애다
✅ "가설 → 최소 범위 실험 → 관찰 → 확대"   → 실험이다
```

> **가설이 없으면 실험이 아니다.** "노드를 죽여보자"가 아니라 **"노드가 죽으면 에러율이 1% 미만일 것이다"** 라고 먼저 적는다.  
> 가설이 맞으면 자신감을 얻고, 틀리면 **가장 싼 방법으로 결함을 찾은 것**이다.

---

## 폭발 반경 제한

```
좁게 시작해서 넓힌다

1. 개발 환경 · 파드 1개
2. 개발 환경 · 서비스 전체
3. 스테이징
4. 프로덕션 · 트래픽 1% · 업무 시간
5. 프로덕션 · 전체
```

| 안전장치 | |
|---|---|
| **중단 버튼** | 언제든 실험을 즉시 멈출 수 있어야 한다 |
| 시간 제한 | 실험은 자동으로 종료되게 |
| 관찰 준비 | 실험 전에 대시보드를 열어둔다 |
| 사전 공지 | 온콜이 실제 장애로 오인하지 않게 |
| 업무 시간 | 대응 인력이 있을 때 |

> ⚠️ **"실험을 멈출 수 없다면 시작하지 않는다."** 이게 카오스 엔지니어링의 절대 규칙이다.  
> 사전 공지 없이 하면 온콜이 실제 장애로 대응하느라 자원을 낭비하고, 신뢰도 잃는다.

## ⭐ 도구 없이 시작하기

**첫 실험에는 도구가 필요 없다.** `kubectl` 세 줄이면 대부분의 가정을 검증할 수 있다.

```bash
# 실험 1 — 파드 하나를 죽인다
#   가설: 에러율 변화 없음, 30초 내 새 파드 Ready
kubectl -n myapp delete pod <POD>
kubectl -n myapp get pods -w

# 실험 2 — 노드 하나를 비운다 (Spot 중단 시뮬레이션)
#   가설: 파드가 다른 노드로 이동, 서비스 무중단
kubectl drain <NODE> --ignore-daemonsets --delete-emptydir-data
kubectl uncordon <NODE>

# 실험 3 — 의존성을 제거한다
#   가설: 추천 서비스가 죽어도 상품 페이지는 200 을 반환
kubectl -n myapp scale deploy/recommendation --replicas=0
curl -s -o /dev/null -w "%{http_code}\n" https://app.example.com/product/1
kubectl -n myapp scale deploy/recommendation --replicas=2

# 실험 4 — 레플리카를 1개로 줄인다
#   가설: PDB 때문에 드레인이 막힌다 (막혀야 정상)
```

> ⭐ **실험 2가 가장 가성비가 높다.** Spot 중단, Karpenter consolidation, 노드 업그레이드가 전부 이 상황이다.  
> `drain`이 안 끝나거나 서비스가 끊기면, **실제 Spot 회수 때도 똑같이 끊긴다.** → `../cost-lab/05-spot-instances/`

## 무엇을 실험할 것인가

| 실험 | 검증하는 가정 |
|---|---|
| **파드 삭제** | 셀프힐링, readiness 정확도 |
| **노드 드레인** | 토폴로지 분산, PDB, 우아한 종료 |
| **노드 강제 종료** | 5분 축출 지연 동안 서비스 유지 |
| **의존성 제거** | 우아한 성능 저하 → `05-resilience-patterns/` |
| **지연 주입** | 타임아웃 설정, 서킷 브레이커 |
| **CPU·메모리 압박** | 리소스 설정, 축출 우선순위 |
| **AZ 격리** | 크로스 AZ 분산, 단일 NAT의 영향 |
| **DNS 실패** | 재시도·캐시 동작 |
| **디스크 가득** | 로그 로테이션, PV 여유 |

### 이 저장소 구성에서 특히 검증할 것

```
□ single_nat_gateway = true  →  그 AZ 를 격리하면 전체 아웃바운드가 끊기는가
                                (설계상 그래야 한다 — 확인이 목적)
□ SPOT 노드                   →  drain 시 서비스가 유지되는가
□ PVC 없는 관측성 스택         →  파드 재시작 시 메트릭이 사라지는가
                                (사라지는 게 정상 — 영향 범위를 아는 게 목적)
□ sample-app                  →  배포 경로 전체의 카나리로 동작하는가
```

> **"의도한 대로 실패하는가"를 확인하는 실험도 가치가 있다.** 단일 NAT의 AZ 장애 영향을 실제로 보면, prod에서 왜 뒤집어야 하는지가 숫자로 남는다. → `01-reliability-basics/`

## 도구

| 도구 | 특징 |
|---|---|
| **Chaos Mesh** | CNCF, K8s 네이티브, CRD 기반, 웹 UI |
| **LitmusChaos** | CNCF, 실험 허브, GitOps 친화 |
| AWS FIS | AWS 관리형, EC2·EKS·RDS 대상 |
| Gremlin | 상용, 안전장치가 강함 |

```yaml
# Chaos Mesh — 파드 장애 주입
apiVersion: chaos-mesh.org/v1alpha1
kind: PodChaos
metadata:
  name: pod-kill-experiment
  namespace: myapp
spec:
  action: pod-kill
  mode: one                        # ⭐ one / fixed / percent — 폭발 반경
  selector:
    namespaces: [myapp]
    labelSelectors:
      app: myapp
  duration: "30s"                  # ⭐ 자동 종료
```

```yaml
# 네트워크 지연 주입 — 타임아웃 설정 검증
apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
metadata:
  name: delay-db
spec:
  action: delay
  mode: all
  selector:
    namespaces: [myapp]
    labelSelectors: { app: myapp }
  delay:
    latency: "2s"
    jitter: "500ms"
  direction: to
  target:
    mode: all
    selector:
      namespaces: [database]
  duration: "5m"
```

> ⚠️ **`mode`와 `duration`이 안전장치다.** `mode: all` + `duration` 없음은 프로덕션에서 절대 쓰지 않는다.  
> 카오스 도구 자체가 클러스터 권한을 많이 요구한다 — **RBAC 범위를 제한**하고 프로덕션에는 신중히 도입한다. → `../security-lab/05-rbac-least-privilege/`

## 게임데이

```
정해진 시간에 팀이 모여 시나리오를 실행하고 대응해본다
  → 시스템만이 아니라 '사람과 절차' 를 테스트한다
```

```
게임데이 시나리오 예시
  "결제 DB 가 응답하지 않는다. 대응하라."
      ├─ 온콜이 알림을 받는가
      ├─ 심각도를 올바르게 판단하는가
      ├─ 런북을 찾을 수 있는가
      ├─ 롤백·페일오버를 실행할 수 있는가
      ├─ 커뮤니케이션이 이뤄지는가
      └─ 몇 분 만에 완화되는가 (MTTR 측정)
```

| 게임데이에서 드러나는 것 | |
|---|---|
| 런북이 오래돼 안 맞는다 | 문서 갱신 |
| 권한이 없어 조치를 못 한다 | break-glass 절차 |
| 알림이 안 왔다 | 알림 설정 |
| 누가 IC인지 몰랐다 | 역할 정의 |
| 대시보드에 필요한 지표가 없다 | 관측성 보강 |

> ⭐ **게임데이는 신규 입사자 온보딩에 특히 효과적이다.** 실제 장애 전에 절차를 한 번 겪어볼 수 있다.  
> 시스템 결함보다 **절차·문서·권한의 결함이 더 많이 발견**된다. → `03-incident-response/` `10-reliability-operations/`

## 언제 시작할 것인가

```
❌ 아직 없는 것들
   관측성이 없다        → 실험 결과를 관찰할 수 없다
   알림이 안 돌아간다    → 실험이 장애가 된다
   롤백을 못 한다       → 실험을 되돌릴 수 없다
   기본 복원력이 없다    → 뻔한 결과만 확인한다 (레플리카 1개면 당연히 죽는다)

✅ 준비됐다면
   SLI·대시보드가 있고
   기본 복원력 설정(probe·PDB·분산)이 되어 있고
   롤백 절차가 검증돼 있다
```

> ⚠️ **관측성 없이 카오스 실험을 하면 그냥 장애다.** 무슨 일이 일어났는지 볼 수 없다.  
> 순서는 **관측성 → 기본 복원력 → 검증(카오스)** 이다. 이건 Argo Rollouts를 관측성 위에 세우는 것과 같은 논리다. → `../cicd-lab/09-argo-rollouts/`

## 실험 기록

```markdown
# 실험: 노드 1대 드레인 (2026-08-09)

## 가설
myapp 파드가 2개 노드에 분산돼 있으므로, 노드 1대를 드레인해도
5xx 에러율은 1% 미만을 유지하고 드레인은 2분 내 완료된다.

## 폭발 반경
dev 클러스터, myapp 네임스페이스, 노드 1대. 중단: uncordon.

## 결과
❌ 가설 반증
- 드레인이 완료되지 않음 (PDB minAvailable=3, 레플리카=3)
- 5xx 는 발생하지 않음 (파드가 안 옮겨졌으므로)

## 발견
PDB 의 minAvailable 이 레플리카 수와 같아 축출이 0개 허용된다.
→ 클러스터 업그레이드도 같은 이유로 멈출 것이다.

## 액션
1. minAvailable 을 2 로 조정 (@a, 08-16)
2. PDB 설정 검증을 매니페스트 리뷰 체크리스트에 추가 (@b, 08-16)
3. kube_poddisruptionbudget_status_pod_disruptions_allowed == 0 알림 추가 (@a, 08-16)
```

> **가설이 반증된 실험이 가장 가치 있다.** 성공한 실험은 자신감을 주고, 실패한 실험은 결함을 준다.  
> 기록 형식은 포스트모템과 같다 — **가설·결과·발견·액션**. → `04-postmortem/`

## 배운 점

- 카오스 엔지니어링은 부수는 게 아니라 **가정을 실험으로 검증**하는 것
- ⭐ **선언한 것과 실제로 동작하는 것은 다르다** — 이 저장소 전체를 관통하는 패턴
- **가설이 없으면 실험이 아니다** — 먼저 예상을 글로 적는다
- 원칙: 정상 상태 정의 → 가설 → 이벤트 주입 → 검증 → **폭발 반경 최소화**
- ⚠️ **"실험을 멈출 수 없다면 시작하지 않는다"**
- 사전 공지 없이 하면 **온콜이 실제 장애로 대응**한다
- ⭐ **첫 실험에는 도구가 필요 없다** — `kubectl delete pod`, `kubectl drain`
- ⭐ **노드 드레인 실험이 가성비 최고** — Spot 중단·consolidation·업그레이드가 전부 같은 상황
- **"의도한 대로 실패하는가"** 를 확인하는 실험도 가치가 있다 (단일 NAT의 AZ 영향)
- Chaos Mesh의 **`mode`와 `duration`이 안전장치** — `all` + 무제한은 프로덕션 금지
- 카오스 도구는 **권한을 많이 요구**한다 — RBAC 범위를 제한한다
- **게임데이는 시스템이 아니라 사람과 절차를 테스트**한다
- 게임데이에서는 **런북·권한·역할의 결함이 더 많이** 발견된다
- 신규 입사자 온보딩에 효과적이다
- ⚠️ **관측성 없이 카오스 실험을 하면 그냥 장애다**
- 순서는 **관측성 → 기본 복원력 → 검증(카오스)**
- **가설이 반증된 실험이 가장 가치 있다** — 가장 싼 방법으로 결함을 찾은 것
