# 01 신뢰성 기초

**신뢰성은 장애를 없애는 일이 아니다.** 분산 시스템에서 부분 고장은 상시 발생하고, 없앨 수 없다.  
목표는 **고장이 사용자에게 도달하지 않게 만들고, 도달했을 때 빨리 회복하는 것**이다.

---

## 실패는 예외가 아니라 정상 상태

```
노드 100대 × 연간 고장률 2%  →  거의 매주 한 대는 죽는다
파드 500개 × 재시작 확률      →  매일 몇 개는 재시작한다
AZ 3개 × 연간 장애 확률       →  언젠가는 한 AZ 가 빠진다
```

| 잘못된 전제 | 현실 |
|---|---|
| 네트워크는 신뢰할 수 있다 | 패킷은 유실되고 지연된다 |
| 지연은 0이다 | 크로스 AZ만 해도 ms 단위 |
| 대역폭은 무한하다 | 한계가 있다 |
| 토폴로지는 변하지 않는다 | 파드는 계속 뜨고 죽는다 |
| 전송 비용은 0이다 | 크로스 AZ는 과금된다 |

> **분산 컴퓨팅의 오류(Fallacies of Distributed Computing)** 로 알려진 목록이다. 시스템이 커질수록 이 전제들이 하나씩 배신한다.  
> 그래서 설계 질문은 **"고장 나지 않게 하려면?"** 이 아니라 **"고장 났을 때 어떻게 되는가?"** 다.

---

## 가용성 vs 신뢰성 vs 복원력

| 용어 | 의미 |
|---|---|
| **가용성 (Availability)** | 지금 쓸 수 있는가 (시간 비율) |
| **신뢰성 (Reliability)** | 정해진 기간 동안 제대로 동작하는가 |
| **복원력 (Resilience)** | 고장이 나도 **기능을 유지·회복**하는 능력 |
| 내결함성 (Fault Tolerance) | 일부 고장에도 전체가 계속 동작 |

```
가용성 99.9% 인데 남은 0.1% 가 매일 정오에 1분씩이라면?
  → 숫자는 같지만 사용자 체감은 최악이다
```

> **가용성 숫자만으로는 부족하다.** 장애의 **빈도·지속시간·시점·영향 범위**가 실제 경험을 만든다.  
> 1년에 한 번 43분 멈추는 것과 매일 7초씩 멈추는 것은 같은 99.99%다.

## MTBF와 MTTR

```
가용성 = MTBF / (MTBF + MTTR)

MTBF (Mean Time Between Failures)  평균 무장애 시간 — 얼마나 안 고장 나나
MTTR (Mean Time To Recovery)       평균 복구 시간 — 얼마나 빨리 고치나
```

```
MTBF 를 2배로 늘리기        →  매우 어렵다 (근본 재설계)
MTTR 를 절반으로 줄이기      →  상대적으로 쉽다 (자동화·롤백·런북)
                                 가용성 개선 효과는 비슷하다
```

> ⭐ **MTTR 단축이 투자 대비 효과가 훨씬 크다.** 이게 SRE의 핵심 전략이다.  
> 그래서 "장애를 없애자"보다 **"롤백을 1분 안에 할 수 있게 하자"** 가 실질적이다. GitOps의 `git revert`가 그 수단이다. → `../cicd-lab/10-pipeline-operations/`  
> DORA의 4지표 중 절반(복구 시간·변경 실패율)이 이 이야기다. → `../cicd-lab/01-cicd-basics/`

### MTTR을 쪼개면

```
장애 발생 ──▶ 탐지 ──▶ 인지 ──▶ 진단 ──▶ 완화 ──▶ 복구
            MTTD    (알림)   (원인)   (증상 제거) (정상화)
             │        │        │        │
          관측성   알림 품질  런북    자동 롤백
```

| 구간 | 단축 수단 |
|---|---|
| 탐지 (MTTD) | 좋은 알림, 증상 기반 SLI → `02-slo-operations/` |
| 인지 | 온콜 로테이션, 에스컬레이션 → `03-incident-response/` |
| 진단 | 런북, 대시보드, 트레이스 |
| **완화** | **롤백·페일오버 — 진단보다 우선한다** |
| 복구 | 자동화 |

> **완화가 진단보다 먼저다.** 원인을 모르더라도 롤백으로 증상을 없앨 수 있으면 그렇게 한다. 원인 분석은 서비스가 정상으로 돌아온 뒤에 해도 늦지 않다.

## 가용성 숫자의 실제 무게

| 가용성 | 월간 허용 다운타임 | 연간 |
|---|---|---|
| 99% | 약 7시간 18분 | 3.65일 |
| 99.9% | 약 43분 | 8.77시간 |
| 99.95% | 약 21분 | 4.38시간 |
| 99.99% | 약 4분 | 52.6분 |
| 99.999% | 약 26초 | 5.26분 |

```
99.99% = 월 4분
  → 사람이 알림을 받고 로그인해서 판단하는 시간만으로도 초과한다
  → 자동 감지 + 자동 복구가 아니면 달성 불가능하다
```

> ⚠️ **목표를 높게 잡는 건 그만큼의 운영 비용을 약속하는 일이다.** 9 하나가 늘 때마다 비용은 대략 한 자릿수 늘어난다.  
> "높을수록 좋다"가 아니라 **"사용자가 체감하는 선이 어디인가"** 로 정한다. 사용자가 쓰는 모바일 네트워크가 이미 99.9%도 안 되는 경우가 흔하다.

### 의존성이 가용성을 깎는다

```
서비스 A (99.9%) → 서비스 B (99.9%) → DB (99.9%)
직렬 의존 시 = 0.999³ ≈ 99.7%   (연간 26시간)
```

> **직렬로 엮인 의존성은 가용성을 곱한다.** 의존 대상이 늘수록 자기 가용성 목표는 달성이 어려워진다.  
> 대응은 두 가지 — **의존성을 줄이거나, 의존이 실패해도 동작하게(우아한 성능 저하) 만들거나.** → `05-resilience-patterns/`

## 안전 여유 (Margin)

```
사용률 95% 로 운영 = "효율적" 인가?
  → 트래픽 10% 증가, 노드 1대 장애, GC 스파이크
  → 여유가 없으면 즉시 장애
```

| 여유의 형태 | 예시 |
|---|---|
| 용량 여유 | 피크 대비 30~50% 헤드룸 → `08-capacity-planning/` |
| 시간 여유 | 배포 후 관찰 시간 |
| 인력 여유 | 온콜이 혼자가 아닐 것 |
| 에러 버짓 | 실패해도 되는 예산 → `02-slo-operations/` |

> **비용 최적화와 정면으로 충돌하는 지점이다.** 사용률을 100%에 가깝게 끌어올리는 게 비용상 이상적이지만, 신뢰성에는 최악이다.  
> ⚠️ **"가용성을 희생한 절감이 가장 비싼 실수"** 라는 원칙이 여기서 나온다 — 장애 1회 비용이 연간 절감액을 넘는 경우가 흔하다. → `../cost-lab/01-finops-basics/`

## 실제 구성에서의 트레이드오프

이 저장소의 dev 클러스터는 **의도적으로 신뢰성을 낮게** 잡았다. 그 선택들이 무엇을 포기한 것인지 아는 게 중요하다.

| 설정 | 얻은 것 | 포기한 것 |
|---|---|---|
| `single_nat_gateway = true` | NAT 비용 1/N | **그 AZ 장애 시 전체 아웃바운드 중단** |
| `node_capacity_type = "SPOT"` | 60~70% 절감 | 2분 예고 후 노드 중단 |
| PVC 없음 (관측성) | EBS 비용 0 | **파드 재시작 시 메트릭·로그 소실** |
| `retention: 7d` | 스토리지 절감 | 장기 추세 분석 불가 |
| 매일 클러스터 파괴 | 미사용 시간 비용 0 | 상시 가용성 없음 |

> **dev이므로 전부 합리적인 선택이다.** 문제는 이 설정을 prod에 그대로 가져갈 때 생긴다.  
> **"이 환경의 신뢰성 목표는 무엇인가"** 를 먼저 정하고 설정을 고른다. 순서가 반대면 "왜 이게 이렇게 돼 있지"가 된다.

## 복잡계에서의 장애

```
단순한 시스템:  원인 하나 → 결과 하나
복잡한 시스템:  여러 요인이 겹쳐야 장애가 된다
```

```
실제 장애의 전형적 형태
  ① 평소에 있던 잠재 결함 (메모리 누수)
  ② + 평소와 다른 조건 (트래픽 2배)
  ③ + 안전장치의 부재 (메모리 limit 미설정)
  ④ + 타이밍 (배포 직후)
  ────────────────────────────────
  → 노드 OOM → 파드 대량 축출 → 연쇄 장애
```

> **"근본 원인 하나"를 찾으려는 시도가 오히려 재발을 부른다.** 실제로는 여러 기여 요인(contributing factors)이 겹친 것이고, 그중 하나만 고치면 다른 조합으로 다시 난다. → `04-postmortem/`

### 연쇄 장애 (Cascading Failure)

```
서비스 A 느려짐
  → 호출자 B 의 스레드가 대기로 묶임
    → B 도 느려짐
      → B 의 호출자 C 가 재시도 → A 에 부하 가중
        → A 완전히 죽음 → 전체 장애
```

> **재시도가 장애를 증폭시킨다.** 이게 타임아웃·서킷 브레이커·백오프가 필요한 이유다. → `05-resilience-patterns/`  
> 복구 시에도 마찬가지다 — 전부 동시에 재접속하면(thundering herd) 회복 직후 다시 죽는다.

## SRE의 기본 원칙

| 원칙 | 의미 |
|---|---|
| **100%는 목표가 아니다** | 적정 신뢰성을 정하고 나머지는 속도에 쓴다 |
| **에러 버짓** | 실패 예산이 남으면 배포하고, 없으면 안정화 |
| **비난하지 않는다** | 사람이 아니라 시스템을 고친다 |
| **토일(toil)을 줄인다** | 반복 수작업을 자동화로 대체 |
| **점진적 변경** | 큰 변경 하나보다 작은 변경 여러 개 |
| **측정 없이 개선 없다** | SLI 없이 신뢰성을 논할 수 없다 |

> **"작게 자주 배포하는 것이 안전하다"** 는 DORA 연구의 결론과 SRE의 원칙이 만나는 지점이다. 큰 배포가 위험한 것이지 잦은 배포가 위험한 게 아니다. → `../cicd-lab/01-cicd-basics/`

## 배운 점

- **신뢰성은 장애를 없애는 게 아니라 고장을 견디고 빨리 회복하는 것**
- 분산 시스템에서 **부분 고장은 상시 발생**한다 — 설계 질문은 "고장 나면 어떻게 되는가"
- 가용성 숫자만으로는 부족하다 — **빈도·지속시간·시점·영향 범위**가 체감을 만든다
- ⭐ **MTBF를 늘리는 것보다 MTTR을 줄이는 게 훨씬 효율적**이다 (SRE의 핵심 전략)
- MTTR은 **탐지 → 인지 → 진단 → 완화 → 복구**로 쪼개서 각각 단축한다
- **완화가 진단보다 먼저다** — 원인을 몰라도 롤백으로 증상을 없앨 수 있다
- **99.99% = 월 4분** — 사람이 개입할 시간이 없다, 자동 복구가 전제
- ⚠️ **9 하나가 늘 때마다 비용은 자릿수로 는다** — 사용자 체감선으로 정한다
- **직렬 의존은 가용성을 곱한다** — 의존성을 줄이거나 실패해도 동작하게 만든다
- **안전 여유가 신뢰성의 실체** — 사용률 95%는 효율이 아니라 위험이다
- ⚠️ 비용 최적화와 정면 충돌 — **가용성을 희생한 절감이 가장 비싼 실수**
- dev의 낮은 신뢰성 설정은 합리적이지만 **prod에 그대로 가져가면 안 된다**
- **"이 환경의 신뢰성 목표"를 먼저 정하고 설정을 고른다**
- 복잡계 장애는 **여러 기여 요인이 겹친 결과** — 근본 원인 하나를 찾으려 하면 재발한다
- **재시도가 연쇄 장애를 증폭**시킨다 (타임아웃·서킷 브레이커가 필요한 이유)
- SRE 원칙: 100%는 목표가 아니다 / 에러 버짓 / 비난 금지 / 토일 축소 / 점진적 변경
