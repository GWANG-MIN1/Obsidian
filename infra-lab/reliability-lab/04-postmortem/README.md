# 04 포스트모템

장애를 겪고도 배우지 못하면 **같은 장애가 반복된다.** 포스트모템은 그 학습을 강제하는 장치다.  
핵심은 **"누가 실수했는가"가 아니라 "왜 그 실수가 가능했는가"** 를 묻는 것이다.

---

## 비난하지 않는(blameless) 문화

```
[ 비난하는 문화 ]
"누가 배포했나?" → 사람을 특정 → 처벌
      ↓
다음부터 실수를 숨긴다 → 정보가 사라진다 → 같은 장애가 반복된다  💥

[ 비난하지 않는 문화 ]
"왜 그 실수가 가능했나?" → 시스템의 결함을 찾는다
      ↓
사람들이 솔직하게 말한다 → 진짜 원인이 드러난다 → 재발이 줄어든다
```

| 비난하는 질문 | 비난하지 않는 질문 |
|---|---|
| "왜 확인 안 했나?" | "확인할 수 있는 도구가 있었나?" |
| "왜 그 명령을 쳤나?" | "그 시점에 그게 합리적으로 보인 이유는?" |
| "누가 승인했나?" | "승인 절차가 무엇을 검증했나?" |

> ⭐ **"그 사람이 그 시점에 가진 정보로는 합리적인 판단이었다"** 를 전제로 시작한다.  
> 사후에는 원인이 명백해 보이지만(**사후 확신 편향**), 당시에는 그렇지 않았다. "왜 몰랐지"가 아니라 "무엇이 그걸 알기 어렵게 만들었나"를 묻는다.

> **비난하지 않는다 ≠ 책임이 없다.** 시스템을 고칠 책임은 팀에 있다. 개인을 처벌하지 않을 뿐이다.

---

## 언제 쓰는가

```
반드시           SEV1·SEV2, 데이터 손실, 반복된 장애
권장             SEV3 중 학습 가치가 있는 것
불필요           단순 오탐, 이미 문서화된 알려진 문제
```

> **아차 사고(near miss)도 포스트모템 대상이다.** 운 좋게 막힌 것은 다음에는 안 막힌다.  
> 시점은 **24~72시간 내** — 너무 빠르면 정보가 부족하고, 너무 늦으면 기억이 흐려진다.

---

## 구성

```markdown
# [SEV2] 결제 API 5xx 급증 (2026-08-09)

## 요약
2026-08-09 14:23~15:07 (44분) 결제 API 요청의 약 40%가 5xx 로 실패.
영향 사용자 약 1,200명, 실패 결제 시도 약 3,400건.
원인은 커넥션 풀 설정과 트래픽 증가가 겹친 것. 롤백으로 완화.

## 영향
- 사용자: 결제 실패 (재시도로 대부분 성공)
- SLO: 에러 버짓 30일치의 62% 소진
- 매출: 추정 손실 확인 중

## 타임라인 (KST)
14:23  결제 API 5xx 증가 시작 (배포 v1.4.2 완료 4분 후)
14:26  ErrorBudgetBurnFast 알림 발화
14:29  온콜 확인 응답, SEV2 선언
14:31  대시보드 확인 — 결제 서비스만 영향, DB 지연 정상
14:38  가설① "DB 문제" → DB 메트릭 정상으로 반증
14:45  가설② "최근 배포" → v1.4.2 롤백 결정
14:52  롤백 완료
15:07  5xx 정상 범위 복귀, 관찰 후 종료 선언

## 기여 요인
1. v1.4.2 에서 커넥션 풀 크기를 20 → 10 으로 줄임 (의도치 않은 변경)
2. 같은 시간대 프로모션으로 트래픽 1.8배 증가
3. 커넥션 풀 고갈에 대한 알림이 없었음
4. 스테이징 트래픽이 운영의 1/50 이라 부하에서 안 드러남

## 잘 된 것
- 번레이트 알림이 3분 만에 발화 (임계값 알림이었으면 더 늦었다)
- 롤백 절차가 문서화돼 있어 7분 만에 완료

## 아쉬운 것
- 가설① 검증에 7분 소모 (DB 대시보드를 먼저 봤다면 1분)
- 커넥션 풀 메트릭이 수집되지 않고 있었음

## 액션 아이템
| # | 액션 | 담당 | 기한 | 유형 |
|---|---|---|---|---|
| 1 | 커넥션 풀 사용률 메트릭 추가 + 알림 | @a | 08-16 | 탐지 |
| 2 | 설정값 변경을 PR 체크리스트에 명시 | @b | 08-16 | 예방 |
| 3 | 스테이징 부하 테스트를 릴리스 게이트에 | @c | 08-30 | 예방 |
| 4 | 결제 서비스 런북 작성 | @a | 08-23 | 완화 |
```

> **타임라인에는 "무엇을 했나"뿐 아니라 "무엇을 알고 있었나"** 를 적는다. 반증된 가설도 남긴다 — 왜 그 방향으로 갔는지가 개선 지점이다.  
> **"잘 된 것"을 반드시 포함**한다. 효과가 있었던 장치를 알아야 그걸 강화할 수 있다.

---

## 기여 요인 — "근본 원인" 하나를 찾지 않는다

```
❌ 근본 원인: 개발자가 커넥션 풀 설정을 잘못 바꿨다
     → "조심하자"로 끝난다 → 재발한다

✅ 기여 요인 (여러 개)
     ① 설정 변경이 리뷰에서 눈에 안 띄었다      (프로세스)
     ② 커넥션 풀 고갈 알림이 없었다            (탐지)
     ③ 스테이징 부하가 운영과 너무 달랐다       (검증)
     ④ 프로모션 일정이 배포팀에 공유 안 됐다    (커뮤니케이션)
     → 각각이 독립적인 개선 지점이 된다
```

> ⭐ **복잡계 장애는 여러 요인이 겹쳐야 일어난다.** 하나만 고치면 다른 조합으로 다시 난다. → `01-reliability-basics/`  
> 그래서 **"근본 원인(root cause)"이라는 단수 표현 자체를 피하고 "기여 요인(contributing factors)"** 을 쓴다.

### 왜(Why)를 계속 묻되, 사람에서 멈추지 않는다

```
5 Whys 의 함정
  왜 장애가? → 설정을 잘못 바꿔서
  왜 잘못 바꿨나? → 개발자가 실수해서
  왜 실수했나? → 부주의해서          ← ⚠️ 여기서 멈추면 개선이 없다

계속 밀어붙인다
  왜 부주의가 장애로 이어졌나? → 리뷰에서 안 걸렸으니까
  왜 리뷰에서 안 걸렸나? → 설정 변경이 diff 에서 눈에 안 띄니까
  왜 눈에 안 띄나? → 설정과 코드가 같은 PR 에 섞여 있으니까  ← 개선 가능
```

> **"사람의 부주의"에 도달했다면 아직 덜 판 것이다.** 사람은 항상 실수한다. 실수가 장애로 이어지는 경로를 끊는 게 목표다.

## 액션 아이템

```
좋은 액션 아이템의 조건
  □ 담당자가 한 명으로 지정됐는가      (팀 이름은 곧 아무도 아님)
  □ 기한이 있는가
  □ 구체적인가                        "모니터링 개선" ❌ / "풀 사용률 알림 추가" ✅
  □ 추적되는가                        이슈 트래커에 등록
  □ 유형이 분류됐는가                 예방 / 탐지 / 완화
```

| 유형 | 목적 | 예시 |
|---|---|---|
| **예방** | 다시 안 일어나게 | 설정 검증 자동화, 정책 추가 |
| **탐지** | 더 빨리 알아채게 | 메트릭·알림 추가 (MTTD 단축) |
| **완화** | 더 빨리 복구하게 | 런북, 자동 롤백 (MTTR 단축) |

> ⭐ **예방에만 몰리면 안 된다.** 모든 장애를 예방할 수는 없으므로 **탐지·완화 액션이 실질적으로 더 가치 있는 경우가 많다.** MTTR 단축이 MTBF 연장보다 효율적이라는 원칙과 같다. → `01-reliability-basics/`  
> ⚠️ **액션 아이템의 완료율을 추적하지 않으면 포스트모템은 의식(ritual)이 된다.** 문서만 쌓이고 아무것도 안 바뀐다.

```
분기별 점검
  □ 지난 분기 액션 아이템 완료율은?
  □ 미완료 항목은 여전히 유효한가?
  □ 반복해서 나오는 기여 요인이 있는가?   ← 구조적 문제의 신호
```

---

## 공유

```
팀 내부   상세 포스트모템 전문
조직 전체 요약 + 학습 포인트 (다른 팀도 같은 실수를 한다)
고객      필요 시 요약 (원인·조치·재발 방지)
```

> **다른 팀의 포스트모템을 읽는 것이 가장 싼 학습이다.** 직접 겪지 않고 배울 수 있다.  
> 포스트모템 저장소를 검색 가능하게 유지하면, 비슷한 증상이 났을 때 과거 사례가 먼저 나온다.

## 트러블슈팅 문서와의 관계

```
포스트모템     사용자 영향이 있었던 '장애' 를 조직 차원에서 회고
트러블슈팅 문서  개인·팀이 겪은 '기술적 막힘' 을 기록
```

```markdown
## 현상       무엇이 어떻게 안 됐는가 (에러 메시지 원문)
## 환경       OS/버전/구성 — 재현에 필요한 최소 정보
## 원인       왜 그랬는가 (추측이 아니라 확인한 근거)
## 해결       실제로 통한 명령·설정
## 재발 방지   다음에 안 겪으려면 무엇을 바꿔야 하는가
```

> **둘은 형식이 비슷하고 목적이 다르다.** 포스트모템의 "기여 요인"과 트러블슈팅의 "원인"은 같은 규율을 요구한다 — **추측이 아니라 확인한 근거.**  
> 실제로 겪은 사례에서도 1차 가설(caBundle 주입)을 반증하고 실제 diff를 확인해서야 진짜 원인(`selectableFields`가 k8s 1.31+ 기능)에 도달했다. → `../cicd-lab/05-argocd-advanced/`

## 포스트모템이 실패하는 방식

| 실패 | 결과 |
|---|---|
| 비난이 섞인다 | 다음부터 정보를 숨긴다 |
| 액션 아이템이 추적 안 됨 | 문서만 쌓이는 의식이 된다 |
| "근본 원인" 하나로 정리 | 다른 조합으로 재발 |
| 너무 늦게 작성 | 기억 왜곡, 관심 소멸 |
| 예방 액션만 나열 | 못 막는 장애에 무력하다 |
| 작성만 하고 공유 안 함 | 학습이 팀 안에 갇힌다 |
| 잘 된 것을 안 적음 | 효과 있던 장치를 모른다 |

---

## 배운 점

- 포스트모템의 핵심 질문은 **"왜 그 실수가 가능했는가"**
- ⭐ **비난하면 정보를 숨기게 되고, 숨기면 재발한다**
- **"그 시점의 정보로는 합리적이었다"** 를 전제로 시작 (사후 확신 편향 경계)
- 비난하지 않는다 ≠ 책임이 없다 — **시스템을 고칠 책임은 팀에 있다**
- **아차 사고(near miss)도 포스트모템 대상** — 운은 반복되지 않는다
- 작성 시점은 **24~72시간 내**
- 타임라인에는 **반증된 가설도** 남긴다 (왜 그 방향으로 갔는지가 개선 지점)
- **"잘 된 것"을 반드시 포함**한다 — 효과 있던 장치를 강화하려면 알아야 한다
- ⭐ **"근본 원인" 단수 대신 "기여 요인" 복수**로 쓴다
- **"사람의 부주의"에 도달했다면 아직 덜 판 것** — 실수가 장애로 이어지는 경로를 끊는다
- 액션 아이템은 **담당자 1명 + 기한 + 구체성 + 추적**
- 유형을 **예방 / 탐지 / 완화**로 분류한다
- ⭐ **예방에만 몰리지 않는다** — 탐지·완화가 실질적으로 더 가치 있는 경우가 많다
- ⚠️ **완료율을 추적하지 않으면 포스트모템은 의식이 된다**
- 반복해서 나오는 기여 요인은 **구조적 문제의 신호**
- **다른 팀의 포스트모템을 읽는 게 가장 싼 학습**
- 포스트모템과 트러블슈팅 문서 모두 **추측이 아니라 확인한 근거**를 요구한다
