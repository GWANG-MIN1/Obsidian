# 01 관측성 기초

**모니터링은 "아는 문제"를 감시하고, 관측성은 "모르는 문제"를 질문할 수 있게 한다.**  
CPU 그래프만 있으면 "CPU가 높다"까지만 알 수 있다. 관측성은 시스템이 충분히 계측되어 있어서, 미리 정해두지 않은 질문에도 답할 수 있는 상태를 뜻한다.

---

## 모니터링 vs 관측성

| | 모니터링 | 관측성 |
|---|---|---|
| 질문 | **알려진** 실패를 감시 ("디스크 80% 넘었나") | **모르는** 문제를 탐색 ("왜 이 사용자만 느리지") |
| 방식 | 미리 정한 지표에 임계값 | 임의의 차원으로 파고들기 |
| 대상 | 서버 몇 대 | 분산된 수십 개 서비스 |
| 결과 | 대시보드·알림 | 원인 규명 |

```
모니터링:  "5xx 에러율이 5%를 넘었다"           ← 문제가 있다는 사실
관측성:    "그중 90%가 특정 파드에서 나오고,
            그 파드는 DB 커넥션 풀이 고갈됐고,
            배포 직후부터 시작됐다"              ← 왜 그런지
```

> 관측성은 도구를 깔면 생기는 게 아니라 **애플리케이션이 자기 상태를 내보내도록 계측(instrument)했을 때** 생긴다. Prometheus를 설치했다고 관측 가능해지지 않는다.

---

## 관측성의 3요소

```
┌──────────────┬──────────────────────┬────────────────────────────┐
│   메트릭      │        로그          │         트레이스            │
│  (Metrics)   │       (Logs)         │        (Traces)            │
├──────────────┼──────────────────────┼────────────────────────────┤
│ 수치의 시계열  │ 시점의 이벤트 기록      │ 요청 하나의 전체 여정        │
│ "지금 몇 %"   │ "그때 무슨 일이"       │ "어느 구간에서 느렸나"        │
│ 저렴·집계 쉬움 │ 상세하지만 무겁다       │ 원인 구간 특정에 최적        │
│ Prometheus   │ Loki / ELK           │ Tempo / Jaeger             │
└──────────────┴──────────────────────┴────────────────────────────┘
```

| 요소 | 답하는 질문 | 비용 | 카디널리티 |
|---|---|---|---|
| **메트릭** | 무엇이, 얼마나? | 낮다 (집계된 수치) | 낮게 유지해야 한다 |
| **로그** | 그때 정확히 무슨 일이? | 중간~높다 (원문 저장) | 자유롭다 |
| **트레이스** | 어디서 느려졌나? | 높다 (샘플링 필수) | 높다 |

### 실제 장애 대응 흐름

```
1. 알림      "5xx 에러율 급증"                  ← 메트릭
2. 대시보드   특정 서비스·특정 파드로 좁힘          ← 메트릭
3. 트레이스   그 요청이 DB 구간에서 3초 걸림        ← 트레이스
4. 로그       "connection pool exhausted"       ← 로그
```

> 세 가지는 **좁혀 들어가는 순서**로 쓴다. 메트릭으로 범위를 좁히고, 트레이스로 구간을 찾고, 로그로 확정한다.  
> 그래서 Grafana 한 화면에서 메트릭 → 로그로 바로 넘어갈 수 있는 구성이 중요하다. → `04-grafana/`

## SLI · SLO · SLA

무엇을 재고, 어느 수준을 지키고, 못 지키면 어떻게 되는지에 대한 계층이다.

| 용어 | 뜻 | 예시 |
|---|---|---|
| **SLI** (Indicator) | 실제로 재는 지표 | 성공한 요청 비율 = 99.95% |
| **SLO** (Objective) | 내부 목표 | 30일간 가용성 99.9% 이상 |
| **SLA** (Agreement) | 고객과의 계약 (위반 시 배상) | 99.5% 미만이면 요금 10% 환불 |

```
SLI  ── 측정값 ──▶  SLO ── 목표 ──▶  SLA ── 계약 ──▶ 배상
99.95%             99.9%           99.5%
                     └─ SLO는 SLA보다 항상 엄격하게 잡는다
```

### 에러 버짓

```
SLO 99.9%  →  허용 실패 0.1%  →  30일 기준 약 43분
```

| 가용성 | 월간 허용 다운타임 |
|---|---|
| 99% | 약 7시간 18분 |
| 99.9% | 약 43분 |
| 99.95% | 약 21분 |
| 99.99% | 약 4분 |

> 에러 버짓은 **"이만큼은 실패해도 된다"는 예산**이다. 남아 있으면 과감하게 배포하고, 다 쓰면 기능 개발을 멈추고 안정화에 집중한다.  
> 99.99%를 목표로 잡으면 월 4분 안에 감지·대응·복구가 끝나야 한다. **목표를 높게 잡는 것은 그만큼의 운영 비용을 약속하는 일이다.**

### SLI를 고르는 기준

```
❌ CPU 사용률 80% 미만            ← 사용자는 CPU를 신경 쓰지 않는다
✅ 요청의 99.9%가 300ms 안에 응답  ← 사용자가 체감하는 것
```

> **사용자 관점에서 재는 것**만 SLI가 될 자격이 있다. CPU·메모리는 원인 분석용 지표이지 목표가 아니다.

## 무엇을 볼 것인가 — USE와 RED

지표를 고르는 두 가지 정형화된 방법이다.

### USE — 자원(리소스) 관점

| | 뜻 | 예시 |
|---|---|---|
| **U**tilization | 사용률 | CPU 70%, 메모리 80% |
| **S**aturation | 포화 (대기열) | run queue 길이, 스왑 사용 |
| **E**rrors | 에러 | 디스크 I/O 에러, 패킷 드롭 |

> 리눅스 성능 분석에서 쓰던 그 방법론이다. → `../linux-scripts/10-monitoring-performance/`  
> **노드·디스크·네트워크 같은 인프라 자원**에 적용한다.

### RED — 요청(서비스) 관점

| | 뜻 | PromQL |
|---|---|---|
| **R**ate | 초당 요청 수 | `sum(rate(http_requests_total[5m]))` |
| **E**rrors | 실패한 요청 수·비율 | `sum(rate(http_requests_total{status=~"5.."}[5m]))` |
| **D**uration | 응답 시간 분포 | `histogram_quantile(0.95, ...)` |

> **마이크로서비스에는 RED**를 쓴다. 서비스마다 이 세 개짜리 대시보드 한 장이면 대부분의 상황이 보인다.  
> 구글 SRE의 **Four Golden Signals**(지연·트래픽·에러·포화)는 RED에 포화를 더한 것이다.

```
인프라 자원  →  USE  (Utilization, Saturation, Errors)
서비스 요청  →  RED  (Rate, Errors, Duration)
```

## 평균의 함정 — 백분위수를 봐라

```
요청 100건: 99건이 10ms, 1건이 10초
평균 = 109ms        ← "괜찮아 보인다"
p99  = 10,000ms     ← 100명 중 1명은 10초를 기다렸다
```

| 지표 | 의미 |
|---|---|
| p50 (중앙값) | 절반의 사용자가 겪는 경험 |
| p95 | 대부분의 사용자 |
| **p99** | 최악의 1% — 여기가 보통 문제의 신호 |

> **평균 응답시간은 거의 항상 거짓말을 한다.** SLO는 p95·p99로 잡는다.  
> Prometheus에서는 히스토그램 메트릭 + `histogram_quantile()`로 구한다. → `03-promql/`

## 관측성이 죽는 방식

| 실패 패턴 | 결과 |
|---|---|
| **알림이 너무 많다** | 아무도 안 본다. 진짜 장애가 묻힌다 |
| **항상 빨간 대시보드** | "원래 그래요"가 되어 신호가 사라진다 |
| **행동할 수 없는 알림** | 받아도 뭘 해야 할지 모른다 |
| **카디널리티 폭발** | 모니터링 시스템 자체가 죽는다 |
| **계측 안 된 앱** | 인프라 지표만 보이고 앱 내부는 깜깜하다 |

> 실제로 EKS에 kube-prometheus-stack을 기본값으로 깔면 **etcd·scheduler·controller-manager 타겟이 영원히 빨갛다.** AWS가 관리하는 영역이라 스크랩할 수 없기 때문이다.  
> 이걸 끄지 않으면 "우리 모니터링은 원래 빨개요"가 되고, 그 순간 알림 전체가 무의미해진다. → `08-kube-prometheus-stack/`

### 좋은 알림의 조건

```
□ 사람이 지금 행동해야 하는가?     아니면 대시보드로 충분하다
□ 사용자에게 영향이 있는가?        내부 지표 이상만으로 깨우지 않는다
□ 무엇을 해야 하는지 적혀 있는가?   runbook 링크를 넣는다
□ 자동으로 복구되지 않는가?        셀프힐로 해결되면 알릴 필요 없다
```

## 배운 점

- **모니터링은 아는 문제를 감시, 관측성은 모르는 문제를 질문**할 수 있는 상태
- 관측성은 도구 설치가 아니라 **애플리케이션 계측**에서 나온다
- 3요소는 좁혀 들어가는 순서로 쓴다: **메트릭(범위) → 트레이스(구간) → 로그(확정)**
- 메트릭은 싸고 카디널리티에 민감, 로그는 상세하고 무겁고, 트레이스는 샘플링이 필수
- **SLI는 사용자가 체감하는 것**으로 고른다 — CPU 사용률은 SLI가 아니다
- SLO는 SLA보다 엄격하게, 남은 **에러 버짓**이 배포 속도를 결정한다
- 99.99%는 월 4분 — **목표를 높이는 건 운영 비용을 약속하는 일**
- 인프라 자원은 **USE**, 서비스 요청은 **RED**로 본다
- **평균 응답시간은 거짓말을 한다** — p95·p99로 SLO를 잡는다
- 관측성이 죽는 가장 흔한 방식은 **항상 빨간 대시보드와 알림 피로**
- 좋은 알림의 기준: 지금 행동해야 하고, 사용자 영향이 있고, 할 일이 적혀 있을 것
