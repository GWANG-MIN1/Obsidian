# 11. 캘린더 skill 은 성공했다는데 일정이 0건

- **발생**: 2026-06-10 ~ 06-11 (Day 19) · 저장소 함정 **#59~64**
- **증상 한 줄**: `calendar` 호출이 `ok: true` 인데 `count: 0` — 아이폰엔 일정이 분명히 있다

---

## 현상

Day 19 에서 iCloud 공개 ICS 를 읽는 `calendar()` skill 을 넣었다
([결정 12](../decisions/12-캘린더를-공개-ICS-읽기-전용으로.md)).

에이전트에게 "이번 주 일정 뭐 있어?" 라고 물으면 이렇게 답한다.

```
등록된 일정이 없습니다.
```

`skillCalls` 에는 `{ name: "calendar", ok: true }` 로 찍힌다.
**호출은 성공했고 반환값이 `count: 0`** 이다.

아이폰 캘린더 앱에는 이번 주 일정이 분명히 들어 있다.

## 환경

- iCloud 공개 캘린더 `webcal://...icloud.com/published/...`
- Worker Lambda, `node-ical` 파서
- 검증 경로: 웹 UI + Discord `/ask`

## 진단 — 코드를 다섯 번 고쳤다

`fix(day-19)` 커밋이 7개다. 순서대로 이렇다.

### 1) CommonJS 번들 문제

`node-ical` 이 ESM 번들에서 안 로드됐다. Worker 를 CJS 로 번들하도록 바꿨다.
(이 문제의 사촌이 나중에 [트러블 12](12-재배포하니-전-요청이-500.md) 로 돌아온다.)

### 2) 시간대가 어긋난다 (#61)

일정 시각이 9시간씩 밀렸다. `calendarTimeZone=Asia/Seoul` 을 안 넘겨서
UTC 로 해석되고 있었다.

### 3) 반복 일정이 빠진다 (#62)

처음엔 ICS 를 문자열 파싱으로 읽었다. `RRULE`, `EXDATE`, `RECURRENCE-ID` 를 처리 못 해서
매주 반복하는 일정이 통째로 안 나왔다.
`node-ical` 의 recurrence expansion 으로 바꿨다.

### 4) 종일 일정의 날짜가 하루 밀린다

`VALUE=DATE` 인 종일 일정을 시각으로 해석하면서 timezone 변환에 하루가 먹혔다.
Lambda 안에서 종일 날짜를 그대로 보존하도록 고쳤다.

### 5) 응답 포맷을 LLM 이 뭉갠다

날짜/시간을 모델이 다시 쓰면서 틀렸다.
skill 이 **미리 포맷한 문자열**을 만들고 모델은 그걸 그대로 쓰게 했다
(`preformat calendar event labels`, `preserve calendar answer lines verbatim`).

**여기까지 고쳤는데도 `count: 0` 이었다.**

### 6) 코드 밖을 본다 (#64)

파서를 의심하는 걸 멈추고 **입력 데이터**를 직접 봤다.

```powershell
$url = $env:CALENDAR_ICS_URL -replace '^webcal://', 'https://'
$ics = curl.exe -sS -L --max-time 20 $url
($ics | Select-String '^BEGIN:VEVENT$').Count
```

```
0
```

**공개 ICS 피드 자체가 비어 있었다.**
파서 문제도, 시간대 문제도, 에이전트 문제도 아니었다.

## 원인

**일정을 공개한 캘린더가 아니라 다른 캘린더에 저장했다.**

아이폰에서 `Day 19 test` 캘린더를 만들어 공개했는데,
테스트 일정을 만들 때 **기본 캘린더에 저장**됐다.
공개 링크는 `Day 19 test` 를 가리키므로, 그 안에는 아무것도 없다.

```
아이폰 일정  →  기본 캘린더        (공개 안 됨)
공개 링크    →  Day 19 test 캘린더  (비어 있음)
```

앞의 다섯 개는 **진짜 버그였고 실제로 고쳐야 했다.**
하지만 `count: 0` 의 원인은 아니었다. 그래서 고칠 때마다 증상이 안 바뀌었다.

## 해결

아이폰에서 일정을 열고 → **편집** → **캘린더** 항목을 `Day 19 test` 로 변경 → 저장.
iCloud 동기화에 1~5분.

그리고 **확인 절차를 README 에 넣었다.**

```powershell
# 공개 피드에 실제로 몇 건이 들어 있는지 (URL 은 출력하지 않는다)
($ics | Select-String '^BEGIN:VEVENT$').Count
```

테스트 일정을 2개 만들었으면 결과가 **최소 2** 여야 한다.
`0` 이면 에이전트나 파서 문제가 아니라 **피드가 비어 있는 것**이다.

계속 0 이면 공개 캘린더를 껐다 켜서 링크를 재발급하고 재배포한다.

## 재발 방지

- **파이프라인 디버깅은 입력 끝에서 시작한다.** 데이터가 흐르는 경로가
  `아이폰 → iCloud → 공개 ICS → fetch → 파서 → skill → LLM → 답변` 인데,
  나는 **파서부터** 봤다. 가장 앞(피드에 몇 건 있나)을 확인하는 데 명령 한 줄이면 됐다.
- **각 단계를 독립적으로 확인할 수 있는 명령을 README 에 적어 둔다.**
  `curl | grep -c BEGIN:VEVENT` 는 그 이후로 첫 번째 확인 단계다.
- **"고쳤는데 증상이 그대로면 원인이 아니다."** 다섯 번 고치고 증상이 그대로였을 때
  가설을 바꿨어야 했다. 두 번째쯤에서 멈추고 입력을 봤어야 한다.

## 왜 이렇게 됐나 — 편향

**고칠 수 있는 곳부터 본다.** 코드는 내가 고칠 수 있고, 즉시 재배포해서 확인할 수 있다.
아이폰 캘린더 설정은 "그건 당연히 맞겠지"로 넘어간다.

그리고 **고치는 동안 진짜 버그가 계속 나왔기 때문에** 방향이 맞다고 착각했다.
시간대도 틀렸고 반복 일정도 빠졌으니, 매번 "이게 원인이었나 보다" 싶었다.
**진짜 버그를 고치는 것과 증상의 원인을 찾는 것은 다른 일이다.**

## 배운 점

**증상이 안 바뀌면 계층을 바꾼다.** 같은 계층에서 고치기를 반복하면
"고칠 게 아직 남았나 보다"로 계속 간다.

**시스템 밖에 원인이 있을 수 있다.** 이 프로젝트에서 원인이 코드 밖에 있던 게 두 번이다 —
여기(아이폰 설정)와 [트러블 13](13-키리스-배포가-자격증명을-못-읽는다.md)(워크플로 파일 위치).
둘 다 "코드는 맞는데 안 된다" 였다.

**하루 안에 안 끝난 유일한 day 였고, 그 이유가 코드가 아니었다.**
Day 19 는 커밋 16개에 이틀이 걸렸는데, 진짜 해결은 아이폰에서 일정 하나를 편집한 것이었다.
