# Troubleshooting

aws-serverless-agent 에서 실제로 막혔던 것들.
형식과 원칙은 [`infra-lab/troubleshooting/`](../../../infra-lab/troubleshooting/README.md) 와 같다.

```
## 현상       무엇이 어떻게 안 됐는가 (에러 메시지 원문 포함)
## 환경       재현에 필요한 최소 정보
## 진단       가설 → 검증 → 반증의 과정 (막다른 길도 남긴다)
## 원인       왜 그랬는가 (확인한 근거로)
## 해결       실제로 통한 명령·설정
## 재발 방지   다음에 안 겪으려면 무엇을 바꿔야 하는가
## 배운 점
```

## 78개 중 13개를 골랐다

저장소는 각 `day-XX-*/README.md` 에 그날의 함정을 **번호로 누적**해 78개까지 갔다.
표 한 줄(`증상 | 원인 | 회피`)로 끝나는 것이 대부분이고,
여기에는 **원인이 여러 겹이거나 진단 과정이 남을 만한 것** 13개만 풀어 적었다.

번호는 저장소의 원본 번호를 그대로 인용한다 (`#39` 등).
나머지 65개는 저장소 README 에 있고 옮겨 적지 않는다.

## 이 프로젝트의 함정에는 성격이 있다

Day 10 회고에서 함정 12개를 세어 보고 남긴 관찰이 끝까지 유효했다.

> 12개 중 9개가 **"코드는 컴파일·deploy 되는데 실행 시점에 깨지는"** 종류.
> `cdk synth` 만으로는 안 잡힘 — 실배포 + 실호출까지 가야 발견.

78개까지 가도 비율이 비슷하다. 그리고 반복되는 유형이 있다.

## 특히 남길 만한 것

- **[12](12-재배포하니-전-요청이-500.md) ⭐** — 프로젝트에 마침표를 찍고 **8일 뒤** 재배포하다 발견했다.
  `#78` 이라는 번호가 그 뒤늦음을 그대로 보여준다. 검증 범위가 한 환경뿐이었다는 뜻이다.
- **[11](11-캘린더가-0건을-돌려준다.md)** — `fix` 커밋 7개를 코드에 쏟았는데 원인은 아이폰 설정이었다.
  "고칠 수 있는 곳"부터 보게 되는 편향의 사례.
- **[04](04-toolResult를-넣으면-ValidationException.md)** — 에러 메시지가 원인을 안 가리키는 종류.
  `ValidationException` 만 보고는 `toolUseId` 짝을 의심할 수 없다.
