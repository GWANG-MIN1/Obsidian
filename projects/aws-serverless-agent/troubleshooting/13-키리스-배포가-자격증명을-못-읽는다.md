# 13. GitHub Actions 가 자격증명을 못 읽는다 — 코드는 맞는데

- **발생**: 2026-06-12 (Day 21) · 저장소 함정 **#71~77**
- **증상 한 줄**: `Error: Credentials could not be loaded` / 워크플로가 아예 안 돈다

---

## 현상

Day 21 에서 GitHub Actions OIDC 로 키리스 배포를 붙였다
([결정 13](../decisions/13-배포를-GitHub-OIDC로.md)).

세 단계로 막혔고, **셋 다 코드 밖에 원인이 있었다.**

1. 워크플로가 **아예 안 돈다** — push 해도 Actions 탭에 아무것도 안 뜬다
2. 돌기 시작하니 `Error: Credentials could not be loaded`
3. 자격증명은 읽히는데 bootstrap 에러

## 환경

- GitHub Actions, `aws-actions/configure-aws-credentials@v4`
- AWS IAM OIDC provider + 배포 역할 (`Day21PipelineStack`)
- 배포 대상: `Day21CicdStack` (에이전트 본체)

## 진단

### 1) 워크플로 YAML 을 day 폴더에 뒀다 (#76)

파일을 여기 뒀다.

```
day-21-cicd/.github/workflows/deploy.yml
```

**GitHub 은 저장소 루트의 `.github/workflows/` 만 인식한다.**
하위 디렉터리에 있으면 그냥 무시한다 — 에러도 경고도 없다.

[결정 01](../decisions/01-원본을-한-번에-복제하지-않는다.md) 의
"day 폴더는 독립 CDK 프로젝트" 원칙을 따르다 보니 자연스럽게 그 안에 넣었다.
**이 day 만은 그 원칙이 안 통한다** — CI 는 저장소 단위지 폴더 단위가 아니다.

```
.github/workflows/          ← 루트로 옮김
day-21-cicd/                ← 배포 대상은 여기
```

### 2) `permissions: id-token: write` 를 빠뜨렸다 (#77)

워크플로가 돌기 시작하니 이 에러가 났다.

```
Error: Credentials could not be loaded
```

OIDC 는 **GitHub 이 워크플로에 토큰을 발급**해 주고, 그걸 AWS 에 제시하는 방식이다.
그 토큰 발급 권한을 워크플로가 명시적으로 요청해야 한다.

```yaml
permissions:
  id-token: write      # ← 이게 없으면 토큰이 발급 안 된다
  contents: read
```

**기본값은 `id-token: none`** 이다. 명시 안 하면 안 준다.

에러 메시지가 "자격증명을 못 읽었다"라서 **역할 ARN 이나 신뢰 정책을 의심하게 된다.**
실제로는 그 앞 단계에서 토큰이 아예 안 나온 것이다.

### 3) bootstrap 이 안 돼 있었다 (#75)

자격증명이 붙으니 `cdk deploy` 가 bootstrap 에러를 냈다.
새 계정/리전은 `cdk bootstrap` 이 선행돼야 한다. 로컬에서 한 번 돌렸다.

## 원인

**셋 다 코드가 아니라 배치와 선언의 문제였다.**

| # | 원인 | 성격 |
|---|---|---|
| 76 | 워크플로 파일이 루트가 아닌 곳에 | **파일 위치** |
| 77 | `id-token: write` 미선언 | **권한 선언 (기본값 none)** |
| 75 | CDK bootstrap 미실행 | **선행 조건** |

문법 오류도, 로직 오류도 아니다. 그래서 **코드를 아무리 봐도 안 나온다.**

## 함께 정리한 것 — 설계 쪽 함정

**#73 — 닭-달걀 순환**

배포 역할을 에이전트 스택 안에 두면 이렇게 된다.

```
CI 가 배포하려면 → 배포 역할이 필요 → 스택이 배포돼야 함 → CI 가 배포해야 함 → …
```

`Day21PipelineStack`(정체성)과 `Day21CicdStack`(배포 대상)으로 갈랐다.
정체성은 **1회 수동 배포**, 그다음부터 대상은 자동.
→ [결정 13](../decisions/13-배포를-GitHub-OIDC로.md)

**#71 — OIDC provider 가 이미 있다**

```
EntityAlreadyExists: ...OIDC provider
```

GitHub OIDC provider 는 **계정에 하나**만 있으면 된다. 다른 프로젝트에서 이미 만들었으면
새로 만들 게 아니라 **import** 해야 한다.

```
npx cdk deploy -c oidcProviderArn=<기존 arn>
```

**#72 — 신뢰 범위가 너무 넓다**

신뢰 정책의 `sub` 조건을 안 좁히면 **아무 레포나 이 역할을 빌릴 수 있다.**

```
repo:GWANG-MIN1/aws-serverless-agent:*            ← 이 저장소로 한정
repo:GWANG-MIN1/aws-serverless-agent:ref:refs/heads/main   ← 브랜치까지
```

이건 에러가 안 나는 종류다. **동작은 하는데 위험하다.**

**#74 — CI 역할에 과한 권한**

관리자 정책을 그대로 붙이면 편하다. 그러면 GitHub 워크플로가 계정 전체 권한을 갖는다.

```
sts:AssumeRole on cdk-*      ← 이것만
```

실제 배포 권한은 **CDK 부트스트랩 역할**이 갖는다.
CI 는 "그 역할을 빌릴 권한"만 있으면 된다.

## 재발 방지

- **워크플로 파일은 저장소 루트 `.github/workflows/` 에만 둔다.**
  모노레포든 day 폴더 구조든 예외 없다. 안 돌면 이걸 먼저 본다.
- **OIDC 를 쓰는 워크플로에는 `permissions: id-token: write` 를 항상 적는다.**
  기본값이 none 이라는 걸 기억한다.
- **"Credentials could not be loaded" 는 토큰 발급 실패일 수 있다.**
  역할 ARN 을 의심하기 전에 `permissions` 블록을 본다.
- **신뢰 정책의 `sub` 를 반드시 좁힌다.** 에러가 안 나는 종류라 리뷰가 없으면 그대로 남는다.
- **CI 역할에 직접 권한을 주지 않는다.** `sts:AssumeRole on cdk-*` 로 두고
  실제 권한은 부트스트랩 역할이 갖게 한다.

## 배운 점

**"안 돈다"와 "돌다가 실패한다"는 다른 문제다.**
Actions 탭에 실행이 안 뜨면 그건 워크플로가 인식되지 않은 것이고,
코드나 권한 문제가 아니다. **아무 로그도 없다는 게 가장 큰 단서**였는데
처음엔 그걸 못 읽었다.

**기본값이 안전한 쪽인 게 불편할 때가 있다.** `id-token: none` 이 기본인 건 맞는 설계다
(모든 워크플로가 OIDC 토큰을 받을 이유가 없다). 그런데 그 결과로
"명시하지 않으면 조용히 안 되는" 상태가 된다.
[트러블 03](03-분리했는데-API가-Worker를-기다린다.md) 의 `InvocationType` 과 같은 구조지만,
그쪽은 기본값이 위험한 쪽(동기)이고 이쪽은 안전한 쪽이다.
**어느 쪽이든 명시하는 게 답이다.**
