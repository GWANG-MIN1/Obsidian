# 01. S3 버킷은 만들어졌는데 브라우저는 403

- **발생**: 2026-05-31 (Day 8) · 저장소 함정 **#9**
- **증상 한 줄**: `publicReadAccess: true` 로 배포가 성공했는데 웹사이트 엔드포인트가 403

---

## 현상

Day 8 에서 Vite 로 빌드한 React 앱을 S3 정적 웹사이트로 올렸다.
`cdk deploy` 는 성공하고, `BucketDeployment` 도 끝나서 `index.html` 이 버킷에 있다.

그런데 브라우저로 웹사이트 엔드포인트를 열면 **403 Forbidden**.

**배포는 성공했는데 접근이 안 된다.** 이게 이 함정의 성격이다 —
CloudFormation 은 아무 불평도 안 한다.

## 환경

- AWS CDK v2, `aws-cdk-lib/aws-s3` + `aws-s3-deployment`
- 새로 만든 S3 버킷 (2023년 이후 기본 설정)
- `websiteIndexDocument: 'index.html'`, `publicReadAccess: true`

## 진단

### 1) 버킷에 파일은 있나 → 있다

`BucketDeployment` 가 만든 임시 Lambda 가 정상 종료했고,
콘솔에서 `index.html` 과 `assets/index-*.js` 가 보인다. 업로드는 됐다.

### 2) 버킷 정책은 붙었나 → 붙었다

`publicReadAccess: true` 를 주면 CDK 가 퍼블릭 읽기 정책을 자동으로 만든다.
정책 문서도 콘솔에 보인다. **정책은 있는데 안 먹는다.**

### 3) 퍼블릭 액세스 차단 설정을 본다 → 여기다

S3 는 **2023년부터 신규 버킷의 BlockPublicAccess 4종이 전부 기본 ON** 이다.

| 설정 | 하는 일 |
|---|---|
| `BlockPublicAcls` | 퍼블릭 ACL 을 새로 못 만들게 |
| `IgnorePublicAcls` | 기존 퍼블릭 ACL 을 무시 |
| **`BlockPublicPolicy`** | **퍼블릭 버킷 정책을 거부** |
| `RestrictPublicBuckets` | 퍼블릭 버킷에 대한 크로스계정 접근 제한 |

세 번째가 범인이다. CDK 가 정책을 붙이긴 했는데,
`BlockPublicPolicy` 가 **그 정책을 무시한다.**

정책이 존재하는 것과 정책이 적용되는 것이 다르다.

## 원인

**퍼블릭 액세스 차단이 퍼블릭 버킷 정책을 무력화했다.**

```
publicReadAccess: true
  → CDK 가 퍼블릭 읽기 정책 생성        (성공)
    → 버킷에 정책 부착                  (성공, 콘솔에 보임)
      → BlockPublicPolicy 가 무시       ← 여기서 조용히 끊긴다
        → 브라우저 403                  ← 여기서 처음 보인다
```

**배포 성공과 실제 동작 사이에 조용한 단절이 있다.**
어느 단계에서도 에러가 안 난다.

## 해결

ACL 계열만 막고 **버킷 정책은 허용**하도록 차단 설정을 바꾼다.

```ts
blockPublicAccess: s3.BlockPublicAccess.BLOCK_ACLS,
//   ↑ 3종 ON / blockPublicPolicy 만 OFF
objectOwnership: s3.ObjectOwnership.BUCKET_OWNER_ENFORCED,
//   ↑ ACL 자체를 끔 — 권한은 정책으로만 (2023 이후 신규 기본)
```

`BUCKET_OWNER_ENFORCED` 를 같이 준 이유: ACL 을 아예 끄면
"정책으로만 권한을 준다"가 한 가지 경로로 확정된다. ACL 과 정책이 섞이면 추적이 어렵다.

## Day 9 에서 이 설정을 되돌렸다

CloudFront + OAC 를 세우면서 버킷을 **다시 private 으로 잠갔다.**

```ts
origins.S3BucketOrigin.withOriginAccessControl(bucket)
```

이 한 줄이 OAC 리소스를 만들고, 버킷 정책에 `Service: cloudfront.amazonaws.com` 의
`GetObject` 를 그 distribution 한정으로 허용한다. `BlockPublicAccess.BLOCK_ALL` 과 호환된다.

즉 **Day 8 의 이 문제는 Day 9 에서 통째로 사라진다.**
버킷을 퍼블릭으로 만들 필요가 없어지기 때문이다.
Day 9 이후 버킷에 직접 GET 하면 403 이 뜨는데, **그건 의도된 동작**이다.

## 재발 방지

- **퍼블릭 S3 버킷을 만들려 하는 순간을 의심한다.** 2023년 이후 AWS 가 기본값으로 막아 둔 것에는
  이유가 있다. 정적 호스팅이면 CloudFront + OAC 가 정답이고, 퍼블릭 버킷은 학습 단계의 임시 경로다.
- **"배포 성공 = 동작"이 아니다.** 이 프로젝트에서 78개 함정 중 대부분이 이 종류다.
  실배포 뒤 반드시 실제 호출까지 해 본다.
- 콘솔에서 만든 버킷이면 "퍼블릭 액세스 차단"의 네 항목을 개별로 확인한다.
  CDK 로 만들면 코드에 남아서 나중에 읽을 수 있다.

## 같이 밟은 것 — Vite env 는 빌드 타임이다 (#10)

같은 day 에 한 번 더 헤맸다. Function URL 을 바꿨는데 반영이 안 됐다.

`VITE_*` prefix 가 붙은 값은 `import.meta.env` 로 노출되는데,
**빌드 타임에 문자열로 치환된다.** 즉 `web/dist/assets/index-XXX.js` 안에 URL 이 박혀 있다.

```
.env 만 바꿈  →  dist 는 옛 URL 그대로  →  재배포해도 옛 URL
```

`.env` 를 건드렸으면 **무조건 재빌드 + 재배포**다.
런타임에 바꾸고 싶으면 `/config.json` 을 S3 에 같이 올리고 부팅 시 fetch 하는 방식이 있는데,
학습 단계에서는 과하다고 보고 안 했다.

## 배운 점

**"설정이 있다"와 "설정이 적용된다"는 다르다.** 정책은 붙어 있었다. 무시됐을 뿐이다.
콘솔에서 정책 문서를 보고 "정책은 맞는데?" 하고 한참 갔다.
권한을 볼 땐 **정책 + 그 위의 차단 설정**을 같이 봐야 한다.

**클라우드 제공자가 기본값을 바꿨다면 그건 대개 사고가 많았기 때문이다.**
2023년 이전 자료를 그대로 따라 하면 이 부류에 걸린다.
"예전엔 됐는데"가 아니라 "왜 막았나"를 먼저 읽는 게 빠르다.
