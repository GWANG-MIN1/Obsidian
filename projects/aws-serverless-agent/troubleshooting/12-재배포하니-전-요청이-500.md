# 12. 마침표를 찍고 8일 뒤, 재배포하니 전 요청이 500

- **발생**: 2026-06-24 (Day 20 스택 재배포) · 저장소 함정 **#78 ⭐**
- **증상 한 줄**: `Dynamic require of "util" is not supported` — API Lambda 가 요청을 받기도 전에 죽는다

---

## 현상

2026-06-16 에 Day 22 캡스톤으로 프로젝트를 닫았다.
8일 뒤인 06-24, Day 20 스택을 **새 환경에 재배포**했더니 API 가 전 요청에 500 을 낸다.

```
Dynamic require of "util" is not supported
```

- **Worker 는 멀쩡하다.** Agent Loop 도, Bedrock 호출도 정상이다.
- API 만 죽는다. 그것도 **전부** — `/health` 조차 500 이다.
- 로그에 이 에러 하나만 있고 요청 처리 로그가 없다.

## 환경

- AWS CDK `NodejsFunction` (esbuild 번들)
- **API Lambda: ESM 출력** / **Worker Lambda: CJS 출력**
- `aws-xray-sdk-core` (Day 20 에서 추가) → 내부적으로 `cls-hooked` 의존

## 진단

### 1) `/health` 도 500 이라는 게 단서다

`/health` 는 `{ok: true}` 를 돌려주는 라우트다. DDB 도, Bedrock 도 안 부른다.
그게 500 이면 **핸들러 코드가 실행되지 않았다는 뜻**이다.

요청이 핸들러에 닿기 전에 죽었다 — **모듈 로드(INIT) 단계**다.

### 2) 왜 API 만 죽나 → 출력 포맷이 다르다

같은 X-Ray SDK 를 Worker 도 쓴다. Worker 는 멀쩡하다.

| | 출력 포맷 | 결과 |
|---|---|---|
| Worker | **CJS** | 정상 |
| API | **ESM** | INIT 크래시 |

이게 결정적 단서였다.

### 3) ESM 번들에는 `require` 가 없다

`aws-xray-sdk-core` 는 v2 capture 경로에서 `require('aws-sdk')`, `require('util')` 같은
**동적 `require()`** 를 부른다. 실제로 쓰지도 않는 코드 경로인데, **모듈 로드 시점에 평가된다.**

CJS 번들에는 `require` 가 있으니 문제없다.
**ESM 번들에는 `require` 가 없다.**

esbuild 는 이럴 때 `__require` shim 을 넣는데, 그 shim 의 동작이 이렇다.

```
전역 require 가 있으면 → 그걸 쓴다
없으면                → throw
```

Lambda 의 ESM 실행 컨텍스트에는 전역 `require` 가 없다. 그래서 던진다.

### 4) 왜 8일 전엔 안 터졌나

Day 20 당시 환경에서는 번들 결과나 의존성 해석이 달랐던 것으로 보인다.
`npm audit fix` 로 같은 주에 의존성이 바뀌기도 했다 (`9ba48c8 chore(day-20): npm audit fix`).

정확히 무엇이 달라졌는지는 **끝까지 못 밝혔다.**
확실한 것은 **"그때 그 환경에서는 통과했고, 새 환경에서는 안 통과했다"** 는 것이다.

## 원인

**ESM 번들 안에서 동적 `require()` 가 호출됐고, 그게 모듈 로드 시점에 터졌다.**

```
aws-xray-sdk-core → cls-hooked → require('util')
  → esbuild ESM 출력의 __require shim
    → 전역 require 없음 → throw
      → 모듈 로드 실패 → 핸들러가 아예 등록 안 됨
        → 모든 요청 500 (INIT 크래시)
```

**함수가 실패한 게 아니라 모듈이 로드되지 않았다.**
그래서 요청 처리 로그가 하나도 없다.

## 해결

esbuild 의 `banner` 로 ESM 번들 최상단에 `require` 를 만들어 준다.

```ts
new nodejs.NodejsFunction(this, 'ApiFunction', {
  bundling: {
    format: nodejs.OutputFormat.ESM,
    banner: 'import { createRequire } from "module"; const require = createRequire(import.meta.url);',
    externalModules: ['aws-sdk'],       // #66 — 미사용인데 해석하려 들어서
  },
});
```

한 줄이 전역 `require` 를 만들고, esbuild 의 `__require` shim 이 그걸 쓴다.
**ESM 을 유지하면서 CJS 로 전환하지 않아도 된다.**

## 이 문제가 이 프로젝트에서 갖는 의미

**이건 이 프로젝트의 가장 정직한 결론이다.**

- 프로젝트는 06-16 에 "완성"으로 닫혔다. 캡스톤에 아키텍처, 비용, 보안까지 정리했다.
- 그 시점에 **동작하는 배포가 하나 있었고**, 그게 검증의 전부였다.
- 8일 뒤 **같은 코드를 다른 환경에 올리니 안 돌았다.**

**"검증했다"의 범위가 한 환경이었다는 뜻이다.**

자동 테스트가 없다는 빈칸이 정확히 여기서 드러났다.
번들이 로드되는지만 확인하는 테스트 하나 — `import` 해 보고 `handler` 가 함수인지 보는 정도 —
가 있었으면 CI 에서 잡혔다. 그리고 [Day 21 에서 CI 를 만들었지만](../decisions/13-배포를-GitHub-OIDC로.md),
그 CI 는 `cdk synth` 만 한다. **synth 는 번들 로드까지 안 본다.**

함정 번호 **#78** 이 그 뒤늦음을 그대로 보여준다.
Day 20 의 함정은 #65~70 인데, 이건 #78 이다. 번호가 시간 순서를 기록한다.

## 재발 방지

- **번들 포맷(ESM/CJS)을 함수마다 의식한다.** 같은 의존성이 포맷에 따라 다르게 동작한다.
  "Worker 는 되는데 API 는 안 된다"의 답이 여기 있었다.
- **INIT 단계 크래시를 알아보는 법을 기억한다.** 증상은 셋이다 —
  **모든 요청이 실패**, **`/health` 도 실패**, **요청 처리 로그가 없음**.
  이 셋이 같이 나오면 핸들러 안이 아니라 **모듈 로드**를 본다.
- **최소한 "번들이 로드되는가" 테스트를 CI 에 넣는다.**
  `cdk synth` 는 CloudFormation 템플릿만 본다. 번들 결과물이 Node 에서 로드되는지는 안 본다.
  이 프로젝트에 딱 하나 테스트를 넣는다면 이거다.
- **"완성"이라고 쓰기 전에 깨끗한 환경에 한 번 더 배포해 본다.**
  같은 계정, 다른 리전이라도 좋다.

## 배운 점

**"동작한다"는 환경에 대한 진술이지 코드에 대한 진술이 아니다.**
06-16 에 동작한 건 사실이고, 06-24 에 안 동작한 것도 사실이다. 코드는 그대로였다.

**끝났다고 선언한 뒤에 나오는 버그가 가장 많은 걸 알려준다.**
이 하나가 [프로젝트 README 의 "아직 안 한 것"](../README.md#아직-안-한-것과-이유) 첫 항목을 정했다.

**gym-management-db 와 정반대다.** 그쪽은 코드 리뷰를 받아 테스트 56개를 넣으면서
검증 체계를 세웠고, 이쪽은 실배포 검증을 22일 내내 하고도 자동 테스트가 0이다.
**손으로 하는 검증은 환경이 바뀌면 재현되지 않는다** — gym 의
[트러블 09](../../gym-management-db/troubleshooting/09-Secrets-Manager-조회-실패.md) 에서
"사람이 콘솔에서 값을 복사해 붙여 넣는 단계는 재현되지 않는다"고 쓴 것과 같은 결론이다.

Day 20 에서 X-Ray 를 붙이며 밟은 것들. 이것들은 표 한 줄로 끝난다.

| # | 함정 | 회피 |
|---|---|---|
| 65 | Lambda@Edge 에 tracing 주면 배포 실패 | 엣지만 `Tracing.ACTIVE` 제외 (미지원) |
| 66 | esbuild `Could not resolve 'aws-sdk'` | `externalModules` 에 `aws-sdk` 추가 (미사용인데 해석하려 든다) |
| 67 | trace 에 함수만 뜨고 Bedrock 호출은 안 보임 | active tracing **만으론 부족** — `captureAWSv3Client` 로 클라이언트 래핑 |
| 68 | API 와 Worker 가 **따로** 추적됨 | async invoke 가 trace 를 안 잇는다 → API 의 `lambdaClient` 도 래핑 |
| 69 | 알람이 계속 `INSUFFICIENT_DATA` | 트래픽이 없으면 에러 지표가 빈값 → `treatMissingData: NOT_BREACHING` |
| 70 | 알람 메일이 안 옴 | SNS 이메일 구독 **확인 링크**를 클릭해야 수신 |

**#67 · #68 이 짝이다.** "계측을 켰다"와 "호출이 보인다"가 다르고,
"두 함수를 다 계측했다"와 "두 함수가 한 trace 로 이어진다"가 또 다르다.
[트러블 03](03-분리했는데-API가-Worker를-기다린다.md) 의 "구조를 바꿨으면 동작이 바뀌었는지 따로 재야 한다"와 같은 결이다.
