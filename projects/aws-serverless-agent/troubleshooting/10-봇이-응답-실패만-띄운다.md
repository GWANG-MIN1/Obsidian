# 10. Discord 봇이 "응답 실패"만 띄운다 — 3초의 벽

- **발생**: 2026-06-09 (Day 18) · 저장소 함정 **#55 · #56 · #57**
- **증상 한 줄**: `/ask` 를 치면 즉시 "애플리케이션이 응답하지 않았습니다"

---

## 현상

[서명 검증](09-Discord가-Endpoint-URL을-저장-못-함.md)을 통과해서 Endpoint URL 등록까지 됐다.
그런데 `/ask` 슬래시 명령을 치면 Discord 가 곧바로 실패를 띄운다.

Lambda 로그를 보면 **Worker 는 정상으로 돌고 있다.** Bedrock 을 부르고, 답을 만들고, DDB 에 저장한다.
**결과는 나오는데 Discord 에 안 간다.**

## 환경

- Discord Interactions (웹훅)
- Discord Lambda (Function URL) → Worker Lambda async invoke
- Agent Loop: Bedrock 왕복 + `executeCode` 샌드박스 (수 초 ~ 수십 초)

## 진단

### 1) Discord 의 응답 시간 제한을 확인한다 → 여기다

**Discord Interactions 는 3초 안에 응답을 요구한다.**

Agent Loop 는 Bedrock 을 여러 번 왕복한다. Bedrock 한 번이 1~5초고,
도구를 쓰면 샌드박스 실행이 더 붙는다. **3초 안에 끝날 수가 없다.**

그런데 Discord Lambda 는 Worker 를 부르고 결과를 기다리고 있었다.
구조가 이랬다.

```
Discord ──▶ Discord Lambda ──(기다림)──▶ Worker ──▶ Bedrock…
              ↑ 3초 초과 → Discord 가 포기
```

### 2) Discord 가 제공하는 해법 — deferred response

Discord 는 이 상황을 위해 **deferred** 를 정의해 뒀다.

```
type 5  =  DEFERRED_CHANNEL_MESSAGE_WITH_SOURCE
```

`{ type: 5 }` 를 즉시 반환하면 Discord 는 "생각 중…" 상태를 띄우고 기다린다.
그다음 **followup webhook** 으로 내용을 채운다.

이건 [결정 04](../decisions/04-API와-Worker를-async-invoke로-분리.md) 의 async 분리와 정확히 같은 모양이다.
Discord 는 그 패턴을 **프로토콜로 강제**한다.

### 3) followup URL 을 틀렸다 (#56)

deferred 로 바꾸니 "생각 중…"은 뜨는데 **내용이 안 채워진다.**

followup 은 이 경로다.

```
PATCH https://discord.com/api/v10/webhooks/{application_id}/{interaction_token}/messages/@original
```

- `application_id` — 애플리케이션 ID (봇 ID 가 아니다)
- `interaction_token` — 그 interaction 의 토큰 (15분 유효)
- **bot token 이 필요 없다** — interaction token 자체가 인증이다

`@original` 이 "deferred 로 만들어 둔 그 메시지"를 가리킨다.

### 4) `/ask` 가 안 보인다 (#57)

명령을 등록했는데 Discord 클라이언트에 안 뜬다.

**global 명령은 전파에 최대 1시간**이 걸린다.
개발 중에는 **guild(서버) 명령**으로 등록하면 즉시 반영된다.

```
POST /applications/{app_id}/guilds/{guild_id}/commands    ← 즉시
POST /applications/{app_id}/commands                      ← ~1시간
```

## 원인

**Agent Loop 의 실행 시간이 Discord 의 3초 제한을 넘는다.**
그리고 그 사실을 구조에 반영하지 않았다 — Discord Lambda 가 Worker 를 기다리고 있었다.

이어서 **followup 경로와 명령 등록 범위**를 몰라서 두 번 더 막혔다.

## 해결

```
Discord ──▶ Discord Lambda
              1) 서명 검증
              2) { type: 5 } 즉시 반환             ← 3초 안에 끝
              3) Worker async invoke { channel: "discord", interactionToken, applicationId, ... }
                        │
                        ▼
                   Worker (Agent Loop 그대로)
                        │
                        ▼
              PATCH /webhooks/{app_id}/{token}/messages/@original
```

Worker 는 기존 payload 에 **`channel: "discord"` 한 칸**을 더 받는다.
Agent Loop, skill, DDB, MQTT 는 전혀 안 바뀌었다.

명령 등록은 개발 중 guild 명령으로 하고, bot token 은 **등록 1회에만** 쓴다.
런타임 응답은 interaction token 으로 하므로 bot token 을 Lambda 에 안 넣는다.

## 재발 방지

- **외부 플랫폼의 응답 시간 제한을 먼저 확인한다.** Discord 3초, Slack 3초,
  Telegram 은 좀 더 관대하다. LLM 을 붙이는 순간 대부분의 제한을 넘는다.
- **긴 작업 앞에는 항상 즉시 응답 계층을 둔다.** 이 프로젝트는 이미 그 구조였는데
  ([결정 04](../decisions/04-API와-Worker를-async-invoke로-분리.md)),
  새 채널을 붙일 때 그 원칙을 다시 적용하는 걸 잊었다.
- **개발 중에는 전파가 즉시인 경로를 쓴다.** guild 명령 / 테스트 서버.
  "안 보인다"의 원인이 전파 지연이면 코드를 아무리 봐도 안 나온다.
- **bot token 이 필요한 경로와 아닌 경로를 구분한다.** 런타임에 bot token 을 안 쓰면
  Lambda 에 그 비밀을 안 넣어도 된다.

## 배운 점

**같은 문제를 다른 계층에서 다시 만난다.**
"HTTP 응답 시간과 실제 작업 시간을 분리한다"는 Day 11 에서 이미 배웠다.
Day 18 에서 채널을 붙일 때 그걸 안 떠올렸다.
**패턴을 배웠다고 다음에 자동으로 적용되지는 않는다.**

**제약이 설계를 알려주기도 한다.** Discord 의 3초 제한은 불편이 아니라
"긴 작업은 deferred 로 하라"는 **설계 지침**이다.
플랫폼이 그런 제약을 두면 대개 해법도 같이 정의해 뒀다.
