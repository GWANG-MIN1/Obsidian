# 08. 브라우저 권한을 AssumeRole + 세션정책으로 좁힌다

> 메모: Lambda 자기 자격증명으로 서명해서 URL 을 내려주면 브라우저가 그 Lambda 권한을 전부 갖게 됨. AssumeRole + 세션정책으로 "이 세션 토픽 구독만" 으로 깎음

---

## 상황

Day 15 에서 브라우저가 IoT Core 에 직접 WebSocket 으로 붙어야 했다.
브라우저에는 AWS 자격증명이 없으니, **서버가 SigV4 로 미리 서명한 WSS URL** 을 발급해 내려준다.

문제는 **무엇으로 서명하느냐**다. 가장 쉬운 건 API Lambda 자기 자격증명으로 서명하는 것이다.
그런데 그러면 **그 URL 을 가진 사람은 API Lambda 의 IoT 권한을 전부 갖는다.**
다른 세션 토픽을 구독할 수도, publish 할 수도 있다.

## 결정

API 가 **`RealtimeRole` 을 AssumeRole** 하되, `Policy`(세션정책)로 그 세션 토픽 하나까지 좁힌다.
그 임시 자격증명으로 서명한 URL 을 브라우저에 준다.

```js
const creds = await sts.send(new AssumeRoleCommand({
  RoleArn: process.env.REALTIME_ROLE_ARN,
  RoleSessionName: `rt-${sessionId}`,
  DurationSeconds: 3600,
  Policy: JSON.stringify({                      // ← 세션정책: 여기서 더 좁힌다
    Version: "2012-10-17",
    Statement: [{
      Effect: "Allow",
      Action: ["iot:Connect", "iot:Subscribe", "iot:Receive"],
      Resource: [ /* 이 sessionId 토픽만 */ ],
    }],
  }),
}));
```

브라우저가 실제로 갖는 권한은 **두 정책의 교집합**이다.

| 계층 | 허용 | 어디서 |
|---|---|---|
| `RealtimeRole` 자체 | `iot:Connect/Subscribe/Receive` on `sessions/*/events` | CDK (상한선) |
| AssumeRole `Policy` | 같은 액션 on `sessions/<이 id>/events` | 런타임 (좁히기) |
| **브라우저 실제 권한** | **이 세션 토픽 구독만** | 교집합 |

publish 권한은 **어디에도 없다.** 브라우저는 듣기 전용이다.

## 왜

- **URL 이 새도 피해가 그 세션에 갇힌다.** presigned URL 은 링크를 아는 사람이 쓸 수 있는 접근 키다.
  스크린샷, 로그, 브라우저 히스토리로 샐 수 있다고 가정해야 한다.
- **상한선과 좁히기를 분리하면 실수해도 안전하다.** 세션정책 생성 코드에 버그가 나서
  `sessions/*/events` 를 넣더라도, 역할 자체가 그 이상을 못 준다.
  세션정책은 **더 좁힐 수만 있지 넓힐 수 없다.**
- **1시간짜리다.** `DurationSeconds: 3600`. 영구 자격증명이 브라우저로 나가지 않는다.
- **원본이 같은 패턴이다.** `backend/src/lambda-api/routes/realtime.ts` 의
  `scopedIotCredentialsFor`. 다만 원본은 **유저별 토픽**이고 우리는 **세션별**로 더 좁혔다.

## 왜 다른 건 안 썼나

**Lambda 자기 자격증명으로 서명**

한 줄이면 된다. 그리고 **브라우저에 Lambda 권한을 통째로 넘기는 것**이다.
API Lambda 는 DDB 3개 테이블 RW + Lambda invoke + STS 권한도 갖고 있다.
IoT 서명에만 쓴다고 해도, 그 자격증명으로 만든 URL 의 서명 범위를 좁힐 방법이 없다.

**Cognito Identity Pool (미인증 자격증명)**

브라우저에 임시 자격증명을 주는 정공법이고 관리형이다.
안 쓴 이유: **원본이 안 쓰고**(원본은 자체 auth), 리소스를 하나 더 들여야 하며,
무엇보다 **세션 단위로 좁히는 게 더 번거롭다.** Identity Pool 의 역할은 사용자 단위지
"이 요청의 이 세션" 단위가 아니다. 그걸 하려면 결국 세션정책이나 정책 변수를 또 써야 한다.

**IoT X.509 인증서**

IoT Core 의 표준 디바이스 인증 방식. 브라우저마다 인증서를 발급/관리해야 한다.
디바이스가 아니라 브라우저에는 과하다. IAM 만으로 붙는 경로가 있는데 굳이.

**API 가 MQTT 를 중계 (브라우저 ↔ API ↔ IoT)**

브라우저에 권한을 아예 안 주는 방법. 그런데 그러면 API 가 **연결을 유지해야** 하고,
그건 [결정 07](07-실시간을-IoT-MQTT-push로.md) 에서 피하려던 바로 그 구조다.

## SigV4 서명의 IoT 특례

IoT 의 WSS 서명은 **일반 SigV4 와 한 군데가 다르다.**

```js
// service = iotdevicegateway, path = /mqtt
const canonicalRequest = ["GET", "/mqtt", canonicalQuery, `host:${host}\n`, "host", sha256hex("")].join("\n");
// ... 서명 계산 ...
let url = `wss://${host}/mqtt?${canonicalQuery}&X-Amz-Signature=${signature}`;
if (creds.sessionToken) url += `&X-Amz-Security-Token=${encodeURIComponent(creds.sessionToken)}`;
//                                    ↑ 서명 계산에서 빼고 URL 끝에만 붙인다 (IoT 만 이렇다)
```

`X-Amz-Security-Token` 을 canonical query 에 넣으면 서명이 안 맞는다.
이걸 모르고 반나절 갔다 → [트러블 06](../troubleshooting/06-WSS-서명이-계속-거부된다.md)

## 결과

- Day 15 에서 브라우저가 빌드 없이 (esm.sh 의 mqtt.js 한 줄) 실시간 구독에 성공했다.
- Day 16 이후로도 이 경로는 **CDN 을 우회한다.** CloudFront 를 앞에 세워도
  WSS 는 브라우저 → IoT Core 직결이다. presigned URL 에 host 가 박혀 있어서 그렇다.

## 확인하지 못한 것

**만료와 재연결.** URL 은 1시간짜리인데 만료되면 그냥 끊긴다.
재발급 로직이 없어서 새로고침해야 한다. 원본은 RxJS 백오프로 재연결하는데,
데모 범위에서는 단발 연결로 끝냈다.

**세션 ID 를 아는 사람은 구독할 수 있다.** 인증이 없으므로
`GET /sessions/:id/realtime` 을 아무나 부를 수 있다. 세션 ID 가 uuid 라 추측은 어렵지만,
이건 **보안이 아니라 난독화**다. → 인증 부재는 [프로젝트 README](../README.md#아직-안-한-것과-이유) 에 적어 뒀다.
