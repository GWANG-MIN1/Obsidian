# 03. 메시지 정렬키를 타임스탬프 단독에서 `${ISO}#${uuid}` 합성으로

> 메모: Day 5 에 SK=ts 로 두고 "같은 ms 면 덮어써짐"을 README 에 적어만 뒀는데, Day 7 에서 실제로 고침. 원본도 `${created_at}#${id}` 로 같은 발상

---

## 상황

Day 5 에서 대화 이력 테이블을 이렇게 잡았다.

```ts
partitionKey: { name: 'sessionId', type: STRING },
sortKey:      { name: 'ts',        type: STRING },   // ISO timestamp
```

ISO 문자열은 사전순 = 시간순이라 추가 인덱스 없이 정렬된다. 여기까진 맞다.

문제는 **PK+SK 가 같으면 `PutItem` 은 덮어쓴다**는 것이다. 같은 밀리초에 메시지 두 개가 들어오면
두 번째가 첫 번째를 지운다. Day 5 README 에 이걸 "막힐 만한 곳"으로 적어만 두고 넘어갔다.

> 현재는 user/assistant 사이 Bedrock 호출(수초)이 끼므로 자연 회피.
> 외부에서 burst 호출 들어오면 깨질 수 있음.

## 결정

SK 를 `${ISO}#${uuid}` 합성으로 바꾼다. 테이블 정의는 안 건드린다 (DDB 입장에선 여전히 STRING).

```js
const makeSk = () => `${new Date().toISOString()}#${randomUUID()}`;
// 2026-05-30T07:46:53.761Z#f2d4fb16-6bad-42fe-a60d-60b1bc596879
```

## 왜

- **정렬은 그대로 유지된다.** ISO 부분이 앞에 있어서 사전순 정렬이 시간순 그대로다.
  uuid 는 같은 ms 안에서만 순서를 가르는데, 같은 ms 안의 순서는 어차피 의미가 없다.
- **고유성이 보장된다.** 덮어쓰기가 구조적으로 불가능해진다.
- **테이블을 다시 안 만들어도 된다.** 키 타입이 그대로 STRING 이라 스키마 변경이 없다.
- **원본이 같은 발상이다.** 원본 `chat-messages` 테이블의 SK 가 `created_at_id`,
  즉 `created_at` + `id` 합성이다. Day 12 에서 컬럼명까지 원본에 맞췄다.
- **실제로 확인됐다.** Day 7 검증에서 같은 sessionId 로 계속 호출했더니 `count: 8` 까지
  누적됐다 — 덮어쓰기 없이 별개 행으로 쌓이는 게 눈으로 보였다.

## 왜 다른 건 안 썼나

**`ts` 에 마이크로초/나노초 정밀도 넣기**

정밀도를 올리면 충돌 확률은 줄지만 0 이 되지는 않는다. 그리고 JS `Date` 는 ms 가 한계라
직접 카운터를 붙여야 하는데, 그러면 **Lambda 인스턴스가 여러 개일 때 다시 깨진다.**

**ULID 하나만 SK 로**

ULID 는 시간 정렬 + 고유성을 한 문자열로 준다. 실제로 Day 5 README 에도
"`ts#ulid` 합성 키 패턴이 정석"이라고 적어 뒀었다.

안 쓴 이유는 두 가지다. **의존성이 하나 는다**는 것, 그리고 **ISO 가 눈에 읽힌다**는 것.
`aws dynamodb query` 결과를 콘솔에서 직접 볼 일이 많은데,
`01HXYZ...` 보다 `2026-05-30T07:46:53.761Z#...` 가 디버깅에 훨씬 낫다.
원본도 ULID 대신 `created_at + id` 를 썼다.

**조건부 Put 으로 충돌을 감지하고 재시도**

`ConditionExpression: attribute_not_exists(sk)` 로 막고 실패하면 SK 를 다시 만들어 재시도하는 방법.
동작은 한다. 그런데 **실패를 감지해서 고치는 것보다 실패가 불가능한 키를 쓰는 게 낫다.**
재시도 경로는 테스트도 어렵다.

## 결과

- Day 7 이후 모든 day 가 이 패턴을 그대로 쓴다.
- Day 12 에서 컬럼명만 원본에 맞춰 `sk` → `created_at_id` 로 바꿨다.
  이때 **커서 페이지네이션이 한 번 깨졌다** — `nextBefore` 가 옛 컬럼명을 보고 있었다 (함정 #19).
  키 이름을 바꿀 땐 그 키를 참조하는 모든 곳을 같이 봐야 한다.

## 같은 날 고친 다른 것 — `ScanIndexForward`

Day 7 에서 정렬키를 손보다가 **Day 5/6 의 진짜 버그**를 발견했다.

| `ScanIndexForward` | 의미 |
|---|---|
| `true` (기본값) | SK 오름차순 → `Limit N` 은 **가장 오래된 N개** |
| `false` | SK 내림차순 → `Limit N` 은 **가장 최근 N개** |

Day 5/6 은 기본값 `true` 였다. 즉 세션이 길어지면 모델이 **첫 대화만** 컨텍스트로 받았다.
이력이 짧아서 티가 안 났을 뿐, 챗봇으로서는 치명적인 버그다.

```js
ScanIndexForward: false,     // 최근 N개를 가져오고
Limit: HISTORY_LIMIT,
// 받은 뒤 reverse → Bedrock 엔 시간순(과거→최신)으로 넘긴다
const history = items.slice().reverse().map(...)
```

**"동작한다"와 "맞다"는 다르다.** 두 턴만 테스트하면 둘이 구별되지 않는다.
