# 05. 단일 테이블 대신 도메인별 멀티 테이블

> 메모: DDB 커뮤니티 정설은 single-table design 인데 원본은 도메인별 8개 테이블을 씀. 왜인지 확인하고 3개만 차용

---

## 상황

Day 11 까지 모든 데이터가 `ConversationsTable` 하나에 들어 있었다 (PK `sessionId`, SK `ts`).

이 구조로는 **`sessionId` 를 알아야만 조회가 된다.** "이 유저의 세션 목록"을 뽑으려면
`Scan` 밖에 길이 없다. Day 4 README 에 "Scan 은 학습용일 뿐, 실서비스에선 금기"라고
적어 놓고 정작 접근 패턴이 Scan 을 부르는 모양이었다.

그런데 DynamoDB 커뮤니티의 정설은 **single-table design** 이다 —
모든 엔티티를 한 테이블에 PK/SK 오버로딩으로 욱여넣는 방식. 조인 흉내, 트랜잭션, 핫파티션 분산에 유리하다.

**원본은 도메인별 멀티 테이블(8개)을 택했다.** 정설과 반대다. 왜인지 확인해야 했다.

## 결정

원본의 8개 중 채팅 MVP 핵심 **3개만** 차용한다. 키 스키마는 원본 그대로 미러링한다.

| 우리 (Day 12) | 원본 | PK | SK |
|---|---|---|---|
| `UsersTable` | `${id}-users` | `id` | — |
| `SessionsTable` | `${id}-chat-sessions` | **`user_id`** | `id` |
| `MessagesTable` | `${id}-chat-messages` | `session_id` | `created_at_id` |

제외한 5개: `accounts` / `sessions`(auth, TTL) / `profiles` / `memories` / `user-skills`.
auth·메모리 전용이라 MVP 범위 밖이다.

## 왜

- **접근 패턴이 테이블 경계와 1:1 로 맞으면 멀티가 더 단순하다.**
  `SessionsTable` 의 PK 를 `user_id` 로 두는 순간 "이 유저의 세션 목록"이
  **`Query` 한 번**으로 풀린다. GSI 도, PK 오버로딩 규칙도 머리에 들고 있을 필요가 없다.

  ```
  GET /users/:userId/sessions  →  Query(SessionsTable, user_id = :uid)
  GET /sessions/:sid/messages  →  Query(MessagesTable, session_id = :sid)
  ```

  둘 다 한 테이블의 Query 한 번이다.
- **테이블별로 설정이 갈린다.** TTL(원본은 auth `sessions` 에만 `expires_at_epoch`),
  용량 모드, 백업 정책, 그리고 **권한**. 이게 제일 크다.
- **IAM 이 테이블 단위로 최소화된다.** Worker 는 Messages + Sessions 만 RW 고,
  **Users 는 아예 못 본다.** 단일 테이블이면 "Worker 는 유저 행만 못 읽게"를
  IAM 조건으로 표현해야 하는데 훨씬 까다롭다. → [결정 04](04-API와-Worker를-async-invoke로-분리.md) 의 책임 분리가
  여기서 정책으로 강제된다.
- **도메인 경계가 코드에서 드러난다.** `MESSAGES_TABLE` 과 `SESSIONS_TABLE` 이라는 환경변수 두 개가
  곧 책임 분리다.

## 왜 다른 건 안 썼나

**Single-table design (PK/SK 오버로딩)**

정설이고, 대규모에서는 대체로 맞다. 안 쓴 이유는 **얻는 것이 이 프로젝트에 없기 때문**이다.

- 조인 흉내 — 우리 접근 패턴은 세션 → 메시지 **단방향**이다. 한 번에 여러 엔티티를 긁을 일이 없다.
- 트랜잭션 — 여러 도메인을 원자적으로 쓰는 경로가 없다.
- 핫파티션 분산 — 학습 트래픽에서 논할 문제가 아니다.

대신 잃는 게 명확하다. **PK/SK 오버로딩 규칙을 계속 머리에 들고 있어야 한다.**
`PK=USER#123, SK=SESSION#456` 같은 문자열 규약이 코드 곳곳에 흩어지고,
그 규약을 어기는 순간 조용히 이상한 데이터가 들어간다.

**단일 테이블에 GSI 를 붙이기**

`ConversationsTable` 에 `userId` GSI 를 만들면 세션 목록 Query 는 열린다.
그런데 GSI 는 **읽기/쓰기 용량이 따로 붙고**, 결국 테이블을 나눈 것과 비용이 비슷해진다.
게다가 IAM 최소권한은 여전히 안 된다 — GSI 는 테이블 권한을 따라간다.

**원본의 8개를 그대로 다 만들기**

`profiles`/`memories`/`user-skills` 는 아직 쓸 코드가 없다. 빈 테이블을 만들어 두면
"이건 뭐 하는 건지 모르겠지만 원본에 있어서" 상태가 된다.
→ [결정 01](01-원본을-한-번에-복제하지-않는다.md) 과 같은 이유로 안 만들었다.

## 결론 한 줄

**"single-table 이 항상 정답"이 아니라, 접근 패턴이 도메인별로 깔끔하면 멀티가 읽기 쉽다.**

## 결과

- `GET /users/:userId/sessions` 가 열렸다 — 단일 테이블에선 불가능했던 질의.
- `POST /chat` 입력이 `{sessionId, message}` 에서 `{userId, sessionId, message}` 로 바뀌었다.
  **세션을 다루는 모든 경로에 `userId` 가 따라다니게 됐다** (함정 #17).
  PK 가 `user_id` 라서 `sessionId` 만으로는 세션 단건을 못 집는다 — 원본 스키마를 그대로
  가져오면서 딸려 온 제약이다.
- 세션 `updatedAt` 갱신은 **best-effort** 로 뒀다.
  `/chat` 만 부르고 세션 메타행을 안 만든 경우가 있어서, `ConditionExpression: attribute_exists(user_id)` +
  try/catch 로 감쌌다. bump 가 실패해도 assistant Put 은 이미 성공한 상태다 (함정 #18).

## 확인하지 못한 것

**세션 목록이 시간순으로 안 나온다.** `SessionsTable` 의 SK 가 `id`(uuid) 라서
정렬이 사실상 무작위다. "최근 대화한 세션 순"으로 보려면 GSI 를 붙이거나
SK 를 `updated_at#id` 로 바꿔야 한다. 원본 스키마를 미러링하느라 그대로 뒀고,
Day 12 README 에 "후속" 으로 남겼다. **그 후속은 오지 않았다.**
