# 01. 원본을 한 번에 복제하지 않고 하루에 한 조각씩

> 메모: 원본을 그대로 클론해서 돌리면 "동작은 하는데 왜 되는지 모르는" 상태가 됨. day 폴더를 독립 CDK 프로젝트로 나누고 매일 한 가지만 더함

---

## 상황

원본 [breath103/serverless-agent](https://github.com/breath103/serverless-agent) 는 완성된 제품이다.
`packages/{backend,frontend,edge,shared}` 모노레포에 DynamoDB 8개 테이블, IoT Core, Lambda@Edge,
Google OAuth, Telegram, skill 런타임이 전부 얽혀 있다.

이걸 클론해서 `npm run deploy` 하면 돌긴 한다. 그런데 **어디가 무엇을 하는지 모른 채 돌아간다.**
그리고 안 돌 때 어디부터 봐야 할지도 모른다.

## 결정

원본을 **부품 → 조립 → 차용 → 확장** 4단계로 분해하고, **하루에 한 가지만 더한다.**
각 `day-XX-*/` 는 독립 실행 가능한 CDK 프로젝트로 만든다.

```
Phase 1 (Day 1~4)   부품 하나씩 단독으로      Lambda / DDB / Bedrock 따로
Phase 2 (Day 5~10)  연결해서 MVP 동작        채팅 API → 프론트 → CDN
Phase 3 (Day 11~16) 원본 고급 패턴 차용       Worker 분리 / Agent Loop / MQTT / Edge
Phase 4 (Day 17~21) 원본에서 갈라지기        내 skill / 내 채널 / 관측성 / CI-CD
```

각 day README 최상단에 규칙을 문장으로 박아 뒀다.

> **규칙: 매일 한 가지만 더하기.** Day 13 은 "Agent Loop + 단일 도구" 한 가지.
> 멀티 테이블·API↔Worker 분리는 Day 11/12 것을 그대로 가져온다.

## 왜

- **막힌 지점이 하루 안에 있다.** Day 14 에서 MQTT 가 안 뜨면 원인은 그날 더한 publish 코드 안에 있다.
  전부 한꺼번에 올렸으면 IoT 인지, IAM 인지, Worker 인지, 번들링인지 갈라내는 데만 시간이 든다.
- **diff 가 곧 학습 내용이 된다.** 각 day README 의 "Day N-1 → Day N diff" 표가 그날 배운 것의 목록이다.
  Day 13 표를 보면 "Bedrock 호출 1회 → 루프", "timeout 60s → 300s" 처럼 **바뀐 칸만 남는다.**
- **day 폴더가 독립이라 서로 안 깨진다.** `node_modules` 도 day 마다 따로 깔아서 버전 충돌이 0이었다.
  Day 16 을 고치다 Day 13 을 부술 일이 없다.
- **되돌아갈 지점이 21개 생긴다.** Day 20 에서 X-Ray 가 API 를 죽였을 때
  ([트러블 12](../troubleshooting/12-재배포하니-전-요청이-500.md)), Worker 는 멀쩡했다는 사실이 바로 보였다.
  같은 코드베이스 한 덩어리였으면 "어제까진 됐는데"에서 멈췄을 것이다.

## 왜 다른 건 안 썼나

**원본을 클론해서 고쳐 가며 배우기**

가장 빠르다. 그리고 가장 안 남는다. 완성품에서 한 줄씩 빼 보는 방식은
"이걸 빼면 깨진다"는 알아도 **"이게 왜 필요한가"** 는 안 남는다.
Day 11 의 async invoke 는 "Lambda 가 60초 넘게 일해야 하면?" 이라는 질문이
Phase 2 회고에서 먼저 나왔기 때문에 의미가 있었다. 완성품에는 그 질문이 안 보인다.

**모노레포 하나에 day 별 브랜치**

브랜치를 옮겨 다니면 이전 day 를 **동시에 돌려 놓고 비교**할 수 없다.
Day 9 의 CloudFront Function 과 Day 16 의 Lambda@Edge 를 나란히 두고 읽는 게
"origin 을 못 바꾼다"를 이해하는 가장 빠른 길이었다.
디스크가 좀 더 드는 대신, **비교가 항상 가능한 상태**를 택했다.

**한 CDK 프로젝트에 스택을 21개**

`cdk deploy Day13Stack` 으로 하나만 올릴 수는 있다. 하지만 `package.json` 이 하나라
Day 19에서 `node-ical` 을 깔면 Day 3 의 번들에도 영향이 갈 수 있고, 무엇보다
**한 day 를 통째로 지우고 다시 만드는 게 어려워진다.**

## 결과

- Day 11~21 을 **하루에 한 day씩** 닫았다. 리듬이 안 깨진 건 하루치 범위가 작았기 때문이다.
- 하루를 넘긴 day 는 Day 19 하나다 (커밋 16개, 이틀). 그리고 그 원인은 코드가 아니라
  아이폰 캘린더 설정이었다 → [트러블 11](../troubleshooting/11-캘린더가-0건을-돌려준다.md)
- Day 12부터 브랜치 → PR 로 전환해 PR 12개를 남겼다. day = 브랜치 = PR 이 1:1로 맞았다.

## 확인하지 못한 것

이 방식은 **학습에는 맞지만 제품에는 안 맞는다.** day 폴더 21개는 같은 코드를 21번 복사한 것에 가깝고,
공통 로직을 고치려면 21군데를 고쳐야 한다. 실제로 Day 18 은 Day 16 의 엣지 함수를,
Day 21 은 Day 20 의 스택을 **파일째 동봉**하는 커밋이 있다 (`chore(day-18): edge-origin-request.mjs 동봉`).

제품으로 키우려면 원본처럼 `packages/` 모노레포로 접어야 한다. 이 결정은 **로드맵이 끝나는 날까지만** 유효하다.
