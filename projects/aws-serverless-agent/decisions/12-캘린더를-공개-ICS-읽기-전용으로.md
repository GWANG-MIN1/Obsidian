# 12. 캘린더를 Google OAuth 대신 iCloud 공개 ICS 읽기 전용으로

> 메모: 원본은 Google Calendar OAuth 로 읽기/쓰기 다 함. 아이폰 캘린더 공개 링크를 쓰면 인증 없이 읽기만 됨. 링크 자체가 접근 키라는 게 트레이드오프

---

## 상황

원본은 `google-calendar` skill 을 OAuth 로 붙인다 — 사용자가 동의하고, 토큰을 `user-skills` 테이블에
저장하고, 읽기와 쓰기를 다 한다.

Day 19 에 캘린더 skill 을 넣기로 했는데, OAuth 를 따라가면 딸려 오는 게 많다.
동의 화면, 토큰 저장 테이블, 리프레시 처리, 그리고 **이 프로젝트에 없는 인증 체계**.
사용자 개념이 `userId` 문자열 하나인 상태에서 "누구의 토큰인가"를 관리할 수가 없다.

## 결정

**아이폰(iCloud) 캘린더의 공개 `webcal://` 링크를 읽기 전용으로** 쓴다.
링크는 배포 시점에 CDK context 로 넣고, Worker 환경변수로 고정한다.
LLM 은 URL 을 볼 수도, 바꿀 수도 없다.

```js
await calendar({
  range: "today" | "this_week" | "next_7_days",
  // 또는 from/to 를 ISO 로
  limit: 50,
});
```

안전 경계를 명시적으로 그었다.

- **LLM 은 캘린더 URL 을 전달할 수 없다.** 배포 시 설정한 `CALENDAR_ICS_URL` 만 Worker 가 쓴다.
- `webcal://` → `https://` 로 바꾸고, **`icloud.com` 및 하위 도메인만** 허용한다.
- **생성·수정·삭제 API 가 없다.** 반환값은 제목/시간/위치/설명뿐이다.
- 다운로드는 **8초, 2MB** 제한.

## 왜

- **인증이 필요 없다.** OAuth 를 붙이려면 이 프로젝트에 없는 인증 체계부터 만들어야 한다.
  주제(에이전트 구조)에서 비중이 뒤집힌다. [결정 11](11-Telegram-대신-Discord.md) 과 같은 판단이다.
- **읽기 전용이 구조로 강제된다.** 공개 ICS 에는 **쓰기 API 자체가 없다.**
  "쓰기를 안 하도록 조심한다"가 아니라 **할 수가 없다.** LLM 이 무슨 코드를 써도
  캘린더를 지울 방법이 없다.
- **`webcal://` 호스트 화이트리스트로 SSRF 를 막는다.**
  임의 URL 을 fetch 할 수 있으면 그건 [결정 10](10-skill을-샌드박스에-주입.md) 에서
  `fetch` 를 안 준 이유가 무너지는 것이다. `icloud.com` 하위만 허용한다.
- **추가 IAM 이 0이다.** 공개 HTTPS 라서 AWS 권한이 필요 없다.
  Day 19 diff 표의 "권한: 추가 IAM 없음" 이 그 뜻이다.
- **원본의 패턴은 그대로 따라간다.** 외부 캘린더를 정규화된 이벤트 목록으로 반환하고,
  서버가 허용한 skill 만 샌드박스에 노출하고, 호출 내역은 `skillCalls` 로 남기되 LLM 엔 안 준다.
  **바뀐 건 데이터 출처지 구조가 아니다.**

## 왜 다른 건 안 썼나

**Google Calendar OAuth (원본 그대로)**

읽기/쓰기가 다 되고 사용자별로 분리된다. 제품이면 이게 맞다.
안 쓴 이유: 인증 체계가 없고, 토큰 저장/갱신이 딸려 오고,
무엇보다 **이 프로젝트에서 "여러 사용자"가 실재하지 않는다.** 나 하나다.

**CalDAV 로 iCloud 에 직접 붙기**

앱 암호를 발급받으면 iCloud 캘린더에 읽기/쓰기가 된다.
안 쓴 이유: **비밀을 저장해야 한다.** 앱 암호를 Secrets Manager 에 넣고 Worker 에 권한을 주고…
읽기만 필요한데 쓰기 권한까지 갖는 자격증명을 들이는 셈이다.

**ICS 를 직접 파싱 (라이브러리 없이)**

처음엔 문자열 파싱으로 갔다. **반복 일정이 통째로 빠졌다** (함정 #62).
`RRULE`, `EXDATE`, `RECURRENCE-ID`, IANA 시간대를 다 처리하려면 결국 파서가 필요하다.
`node-ical` 로 바꾸고 recurrence expansion 을 맡겼다.

## 트레이드오프 — 공개 링크는 접근 키다

이걸 결정 안에 적어 둔다.

> **공개 URL 은 링크를 아는 사람이 읽을 수 있는 접근 키와 같다.**
> 코드, README, 스크린샷에 노출하지 않는다.

그래서 실제로 한 것:

- CDK context 로만 주입하고 저장소에 안 넣는다
- PowerShell 히스토리에도 안 남기려고 환경변수를 거쳐 넘긴다
- 개인 일정이 많은 기본 캘린더 대신 **`Day 19 test` 캘린더를 따로 만들어** 공개했다
- 스크린샷 3장 모두 링크가 안 보이게 찍었다
- 다 쓰면 아이폰에서 **공개 캘린더를 꺼서 링크를 폐기**한다

OAuth 는 "동의를 철회한다"가 명시적인데, 공개 링크는 **끄는 걸 잊으면 계속 열려 있다.**
이게 이 결정에서 실제로 감수한 위험이다.

## 결과

- 아이폰 캘린더의 실제 일정 2건(종일 일정 1 + 시간 일정 1)을
  Discord `/ask` 답변과 대조해 **일치**를 확인했다.
- skill 을 하나 더 넣는 데 도구 스펙, Agent Loop, DDB, MQTT 를 하나도 안 건드렸다 —
  [결정 10](10-skill을-샌드박스에-주입.md) 이 설계대로 작동한 증거.
