# 02. 매일 destroy 를 전제로 설계했다

> 메모: EKS 는 켜 두는 것만으로 시간 과금이다. 배우려고 띄우고 끝나면 내린다.
> 영구 자원은 state 백엔드(S3 + DynamoDB)뿐. 2026-07-12 로드맵 원칙, 07-13 `b1b8cef` · `ee5636c`

---

## 상황

EKS 는 쓰지 않아도 돈이 든다 — 컨트롤플레인은 클러스터당 시간 과금이고, NAT Gateway 도 시간 과금이고, 노드가 붙는다.
학습용 dev 클러스터를 상시로 둘지, 필요할 때만 만들지를 정해야 했다.

## 결정

**하루 쓰고 destroy 한다.** 그 전제에서 비용 손잡이를 전부 기본값으로 박았다.

| 손잡이 | 값 | 포기한 것 |
|---|---|---|
| 노드 | t3.medium · **SPOT** · 2대 (min 1 / max 3) | 중단 내성 · 파드 밀도 |
| NAT | `single_nat_gateway = true` | AZ 장애 내성 |
| 스토리지 | PVC 없음 (EBS CSI 드라이버 미설치) | 메트릭 · 로그 영속성 → [결정 05](05-관측성-데이터를-영속화하지-않는다.md) |
| 노출 | 전부 ClusterIP + `port-forward` | 공개 URL (ALB · ACM · Route53 은 미룸) |
| 영구 자원 | state 버킷(`prevent_destroy`) + 락 테이블 | — |

state 백엔드만 **매일 사이클 밖**에 뒀다. `terraform/bootstrap/` 이 로컬 state 로 한 번 만들고,
버킷에 `prevent_destroy` 를 걸어 실수로 지워지지 않게 했다.

## 왜

- **IaC 가 있으면 재생성 비용이 0에 가깝다.** [cost-lab/04](../../../infra-lab/cost-lab/04-compute-purchasing/README.md) 가
  같은 논리로 "가장 절감률이 높고 위험이 낮은 조치"라고 적는다.
- **재생성 자체가 검증이다.** Phase 1 기록에 *"destroy → 다음 날 apply 재현이 가능한 상태 확인"* 이 있다.
- **destroy 가 막히지 않는 구성이다.** 매니페스트 기준으로 클러스터가 스스로 만드는 AWS 리소스(LoadBalancer · EBS)가 없다.
  [terraform-lab/09](../../../infra-lab/terraform-lab/09-aws-vpc-eks/README.md) 의 *"destroy 가 VPC 에서 실패 — 클러스터가 만든 ELB 가 남음"* 을
  구조적으로 피했다. 공개 URL 을 미룬 것이 여기서 이득이 됐다.

## 왜 다른 건 안 썼나

**상시 유지하고 노드만 0으로**

컨트롤플레인과 NAT 는 노드 수와 무관하게 시간 과금이라 절감 폭이 작다.

**로컬 클러스터 (kind · minikube)**

[k8s-manifests](../../../infra-lab/k8s-manifests/README.md) 트랙은 로컬로 했다. 이 프로젝트는 목적이 EKS 자체 —
IRSA · VPC CNI · access entry · 관리형 컨트롤플레인의 한계 — 라 대체가 안 된다.
실제로 [트러블 01](../troubleshooting/01-노드-두-대가-파드-34개로-만석.md)(VPC CNI 의 IP 한도)은 로컬에선 안 났을 문제다.

**AZ 별 NAT · ON_DEMAND 노드**

prod 에서 뒤집을 값이다. dev 에서 가용성은 요구사항이 아니다.

## 이 결정의 대가

**재생성이 문제 둘을 만들었다.** [트러블 04](../troubleshooting/04-root-app-직후-아무것도-안-뜬-것처럼-보였다.md)(재생성 직후의 수렴 착시)와
[트러블 05](../troubleshooting/05-재생성하자-kubectl이-no-such-host.md)(엔드포인트가 매번 바뀜)다.
상시 클러스터였다면 한 번 겪고 끝났을 일이 **세션을 시작할 때마다 반복되는 절차**가 됐다.

**그 절차가 코드가 아니다.** 빈 계정에서 Phase 4 상태까지 재생성마다 손으로 치는 명령이 8개다.
트러블 05 가 *"사람이 까먹는 단계는 자동화가 답"* 이라고 적었는데 Makefile 에 `update-kubeconfig` 타깃이 없다.

**영속성이 0이다.** 메트릭 · 로그 · 대시보드가 매일 사라진다. → [결정 05](05-관측성-데이터를-영속화하지-않는다.md)

**그리고 비용을 줄였다는 증거가 없다.** 청구서 숫자가 저장소 어디에도 없다.
게다가 버전 선택 하나가 **반대 방향**으로 움직였다 — 검증 기간의 EKS 1.30 은 연장 지원 구간이라
컨트롤플레인이 시간당 $0.60 였다(표준 $0.10). 이 **할증 $0.50 하나가 t3.medium 세 대를 온디맨드로 돌리는 값보다 크다.**
SPOT 과 단일 NAT 로 아낀 것을 모르는 사이에 상쇄했을 수 있다. → [결정 03](03-전부-버전을-고정했다.md)

## 배운 점

**"매일 destroy"는 비용 전략이면서 재현성 테스트였다.** 매일 새로 만드니까 *"고친 것이 Git 에 있는가"* 가 매번 확인됐고
(07-22 에 Loki · CRD 문제 없이 한 번에 떴다), *"사람이 기억해야 하는 단계"* 도 매번 드러났다(트러블 05).

**그런데 비용 전략을 세우고 비용을 재지 않았다.** 무엇을 줄였는지 모르니 무엇이 늘었는지(연장 지원)도 몰랐다.
[riskdetector](../../riskdetector/README.md) 는 비용으로 무너졌고 [serverless-uptime-monitor](../../serverless-uptime-monitor/README.md) 도
청구서를 안 봤는데, **비용을 설계의 첫 줄에 올린 이 프로젝트도 측정은 안 했다.**
