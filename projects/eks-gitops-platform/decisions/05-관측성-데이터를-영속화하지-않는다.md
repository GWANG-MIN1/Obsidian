# 05. 관측성 데이터를 영속화하지 않는다 — Loki SingleBinary · PVC 없음

> 메모: EBS CSI 드라이버가 없고 클러스터는 매일 사라진다. 메트릭 · 로그는 파드와 함께 죽게 두고, Loki 는 가장 작은 모드로.
> 2026-07-15 `ce4aa0f` · `d932605`, 07-20 수정 `c5dbd9e`

---

## 상황

Phase 3 에서 Prometheus · Grafana · Alertmanager · Loki 를 올리면서 데이터를 어디에 쓸지 정해야 했다.
차트 기본값은 디스크를 전제하거나(Prometheus `storageSpec`, Loki `persistence`) 오브젝트 스토리지를 요구한다
(Loki 기본 모드 SimpleScalable). 이 클러스터엔 EBS CSI 드라이버가 없다.

## 결정

| 컴포넌트 | 설정 | 데이터 수명 |
|---|---|---|
| Prometheus | `storageSpec` 없음 · `retention: 7d` | 파드와 같이 |
| Alertmanager · Grafana | persistence 없음 | 파드와 같이 |
| Loki | **SingleBinary** · filesystem · `persistence: false` · `/var/loki` 에 emptyDir | 파드와 같이 |

Loki 는 SingleBinary 로 가면서 스케일아웃 부품을 전부 껐다 — write · read · backend 0개, gateway · 캐시 2종 · minio · canary · test 끔.
그래서 promtail 은 gateway 가 아니라 Loki 서비스에 **직접** push 한다.

## 왜

- **PVC 를 만들면 영원히 `Pending` 이다.** EBS CSI 드라이버가 없다.
- **매일 destroy 라 영속성의 가치가 0에 가깝다.** → [결정 02](02-매일-destroy를-전제로-설계했다.md)
- **SimpleScalable 은 규모가 안 맞는다.** values 주석 — *"~1TB/일에는 맞는 답이고, t3.medium 두 대에는 터무니없다."*
- **잃을 게 없게 만들었다.** 대시보드를 하나도 손으로 만들지 않았다. kubernetes-mixin 대시보드가 차트로 매일 다시 깔리니
  영속성이 없어도 **같은 대시보드가 돌아온다.**

## 왜 다른 건 안 썼나

**EBS CSI 애드온 + PVC**

Terraform 에 애드온과 드라이버용 IRSA 를 더하면 된다. 그런데 매일 destroy 에서는 볼륨도 같이 치워야 하고,
클러스터가 만든 EBS 는 Terraform state 에 없어서 destroy 를 막는 새 원인이 된다.
→ [terraform-lab/09](../../../infra-lab/terraform-lab/09-aws-vpc-eks/README.md) *"클러스터가 만든 ELB · EBS 는 state 에 없다"*

**Loki + S3 + IRSA**

운영에서의 정답이다 → [observability-lab/06](../../../infra-lab/observability-lab/06-logging/README.md).
S3 버킷은 destroy 에서 살아남을 수 있으니, 로그를 **날짜를 넘겨** 남길 수 있는 유일한 길이기도 했다.
values 주석이 *"체크박스가 아니라 진짜 결정"* 이라며 미뤘다.

**관리형 (Amazon Managed Prometheus · Grafana)**

저장소에서 검토한 흔적이 없다.

## 이 결정의 대가

**① "persistence 를 끈다"가 "쓸 곳이 없다"가 됐다.** 차트는 persistence 가 켜져 있을 때만 `/var/loki` 에 PVC 를 꽂는다.
끄자 그 경로가 비었고, 루트 파일시스템이 read-only 라 Loki 가 기동 즉시 죽었다.
정적 검사로는 안 보이고 라이브에서 CrashLoop 으로 드러났다. → [트러블 02](../troubleshooting/02-persistence를-끄자-Loki가-죽었다.md)

**② 설정값 일부가 의미를 잃었다.** `retention: 7d` 는 매일 사라지는 클러스터에서 **도달할 일이 없는 숫자**다.
Loki 에는 반대로 보존 기간 · 수집 한도(`limits_config`)가 아예 없고, emptyDir 에 `sizeLimit` 도 없어 노드 디스크를 그대로 쓴다.
[observability-lab/06](../../../infra-lab/observability-lab/06-logging/README.md) 이 *"처음부터 정해두지 않으면 디스크가 먼저 죽는다"* 고 적은 설정이다.
하루짜리 클러스터라 드러나지 않았을 뿐이다.

**③ 검증의 증거가 스크린샷뿐이다.** Phase 3 의 메트릭 그래프와 Loki 398줄은 클러스터와 함께 사라졌고,
남은 건 `docs/verification/images/` 의 PNG 다. **이 프로젝트에서 영속성의 대체물은 스크린샷이었다.**

**④ 하루를 넘는 추세를 볼 수 없다.** 메모리가 서서히 늘거나 재시작이 누적되는 종류의 문제는 이 구성으로는 원리적으로 안 보인다.

## 배운 점

**기본값을 끌 때는 그 기본값이 대신 해 주던 일까지 따라가야 한다.** PVC 는 영속성만 주는 게 아니라
**쓰기 가능한 경로**도 주고 있었다. 끈 것은 하나인데 사라진 것은 둘이었다.

**영속성을 포기한 결정이 수동 영속화를 낳았다.** 매일 지우는 환경에서 *"무엇이 남는가"* 를 따로 설계하지 않으면,
남는 것은 사람이 찍은 캡처다.
