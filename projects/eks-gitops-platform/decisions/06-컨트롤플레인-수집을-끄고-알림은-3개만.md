# 06. EKS 컨트롤플레인 수집을 끄고, 알림은 3개만

> 메모: 긁을 수 없는 타겟은 끄고, 그 타겟에 걸린 기본 룰도 같이 끈다. 알림은 차트가 알 수 없는 "이 플랫폼의 약속"만.
> 2026-07-15 `d932605` · `2ec51df`. **대가 ①② 는 이 노트를 쓰며(09-14) 확인했다.**

---

## 상황

kube-prometheus-stack 기본값은 etcd · scheduler · controller-manager · kube-proxy 를 **컴포넌트 엔드포인트에서 직접** 긁고,
그에 맞는 기본 룰도 켠다. EKS 는 컨트롤플레인이 AWS 관리라 그 엔드포인트에 닿지 않는다.
그리고 차트의 기본 알림 수십 개 위에 무엇을 더할지 정해야 했다.

## 결정

**끈 것** — `kubeControllerManager` · `kubeScheduler` · `kubeEtcd` · `kubeProxy` 타겟, 그리고 대응하는 `defaultRules` 그룹
(etcd · kubeControllerManager · kubeSchedulerAlerting · kubeSchedulerRecording · kubeProxy) + windows.

**더한 것** — ArgoCD ServiceMonitor 3개(application-controller · server · repo-server)와 `alerts.yaml` 의 알림 3개.

| 알림 | 조건 | for | severity |
|---|---|---|---|
| `ArgoCDAppNotSynced` | `argocd_app_info{sync_status!="Synced"} == 1` | 15m | warning |
| `ArgoCDAppUnhealthy` | `argocd_app_info{health_status!="Healthy"} == 1` | 15m | warning |
| `SampleAppDown` | `kube_deployment_status_replicas_available{…} == 0` | 5m | critical |

`alerts.yaml` 은 `values.yaml` 과 파일을 나눴다 — *"스택을 어떻게 튜닝하나"와 "무엇을 문제로 보나"는 다른 대화다.*

## 왜

- **영원히 빨간 타겟은 모니터링을 죽인다.** 끄지 않으면 타겟 4개가 늘 빨갛고 룰이 "데이터 없음"으로 계속 울린다 →
  *"원래 빨개요"* → 진짜 알림도 무시된다. values 주석이 이걸 *모니터링이 죽는 가장 흔한 경로*라고 적었다.
- **차트가 이미 아는 것은 다시 적지 않는다.** kubernetes-mixin 이 크래시루프 · 노드 압박 · 볼륨 가득을 다룬다.
  차트가 **알 수 없는** 것은 둘 — *Git 과 클러스터가 일치하는가*, *배포 경로가 실제로 배포하는가*.
- **GitOps 컨트롤러 자체가 관측 대상이다.** Phase 3 검증에서 `argocd_app_info` 8 series 로 앱 8개의 sync · health 를
  메트릭만으로 볼 수 있었다.

## 왜 다른 건 안 썼나

**기본값 그대로**

위의 첫 번째 이유.

**알림을 넉넉히 (Pending 파드 · 노드 수 · CRD 드리프트 …)**

알림 피로. [cicd-lab/05](../../../infra-lab/cicd-lab/05-argocd-advanced/README.md) 가 *"영구 OutOfSync 는 알림 피로를 만들어 진짜 드리프트를 가린다"* 고 적었다.

**클러스터 밖에서 sample-app 을 두드리는 가용성 체크**

공개 URL 이 없어서([결정 02](02-매일-destroy를-전제로-설계했다.md)) 성립하지 않는 구성이었다.

## 이 결정의 대가

### ① "스크레이프 불가"는 반만 맞다 *(AWS 문서에서 확인)*

차트 기본 타겟을 끈 것은 맞다 — 컴포넌트 엔드포인트를 직접 긁는 방식은 EKS 에서 영원히 실패한다.
그런데 AWS 문서에 따르면 **Kubernetes 1.28 이상 EKS 는 kube-scheduler · kube-controller-manager 메트릭을 API 서버 경로로 내준다.**

```
/apis/metrics.eks.amazonaws.com/v1/ksh/container/metrics   # kube-scheduler
/apis/metrics.eks.amazonaws.com/v1/kcm/container/metrics   # kube-controller-manager
# RBAC: apiGroups metrics.eks.amazonaws.com / resources ksh/metrics, kcm/metrics / get
```

이 클러스터(1.30)도 해당된다. etcd 는 목록에 없다.
저장소 values 주석과 [observability-lab/08](../../../infra-lab/observability-lab/08-kube-prometheus-stack/README.md) 의
*"EKS 는 컨트롤 플레인을 스크랩할 수 없다"* 는 **"차트 기본 방식으로는"** 이라는 조건이 빠진 문장이다.
[트러블 01](../troubleshooting/01-노드-두-대가-파드-34개로-만석.md) 에서 hook Job 이 10분 넘게 `Pending` 이었는데,
`scheduler_pending_pods{queue="unschedulable"}` 가 바로 그 상태를 세는 지표다.

### ② 알림이 도착할 곳이 없다 *(차트 87.16.1 values 에서 확인)*

```yaml
# kube-prometheus-stack 87.16.1 기본 alertmanager.config (발췌)
route:
  receiver: 'null'
  routes:
  - receiver: 'null'
    matchers:
      - alertname = "Watchdog"
receivers:
- name: 'null'
```

이 저장소의 values 는 `alertmanager.config` 를 안 건드렸다. 그래서 알림 3개가 전부 `'null'` 로 간다.
차트가 기본으로 넣는 **Watchdog** — *알림 파이프라인 전체가 동작하는지 확인하려고 항상 울리는 알림* — 도 `'null'` 이다.
[serverless-uptime-monitor 결정 05](../../serverless-uptime-monitor/decisions/05-요약-알림을-기존-알림-큐에-얹기.md) 에서
손으로 만든 dead man's switch 가 **차트에 이미 들어 있는데 연결되지 않았다.**

### ③ 한 번도 울려 본 적이 없다

Phase 3 검증은 *"3개 로드, 전부 INACTIVE"* 까지다. sample-app 을 0으로 줄여 `SampleAppDown` 을 Firing 시키는 실험은 후속 과제로 남았다.
그래서 **PromQL 이 실제 라벨과 맞는지**(`deployment="sample-app"` 등)는 확인되지 않았다.

그리고 07-20 에 kyverno · external-secrets 가 영구 OutOfSync 에 머물렀으니 `ArgoCDAppNotSynced` 의 조건을 만족하는 상태가
실제로 있었다. 그 알림이 떴는지는 **알 수 없다** — 받는 곳이 없었고, 메트릭은 클러스터와 함께 사라졌다. → [결정 05](05-관측성-데이터를-영속화하지-않는다.md)

## 배운 점

**알림을 고르는 결정과 알림을 받는 결정은 별개다.** 이 저장소는 *"무엇을 문제로 볼까"* 를 신중하게 골랐고(3개),
*"누구에게 알릴까"* 는 정하지 않았다. 알림 규칙은 **받는 곳이 생긴 뒤에야** 운영 신호가 된다.

**"불가능"이라고 적을 때는 조건을 같이 적어야 한다.** 스크레이프 불가는 차트 기본 방식 기준으로 맞고,
EKS 가 따로 내주는 경로 기준으로는 틀리다. [결정 03](03-전부-버전을-고정했다.md) 의 버전 만료와 같은 모양이다 —
사실에는 **유효 조건**이 붙는다.
