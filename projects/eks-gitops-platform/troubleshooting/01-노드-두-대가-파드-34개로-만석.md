# 01. 노드 두 대가 파드 34개로 만석 — CPU 가 아니라 IP 가 먼저 찼다

- **발생**: 2026-07-20 · Phase 2 검증 중
- **증상 한 줄**: Helm hook Job 2개가 10분 넘게 `Pending`, 그 여파로 kyverno · kube-prometheus-stack Application 이 `OutOfSync` 에서 멈춤
- **원문**: 저장소 [`docs/troubleshooting/01-max-pods-t3-medium.md`](https://github.com/GWANG-MIN1/eks-gitops-platform/blob/main/docs/troubleshooting/01-max-pods-t3-medium.md)

---

## 현상

`kyverno-migrate-resources` 와 `kube-prometheus-stack-admission-create` 의 파드가 스케줄되지 않았다. `describe` 이벤트:

```
Warning  FailedScheduling  ...  0/2 nodes are available: 2 Too many pods.
```

hook Job 이 끝나야 sync 가 진행되는 차트 둘이 그 자리에서 멈췄다.

## 환경

- EKS 1.30 (v1.30.14-eks) · managed node group **t3.medium SPOT × 2** (`desired_size = 2`, `max_size = 3`)
- VPC CNI 기본 설정 (prefix delegation 꺼짐)
- root-app 이 자식 Application 7개를 한꺼번에 올리는 중 — ArgoCD · kube-system · 관측성 · Kyverno · ESO · sample-app 이 동시에 자리를 찾음

## 진단

저장소 기록에 반증된 가설은 없다. **이벤트 메시지가 처음부터 답이었다** — `Insufficient cpu` 가 아니라 `Too many pods`.
전체 파드를 세어 보니 **34개 = 17 × 2**, 정확히 만석이었다.

돌아보면 예측은 있었다. 07-15 observability README 의 용량 메모가
*"t3.medium 두 대에 들어가지만 여유는 없다 — Pending 이면 노드를 늘려라"* 였다.
**증상과 처방은 맞췄고, "들어간다"는 결론만 틀렸다.** 무엇이 먼저 찰지(파드 수)는 계산하지 않았다.

## 원인

**AWS VPC CNI 는 파드마다 VPC IP 를 하나씩 준다.** 노드가 붙일 수 있는 ENI 수와 ENI 당 IP 수가 인스턴스 타입마다 정해져 있어서
노드당 파드 수의 상한이 생긴다.

```
max-pods = ENI 수 × (ENI 당 IPv4 수 − 1) + 2
t3.medium = 3 × (6 − 1) + 2 = 17
          # −1 : ENI 마다 첫 IP 는 ENI 자신의 것
          # +2 : IP 를 따로 안 받는 hostNetwork 파드 (aws-node · kube-proxy)
```

kubelet 은 이 상한을 hostNetwork 파드까지 **전부 세서** 적용한다. 그리고 이 플랫폼은 노드마다 DaemonSet 5개
(aws-node · kube-proxy · eks-pod-identity-agent · node-exporter · promtail)가 먼저 자리를 차지한다.
**노드당 남는 자리는 12개**고, CPU 가 남아도 18번째 파드는 못 들어간다.

## 해결

노드를 3대로 늘렸다. 여기서 두 번째 함정 —

```bash
terraform apply -var="node_desired_size=3"
# → No changes. Your infrastructure matches the configuration.
```

terraform-aws-modules/eks 는 노드 그룹의 `desired_size` 를 **`ignore_changes`** 로 둔다. 오토스케일러가 바꾼 값을
Terraform 이 되돌리며 싸우지 않게 하려는 의도적 설계다. 그래서 생성 이후의 변경은 AWS API 로 했다.

```bash
aws eks update-nodegroup-config --cluster-name eks-gitops-dev \
  --nodegroup-name <nodegroup> --scaling-config desiredSize=3 --region ap-northeast-2
```

약 2분 뒤 새 노드가 `Ready`, Pending 파드 2개가 바로 스케줄됐다.
07-22 · 07-23 재생성에서는 **처음부터** `-var="node_desired_size=3"` 으로 만들어 다시 안 겪었다 — 생성 시점에는 변수가 먹는다.

## 재발 방지

| 저장소가 적은 것 | 2026-09-14 기준 |
|---|---|
| 노드 수 × max-pods 를 먼저 계산 | 교훈으로만 있다 |
| 재생성 땐 처음부터 3대 | **명령줄 `-var`** 로만 — `variables.tf` · `tfvars.example` 기본값은 **2 그대로** |
| VPC CNI prefix delegation 으로 상한 올리기 | 후속 과제, 미적용 |

그래서 저장소를 처음 받은 사람이 README 대로 apply 하면 **이 문제를 다시 겪는다.**
그리고 `max_size = 3` 이라 3대가 곧 천장이다 — 스택이 조금만 커져도 같은 자리로 돌아온다.

코드로 막으려면 기본값을 3(또는 t3.large)으로 올리거나, `vpc-cni` 애드온에 prefix delegation 을 켠다.
→ [cost-lab/07](../../../infra-lab/cost-lab/07-rightsizing/README.md)

## 배운 점

- **작은 노드의 첫 한계는 CPU 가 아니라 IP 다.** 개념은 [cost-lab/07](../../../infra-lab/cost-lab/07-rightsizing/README.md) ·
  [observability-lab/08](../../../infra-lab/observability-lab/08-kube-prometheus-stack/README.md) 에 이미 들어가 있다. 둘 다 이 사건 뒤에 쓰였다.
- **"Terraform 이 관리한다"와 "Terraform 이 바꿀 수 있다"는 다르다.** `ignore_changes` 가 걸린 값은 생성할 때만 Terraform 의 것이다.
- **이 프로젝트에서 Git 과 실제가 처음 갈라진 지점이 여기다.** 클러스터 안은 `kubectl edit` 0회로 지켰는데,
  클러스터의 크기는 CLI 로 바뀌었다. 07-22 의 `-var` 는 **사람이 기억해서** 먹힌 것이지 재발 방지가 아니다.
