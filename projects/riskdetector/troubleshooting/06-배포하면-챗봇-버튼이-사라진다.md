# 06. 배포하면 챗봇 버튼이 사라진다 — 세 커밋짜리 추적

- **발생**: 2026-05-20 · 커밋 `718ea6a` → `58e8bdb` → `8cd6255`
- **증상 한 줄**: 로컬에서는 보이는 "아르디에게 물어보기" 버튼이 배포 환경에서만 안 보였다

---

## 현상

분석 결과 페이지 우하단에 챗봇을 여는 FAB(floating action button)을 뒀다.
**로컬 `npm run dev` 에서는 정상, Render 배포본에서는 없다.**

콘솔 에러도 없고, 요소가 DOM 에 없는 것도 아니었다.
같은 날 세 번 고쳤고, **처음 두 번은 원인이 아니었다.**

## 환경

- Next.js 16 App Router · `ArdiChatbot.tsx` 가 결과 페이지 안에 렌더링됨
- 배포: Render (Docker 빌드, 프로덕션 모드)
- 결과 페이지는 좌측 본문 + 우측 sticky 상세 패널 구조 (중첩 컨테이너가 깊다)

## 진단

### 1) 첫 가설 — CSS 클래스가 프로덕션에서 안 실린다 (반증)

FAB 이 `className="ardi-fab"` / `"ardi-fab-pill"` 같은 전역 CSS 클래스를 쓰고 있었다.
**프로덕션 빌드에서 그 CSS 가 누락됐다**고 의심했다. 그래서 전부 인라인 스타일로 바꿨다.

```diff
-        <div className="ardi-fab">
-          <div className="ardi-fab-mascot">
+        <div style={{
+          position: 'fixed', right: 24, bottom: 32, zIndex: 60,
+          display: 'flex', flexDirection: 'column', alignItems: 'flex-end',
+        }}>
```

`next/image` 도 `<img>` 로 바꿨다 (이미지 최적화가 배포에서 다르게 동작할까 봐).

**여전히 안 보였다.** → CSS 로딩 문제가 아니다.

### 2) 두 번째 가설 — loading/error 상태에서 렌더링을 건너뛴다 (반증)

결과 페이지가 데이터 로딩 중이거나 에러일 때 **early return** 을 하고 있었다.
그러면 FAB 도 같이 안 그려진다. 배포 환경은 API 가 느리거나(콜드스타트) 실패할 수 있으니
그 상태에 오래 머물렀을 가능성이 있었다.

그래서 **loading / error 상태에서도 FAB 은 항상 렌더링**하도록 페이지를 재구성했다
(`102 insertions, 104 deletions` — 렌더 구조를 통째로 바꿨다).

**이것도 근본 원인이 아니었다.** 데이터가 다 로드된 상태에서도 안 보였다.

### 3) 세 번째 — 부모의 stacking context 다 (맞음)

`position: fixed` + `zIndex: 60` 인데도 안 보인다면, 그 `zIndex` 가
**뷰포트 기준이 아니라 부모가 만든 새 stacking context 안에서** 겨루고 있다는 뜻이다.

조상 요소 중 하나라도 `transform` · `filter` · `will-change` · `opacity < 1` ·
`contain` 같은 속성을 가지면 **그 요소가 새 stacking context 를 만들고,
`position: fixed` 자손의 기준이 뷰포트가 아니라 그 요소가 된다.**

결과 페이지는 sticky 패널과 애니메이션(Framer Motion)이 섞인 중첩 구조였고,
**로컬과 배포에서 렌더 트리가 미묘하게 달랐다** (하이드레이션 타이밍·CSS 적용 순서).
그래서 로컬에서는 우연히 보이고 배포에서는 가려졌다.

## 원인

**FAB 이 부모 컨테이너의 stacking context 안에 갇혀 있었다.**
`position: fixed` 와 큰 `z-index` 는 **같은 stacking context 안에서만** 효력이 있다.

## 해결

**`createPortal` 로 `document.body` 에 직접 붙였다.** 부모 트리를 완전히 벗어난다.

```tsx
import { createPortal } from 'react-dom';

// SSR 이후 클라이언트에서만 portal 마운트
const [mounted, setMounted] = useState(false);
useEffect(() => setMounted(true), []);

// SSR에서는 렌더링하지 않음 (portal은 document.body 필요)
if (!mounted) return null;

// createPortal로 document.body에 직접 마운트 → 부모 stacking context 완전 우회
return createPortal(
  <div className="ardi-overlay" style={{ zIndex: 9999 }}>
    ...
  </div>,
  document.body
);
```

`zIndex` 도 60 → **9999** 로 올렸다.

## 재발 방지

- **화면 위에 떠야 하는 것은 처음부터 portal 로 만든다.** FAB · 모달 · 토스트 · 바텀시트는
  전부 같은 부류다. 부모 트리에 두면 **언젠가 조상이 `transform` 을 갖는다.**
- **`position: fixed` 가 안 먹으면 조상을 먼저 본다.** 브라우저 devtools 에서
  조상의 `transform` / `filter` / `will-change` / `contain` 을 확인하는 게
  첫 단계여야 했다. **CSS 로딩을 먼저 의심한 게 두 커밋을 태운 이유다.**
- **로컬과 배포가 다르면 "환경 차이"부터 세지 말고 렌더 트리를 비교한다.**
  세 번의 시도 중 앞의 둘은 *"배포 환경이 뭔가 다를 것"* 이라는 막연한 가정이었다.
  배포본을 devtools 로 직접 열어 봤으면 첫 시도에 끝났다.

## 배운 점

**"배포에서만 안 된다"는 증상은 원인을 배포 환경으로 오인하게 만든다.**
실제 원인(stacking context)은 **로컬에도 있었다.** 거기선 우연히 드러나지 않았을 뿐이다.
환경 차이는 버그를 **노출**시킨 조건이고 원인이 아니었는데,
두 커밋 동안 "배포 환경에서 CSS/이미지/상태가 다를 것"만 뒤졌다.

**가설을 바꿀 때 앞의 변경을 되돌리지 않은 것도 기록해 둘 만하다.**
1차 시도의 인라인 스타일은 지금도 남아 있다. 원인이 아니었는데 코드에는 그 흔적이 있고,
읽는 사람은 *"왜 여기만 인라인 스타일이지"* 를 다시 조사하게 된다.
