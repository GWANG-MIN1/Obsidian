# 02. 환각을 막으려고 조인 범위가 정상 질문까지 막았다

- **발생**: 2026-05-21 ~ 05-29 (8일) · 커밋 `88f0332` `c63b6ba` `43741c6` `8359f35` `d379ac4` `90f7c68`
- **증상 한 줄**: 판례 번호 조작을 막으려고 범위를 좁혔더니 "쉽게 설명해줘"에도 거절 문구가 나갔다

---

## 현상

챗봇의 허용 범위를 **8일 동안 다섯 번** 바꿨다. 커밋 순서가 그대로 기록이다.

| 날짜 | 커밋 | 방향 | 무엇 |
|---|---|---|---|
| 05-21 | `88f0332` | **조임** | 절대 규칙 5개 · 인용 허용목록 · `temperature` 0.4→0.2 |
| 05-21 | `c63b6ba` | **넓힘** | Bedrock KB RAG 연결 (Phase B) |
| 05-22 | `43741c6` | **넓힘** | 칩 라벨을 풀문장으로 → over-rejection 해소 |
| 05-22 | `8359f35` | 조임 | 조항 변경 시 히스토리 자동 리셋 |
| 05-24 | `d379ac4` | **좁힘** | 히스토리 리셋 **철회**(앵커 주입으로 대체) · "비슷한 판례" 칩 제거 · 판례 검색 거절 |
| 05-29 | `90f7c68` | **넓힘** | KB 결과에 답이 있으면 일반 법령 질문 허용 |

시작은 정당했다. `88f0332` 의 커밋 본문이 문제를 이렇게 적고 있다.

> - 손해배상 배수 등 입력 데이터에 없는 수치를 모델이 임의 생성
> - 계약/법률 무관 질문(짜장면 레시피 등)도 친절히 답함

그래서 조였다. 그 결과가 `c63b6ba` 본문에 나온다.

> Phase 1~3는 입력 데이터에 없는 사실 생성을 막는 데 집중했지만, 사용자가
> 입력 분석 데이터 범위 밖의 정보(유사 판례, 일반 법령 등)를 물으면
> **"데이터 없음"만 반복할 수밖에 없었음.**

그리고 `90f7c68` 본문.

> 기존 절대 규칙 1은 (a) 분석 조항 + (b) reasonReference 명시 법령 만 허용하고,
> **"근로기준법 제20조가 뭐야?" 같은 일반 법령 질문은 KB 검색 결과가 해당 조문 발췌문을
> 가져왔어도 거절 문구가 나갔음.**

거절 문구는 이것 하나다.

```
저는 계약서 위험 분석을 도와드리는 아르디예요. 계약 조항에 대해 궁금한 점을 물어봐 주세요!
```

## 환경

- `frontend/riskdetector-web/src/app/api/chatbot/route.ts` (635줄) — Next.js Route Handler
- `gpt-4o-mini` · `temperature: 0.2` · `max_tokens` 400(쉬운 모드) / 800
- KB 검색: `POST /api/chatbot/retrieve` → Spring → `bedrock_lambda(mode=retrieve)` → Bedrock KB
- 검색 타임아웃 4초 · top-K 4

## 진단

### 1) 첫 가설 — 프롬프트가 약하다 (반증)

거절이 나오면 *"거절하지 말라"* 를 더 세게 쓰는 쪽으로 갔다.
프롬프트에 그 흔적이 층층이 쌓여 있다.

```
1. **범위**: 다음에 해당하면 답할 수 있습니다 — 너무 까다롭게 거절하지 마세요.
   …
   **중요**: 현재 선택된 조항이 있고 사용자가 "쉽게 설명", "왜 위험해", "어떻게 바꿔",
   "이거 뭐야"처럼 짧게 물으면 무조건 (a)에 해당합니다.
   KB 검색 결과가 비어 있어도 거절하지 말고 현재 선택 조항 정보만으로 답하세요.
```

**줄어들긴 했지만 0이 되지 않았다.** 프롬프트는 확률을 조정하는 도구고,
*"절대 거절 금지"* 와 *"범위 밖은 거절"* 을 동시에 요구하면 모델이 경계에서 흔들린다.
→ 그래서 코드로 막는 층을 따로 뒀다 → [결정 12](../decisions/12-검증이-필요한-답변은-스트리밍을-포기했다.md)

### 2) 두 번째 가설 — 히스토리가 문제다 (부분 맞음, 그리고 철회)

조항 A 를 물어본 뒤 조항 B 로 옮겨 같은 칩을 누르면 **A 의 답이 미세 변형돼 다시 나왔다.**
`8359f35` 본문이 원인을 정확히 적었다.

> - 챗봇 messages state가 컴포넌트 unmount 전까지 유지됨
> - selectedToxic prop이 바뀌어도 이전 Q&A가 conversation 히스토리로 계속 주입되어
>   OpenAI가 직전 assistant 답을 따라가는 **momentum** 발생
> - 시스템 프롬프트의 "조항 전환 알림" 블록만으로는 **conversation flow 우선시하는
>   모델 성향을 이기지 못함**

그래서 조항이 바뀌면 히스토리를 **비웠다.** 이틀 뒤 `d379ac4` 가 그걸 되돌린다 —
히스토리를 비우면 같은 조항 내 후속 질문("그럼 어떻게 바꿔?")이 맥락을 잃기 때문이다.

대체 방법은 **모델 입력에만** 마커를 붙이는 것이었다.

```ts
// 조항이 방금 바뀐 경우, 마지막 user 메시지에 명시적 마커 prepend
// (모델만 보는 input-only 변형, 클라이언트 messages state에는 영향 없음)
if (body.clauseSwitched && body.selectedToxic?.title) {
  const last = messages[messages.length - 1];
  if (last?.role === 'user' && typeof last.content === 'string') {
    last.content = `[참고: 사용자가 방금 "${body.selectedToxic.title}" 조항으로 전환했습니다. `
                 + `이 질문은 이전 대화 주제가 아니라 위 조항에 대한 것입니다.]\n${last.content}`;
  }
}
```

**히스토리는 유지하고 앵커만 주입한다.** 이게 최종 형태다.

### 3) 세 번째 가설 — 모델이 자기 거절을 따라한다 (맞음)

거절 답변이 히스토리에 남으면 다음 턴에서 **또 거절한다.** 한 번 거절하면 대화가 거기서 죽는다.

```ts
function stripOutOfScopeHistory(messages: ChatRequest['messages']) {
  return messages.filter((message) => {
    if (message.role !== 'assistant') return true;
    return message.content.trim() !== OUT_OF_SCOPE_MESSAGE;
  });
}
```

### 4) 배포 환경에서는 RAG 가 사실상 안 돌았다

`d379ac4`(05-24)에서 "비슷한 판례" 칩을 빼고 판례 검색을 거절 대상으로 되돌렸다.
커밋 본문의 표현이 이렇다.

> **RAG 미연동 환경에서** "비슷한 판례" 류 질문은 명시적으로 거절

RAG 코드는 3일 전(`c63b6ba`)에 붙였는데, **배포 환경에서 실제로 근거가 돌아오지 않는
상태**였다. 이유는 검색 경로가 Render 백엔드를 지나가기 때문이다.

```
브라우저 → Next.js /api/chatbot
              └─ fetch  POST /chatbot/retrieve  (타임아웃 4초)
                    → Render Spring  ← 잠들어 있으면 콜드스타트 30초
                          → bedrock_lambda (mode=retrieve) → Bedrock KB
```

**4초 타임아웃 vs 콜드스타트 30초.** 백엔드가 자고 있으면 검색은 매번 비어서 돌아온다.
→ [트러블 01](01-Spring이-전시-5일-전에-교체됐다.md) 의 콜드스타트

그래서 "근거가 있을 때만 답한다"는 규칙이 배포에서는 *"거의 항상 거절"* 로 작동했다.
판례 검색을 아예 거절 문구로 고정한 것은 **없는 기능을 있는 척하지 않기로 한 선택**이다.
닷새 뒤 검색이 도는 걸 확인하고 다시 열었다(`90f7c68`).

### 5) 그런데 실패와 무결과가 같은 값으로 온다

되돌린 판단 자체는 맞았지만, 그걸 **코드가 알려 주지는 않았다.**

```ts
async function fetchRetrievedContext(query: string, contractType: string): Promise<RetrievedItem[]> {
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(), RETRIEVE_TIMEOUT_MS);   // 4초
  try {
    const res = await fetch(RETRIEVE_ENDPOINT, { ... });
    if (!res.ok) return [];                                   // ← 조용히 빈 배열
    const data: ChatbotRetrieveResponse = await res.json();
    if (!data.success || !Array.isArray(data.results)) return [];   // ← 조용히 빈 배열
    return data.results.filter((r) => r && (r.text ?? '').trim().length > 0);
  } catch {
    return [];                                                // ← 조용히 빈 배열
  } finally {
    clearTimeout(timer);
  }
}
```

**네 가지 상황이 전부 `[]` 로 수렴한다.**

| 실제 상황 | 반환 | 로그 |
|---|---|---|
| 백엔드가 콜드스타트로 자고 있다 (4초 초과) | `[]` | 없음 |
| Bedrock KB 호출이 실패했다 | `[]` | 없음 |
| KB 에 관련 문서가 없다 | `[]` | 없음 |
| 환경변수 `NEXT_PUBLIC_API_BASE_URL` 이 틀렸다 | `[]` | 없음 |

커밋 본문은 이걸 *"silent fallback이라 무해"* 라고 적었다 — 사용자에게 에러를 안 보인다는
뜻에서는 맞다. 하지만 **개발자에게도 안 보인다.** 검색이 왜 비었는지를
매번 사람이 따로 확인해야 했고, 그게 이 왕복을 더 오래 끌었다.

## 원인

**환각이 실제로 나왔고, 그걸 막으려고 좁힌 범위가 정상 질문까지 덮었다.**

문제는 **두 가지를 하나의 스위치로 조절한 것**이다.

| 축 | 무엇을 통제해야 하나 |
|---|---|
| 인용 통제 | 판례 번호·수치를 **데이터에 있는 것만** 쓰게 한다 |
| 응답 범위 | **어떤 질문에 답하는가** 를 정한다 |

`88f0332` 의 규칙 1은 이 둘을 한 문장에 묶었다 —
*"분석 데이터에 명시된 법령·판례에 대해서만 답한다."*
그러면 **인용을 조이면 대답 자체가 막힌다.** "근로기준법 제20조가 뭐야?"는
인용 통제 대상이지 거절 대상이 아닌데, 같은 규칙 하나에 걸려 거절됐다.

여기에 배포 환경 조건(콜드스타트로 KB 검색이 비어서 돌아옴)이 겹쳐서
**규칙이 의도보다 훨씬 세게 작동했다.**

## 해결

`90f7c68`(05-29)이 규칙 1에 **(c)** 를 추가한 것으로 정리됐다.

```
   (c) 이번 계약·계약법·해당 계약 유형(임대차·근로·전속계약 등)을 이해하는 데 도움이 되는
       **일반 법률 개념·원칙·용어 설명** — 단, 구체적인 조문 번호·판례 번호는 (a)·(b) 또는
       100% 확실한 주요 법령에서만 가져오세요.
```

거절 트리거를 *"(a)~(c) 어디에도 해당하지 않고 **동시에** KB 결과가 비거나 무관한 경우"* 로 좁혔다.
인용 허용목록은 `collectAllowedCitations` 가 `retrieved` 텍스트에서 자동 추출하므로 코드 변경이 없었다.

그리고 검증이 필요한 경로(쉬운 모드)는 **스트리밍을 포기하고 응답을 검사**해서
거절이면 결정론적 대체 답으로 갈아치웠다.
→ [결정 12](../decisions/12-검증이-필요한-답변은-스트리밍을-포기했다.md)

## 재발 방지

- **인용 통제와 응답 범위를 다른 규칙으로 분리해서 쓴다.** 프롬프트에서도 두 절로 나누면
  한쪽을 세게 조여도 다른 쪽이 따라 조여지지 않는다. `90f7c68` 이 (c)를 더해 사후에 나눈 것을
  **처음부터 그렇게 썼어야** 했다.
- **환각을 잡았으면 무엇이 잡혔는지 샘플로 남긴다.** 이번엔 증상을 커밋 본문에 문장으로만
  적었다(*"손해배상 배수 등 입력 데이터에 없는 수치를 모델이 임의 생성"*).
  실제 질문·응답 쌍을 몇 개 저장해 뒀으면 **규칙을 풀 때 그게 다시 나오는지 확인**할 수 있었다.
  지금은 조였다 풀 때마다 손으로 다시 물어보는 것밖에 방법이 없었다.
- **거절률을 센다.** 조이면 환각이 줄고 거절이 늘어난다. 이 트레이드오프를 숫자로 안 보고
  느낌으로 다섯 번 조절했다. 거절 횟수만 로그로 세도 방향을 알 수 있었다.
- **`catch { return [] }` 는 실패를 로그로라도 남긴다.** 지금 코드에는 `console.error`
  한 줄도 없어서, 검색이 왜 비었는지를 매번 사람이 따로 확인해야 했다.
- **응답에 검색 상태를 실어 보낸다.** `bedrock_lambda` 는 `retrievalMeta`
  (`searchType` · `rerankApplied` · `rrfApplied`)를 이미 만들어 놓는데
  **챗봇 경로는 그걸 안 쓴다.** 챗봇 응답에 "근거 N건 사용" 표시를 붙였으면
  개발자와 사용자가 동시에 알 수 있었다.
- **타임아웃 값을 환경에 맞춘다.** 4초는 백엔드가 깨어 있을 때의 값이다.
  콜드스타트 30초 환경에서는 warmup 을 먼저 하거나 타임아웃을 늘려야 했다.
  (실제로 팀원이 나중에 `/api/chatbot/warmup` 을 붙였다.)

## 배운 점

**환각 억제와 응답 범위는 같은 스위치가 아니다.**
"판례 번호를 조작하지 않는다"와 "이 질문에 답하지 않는다"는 서로 다른 축인데,
처음엔 **범위 하나로 둘을 같이 조절**했다. 그래서 환각을 막을 때마다 대답도 같이 막혔고,
대답을 열 때마다 환각 위험이 같이 열렸다. 규칙 1에 (c)를 더한 게 축을 나눈 것이고,
그 뒤로는 왕복이 멈췄다.

**LLM 기능은 안전장치를 "얼마나"가 아니라 "어디에" 걸지의 문제다.**
같은 강도라도 인용 단계에 걸면 답변은 살고, 범위 단계에 걸면 답변이 죽는다.
가장 효과가 확실했던 것은 결국 **인용 단계에 걸고, 자주 나오는 답은 LLM 을 안 거치게 한 것**이었다.
→ [결정 11](../decisions/11-인용을-허용목록으로-제한한다.md) ·
[결정 12](../decisions/12-검증이-필요한-답변은-스트리밍을-포기했다.md)

**그리고 조정을 다섯 번 한 건 판단이 틀려서가 아니라 계기가 매번 새로 생겨서다.**
환각 → 과잉 거절 → 히스토리 momentum → 배포 환경에서 근거 없음 → 근거 생김.
**다섯 번 모두 그 시점에는 맞는 대응이었다.** 다만 각 대응이 다음 문제를 만들었고,
그걸 미리 못 본 건 **조이면 무엇이 같이 조여지는지**를 축으로 나눠 보지 않았기 때문이다.
