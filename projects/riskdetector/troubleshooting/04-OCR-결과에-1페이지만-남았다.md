# 04. OCR 결과에 1페이지만 남았다 — 계층 간 계약이 말없이 바뀜

- **발생**: 2026-06-02 · 커밋 `0c7d7f5` (팀원 작업 — 원인이 내 계층과의 계약 변경이라 남긴다)
- **증상 한 줄**: 여러 장 업로드하면 1페이지 블록만 남고 2페이지 이후가 빈 결과로 나왔다

---

## 현상

OCR Lambda 응답에서 **페이지 2 이후의 블록이 전부 사라졌다.**
에러는 없다. `success: true` 에 `html_array` 가 비어 있거나 1페이지 내용만 담겨 있다.

Spring 쪽에서는 이렇게 보인다.

```java
String ocrStatus = savedContents.isEmpty() ? "fail" :
                  (results.size() < files.size() ? "partial_success" : "success");
```

→ `partial_success` 로 내려가거나, 페이지가 적으면 그냥 `success` 인 채로
**내용이 모자란 결과**가 된다.

## 환경

- `backend_ai/lambdas/ocr_lambda/handler.py` — `build_lambda_response()`
- 프론트가 PDF 를 `pdf.js` 로 페이지별 이미지로 **미리 분할**하기 시작한 이후
  (같은 날 커밋 `ff012ce Load pdf.js worker from CDN for reliable multi-page split`)
- Spring 은 페이지당 Lambda 를 한 번씩, 순차로 호출한다
  ([결정 04](../decisions/04-OCR-페이지를-순차로.md))

## 진단

원인은 고친 코드의 주석에 정확히 남아 있다.

```python
# The caller now sends one image per page (frontend pre-splits PDFs),
# so each Upstage response only describes a single page. Filtering by
# element.page == page_idx + 1 used to drop everything except page 1.
```

### 1) 원래 계약 — Lambda 가 여러 페이지를 받는다

초기 구조에서는 **PDF 파일 하나**를 Upstage 에 보냈다.
그러면 응답의 `elements` 안에 여러 페이지의 블록이 섞여 오고,
각 element 에 `page` 필드(1-based)가 붙는다. Lambda 는 그중
**요청받은 페이지만 골라내야** 했다.

```python
# 옛 로직 (개념)
html_array = [ ... for element in elements if element.get("page") == page_idx + 1]
```

### 2) 계약이 바뀌었다 — 이제 페이지당 이미지 1장

프론트가 PDF 를 페이지별 이미지로 쪼개 보내기 시작했다.
그러면 Upstage 응답은 **항상 한 페이지**만 설명하고, 그 안의 `element.page` 는 **전부 1** 이다.

```
Spring 이 pageIdx=1 로 호출
  → Lambda 가 element.page == 2 인 것을 찾는다
    → 없다 (전부 1)
      → html_array = []
        → 에러 없이 빈 결과
```

**`pageIdx=0` 만 우연히 맞는다.** 그래서 "1페이지만 나온다"가 증상이 됐다.

### 3) 왜 아무도 못 잡았나

- **에러가 안 난다.** 필터 결과가 빈 리스트인 것은 정상 반환이다.
- Lambda 는 `success: true` 를 준다. `hasError()` 도 `isSuccess()` 도 통과한다.
- Spring 의 `partial_success` 는 **페이지 수가 안 맞을 때**만 뜨는데,
  블록이 0개라도 `result.isSuccess()` 가 `true` 면 `results` 에 들어간다.
- 한 장짜리 계약서로 테스트하면 **항상 성공한다.**

## 원인

**계층 간 입력 계약이 한쪽에서만 바뀌었다.**

| 계층 | 가정 | 실제 |
|---|---|---|
| 프론트 (변경됨) | 페이지당 이미지 1장을 보낸다 | 그렇게 보냈다 |
| Spring (그대로) | `pageIdx` 를 Lambda 에 넘긴다 | 그대로 넘겼다 |
| **Lambda (그대로)** | **응답에 여러 페이지가 섞여 있다** | **한 페이지만 온다** |

`pageIdx` 라는 파라미터가 **의미를 잃었는데 시그니처는 그대로**였다.
그래서 호출은 성공하고 결과만 비었다.

## 해결

**필터를 없앴다.** 응답 전체를 그 페이지의 블록으로 취급한다.

```python
def build_lambda_response(result, bucket, s3_key, page_idx):
    elements = result.get("elements", []) or []

    # The caller now sends one image per page (frontend pre-splits PDFs),
    # so each Upstage response only describes a single page. Filtering by
    # element.page == page_idx + 1 used to drop everything except page 1.
    html_array = [
        element.get("content", {}).get("html", "")
        for element in elements
        if element.get("content", {}).get("html")
    ]
```

`page_idx` 는 **응답에 그대로 되돌려주는 식별자**로만 남았다 (Spring 이 정렬에 쓴다).

## 재발 방지

- **빈 결과를 성공으로 취급하지 않는다.** `elements` 가 있는데 `html_array` 가 0개면
  그건 정상이 아니다. Lambda 가 `{"success": false, "error": "no html blocks"}` 를
  돌려주거나, 최소한 `elements_count` 와 `len(html_array)` 의 불일치를 로그로 남겨야 했다.
  (`elements_count` 는 응답에 실려 있다 — **아무도 안 봤다.**)
- **입력 계약을 바꿀 때 그 파라미터를 쓰는 곳을 전부 찾는다.** `pageIdx` 는
  프론트 → Spring → Lambda 세 계층을 지나가는 값이었고, 의미가 바뀐 건 맨 끝이었다.
- **여러 장 계약서를 테스트 케이스로 고정한다.** 저장소의
  [`계약서예시/`](https://github.com/LilChaewon/RiskDetector/tree/main/계약서예시) 에
  PDF 7개가 있는데 **자동으로 돌려 보는 건 없다.** 이 저장소의 자동 테스트는 1개다.

## 배운 점

**필터는 "해당하는 것만 남긴다"가 아니라 "해당하지 않으면 전부 버린다"다.**
`if element.page == page_idx + 1` 한 줄이, 상류의 가정이 바뀌자
**조용히 전체를 버리는 코드**로 변했다. 필터는 조건이 틀리면 에러가 아니라 **빈 결과**를 준다.

같은 형태를 내가 다른 저장소에서도 겪었다 —
[serverless-uptime-monitor 트러블 02](../../serverless-uptime-monitor/troubleshooting/02-같은-페이지네이션-버그를-세-번.md)
의 페이지네이션 누락도 *"에러 없이 잘린다"* 였다. **데이터를 줄이는 코드는
잘못됐을 때 예외가 아니라 침묵으로 신호한다.**

**그리고 팀 프로젝트에서는 내 계층이 아닌 곳에서 계약이 바뀐다.**
프론트가 PDF 분할을 맡기로 한 변경을 나는 따라가지 않았고,
그 사이에 있던 Spring 의 `pageIdx` 전달 코드는 **의미 없는 값을 성실하게 넘기고 있었다.**
