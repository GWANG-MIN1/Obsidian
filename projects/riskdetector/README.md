계약서를 OCR로 읽어 AI가 독소조항을 찾아 주는 웹 서비스. **캡스톤디자인 팀 프로젝트 · 장려상.**

- 저장소: https://github.com/LilChaewon/RiskDetector
- 기간: 2026-03-23 ~ 2026-06-07 (커밋 361개 · 병합 144회 · 팀 5명)
- **내 역할: 백엔드** — Spring Boot API, AWS Lambda 3개 연동, 아르디 챗봇(RAG·환각 차단)
- 내 커밋: 77개 (전체의 21%) · 실제 작업일 23일
- 한 줄 요약: **LLM이 "모르는 것을 모른다고 말하게" 만드는 데 프로젝트의 절반을 썼고,
  그렇게 만든 백엔드는 전시 5일 전에 비용 때문에 통째로 교체됐다**

## 이 프로젝트의 축 — 모델이 모른다고 말하게 만들기

계약서 분석은 **틀린 답이 없는 답보다 나쁜** 도메인이다. 잘못된 조문 번호를 근거로
"이 조항은 안전합니다"라고 말하면 서비스가 없는 것보다 해롭다.
그래서 내 작업의 절반은 기능 추가가 아니라 **모델의 입을 막는 쪽**이었다.

| 층 | 무엇을 막나 | 어디서 |
|---|---|---|
| 프롬프트 절대 규칙 5개 | "데이터에 없는 수치 생성" | [결정 11](decisions/11-인용을-허용목록으로-제한한다.md) |
| 인용 허용목록 | **판례 번호 조작** | [결정 11](decisions/11-인용을-허용목록으로-제한한다.md) |
| 결정론적 사전 답변 | 조문 내용 자체를 틀리는 것 | [결정 11](decisions/11-인용을-허용목록으로-제한한다.md) |
| 스트리밍 포기 | 검증 못 한 답이 이미 나가 버린 것 | [결정 12](decisions/12-검증이-필요한-답변은-스트리밍을-포기했다.md) |

막아야 할 이유는 실재했다 — 모델이 **없는 손해배상 배수를 만들고, 판례 번호를 지어냈다.**
그런데 **조이면 정상 질문까지 막힌다.** 8일 동안 다섯 번 조절했고,
그 왕복 자체가 이 프로젝트에서 가장 많이 배운 것이다.
왕복한 이유는 판단이 틀려서가 아니라 **"무엇을 인용할 수 있나"와 "무엇에 답할 수 있나"를
한 규칙으로 묶어 뒀기** 때문이다.
→ [트러블 02](troubleshooting/02-환각을-막으려고-정상-질문까지-막았다.md) ⭐

가장 예상 못 한 원인은 코드가 아니었다. **버튼 라벨을 짧게 썼더니 모델이 전부 거절했다.**

## 개념 노트

재사용 가능한 지식은 [`infra-lab/aws-lab/`](../../infra-lab/aws-lab/README.md) 에 둔다.
이 프로젝트에서 나온 것 중 **아직 안 쓴** 후보는 아래.

- [ ] Lambda `RequestResponse` 6MB / `Event` 256KB 페이로드 한도 — 동기·비동기를 나누는 실제 기준
- [ ] Bedrock Knowledge Base `HYBRID` vs `SEMANTIC` — 벡터 스토어가 hybrid 미지원일 때의 `ValidationException`
- [ ] RAG-Fusion — 쿼리를 LLM으로 N개 만들고 RRF(`1/(k+rank)`, k=60)로 합치기
- [ ] LLM 인용 허용목록(citation whitelist) 패턴 — 프롬프트로 막고, 목록으로 좁히고, 사전으로 대체
- [ ] 스트리밍과 출력 검증은 양립하지 않는다 — 후처리가 필요하면 `stream: false`
- [ ] `SameSite=None` 쿠키를 쓰는 순간 "CSRF 대신 SameSite" 논리가 무너진다
- [ ] Upstage Document Parse — 한국어 계약서(도장·표) OCR과 블록 단위 HTML 출력

기존 노트 중 이 프로젝트와 직접 겹치는 것 —

**주의해서 말할 것**

- **자동 테스트가 사실상 없다.** `backend_ai/tests/local/*.py` 는 `argparse` 로 손으로 돌리는
  실행 스크립트고, Spring 테스트는 컨텍스트 로딩 1개다. 검증은 전부 **실배포 + 손으로 호출**이었다.
- **OCR 10~20초 / 분석 30~60초는 시연 중 체감**이다. 로그에서 집계한 값이 아니다.
  토큰 사용량·호출 횟수도 집계하지 않았다.
- **인증은 있지만 인가는 필터에 없다.** `/api/**` 전체가 `permitAll` 이고 소유권 검사는
  각 서비스의 `hasAccess()` 가 한다. → [결정 06](decisions/06-인가를-서비스-계층에서.md)
- **판례 763건은 저장소 파일 수**다. Bedrock Knowledge Base 에 실제로 인덱싱된 수는 확인하지 않았다.
  생활법령 600건은 파일 수와 일치한다.
- **OCR 엔진 비교(Upstage vs Tesseract vs Google Vision)에 측정 기록이 없다.**
  비교 스크립트도 샘플별 정확도 표도 저장소에 없다. 판단은 체감이었다.
- **Gemini 는 자동 폴백이 아니라 `LLM_PROVIDER` 환경변수로 고르는 제공자**다.
  Bedrock 경로에는 `try/except` 가 없어서 런타임에 Gemini 로 넘어가지 않는다.

## 아직 안 한 것과 이유

**`tagIdx` 가 한 페이지 100블록에서 깨진다** *(이 노트를 쓰며 코드에서 찾은 것 — 안 고침)*

OCR 블록 순서를 `pageIdx * 100 + elIdx` 로 만들고, 분석 때 `tagIdx / 100` 으로 페이지를 되돌린다.
**한 페이지에 블록이 100개를 넘으면 다음 페이지 그룹으로 새어 들어간다.**
계약서 한 장이 블록 100개를 넘은 적이 없어서 티가 안 났을 뿐이다.
→ [결정 05](decisions/05-블록-순서를-tagIdx-합성키로.md)

**게스트 계약서는 URL 을 아는 사람이 볼 수 있다**

`hasAccess()` 는 소유자도 `guestSessionId` 도 없는 계약(초기 게스트 데이터)에 대해 `true` 를 돌려준다.
하위호환을 위해 일부러 남긴 구멍이고, 코드에 주석으로 적혀 있다.
`contractId` 가 UUID 라 추측은 어렵지만 **URL 유출 = 열람 가능**이다.
→ [결정 07](decisions/07-게스트를-X-Guest-Id로.md)

**CSRF 를 끈 근거가 배포 환경에서 성립하지 않는다**

`SecurityConfig` 는 *"JWT + Stateless → CSRF 비활성화 (SameSite=Lax 쿠키로 대체 보호)"* 라고
주석을 달았는데, `OAuth2SuccessHandler` 는 운영에서 **`SameSite=None`** 으로 쿠키를 내린다.
크로스 오리진 배포 때문에 필요했던 선택이지만, **주석에 적은 대체 보호가 사라진 상태**다.
→ [결정 08](decisions/08-JWT를-쿠키와-URL-양쪽으로.md)

**분석 결과 적재 경로가 두 개다**

`bedrock_lambda` 는 `ANALYSIS_RESULT_LOADER_MODE` 기본값(`lambda`)으로 로더를 **직접 호출**하는데,
Spring 쪽 주석은 *"Destination → SQS → loader"* 라고 적혀 있다. 환경변수 하나로 갈리는
두 경로를 **각 계층 문서가 서로 다르게** 적고 있다. 실제로 어느 쪽으로 돌았는지 확인하지 않았다.
지금 안 터지는 이유는 로더가 `DELETE` + `INSERT` 로 **멱등**하기 때문이다.
→ [결정 03](decisions/03-DB-쓰기를-워커에게-넘겼다.md)

**죽은 코드를 안 지웠다**

`AnalysisProcessService` 에 `buildOverallComment` · `buildWarningComment` · `buildAdvice` ·
`formatSourceIds` · `toWarnLevel` 5개가 **정의만 있고 호출부가 없다.** DB 쓰기를 로더로 넘길 때
Spring 쪽 파싱 코드를 남겨 둔 잔재다. 같은 로직이 로더에도 복제돼 있다.

**챗봇 retrieve 에 인증이 없다**

`POST /api/chatbot/retrieve` 는 `permitAll` 이고 바로 Bedrock KB 를 때린다.
스로틀링도 없다. [serverless-uptime-monitor](../serverless-uptime-monitor/README.md) 에서
*"인증이 없다"* 를 이미 한 번 적었는데, 여기선 **비용이 붙는 엔드포인트**라 성질이 다르다.

| 검증 | 실배포 + 손으로 호출 | 테스트 / CI 게이트 / 요약 알림 |
| 무너진 지점 | **내 백엔드가 교체됐다** | 코드가 조용히 멈췄다 |

**혼자일 때보다 테스트를 안 썼다.** 브랜치를 파고 PR 을 올리고 리뷰를 거치는 절차는 다 있었는데
(병합 144회), 그 절차가 검증한 것은 **"머지해도 되는가"였고 "동작하는가"가 아니었다.**
[gym-management-db](../gym-management-db/README.md) 는 혼자 만들고 외부 리뷰를 받아 테스트 56개를
붙였다. 여기선 매일 리뷰가 있었는데도 0에 가까웠다. 절차의 존재가 검증의 존재를 보장하지 않는다.

**그런데 이 프로젝트가 다음 두 프로젝트를 낳았다.** 날짜가 겹친다 —
[serverless-uptime-monitor](../serverless-uptime-monitor/README.md) 는 2026-05-14 시작,
[aws-serverless-agent](../aws-serverless-agent/README.md) 는 05-23 시작.
RiskDetector 가 아직 돌아가던 때다. 여기서 Lambda · Bedrock · S3 를 **팀 코드 안에서 쓰긴 했지만
이해하지는 못한 채** 넘어갔고, 그걸 혼자 부품부터 다시 쌓은 것이 그 두 저장소다.

**그리고 무너진 지점의 성격이 달랐다.** 솔로 프로젝트들은 **코드가 조용히 멈춰서** 무너졌다.
여기선 코드가 아니라 **선택이 무너졌다** — Spring Boot + 상시 인스턴스 + 관리형 DB 라는 구성이
학생 팀이 계속 낼 수 있는 비용이 아니었고, 그래서 비용을 줄이는 쪽으로 교체됐다
([트러블 01](troubleshooting/01-Spring이-전시-5일-전에-교체됐다.md)).
**코드를 잘 쓰는 것으로 방어되지 않는 층이 있다**는 걸 여기서 처음 봤다.

그 층을 나는 솔로 프로젝트에서도 비워 뒀다 —
[serverless-uptime-monitor](../serverless-uptime-monitor/README.md) 도
*"비용을 집계하지 않았다. 프리티어 범위라고 판단했을 뿐 청구서로 확인한 값이 없다"* 다.
팀에서 대가를 치른 항목을 혼자 할 때도 여전히 안 보고 있었다.
