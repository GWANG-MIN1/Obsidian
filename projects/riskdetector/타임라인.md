## 1단계 · 2026-03-23 ~ 04-12 — 뼈대 (커밋 69개 / 내 17개)

2주 만에 백엔드의 골격이 다 선다. 내 몫은 Spring 쪽 전부였다.

```
03-30  Spring Boot 프로젝트 생성
03-31  웹 로그인 API — SecurityConfig · JwtUtil · CustomOAuth2UserService · User
04-01  CORS 설정 + schema.sql
04-02  OCR API (POST /api/ocr/upload)
04-06  ocr_lambda 실제 연동
04-07  OCR API 실제 테스트
04-08  분석 요청/결과 조회 API
04-10  Spring Security 기본 로그인 폼 비활성화
```

첫날 로그인을 **Google OAuth2 + JWT** 로 바로 갔다. 세션을 안 쓴 것은
프론트가 별 도메인에 배포될 것이 이미 정해져 있었기 때문이다.
→ [결정 08](decisions/08-JWT를-쿠키와-URL-양쪽으로.md)

이 구간에 **두 가지 사고**가 있었다.

- 04-02: `.claude/settings.local.json` 에 로컬 PostgreSQL **비밀번호가 평문으로 커밋**됐다.
  다음 커밋에서 `******` 로 덮고, 저녁에 파일을 untrack 했다.
  → [트러블 09](troubleshooting/09-비밀번호를-커밋하고-마스킹으로-덮었다.md)
- 04-06: 저장소 안에 **중첩 git 레포**(`riskdetector/`)가 들어가 있던 것을 제거.

04-10 의 `formLogin(disable)` 한 줄이 이 단계의 마지막이다. API 를 호출하면 JSON 이 아니라
**Spring 기본 로그인 화면 HTML** 이 돌아오던 문제였다.
→ [트러블 07](troubleshooting/07-API가-기본-로그인-폼을-돌려준다.md)

## 2단계 · 2026-04-18 ~ 04-30 — 프론트 결합과 Bedrock 연동 (커밋 64개 / 내 1개)

내 커밋이 **04-29 의 `bedrock_lambda 실제 연동` 하나**뿐인 구간이다.
그 사이 팀은 프론트를 붙이고 Render 에 처음 올렸다(04-28~29 에만 48커밋).

내가 한 그 한 개가 중요하다. `AnalysisProcessService` 가 분석 Lambda 를
**`InvocationType=Event`(fire-and-forget)** 로 호출하도록 바꾼 것이다.
OCR 은 동기(`invokeAndWait`)인데 분석만 비동기다.
→ [결정 01](decisions/01-무거운-일을-Lambda로-밀어냈다.md) · [결정 02](decisions/02-OCR은-동기-분석은-비동기로.md)

비동기로 던지면 **결과를 누가 DB 에 쓰는가**가 문제가 된다. 그 답이 세 번째 Lambda
(`analysis_result_loader`)였다. Spring 은 읽기만 한다.
→ [결정 03](decisions/03-DB-쓰기를-워커에게-넘겼다.md)

## 3단계 · 2026-05-04 ~ 05-12 — 배포 안정화 (커밋 80개 / 내 8개)

배포하고 나서야 드러나는 것들을 고친 구간이다. 전부 **로컬에서는 되는데 Render 에서 안 되는** 종류였다.

| 날짜 | 한 것 |
|---|---|
| 05-04 | Google OAuth `redirect-uri` 명시 · Render Docker build path |
| 05-05 | `application.yaml` 정리 · `AntPathRequestMatcher` deprecated 제거 |
| 05-06 | Dockerfile `ARG` 에 프로덕션 URL 기본값 · `/api/auth/logout` 추가 |

`redirect-uri` 를 명시하지 않으면 Spring 이 **요청 호스트를 보고 콜백 URL 을 만든다.**
Render 프록시 뒤에서는 그 값이 Google 콘솔에 등록한 것과 달라져 `redirect_uri_mismatch` 가 난다.
→ [트러블 08](troubleshooting/08-Google-로그인이-배포에서만-깨졌다.md)

## 5단계 · 2026-05-24 ~ 06-01 — 챗봇 범위 조정 (커밋 84개 / 내 11개)

8일 동안 챗봇의 허용 범위를 **조였다 풀었다** 한다.

| 날짜 | 방향 | 한 것 |
|---|---|---|
| 05-24 | ← 좁힘 | 히스토리 리셋 **철회**, 앵커 주입으로 대체 · "비슷한 판례" 칩 제거 · 판례 검색 거절 |
| 05-27~28 | — | 아바타 크롭, 모바일 게스트 로그인 |
| 05-29 | → 확장 | **KB 검색 결과에 답이 있으면 일반 법령 질문 허용** (규칙 1에 (c) 추가) |
| 06-01 | → 확장 | 조항/법령 응답 수정 (팀원: 콜드스타트 거절 회피 · warmup 후 OpenAI 우선) |

05-24 의 커밋 메시지가 스스로 *"방향 전환"* 이라고 적고 있다. 이틀 전 머지한
히스토리 자동 리셋을 걷어내고, 대신 **모델 입력에만** 조항 전환 마커를 붙이는 방식으로 갔다.
클라이언트 상태는 그대로 두고 프롬프트만 바꾼 것이다.

그리고 같은 커밋이 *"RAG 미연동 환경"* 이라며 판례 검색을 거절 대상으로 돌린다.
코드는 3일 전에 붙였지만 **배포에서는 근거가 돌아오지 않았다** — KB 검색이 Render 백엔드를
지나가는데 타임아웃이 4초고 콜드스타트가 30초였다. 없는 기능을 있는 척하지 않기로 하고
판례 질문을 거절 문구로 고정했다. → [트러블 02](troubleshooting/02-환각을-막으려고-정상-질문까지-막았다.md)

닷새 뒤(05-29) 검색이 도는 걸 확인하고 다시 넓혔다.
**환각을 막으려 조이고 → 과잉 거절을 풀고 → 근거가 없어 좁히고 → 근거가 생겨 넓혔다.**
다섯 번 다 그 시점에는 맞는 대응이었고, 문제는 **인용 통제와 응답 범위를 한 규칙으로
같이 조절한 것**이었다.

## 6단계 · 2026-06-02 — Supabase 이전 (커밋 9개 / 내 0개)

팀원이 하루에 커밋 7개로 **Spring Boot 백엔드를 Supabase Edge Function 으로 교체**했다.

```
render.yaml   riskdetector-backend 서비스 블록 삭제 (49줄 → 13줄)
supabase/functions/rd-api/index.ts   신규 977줄 — 내 엔드포인트 10개를 재구현
supabase/migrations/…init_riskdetector.sql   신규 126줄
supabase/seed.sql   신규 2,923줄
인증   Spring OAuth2 + 자체 JWT  →  Supabase Auth
```

**이유는 비용이다.** Render 에 웹 서비스 2개 + PostgreSQL 을 상시로 띄우고 있었는데,
Supabase 로 옮기면 그중 둘이 무료 티어 안으로 들어온다. 그래서 데이터도 안 옮겼다 —
*"기존 Render PostgreSQL 데이터는 복구하지 않고 새 Supabase DB에서 시작합니다."*
덤으로 Spring 의 콜드스타트 30초도 사라졌다.

내 백엔드 코드는 저장소에 그대로 남았지만 **배포 대상에서 빠졌다.**
→ [트러블 01](troubleshooting/01-Spring이-전시-5일-전에-교체됐다.md) ⭐
