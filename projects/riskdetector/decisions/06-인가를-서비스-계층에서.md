# 06. 인가를 시큐리티 필터 대신 서비스 계층에서

> 메모: `/api/**` 가 전부 `permitAll` 이다. 소유권 검사는 각 서비스의 `hasAccess()` 가 한다.
> 게스트를 받기로 한 순간 필터로는 풀 수 없었다. 2026-03-31 ~

---

## 상황

로그인 없이도 계약서를 분석할 수 있어야 했다([결정 07](07-게스트를-X-Guest-Id로.md)).
그러면 같은 엔드포인트가 **두 종류의 호출자**를 받는다.

| 호출자 | 식별 | 접근 가능 범위 |
|---|---|---|
| 로그인 사용자 | JWT 의 `sub`(이메일) | 자기가 올린 계약서 |
| 게스트 | `X-Guest-Id` 헤더 | 그 브라우저가 올린 계약서 |

Spring Security 의 `authorizeHttpRequests` 는 **"인증됐는가"** 를 본다.
게스트는 인증되지 않았지만 **접근은 허용**해야 한다. 그리고 로그인 사용자든 게스트든
*"이 계약서가 당신 것인가"* 는 **DB 를 읽어야** 알 수 있다.

## 결정

**필터에서는 전부 통과시키고, 서비스 메서드마다 소유권을 검사했다.**

```java
// SecurityConfig
.authorizeHttpRequests(auth -> auth
        .requestMatchers("/oauth2/**").permitAll()
        .requestMatchers("/login/oauth2/**").permitAll()
        .requestMatchers("/actuator/health").permitAll()
        .requestMatchers("/error").permitAll()
        .requestMatchers("/api/auth/logout").permitAll()
        .requestMatchers("/api/**").permitAll()        // ← 전부 공개
        .anyRequest().authenticated()
)
```

JWT 필터는 **인증을 시도하지만 실패해도 막지 않는다.**

```java
// JwtAuthenticationFilter
} catch (Exception e) {
    logger.error("Could not set user authentication in security context", e);
    // 인증 설정에 실패하더라도 filterChain은 계속 타야 permitAll 경로가 작동함
}
filterChain.doFilter(request, response);
```

실제 인가는 서비스에 있고, **`OcrProcessService` 와 `AnalysisProcessService` 에 같은 메서드가 복제**돼 있다.

```java
private boolean hasAccess(Contract contract, String email, String guestSessionId) {
    // 소유자가 있으면 이메일 일치 필요
    if (contract.getUser() != null) {
        return !isGuest(email) && contract.getUser().getEmail().equals(email);
    }
    // 이전 게스트 계약은 session id가 없을 수 있어 contractId 접근을 유지한다.
    if (!StringUtils.hasText(contract.getGuestSessionId())) return true;
    return StringUtils.hasText(guestSessionId) && contract.getGuestSessionId().equals(guestSessionId.trim());
}
```

그리고 **권한 없음을 404 로 돌려준다.**

```java
if (!hasAccess(contract, email, guestSessionId)) {
    throw new ResourceNotFoundException("Contract not found: " + contractId);
}
```

## 왜

- **게스트를 받는 순간 "인증 여부"가 인가 기준이 될 수 없다.** 필터는 요청 헤더만 보는데,
  `X-Guest-Id` 가 이 계약서의 것인지는 DB 를 봐야 안다. 필터에서 하려면 필터가 리포지토리를
  들고 있어야 하고, 그건 필터가 아니다.
- **403 대신 404 를 주면 존재 여부가 안 샌다.** 남의 `contractId` 를 넣었을 때
  403 이면 *"그 계약서는 존재한다"* 는 정보를 준다. 404 는 안 준다.
- 엔드포인트가 10개였다. 메서드 레벨 보안(`@PreAuthorize`)을 설계하는 비용보다
  **서비스 진입부에 한 줄 검사**가 빨랐다.

## 왜 다른 건 안 썼나

**`@PreAuthorize("@contractGuard.canRead(#contractId, authentication)")`**

정석이다. 검사 로직이 한 군데 모이고 컨트롤러 시그니처에서 보인다.
안 쓴 이유는 (가) 게스트가 `authentication` 에 없어서 `X-Guest-Id` 를 따로 주입해야 하고,
(나) SpEL 표현식을 팀원이 읽기 어려울 것이라 판단했다. **(나)는 지금 보면 약한 근거다.**

**`requestMatchers("/api/**").authenticated()` 로 잠그고 게스트에게도 JWT 발급**

게스트에게 익명 JWT 를 주면 필터 단에서 잠글 수 있다. 이게 더 깔끔한데,
게스트 토큰의 수명·재발급·`X-Guest-Id` 와의 관계를 새로 설계해야 했다.
**시간이 없어서 안 했다** — 게스트는 이미 프론트가 localStorage 에 id 를 들고 있었다.

**필터에서 계약 소유권까지 검사**

필터에 리포지토리를 주입하면 가능하지만, URL 패턴에서 `contractId` 를 파싱해야 하고
엔드포인트가 늘 때마다 파싱 규칙이 늘어난다.

## 결과

**"인증은 있는데 인가는 필터에 없는" 상태가 됐다.**
밖에서 보면 "Google OAuth2 + JWT" 인데, 실제 접근 통제는 시큐리티 설정이 아니라
**서비스 메서드 진입부에 흩어져 있다.**

구체적인 구멍 둘.

- **`hasAccess()` 가 두 서비스에 복제**돼 있다. 한쪽만 고치면 어긋난다.
  실제로 두 파일의 구현이 지금은 동일하지만, 그걸 보장하는 건 없다.
- **소유자도 `guestSessionId` 도 없는 계약은 누구나 볼 수 있다** (`return true`).
  초기 게스트 데이터 하위호환을 위해 **의도적으로** 남겼고 주석도 달았다.
  `contractId` 가 UUID 라 추측은 어렵지만 **URL 을 아는 사람은 열 수 있다.**
- **`POST /api/chatbot/retrieve` 는 소유권 검사 자체가 없다.** 계약서에 묶인 게 아니라
  쿼리 문자열만 받기 때문인데, 그 결과 **누구나 Bedrock KB 검색을 무제한으로 부를 수 있다.**
  스로틀링도 없다.

## 배운 점

**게스트 지원은 인증이 아니라 인가의 문제다.**
"로그인 없이 쓰게 하자"는 제품 결정 하나가 **시큐리티 필터를 무력화**시켰다.
필터가 할 수 있는 일이 없어지자 검사가 서비스로 흩어졌고, 흩어지자 복제됐다.

[gym-management-db 결정 06](../../gym-management-db/decisions/06-API-Key만-넣고-역할-분리는-보류.md)
에서 나는 *"API Key 만 넣고 역할 분리는 보류"* 라고 적었다. 여기선 한 칸 더 갔다 —
**인증 수단은 두 개고 인가는 서비스마다다.** 둘 다 "시간이 없어서 약한 쪽"인데,
여기는 그 사실이 코드 어디에도 적혀 있지 않았다는 게 차이다.
