# Decisions

RiskDetector 에서 **무엇을 왜 그렇게 정했는가**의 기록.
형식과 원칙은 [`../../gym-management-db/decisions/README.md`](../../gym-management-db/decisions/README.md) 와 같다.

```
## 상황              무엇을 정해야 했는가
## 결정              무엇을 택했는가
## 왜                근거 — 확인한 사실 기준으로
## 왜 다른 건 안 썼나   버린 선택지와 그 이유
```

## 팀 프로젝트라서 다른 점

**"내가 정한 것"과 "정해진 채로 받은 것"이 섞여 있다.** 아래 노트는 내 커밋으로
코드가 그렇게 된 것만 적는다. 스택 선택(Next.js · Spring · Supabase)처럼 팀이 정한 것은
내 결정이 아니므로 노트로 쓰지 않고, **그 전제 아래서 내가 뭘 골랐는지**를 적는다.

예: "Spring Boot 를 쓴다"는 내 결정이 아니지만, "Spring 은 즉시 응답하고 무거운 일은
Lambda 로 던진다"([결정 01](01-무거운-일을-Lambda로-밀어냈다.md))는 내 결정이다.

## 이 프로젝트에서 특히 남길 만한 것

- **01 · 02 · 03** 은 한 묶음이다. 무거운 일을 밀어내면(01) 동기·비동기를 나눠야 하고(02),
  비동기로 던지면 **결과를 누가 DB 에 쓰는가**가 새 문제로 올라온다(03).
  세 노트가 그 연쇄를 순서대로 담고 있다.
- **11 · 12** 는 LLM 을 제품에 넣을 때의 대가를 적은 것이다. 11 이 *"무엇을 말해도 되는가"* 라면
  12 는 *"검증하려면 무엇을 포기해야 하는가"* 다. 스트리밍과 출력 검증은 양립하지 않는다.
- **06 · 07 · 08** 은 전부 **의도적으로 약한 쪽을 고른** 것들이다. 시연까지 시간이 없어서
  택한 타협이고, 타협한 이유와 남은 구멍을 적어 두는 것이 목적이다.

## 저장소 문서와의 관계

이 저장소에는 ADR 이나 설계 문서가 없다. 대신 **챗봇 관련 커밋 메시지가 설계 문서 수준으로 길다**
(`문제 / 원인 / 해결 / 영향` 구조). 10~12 는 그 커밋 본문에서 복원했고,
01~09 는 커밋이 한 줄이라 **코드에서 역추적**했다. 그래서 "왜"가 약한 노트가 섞여 있고,
추정인 부분은 추정이라고 적었다.
