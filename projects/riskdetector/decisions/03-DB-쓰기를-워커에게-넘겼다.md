# 03. 분석 결과 DB 쓰기를 API 서버가 아니라 워커가

> 메모: 분석을 fire-and-forget 으로 던졌으니 결과를 받을 사람이 없다.
> Spring 을 읽기 전용으로 두고 세 번째 Lambda 가 직접 `upsert` 한다. 2026-04-29

---

## 상황

[결정 02](02-OCR은-동기-분석은-비동기로.md) 에서 분석을 `InvocationType=Event` 로 던졌다.
Spring 은 `analysisId` 만 만들어 놓고 반환한다. 그러면 30~60초 뒤 나온 분석 결과를
**누가 `contract_analyses` / `toxic_clauses` 에 쓰는가.**

선택지는 셋이었다.

1. Lambda 가 Spring 의 콜백 엔드포인트를 호출 → Spring 이 쓴다
2. Lambda 결과를 S3 에 두고 Spring 이 폴링해서 읽어 쓴다
3. **별도 Lambda 가 PostgreSQL 에 직접 쓴다**

## 결정

**3번.** `analysis_result_loader` 를 만들고 Spring 은 이 테이블을 **읽기만** 한다.

```
bedrock_lambda ── 분석 완료
      ↓ invoke (Event)  또는  Destination → SQS
analysis_result_loader
      ↓ pg8000 직접 연결
PostgreSQL (prod.contract_analyses · prod.toxic_clauses)
      ↑ 읽기만
Spring Boot  GET /api/contracts/{id}/analysis/{aid}
```

핵심은 **멱등하게 만든 것**이다.

```python
# 분석 요약은 upsert
INSERT INTO prod.contract_analyses (...) VALUES (...)
ON CONFLICT (id) DO UPDATE SET ..., updated_at = NOW()

# 독소조항은 통째로 교체
DELETE FROM prod.toxic_clauses WHERE analysis_id = %s
INSERT INTO prod.toxic_clauses (...) VALUES (...)   # N건
```

`DELETE` + `INSERT` 를 한 트랜잭션에서 하고 마지막에 `conn.commit()` 한다.
**같은 이벤트가 두 번 와도 결과가 같다.**

## 왜

- **`InvocationType=Event` 는 실패 시 AWS 가 2번 더 재시도한다.** 즉 같은 분석 결과가
  **최대 3번** 로더에 도달할 수 있다. 멱등성이 선택이 아니라 전제였다.
- **적재 경로가 실제로 두 개다.** `bedrock_lambda` 는 `ANALYSIS_RESULT_LOADER_MODE`
  기본값(`lambda`)으로 로더를 **직접 호출**하고, 동시에 Lambda Destination → SQS 배선도
  존재한다(Spring 쪽 주석이 그 경로를 설명한다). 두 경로가 다 살아 있으면 **같은 결과가
  두 번 들어온다.** 멱등이라 안 터졌다.
- **Spring 을 읽기 전용으로 두면 쓰기 실패가 API 응답에 영향을 안 준다.** 조회는 계속 된다 —
  그냥 `processStatus` 가 `IN_PROGRESS` 에 머문다.
- Spring 에 콜백 엔드포인트를 열면 **그 엔드포인트를 보호**해야 한다. 지금 `/api/**` 가
  전부 `permitAll` 인 상태([결정 06](06-인가를-서비스-계층에서.md))에서
  *"아무나 분석 결과를 덮어쓸 수 있는 경로"* 를 만드는 건 위험했다.

## 왜 다른 건 안 썼나

**Lambda → Spring 콜백 (1번)**

가장 자연스럽고, 엔티티·JPA·검증을 다 재사용할 수 있다. 안 쓴 이유가 둘이다.
(가) 위의 인증 문제. (나) **Render 백엔드가 콜드스타트로 30초 정도 잠들어 있다.**
분석이 끝난 시점에 Spring 이 깨어 있다는 보장이 없고, Lambda 쪽에서 그 재시도를 관리해야 한다.

**S3 에 결과 두고 Spring 이 폴링 (2번)**

프론트가 이미 Spring 을 폴링하고 있어서 **폴링이 두 단으로 겹친다.**
그리고 S3 를 읽어 파싱하는 코드가 Spring 에 또 필요하다.

## 결과

**Spring 쪽에 죽은 코드가 남았다.** 원래 Spring 이 분석 응답을 파싱해 저장하던 흔적이다.

```java
// AnalysisProcessService — 정의만 있고 호출부가 없는 private 메서드 5개
private String buildOverallComment(AnalysisLambdaResponse.AnalysisResult result) { ... }
private String buildWarningComment(List<AnalysisLambdaResponse.Toxic> toxics) { ... }
private String buildAdvice(List<AnalysisLambdaResponse.Toxic> toxics) { ... }
private String formatSourceIds(List<String> sourceIds) { ... }
private int toWarnLevel(String riskLevel) { ... }
```

`build_warning_comment` · `build_advice` · `map_warn_level` 이 **로더에 같은 이름으로 복제**돼 있다.
Java 쪽을 지우지 않아서 **같은 규칙이 두 언어로 두 곳에** 있다. 안 지운 건 실수다.

**그리고 스키마 정의가 두 곳이 됐다.** JPA 엔티티(`ToxicClause`)와 로더의
`CREATE TABLE IF NOT EXISTS` 가 같은 테이블을 각자 정의한다. 한쪽만 바꾸면 조용히 어긋난다.
실제로 한 번 어긋났다 → [결정 09](09-suggestion을-마커에서-전용-컬럼으로.md)

## 배운 점

**쓰기 주체를 옮기면 스키마의 소유권도 같이 옮겨진다.**
"DB 쓰기를 워커가 한다"는 결정에는 *"스키마를 워커도 정의한다"* 가 딸려 온다.
[gym-management-db 결정 04](../../gym-management-db/decisions/04-스키마-정의-3곳-유지와-자동-비교.md)
에서 나는 정의가 3곳인 것을 **받아들이고 자동 비교를 붙였다.** 여기선 2곳인데
비교 장치가 없어서 어긋난 걸 사람이 발견했다. **정의가 여러 곳인 것 자체보다,
어긋났을 때 알려 주는 장치가 없는 것이 문제다.**
