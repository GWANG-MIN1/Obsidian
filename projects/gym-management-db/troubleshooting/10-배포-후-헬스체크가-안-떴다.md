# 10. 배포는 끝났는데 헬스체크가 통과하지 않았다

- **발생**: 2026-05-13, gym-management-db
- **증상 한 줄**: CD는 이미지까지 올렸는데 `/health`가 응답하지 않았고, 컨테이너 로그가 없어 원인을 볼 수 없었다

> 이 노트도 **커밋 기록에서 되짚은 것**이다.

---

## 현상

CD 파이프라인이 헬스체크에서 멈췄다. 당시 배포 스크립트는 이랬다.

```bash
docker run -d --name gym-api ... "$IMAGE"

for i in $(seq 1 6); do
  sleep 5
  if curl -sf http://localhost:8000/health; then
    echo "Deploy succeeded"
    exit 0
  fi
done
echo "Health check failed" && exit 1
```

30초를 기다리다 `Health check failed`만 남기고 끝난다.
**왜 실패했는지는 아무 데도 안 나온다.** 컨테이너가 죽었는지, 떠 있는데 응답을 못 하는지도 모른다.

## 환경

- EC2 + Docker, GitHub Actions `appleboy/ssh-action`
- 로그 드라이버는 `awslogs`(CloudWatch)로 설정돼 있었지만, 컨테이너가 기동에 실패하면 볼 것이 거의 없다

## 진단

커밋 `06ecb8b`가 추가한 것은 딱 두 줄이다.

```diff
             done
+            echo "=== Docker logs ==="
+            docker logs gym-api --tail 50
             echo "Health check failed" && exit 1
```

**원인을 고친 게 아니라 원인을 볼 수 있게 만든 커밋이다.**

그리고 바로 다음 커밋이 `a4f560d` — Secrets Manager 조회 방식 변경이다.

```
0940161  feat: AWS Secrets Manager로 DB 비밀번호 관리
06ecb8b  ci: 헬스체크 실패 시 docker logs 출력 추가     ← 이 노트
a4f560d  fix: SECRET_ARN 대신 시크릿 이름으로 조회      ← 트러블 09
```

커밋 순서로 보면 **Secrets Manager를 붙인 직후 기동이 실패했고, 로그를 볼 수 있게 만든 뒤
원인(시크릿 조회)을 고쳤다**는 흐름이다.

코드를 보면 그 흐름이 성립한다. 당시 `database.py`는 **모듈 최상단에서** 접속 정보를 만들었다.

```python
DATABASE_URL = _get_database_url()      # import 시점에 실행
```

시크릿 조회가 실패하면 uvicorn이 뜨기도 전에 프로세스가 끝난다.
`docker run -d`는 그 전에 이미 성공을 돌려줬으므로 **스크립트는 배포됐다고 판단하고
헬스체크로 넘어간다.** 그리고 30초 동안 아무 응답도 받지 못한다.

> **확정하지 못한 것:** 로그에서 무엇을 보고 원인을 특정했는지.

## 원인

**실패했을 때 정보를 남기지 않는 배포 스크립트.**

기동 실패의 근본 원인은 [트러블 09](09-Secrets-Manager-조회-실패.md) 쪽이고,
이 노트의 원인은 **그것을 볼 수 없었다는 것**이다.

`docker run -d`는 컨테이너를 백그라운드로 띄우고 즉시 성공을 돌려준다.
그 안에서 앱이 죽어도 `docker run` 자체는 성공이라, 스크립트는 "배포됐다"고 판단하고 헬스체크로 넘어간다.

## 해결

헬스체크 실패 시 컨테이너 로그 50줄을 출력하도록 했다.

```bash
echo "=== Docker logs ==="
docker logs gym-api --tail 50
```

**9월에 추가로 한 것** — `/health`가 DB까지 확인하도록 바꿨다.

```python
@app.get("/health")
def health(db: Session = Depends(get_db)):
    try:
        db.execute(text("SELECT 1"))
    except SQLAlchemyError:
        raise HTTPException(503, "database unavailable") from None
```

예전에는 고정 응답만 돌려줬다. DB 접속이 끊긴 컨테이너도 "정상"으로 보였고,
CD가 그대로 배포 성공으로 판정했을 것이다.

## 재발 방지

- **실패 경로에 반드시 진단 정보를 남긴다.** 성공했을 때는 아무것도 필요 없지만, 실패했을 때는 로그가 전부다.
- 헬스체크는 **의존하는 것까지** 확인한다. 프로세스가 떠 있는 것과 서비스가 되는 것은 다르다.
- 라이브니스(`/health/live`)와 레디니스(`/health`)를 나눠 두면 "프로세스는 살아 있는데 DB가 안 된다"를 구분할 수 있다.

## 배운 점

**디버깅할 수 없는 실패는 실패보다 나쁘다.**
`Health check failed` 한 줄만 남기는 스크립트는, 문제가 생겼을 때 아무 도움이 안 된다.
로그 두 줄을 추가하는 게 원인 수정보다 먼저였던 게 맞는 순서였다.

**백그라운드 실행은 성공을 보장하지 않는다.** `docker run -d`가 성공했다는 건
컨테이너를 만들었다는 뜻이지, 그 안의 앱이 살아 있다는 뜻이 아니다.
