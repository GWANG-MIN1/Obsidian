# 07. 큰 숫자를 넣으면 400대가 아니라 500이 났다

- **발생**: 2026-09-06
- **증상 한 줄**: `remaining_pt_count` 등에 범위를 넘는 값을 보내면 422가 아니라 500

---

## 현상

```bash
POST /members  {"remaining_pt_count": 9999999999, ...}
→ 500 Internal Server Error
```

잘못된 입력이니 422를 기대했는데 서버 오류가 났다.

## 환경

- PostgreSQL 15 / psycopg2 2.9.10 / Pydantic 2.9.2

## 진단

### 1) 실제 예외 확인

```
sqlalchemy.exc.DataError: (psycopg2.errors.NumericValueOutOfRange) integer out of range
[SQL: INSERT INTO member (...) VALUES (...) RETURNING member.member_id, member.created_at]
[parameters: {..., 'remaining_pt_count': 9999999999}]
```

PostgreSQL의 `INTEGER`는 최대 2,147,483,647이다. 그걸 넘는 값이 그대로 내려가
SQLSTATE `22003` 오류가 났다.

### 2) 왜 오류 처리에 안 걸렸나

`errors.py`는 **`IntegrityError`만** 잡는다.

```python
except IntegrityError as exc:
    db.rollback()
    raise integrity_error_to_http(exc) from exc
```

범위 초과는 `IntegrityError`가 아니라 **`DataError`**다. 상위 타입만 같고 계통이 다르다.
그래서 잡히지 않고 그대로 올라가 500이 됐다.

### 3) 어디까지 그런지 전부 확인

```
POST /members  remaining_pt_count=BIG   → 500
POST /trainers career_year=BIG          → 500
POST /workouts sets=BIG                 → 500
POST /workouts reps=BIG                 → 500
POST /payments member_id=BIG            → 500   ← 처음엔 놓쳤던 경로
GET  /members?offset=10^19              → 500   ← bigint 범위 초과
GET  /members?offset=10^10              → 200   (bigint 안이라 통과)
POST /sessions member_id=BIG            → 404   (INSERT 전에 조회해서 없다고 끝남)
```

`/sessions`는 INSERT 전에 회원을 조회해 404로 끝나는데,
`/workouts`와 `/payments`는 **FK 위반으로 처리하려고 INSERT까지 내려가서** 범위 초과가 났다.
같은 원인인데 경로에 따라 결과가 달랐다.

## 원인

**입력 스키마에 상한이 없었다.** `ge=0`, `gt=0`으로 하한만 있고 위쪽이 열려 있었다.

## 해결

Pydantic 단계에서 막는다. 상한을 두 종류로 구분했다.

```python
MAX_INT4 = 2_147_483_647  # PostgreSQL INTEGER 상한 (ID 컬럼의 물리적 한계)
MAX_PT_COUNT = 1_000      # 아래 셋은 업무상 상한
MAX_CAREER_YEAR = 70
MAX_SETS = 100
MAX_REPS = 1_000
```

| 대상 | 상한 |
|---|---|
| `remaining_pt_count` | 1,000 |
| `career_year` | 70 |
| `sets` / `reps` | 100 / 1,000 |
| `member_id`, `trainer_id`, `exercise_id` (요청 본문) | `MAX_INT4` |
| `offset` | 100,000 |

`offset`은 범위 안이어도 크면 그만큼 행을 건너뛰느라 느려지므로 함께 제한했다.

커밋 `328b516`. 테스트 11개로 고정했고, **경계값이 통과하는 것**까지 확인한다.

## 재발 방지

- 숫자 필드는 **하한과 상한을 같이 적는다.** 하한만 적으면 반쪽이다.
- 업무 상한과 물리 상한을 상수로 구분해 뒀다. `MAX_SETS = 100`은 협의할 수 있는 값이고, `MAX_INT4`는 DB가 정한 값이다.
- `MAX_INT4`를 그대로 보내면 404가 나오는지도 테스트에 넣었다. 상한 자체는 유효한 값이어야 한다.

## 배운 점

**입력 검증의 상한을 빼먹기 쉽다.** "음수만 막으면 되지"로 끝내면 위쪽이 열린다.

**예외를 타입으로 잡을 때는 계통을 확인해야 한다.** `IntegrityError`만 잡고 "DB 오류는 다 처리했다"고
생각했는데, `DataError`는 그 밖이었다. 잡는 범위를 넓히는 것보다 **애초에 DB까지 내려가지 않게 막는 쪽**이 낫다.
DB에 도달하기 전에 거르면 오류 문구도 우리가 정할 수 있다.
