# 01. 테스트를 돌렸더니 개발 DB 테이블이 사라졌다

- **발생**: 2026-09-06, gym-management-db
- **증상 한 줄**: 테스트는 통과했는데 `gymdb`의 애플리케이션 테이블이 0개가 됐다

---

## 현상

코드 리뷰에서 지적받아 알았다. 리뷰어가 README에 적힌 명령을 그대로 실행해 본 결과다.

```bash
docker compose up -d db
cd api && DATABASE_URL=postgresql://gymadmin:gymadmin123@localhost:5433/gymdb pytest -q
```

> 별도 임시 DB에 샘플 회원 10명을 넣고 헬스체크 테스트만 실행했는데,
> 테스트는 통과하면서 종료 후 애플리케이션 테이블이 0개가 됐습니다.

**테스트는 초록불인데 DB가 비어 있다.** README가 안내하는 대로 실행하면
개발용 `gymdb`에 같은 일이 일어나는 상태였다. 다행히 실제로 잃은 데이터는 없었다.

## 환경

- PostgreSQL 15 (docker compose, 호스트 5433)
- pytest 8.3.3 / SQLAlchemy 2.0.36

## 진단

### 1) 테스트 준비 코드부터 확인

`conftest.py`의 세션 픽스처가 범인이었다.

```python
@pytest.fixture(scope="session")
def _database():
    Base.metadata.drop_all(bind=engine)    # ← 시작할 때 지우고
    Base.metadata.create_all(bind=engine)
    yield
    Base.metadata.drop_all(bind=engine)    # ← 끝날 때 또 지운다
```

테스트마다 스키마를 초기화하려는 의도였다. 그 자체는 잘못이 아니다.

### 2) 그 `engine`이 무엇을 가리키는가

```python
_DB_URL = os.environ.get("TEST_DATABASE_URL") or os.environ.get("DATABASE_URL")
```

`TEST_DATABASE_URL`이 없으면 **`DATABASE_URL`로 폴백**한다.
그리고 README가 안내한 명령이 `DATABASE_URL`에 **개발 DB**를 넣고 있었다.

두 개가 만나 "개발 DB의 테이블을 전부 지우는 명령"이 된 것이다.

## 원인

`drop_all()`을 부르는 코드가 **어느 DB에 붙었는지 확인하지 않았다.**

- 폴백(`or DATABASE_URL`)이 편의를 위해 있었지만, 그 편의가 곧 사고 경로였다
- README가 그 경로를 정문으로 안내하고 있었다

## 해결

접속 정보를 **`TEST_DATABASE_URL`로만** 받고, DB 이름이 `_test`로 끝나지 않으면 실행을 거부한다.

```python
_DB_URL = os.environ.get("TEST_DATABASE_URL")     # DATABASE_URL 폴백 제거
if not _DB_URL:
    raise RuntimeError("테스트는 전용 DB 에서만 실행합니다. TEST_DATABASE_URL 을 설정하세요.\n" + _USAGE)

_DB_NAME = urlsplit(_DB_URL).path.lstrip("/")
if not _DB_NAME.endswith("_test"):
    raise RuntimeError(f"... 지정된 DB: '{_DB_NAME}'\n" + _USAGE)
```

확인:

```
$ TEST_DATABASE_URL=postgresql://x@localhost/gymdb pytest -q
RuntimeError: 테스트는 테이블을 삭제·재생성하므로 '_test' 로 끝나는 전용 DB 에서만 실행합니다. 지정된 DB: 'gymdb'

$ pytest -q          # 환경변수 없이
RuntimeError: 테스트는 전용 DB 에서만 실행합니다. TEST_DATABASE_URL 을 설정하세요.
```

README와 CI(`gymdb_test`)도 함께 고쳤다. 커밋 `50d80da`.

## 재발 방지

- **검사를 임포트 시점에 둔다.** 픽스처 안이 아니라 `conftest.py` 최상단에서 막는다. DB에 연결하기 전에 멈추므로, 실수해도 데이터에 손이 닿지 않는다.
- **폴백을 만들지 않는다.** 파괴적인 작업에서 "없으면 이걸 쓴다"는 편의는 사고 경로가 된다.
- DB 이름 규칙(`_test` 접미사)을 정하고 그것을 코드가 강제한다.

## 배운 점

**파괴적인 코드는 대상을 스스로 확인해야 한다.**
`drop_all()`은 시키는 대로 지울 뿐이고, 어디에 붙었는지는 환경변수가 정한다.
"올바르게 실행하면 안전하다"는 안전장치가 아니다.

문서가 사고를 안내할 수도 있다. README의 명령 한 줄이 개발 DB를 가리키고 있었다.
그대로 복사해 실행하는 것이 정상적인 사용법이었으니, 사고는 시간 문제였다.
