# 08. 린트를 통과 못 해 우회했더니, 4개월 뒤 검증이 통째로 죽어 있었다

- **발생**: 2026-05-12 (원인 제공) / 2026-09-05 (발견)
- **증상 한 줄**: sqlfluff 위반을 고치다 막혀 `|| true`를 붙였고, 이후 어떤 위반이 있어도 CI가 초록색이었다

---

## 현상

커밋 로그에 그날의 흐름이 그대로 남아 있다.

```
2026-05-11  df6b20c  feat: Docker 컨테이너화 및 GitHub Actions SQL 린트 추가
2026-05-11  7d347c4  fix: CP02 규칙 제외 및 sqlfluff auto-fix 추가
2026-05-11  f53fb0a  fix: sqlfluff 위반 수정 - 정렬 공백 제거 및 트리거 noqa 추가
2026-05-11  6f5e3ab  fix: AM05 규칙 제외 및 쿼리 파일 포맷 수정
2026-05-11  6787d94  fix: 들여쓰기 및 괄호 앞 공백 수정
2026-05-12  2715eca  fix: sqlfluff lint 실패 시 CI 종료 방지 (|| true)     ← 우회
...
2026-09-05  adf4b1d  ci: 린트·스키마 검증이 실제로 실패하도록 수정          ← 4개월 뒤
```

린트를 붙이고 **네 번 고치다가**, 다섯 번째에 우회했다.

`2715eca`가 바꾼 내용:

```diff
-        run: sqlfluff lint *.sql --dialect oracle
+        run: sqlfluff lint *.sql --dialect oracle || true
+
+      - name: Fix SQL formatting
+        run: sqlfluff fix *.sql --dialect oracle --force || true
```

## 환경

- GitHub Actions / sqlfluff (버전 미고정 — 매 실행마다 최신)

## 진단

> 당시 무엇이 막혔는지, 왜 우회를 택했는지는 기록이 없다. 커밋 메시지만 남아 있다.
> **여기는 기억을 되살려 채울 것:**
>
> - 어떤 규칙에서 막혔나 (LT01 정렬? RF04 예약어 컬럼명?)
> - 왜 그때 고치지 못했나 (시간? 규칙을 이해 못 함? 고칠수록 다른 게 깨짐?)
> - `|| true`를 넣을 때 임시 조치라고 생각했나

4개월 뒤 확인한 사실은 이렇다.

**우회한 뒤에도 위반은 그대로 있었다.**

```
   8 file=01_create_tables.sql LT01     (정렬 공백)
   5 file=01_create_tables.sql RF04     (name, sets, method — 예약어 컬럼명)
   4 file=03_project_queries.sql LT02   (들여쓰기)
   2 file=03_project_queries.sql RF02   (서브쿼리 참조 한정)
```

**`sqlfluff fix` 단계는 아무것도 하지 않았다.** CI에서 파일을 고쳐도 커밋되지 않아 러너와 함께 사라진다.

**그리고 이 우회가 다른 검증까지 덮었다.** 배지가 초록이니 스키마 테스트에
`ON_ERROR_STOP`이 없다는 것도(→ [트러블 05](05-CI가-위반이-있어도-항상-성공.md)) 함께 묻혔다.

## 원인

**규칙을 만족시키지 못하자 규칙이 실패하지 못하게 만들었다.**

`|| true`는 "지금은 넘어가자"의 표현이었는데, 그 상태를 알려 줄 것이 아무것도 없었다.
빨간불이 없으니 되돌아볼 계기도 없었다.

## 해결

2026-09-05, `adf4b1d`에서 되돌렸다.

- `|| true` 제거, 의미 없던 `fix` 단계 삭제, **버전 고정**(`sqlfluff==4.3.0`)
- 실제 위반 수정 — 자동 수정 가능한 것은 `sqlfluff fix`, RF02는 서브쿼리에 별칭을 붙여 직접
- **고칠 수 없는 것은 우회 대신 명시적으로 제외**

  ```ini
  # 검사 제외 규칙
  #   RF05/LT05/CP02/AM05: 기존 설정 유지
  #   RF04: name / sets / reps / method 처럼 업무상 자연스러운 컬럼명을 그대로 사용
  exclude_rules = RF05, LT05, CP02, AM05, RF04
  ```

`|| true`와 `exclude_rules`의 차이는 크다.
앞은 **모든 규칙을 무력화**하고 아무 기록도 남기지 않는다.
뒤는 **어떤 규칙을 왜 껐는지**가 파일에 남고, 나머지는 계속 검사한다.

## 재발 방지

- 검증 단계에 `|| true` / `continue-on-error`를 쓰지 않는다.
- 규칙을 못 지키겠으면 **그 규칙만, 이유를 적어서** 끈다.
- 도구 버전을 고정한다. 고정하지 않으면 새 규칙이 추가되는 날 갑자기 깨지고, 그게 다시 우회할 이유가 된다.
- 임시 조치에는 만료가 필요하다. 최소한 이슈나 TODO로 남겨 되돌아볼 계기를 만든다.

## 배운 점

**우회는 문제를 미루는 게 아니라 문제를 안 보이게 만든다.**
미룬 것은 언젠가 떠오르지만, 안 보이게 만든 것은 떠오르지 않는다. 4개월 동안 아무 일도 없었던 이유다.

지적받아 고친 다른 노트들과 달리, 이건 **내 판단의 결과를 내가 되짚은 기록**이다.
그때 4번 고치다 지쳤다는 것도 사실이고, 5번째에 무엇을 택했는지가 남았다.

**"나중에 고치자"고 넣은 것은 알림을 남겨야 한다.** 스스로 없어지는 임시 조치는 없다.
