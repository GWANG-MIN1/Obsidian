# 02. 기존 DB에 새 버전을 배포하니 등록이 전부 422

- **발생**: 2026-09-06, gym-management-db
- **증상 한 줄**: `/health`는 200인데 회원·트레이너·예약 등록이 모두 422로 실패한다

---

## 현상

예전 스키마로 만들어진 DB에 새 버전을 올렸더니 이런 상태가 됐다.

| 요청 | 결과 |
|---|---|
| `GET /health` | 200 정상 |
| `POST /members` | **422** |
| `POST /trainers` | **422** |
| `POST /sessions` | **422** |

읽기는 되는데 쓰기만 전부 막혔다. 그리고 422는 보통 **입력값이 잘못됐을 때** 나오는 코드라
처음에는 요청 본문을 의심하게 된다.

## 환경

- 예전 스키마: 2026-05 버전(`1b688ce`)의 `api/models.py`가 `create_all()`로 만든 3개 테이블
- 새 코드: 2026-09 버전
- PostgreSQL 15 / SQLAlchemy 2.0.36

## 진단

### 1) 예전 스키마를 실제로 다시 만들어 본다

옛 `models.py`를 꺼내 빈 DB에 `create_all()`을 돌리고 컬럼을 확인했다.

```
 table_name |  column_name  | is_nullable |  col_default
------------+---------------+-------------+---------------
 member     | created_at    | NO          | (없음)
 trainer    | created_at    | NO          | (없음)
 pt_session | created_at    | NO          | (없음)
```

`created_at`이 **NOT NULL인데 기본값이 없다.**

### 2) 왜 NOT NULL이 됐나

옛 모델의 선언은 이랬다.

```python
created_at: Mapped[date] = mapped_column(Date)
```

SQLAlchemy 2.0은 **`Mapped[T]`의 타입에서 널 허용 여부를 추론한다.**
`Mapped[date]`는 NOT NULL, `Mapped[date | None]`이라야 NULL 허용이다.
당시에는 `date.today()`를 코드에서 직접 넣고 있었으니 문제가 없었다.

### 3) 새 코드는 그 값을 보내지 않는다

새 모델은 DB 기본값에 맡긴다.

```python
created_at: Mapped[date | None] = mapped_column(Date, server_default=func.current_date())
```

새 테이블에는 `DEFAULT CURRENT_DATE`가 붙지만, **예전 테이블에는 그 기본값이 없다.**
그래서 `INSERT`에 `created_at`이 빠지고 → NOT NULL 위반.

### 4) 왜 500이 아니라 422였나

NOT NULL 위반은 SQLSTATE `23502`이고 `IntegrityError`로 올라온다.
`errors.py`가 그것을 **입력값 문제(422)** 로 매핑하고 있었다.

```python
if pgcode in (_CHECK_VIOLATION, _NOT_NULL_VIOLATION):
    return HTTPException(422, ...)
```

오류 처리가 오히려 원인을 가렸다. 500이었다면 스택 트레이스를 봤을 텐데,
422는 "요청이 잘못됐나 보다"로 넘어가기 쉽다.

### 5) `create_all()`이 왜 못 고치나

`create_all()`은 **없는 테이블만 만든다.** 기존 테이블의 컬럼 기본값·제약·인덱스는 손대지 않는다.
그래서 새 3개 테이블(운동·운동기록·결제)만 생기고, 예전 3개는 그대로 남았다.

## 원인

**기존 테이블의 스키마를 바꾸는 수단이 없었다.**

- 예전 테이블: `created_at NOT NULL`, 기본값 없음
- 새 코드: `created_at`을 보내지 않음 (DB 기본값에 의존)
- `create_all()`: 기존 테이블을 바꾸지 못함

같은 원인의 문제가 하나 더 있었다. 예전의 `uq_trainer_slot`은 일반 UNIQUE 제약이라
**취소한 예약의 시간대를 다시 쓸 수 없었다**(→ [결정 02](../decisions/02-중복-예약을-부분-유니크-인덱스로.md)).

## 해결

Alembic 마이그레이션을 도입하고, 앱 시작 시 `create_all()` 대신 마이그레이션을 실행한다
(→ [결정 03](../decisions/03-Alembic-도입과-기존-DB-편입.md)).

`0002`가 하는 일:

```sql
ALTER TABLE member ALTER COLUMN created_at SET DEFAULT CURRENT_DATE;
ALTER TABLE member ALTER COLUMN created_at DROP NOT NULL;
ALTER TABLE pt_session DROP CONSTRAINT IF EXISTS uq_trainer_slot;
CREATE UNIQUE INDEX uq_trainer_slot ON pt_session (...) WHERE status <> 'CANCELLED';
-- 테이블 3개 추가, 시각 형식 CHECK, 인덱스, SERIAL → IDENTITY
```

검증 (`test_migration_from_legacy.py`):

```
컬럼: 일치 (40건)
제약: 일치 (24건)
인덱스: 일치 (15건)
기존 행 유지: 1
```

커밋 `945a3d6`, `4c254ef`.

## 재발 방지

- **업그레이드 경로를 테스트로 고정했다.** 예전 스키마 DB를 만들고 마이그레이션을 돌려
  ORM 정의와 일치하는지, 기존 행이 남는지, 등록이 되는지까지 확인한다.
- 그 테스트에 **마이그레이션 전에는 422가 나는 것**도 넣었다. 문제 자체가 회귀 테스트가 된다.
- 빈 DB도 `0001 → 0002`를 지나게 해서, 업그레이드 코드가 항상 실행되게 했다.

## 배운 점

**빈 DB에서만 테스트하면 "기존 DB 위에 배포하는" 경로는 한 번도 검증되지 않는다.**
그때까지의 테스트 38개는 전부 빈 DB에서 시작했고, 그래서 이 문제를 잡지 못했다.

`Mapped[date]`와 `Mapped[date | None]`은 파이썬 타입 힌트처럼 보이지만 **DDL을 바꾼다.**
→ [SQLAlchemy Mapped 널 추론](../../../infra-lab/db-lab/SQLAlchemy-Mapped-널-추론.md)

그리고 **오류 매핑이 원인을 가릴 수 있다.** 422는 "네 요청이 잘못됐다"는 뜻인데
실제로는 서버 스키마가 낡아서 난 오류였다.
