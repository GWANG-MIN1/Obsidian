# 03. GET /members p95가 2초 — 원인을 인덱스로 잘못 짚었다

- **발생**: 2026-05-13 (측정) / 2026-09-05 (원인 정정)
- **증상 한 줄**: 부하 테스트에서 에러는 0%인데 목록 조회 p95가 2,046ms

---

## 현상

k6로 VU 10 → 30 → 50까지 올리며 3분 30초 측정한 결과.

| 지표 | 결과 | 목표 |
|---|---:|---|
| 총 요청 수 | 6,354건 | — |
| 처리량 | 30.2 req/s | — |
| 에러율 | 0% | < 1% ✅ |
| 전체 p(95) | 1.66s | < 500ms ❌ |
| `POST /members` p(95) | 365ms | < 500ms ✅ |
| `GET /members` p(95) | **2,046ms** | < 300ms ❌ |

**쓰기는 빠른데 읽기만 느렸다.** 그리고 에러가 0%라 "통과"로 보이지만,
k6는 threshold를 못 넘기면 실패로 처리한다. 실제로는 응답시간 목표 두 개를 놓쳤다.

## 환경

- EC2 t3.micro + RDS db.t3.micro (ap-northeast-2)
- k6 스크립트: 회원 목록 조회 → 트레이너 목록 조회 → **회원 등록**을 반복

## 진단

### 1) 첫 가설 — 인덱스가 없어서 전체 스캔 → **반증**

README에 이렇게 적었다.

> 부하 테스트 중 회원이 계속 등록되면서 데이터가 누적되고, 인덱스 없이 전체 스캔이 발생했습니다.

그럴듯했지만 틀렸다. 두 가지가 맞지 않는다.

- **PostgreSQL은 PK와 UNIQUE 제약에 인덱스를 자동으로 만든다.** `member_pkey`, `member_phone_key`가 이미 있었다. "인덱스가 아예 없는" 상태가 아니었다.
- 애초에 이 쿼리는 **조건이 없다.** `WHERE`가 없는 전체 목록 조회라서 인덱스가 도와줄 여지가 없다.

### 2) 실제 쿼리를 본다

```python
@router.get("", response_model=list[MemberResponse])
def list_members(db: Session = Depends(get_db)):
    return db.query(Member).all()      # 전부 반환
```

`LIMIT`이 없다. 테이블의 모든 행을 가져온다.

### 3) 부하 테스트가 데이터를 계속 늘리고 있었다

시나리오가 매 반복마다 회원을 등록한다. 6,354건 중 3분의 1이 `POST /members`였으니
**테스트가 진행될수록 목록이 길어졌다.** 뒤로 갈수록 느려지는 게 당연했다.

한 번의 조회에서 늘어나는 것은 DB 조회만이 아니다.

```
행 수 증가 → SELECT 결과 증가
           → ORM 객체 생성 증가
           → Pydantic 직렬화 증가
           → JSON 응답 전송량 증가
```

## 원인

**페이지네이션 없이 전체 행을 반환했다.**

인덱스 문제가 아니었다. 반환하는 양 자체를 제한하지 않은 것이 원인이다.

## 해결

모든 목록 API에 `limit`(기본 50 · 최대 200) / `offset`을 넣었다.

```python
DEFAULT_LIMIT = 50
MAX_LIMIT = 200

def pagination(
    limit: int = Query(DEFAULT_LIMIT, ge=1, le=MAX_LIMIT),
    offset: int = Query(0, ge=0, le=MAX_OFFSET),
) -> Pagination: ...
```

함께 한 것

- FK·조회 조건 컬럼 인덱스 추가 (`idx_member_expiry`, `idx_pt_session_date` 등) — 목록 조회와는 별개로 필요한 것
- 읽기 커넥션 분리 (→ [결정 05](../decisions/05-읽기-커넥션-분리.md))
- 커넥션 풀 명시 (→ [결정 07](../decisions/07-커넥션-풀-크기를-15로.md))
- k6 스크립트가 `?limit=50`을 쓰도록 수정

커밋 `a4409ac`, `e1a81d0`.

## 재발 방지

- 목록 엔드포인트는 **공통 의존성**(`pagination.py`)으로만 만든다. 새 목록 API를 추가할 때 `limit`을 빼먹기 어렵게.
- 상한(`MAX_LIMIT = 200`)을 두어 `?limit=999999`로 우회할 수 없게 했다.
- 테스트로 고정: `?limit=9999` → 422.

## 아직 안 한 것

**개선 후 재측정을 하지 않았다.** 위 수치는 전부 개선 전 값이다.
README에도 "개선 전 기록"이라고 표시해 뒀다. 같은 조건으로 다시 돌려야 개선 효과를 말할 수 있다.

## 배운 점

**그럴듯한 원인을 검증 없이 적으면 그게 기록으로 남는다.**
"인덱스가 없어서"는 성능 문제의 단골 설명이라 의심 없이 넘어갔고, README에 4개월간 그대로 있었다.

느린 원인을 찾을 때 **쿼리만 보지 말고 반환량 전체를 봐야 한다.**
DB에서 빨리 가져와도 직렬화와 전송이 남는다.

**에러 0%가 통과는 아니다.** threshold를 보지 않으면 부하 테스트는 "돌았다"로 끝난다.
