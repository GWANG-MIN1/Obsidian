# 09. 오류 매핑을 제약 '이름' 기준으로

> 메모: 제약 이름으로 메시지를 고르기 때문에 SQL·ORM·마이그레이션 세 곳의 제약 이름이 같아야 함 → 04번 결정으로 이어짐

---

## 상황

전화번호 중복이나 트레이너 시간대 중복은 DB 제약이 막고 있었다.
그런데 **그 예외를 아무도 잡지 않아서** psycopg2 오류가 그대로 올라가 500이 됐다.

사용자 입장에서는 "이미 등록된 번호입니다"가 아니라 그냥 서버 오류였다.

## 결정

`IntegrityError`를 잡아 **SQLSTATE와 제약 이름**으로 상태 코드와 메시지를 고른다.

| SQLSTATE | 의미 | 응답 |
|---|---|---|
| 23505 | UNIQUE 위반 | 409 |
| 23503 | FK 위반 | 404 |
| 23514 / 23502 | CHECK / NOT NULL 위반 | 422 |

```python
_CONSTRAINT_MESSAGES = {
    "member_phone_key": "이미 등록된 전화번호입니다.",
    "uq_trainer_slot": "해당 트레이너는 같은 날짜·시간에 이미 예약이 있습니다.",
    "uq_member_slot": "이 회원은 같은 날짜·시간에 이미 다른 예약이 있습니다.",
    ...
}
```

커밋과 함께 `safe_commit(db)` 헬퍼를 만들어, 라우터는 `db.commit()` 대신 이걸 부른다.

## 왜

- **어떤 규칙을 어겼는지는 DB가 가장 정확히 안다.** 제약 이름이 곧 규칙 이름이다.
- **동시성에서 새지 않는다.** 미리 조회해서 "이 번호 있나?" 검사하면, 검사와 INSERT 사이에 다른 요청이 같은 번호를 넣을 수 있다. 제약 위반을 받아서 변환하는 쪽은 그 틈이 없다.
- 검사 코드와 제약이 따로 놀지 않는다. 제약을 추가하면 매핑 표에 한 줄 더할 뿐이다.

## 파급 — 04번 결정으로 이어진다

제약 **이름**으로 메시지를 고르므로, 이름이 환경마다 다르면 같은 위반에 다른 응답이 나간다.

실제로 어긋나 있었다. SQL 파일은 컬럼에 인라인으로 CHECK를 썼는데,
PostgreSQL이 자동으로 `member_gender_check` 같은 이름을 붙인다. ORM은 `ck_member_gender`였다.

```
SQL 에만 : ('member', 'member_gender_check', "CHECK (...)")
ORM 에만 : ('member', 'ck_member_gender',   "CHECK (...)")
```

정의는 같은데 이름만 달랐다. SQL 파일 쪽에 이름을 명시해 맞췄고,
이후로는 [결정 04](04-스키마-정의-3곳-유지와-자동-비교.md)의 비교 테스트가 이름까지 지킨다.

## 왜 다른 건 안 썼나

**사전 조회 후 검사**

동시 요청에서 샌다. 그리고 조회가 한 번 더 늘어난다.

**전역 예외 핸들러로 500 → 400 일괄 변환**

상태 코드는 나아지지만 "무엇이 잘못됐는지"를 못 알려준다. 409와 422와 404는 사용자가 해야 할 행동이 다르다.

**DB 오류 원문을 그대로 내려주기**

테이블·컬럼 이름과 SQL 구조가 노출된다.
