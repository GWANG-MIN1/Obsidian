# 04. 스키마 정의를 3곳에 두고 테스트로 비교

> 메모: SQL 파일 / ORM 모델 / 마이그레이션. 하나로 합치지 않고 CI에서 컬럼·제약·인덱스를 비교하는 쪽을 택함

---

## 상황

정의가 어긋나 있었다.

| 정의 | 테이블 수 |
|---|---|
| `sql/01_create_tables_pg.sql` | 6 |
| `api/models.py` | 3 |

로컬 docker compose는 SQL 파일로 6개를 만들고, 배포는 `create_all()`로 3개만 만들었다.
**같은 코드가 환경에 따라 다른 스키마 위에서 돌고 있었다.**

## 결정

세 정의를 **모두 유지**하고, 어긋나면 테스트가 잡도록 한다.

| 정의 | 역할 |
|---|---|
| `sql/01_create_tables_pg.sql` | 읽고 이해하는 문서 겸 로컬 초기화 |
| `api/models.py` | 앱이 쓰는 타입, 테스트 |
| `api/migrations/` | 기존 DB를 바꾸는 유일한 경로 |

| 테스트 | 비교 대상 |
|---|---|
| `test_schema_parity.py` | SQL 파일 ↔ ORM |
| `test_migration_from_legacy.py` | 마이그레이션 결과 ↔ ORM |

비교 방법은 임시 스키마(`sql_ref`)에 SQL 파일을 적용한 뒤 `information_schema`와 `pg_constraint`,
`pg_indexes`를 뽑아 집합으로 맞춰 보는 것이다.

```
컬럼: 일치 (40건)
제약: 일치 (24건)
인덱스: 일치 (15건)
```

## 왜

- **역할이 다르다.** SQL 파일은 "이 프로젝트가 무슨 데이터를 다루는가"를 보여주는 출발점이고, ORM은 앱의 타입이고, 마이그레이션은 이미 있는 DB를 바꾸는 수단이다. 하나로 합치면 나머지 역할이 아쉬워진다.
- **어긋남은 사람이 아니라 테스트가 잡는다.** 실제로 눈으로 맞추는 데 실패해서 6 대 3이 됐다.
- **제약 이름까지 비교한다.** [결정 09](09-오류-매핑을-제약-이름-기준으로.md)가 제약 이름으로 오류 메시지를 고르기 때문에, 이름이 환경마다 다르면 같은 위반에 다른 응답이 나간다.
- **드리프트를 실제로 잡는지 역검증했다.** 모델의 `String(50)`을 `String(60)`으로 바꿔 보고 테스트가 실패하는 것을 확인했다.

  ```
  E  AssertionError: 컬럼 불일치
  ```

## 왜 다른 건 안 썼나

**ORM 하나로 통일 (SQL 파일 삭제)**

DB 설계를 SQL로 보여주는 게 이 프로젝트의 출발점이다. 지우면 "무엇을 저장하는가"를 파이썬 클래스로 읽어야 한다.

**SQL 파일 하나로 통일 (ORM 삭제)**

FastAPI에서 매번 raw SQL을 쓰게 된다. 얻는 것보다 잃는 게 크다.

**눈으로 맞추기**

이미 실패했다. 6개와 3개로 벌어진 걸 4개월 동안 아무도 몰랐다.
