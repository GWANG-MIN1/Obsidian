# 07. 커넥션 풀 크기를 15로 제한

> 메모: CloudWatch DatabaseConnections 알람 임계값이 20이라 pool_size 5 + overflow 10으로 맞춤

---

## 상황

SQLAlchemy 엔진을 기본 설정으로 만들고 있었다. 풀 크기를 명시하지 않으면 기본값(`pool_size=5`, `max_overflow=10`)이 적용되는데, **그 값이 얼마인지 코드만 봐서는 알 수 없었다.**

한편 CloudWatch에는 이미 커넥션 알람이 있었다.

```hcl
# terraform/cloudwatch.tf
metric_name        = "DatabaseConnections"
threshold          = 20
period             = 300
evaluation_periods = 2
```

## 결정

풀 설정을 **명시**하고, 컨테이너 1대의 최대 커넥션이 알람 임계값 아래에 오도록 맞춘다.

```python
_ENGINE_OPTIONS = {
    "pool_size": 5,
    "max_overflow": 10,      # 최대 15 < 알람 임계값 20
    "pool_pre_ping": True,   # RDS 유휴 커넥션 끊김 대비
    "pool_recycle": 1800,
}
```

## 왜

- **알람이 실제 이상에만 울리게 하려고.** 앱이 정상 동작하는 것만으로 알람이 울리면, 그 알람은 곧 무시된다.
- `pool_pre_ping` — RDS가 유휴 커넥션을 끊어도 다음 요청에서 재연결한다. 없으면 한동안 요청이 없다가 들어온 첫 요청이 죽는다.
- `pool_recycle=1800` — 30분마다 커넥션을 새로 만든다.
- **기본값이더라도 적어 두면 근거가 남는다.** 숫자 자체보다 "왜 15인가"에 답할 수 있는 게 중요하다.

## 왜 다른 건 안 썼나

**풀을 더 크게 잡기**

`db.t3.micro`의 `max_connections`도 여유가 크지 않고, 무엇보다 알람 임계값을 넘긴다.
알람을 올리는 것도 방법이지만, 그러면 "몇이 정상인지" 기준이 사라진다.

**부하가 부족하면 풀부터 늘리기**

처리량이 안 나올 때 풀을 키우는 건 대개 늦은 대응이다.
이 프로젝트에서도 실제 원인은 풀이 아니라 **페이지네이션 없이 전체를 반환한 것**이었다
(→ [트러블 03](../troubleshooting/03-GET-members-p95-2초.md)).
쿼리와 반환량을 먼저 보고, 그 다음이 풀이다.

## 확인하지 못한 것

컨테이너를 여러 대로 늘리면 최대 커넥션은 15 × 대수가 된다.
지금은 EC2 1대에 컨테이너 1개라 문제가 없지만, 늘릴 때 이 숫자를 같이 봐야 한다.
