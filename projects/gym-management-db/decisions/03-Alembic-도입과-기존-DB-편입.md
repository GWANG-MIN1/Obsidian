# 03. Alembic 도입과 기존 DB 편입(stamp) 방식

> 메모: 0001을 '예전 스키마'로 두고 이력 없는 기존 DB를 stamp로 편입. 0002는 여러 번 실행해도 안전하게 작성

---

## 상황

앱이 시작할 때 `Base.metadata.create_all()`을 호출하고 있었다.
`create_all()`은 **없는 테이블만 만들고 기존 테이블은 손대지 않는다.**

그래서 예전 스키마가 있는 DB에 새 버전을 배포하면 등록이 전부 실패했다
(→ [트러블 02](../troubleshooting/02-기존-스키마에-배포하면-등록이-422.md)).

게다가 운영 DB는 **예전 3개 테이블 + `create_all`이 만든 새 3개 테이블**이 섞인 상태일 수 있었다.

## 결정

Alembic을 도입하고, 리비전을 두 개로 나눈다.

| 리비전 | 내용 |
|---|---|
| `0001` | **예전 스키마** (회원·트레이너·PT 3개 테이블) |
| `0002` | 테이블 3개 추가, 기본값 부여, 제약·인덱스 정리, SERIAL → IDENTITY |

이력이 없고 테이블만 있는 DB는 `0001`로 **stamp**한 뒤 `0002`만 적용한다.

```python
if "alembic_version" not in tables and "member" in tables:
    command.stamp(config, "0001")   # 예전 스키마 기준으로 이력을 맞춘다
command.upgrade(config, "head")
```

```
빈 DB            → 0001 → 0002
기존 DB(이력 없음) → 0001 로 stamp → 0002 만 적용
이미 최신 DB      → 아무것도 하지 않음
```

## 왜

- **빈 DB도 같은 경로를 지난다.** 0001 → 0002를 거치므로 업그레이드 경로가 테스트·CI에서 매번 실행된다. "배포할 때만 도는 코드"가 되지 않는다.
- **`0002`를 멱등하게 썼다.** `DROP CONSTRAINT IF EXISTS` → `ADD`, `CREATE INDEX IF NOT EXISTS`, IDENTITY는 `is_identity`를 먼저 확인. 섞인 상태의 운영 DB에서도 그대로 적용된다.
- **위반 데이터를 먼저 검사한다.** 새 제약을 붙이기 전에 `99:99` 같은 시각이나 중복 예약이 있는지 보고, 있으면 **어떤 행이 문제인지 알려주고 중단**한다. 그냥 ALTER를 실행하면 PostgreSQL 오류만 올라와 어느 행인지 알 수 없다.

## 왜 다른 건 안 썼나

**`create_all()` 유지**

이 문제의 원인 자체다. 컬럼 기본값도, 제약 변경도 반영하지 못한다.

**수동 ALTER 스크립트**

어디까지 적용했는지 추적할 방법이 없다. 두 번 실행하면 어떻게 되는지도 매번 생각해야 한다.

**`0001`을 '현재 스키마'로 두기**

이게 더 자연스러워 보이지만 두 가지가 깨진다.
기존 DB에 stamp하면 **이미 최신인 셈 쳐서** 실제 변경이 영영 적용되지 않는다.
그리고 빈 DB에서 업그레이드 경로가 한 번도 실행되지 않아, 그 코드가 맞는지 알 수 없다.

**downgrade 제공**

`0002`는 테이블 추가와 SERIAL → IDENTITY 전환을 포함한다. 자동 복구가 안전하지 않아
`NotImplementedError`로 막고, 되돌려야 하면 RDS 스냅샷에서 복구하도록 README에 적었다.
