# 06. API Key 인증만 넣고 역할 기반 권한은 보류

> 메모: 환경변수가 있을 때만 동작하는 선택적 인증. 사용자 테이블·토큰 발급까지 가지 않은 이유를 정리

---

## 상황

인증이 전혀 없었다. 주소만 알면 누구나 회원을 등록하고 예약을 잡을 수 있었다.
EC2 퍼블릭 IP로 열려 있었으니 실제로 가능한 상태였다.

## 결정

`API_KEY` 환경변수가 **설정돼 있을 때만** 쓰기 요청(POST/PATCH)에 `X-API-Key`를 요구한다.
역할(관리자/트레이너/회원) 기반 권한 분리는 **하지 않는다.**

```python
def require_api_key(x_api_key: str | None = Header(default=None, alias="X-API-Key")) -> None:
    expected = os.getenv("API_KEY")
    if not expected:
        return  # 키 미설정 = 인증 비활성화
    if x_api_key is None or not hmac.compare_digest(x_api_key, expected):
        raise HTTPException(401, "유효한 X-API-Key 헤더가 필요합니다.")
```

## 왜

- **기존 배포와 로컬 개발, 부하 테스트 스크립트를 깨지 않는다.** 키를 설정하지 않으면 지금까지와 똑같이 동작하고, 설정하는 순간 쓰기가 잠긴다.
- 조회는 열어 뒀다. Swagger로 확인하는 용도가 이 프로젝트의 사용 방식이라서.
- `hmac.compare_digest`로 비교한다. 문자열 `==`는 앞에서부터 비교하다 다르면 멈춰서 응답 시간에 정보가 샌다.

## 왜 다른 건 안 썼나

**역할 기반 권한 (JWT 등)**

사용자 테이블, 비밀번호 해시, 토큰 발급·만료·갱신, 역할별 엔드포인트 분기까지 따라온다.
이 프로젝트의 주제는 DB 설계와 서버 운영이고, 인증 시스템을 얹으면 그 비중이 뒤집힌다.

**어설픈 자체 인증**

직접 만든 세션 관리나 토큰은 없느니만 못한 경우가 많다.
지금은 **"쓰기 잠금 하나"만 정확히 하고, 없는 건 없다고 README에 적는 쪽**을 택했다.

> 역할(관리자/트레이너/회원) 기반 권한 분리는 아직 없습니다.

**키를 필수로 만들기**

이미 도는 배포와 k6 스크립트가 전부 401을 받는다. 선택적으로 두고 켜는 쪽이 안전하다.

## 다시 한다면

역할 분리가 필요해지는 시점은 "트레이너가 자기 수업만 봐야 할 때"다.
그때는 `Trainer` 테이블에 로그인 정보를 붙이는 것부터 시작하면 된다.
