# 02. 같은 페이지네이션 버그를 세 곳에서 세 번 고쳤다

- **발생**: 2026-06-27 (2건, 커밋 `537cfa4` · `0101460`) → 2026-07-10 (1건, 커밋 `fbf87a5`)
- **증상 한 줄**: 에러가 안 난다. 엔드포인트가 조용히 빠지고 통계가 조용히 틀어진다

---

## 현상

셋 다 **증상이 없다.** 로그도 깨끗하고 응답도 200이다.

| # | 위치 | 무엇이 조용히 틀어지나 |
|---|---|---|
| 1 | `health_check` enumerator | 일부 엔드포인트가 **체크되지 않는다** |
| 2 | `register` `GET /endpoints` | 목록에 **일부가 안 나온다** |
| 3 | `report` 월별 리포트 | uptime% · 평균 응답시간 · 장애 건수가 **틀린 값으로 계산된다** |

## 환경

- DynamoDB `endpoints`(scan) / `check-history`(query, 파티션키 `endpoint_id` · 정렬키 `checked_at`)
- 헬스체크 1분 주기 → 엔드포인트 하나당 **하루 1,440건**, 한 달이면 **수만 건**

## 진단

### 1) DynamoDB 의 응답 한도

`scan` 과 `query` 는 **한 번에 최대 1MB** 만 돌려준다. 나머지가 있으면 응답에
`LastEvaluatedKey` 를 넣어 주고, 그걸 `ExclusiveStartKey` 로 넘겨 이어받아야 한다.

**넘겨받지 않으면 에러가 안 난다.** 그냥 첫 페이지만 돌려주고 정상 종료한다.
이게 이 버그의 성질 전부다 — **실패가 아니라 조용한 절단.**

```python
result = endpoints_table.scan()
endpoints = result.get("Items", [])     # 첫 페이지만. 에러 없음
```

### 2) 왜 안 보였나

엔드포인트 3개, 이력 며칠치로는 **1MB 근처에도 안 간다.** 개발 중에는 영원히 안 드러난다.
드러나는 시점은 **운영에서 데이터가 자란 뒤**고, 그때도 에러가 아니라 **숫자가 이상한** 형태로 온다.

### 3) 세 번째는 왜 3주 뒤에야 나왔나

6/27에 두 곳을 고치면서 **"이 버그를 고쳤다"고 생각했다.** 실제로 고친 것은
그때 눈에 들어온 두 곳이었고, `report` 는 그날 손대지 않은 파일이라 그대로 남았다.

`docs/upgrades/07` 이 이걸 그대로 적고 있다.

> `health_check` 와 `register` 의 목록 조회는 이미 페이지네이션이 되어 있는데
> (커밋 `0101460`, `537cfa4`) 리포트만 빠져 있었다. **같은 버그의 마지막 잔재다.**

그리고 리포트가 제일 아프다. 앞의 둘은 "일부가 빠진다"인데, **리포트는 틀린 숫자를
S3 에 영구 저장한다.** 나중에 보면 그게 정답인 줄 안다.

## 원인

`scan` / `query` 를 **한 번만 호출하고 첫 페이지만 사용했다.** 세 곳 모두 같은 형태.

## 해결

전부 같은 모양의 루프로 바꿨다.

```python
def _scan_all(table):
    items = []
    kwargs = {}
    while True:
        result = table.scan(**kwargs)
        items.extend(result.get("Items", []))
        last_key = result.get("LastEvaluatedKey")
        if not last_key:
            break
        kwargs["ExclusiveStartKey"] = last_key
    return items
```

`query` 쪽은 **조건은 유지하고 커서만 추가**해야 한다는 게 포인트다.

```python
def _query_all(table, **query_kwargs):
    kwargs = dict(query_kwargs)          # KeyConditionExpression 등 그대로
    while True:
        result = table.query(**kwargs)
        ...
        kwargs["ExclusiveStartKey"] = last_key    # 커서만 얹는다
```

테스트(`tests/test_report.py`)로 고정한 것

- `scan` 이 여러 페이지여도 전체 수집
- `query` 페이지네이션 시 `KeyConditionExpression` 이 유지되고 `ExclusiveStartKey` 만 추가되는지
- `get_stats` 가 **페이지를 합산해서** 통계를 계산하는지

## 재발 방지

- **`scan`/`query` 를 직접 부르지 않고 `_scan_all`/`_query_all` 을 쓴다.**
  `heartbeat` 를 새로 만들 때는 **처음부터** 이 형태로 썼다 (`_scan_all`, `_get_history`).
  이력 query 에는 `ProjectionExpression` 까지 붙여 페이지당 크기를 줄였다.
- 새 조회 경로를 추가할 때 **"이게 1MB 를 넘을 수 있나"를 먼저 묻는다.**
  1분 주기 데이터는 거의 항상 넘는다.

## 남아 있는 문제

**이 루프가 지금 네 곳에 복제돼 있다** — `report`·`heartbeat` 는 `_scan_all` 이라는 이름으로,
`health_check`·`register` 는 이름 없는 인라인 `while` 로. 람다별 zip 구조 때문에 공용 모듈을
안 쓴 결과다. → [결정 11](../decisions/11-로그-헬퍼를-핸들러마다-복제.md)

**그리고 `register` 의 `GET /endpoints` 는 전체를 다 반환한다.** 페이지네이션은 고쳤지만
**응답 크기 제한(limit/offset)은 없다.** 엔드포인트가 많아지면 이번엔 API 응답이 커진다.
[gym-management-db 트러블 03](../../gym-management-db/troubleshooting/03-GET-members-p95-2초.md) 에서
정확히 이 문제를 겪고 `limit` 기본 50 / 최대 200 을 넣었는데, **여기선 안 넣었다.**

## 배운 점

**같은 버그를 한 번 고쳤다고 다 고친 게 아니다.** 패턴 버그는 "이 파일에서 고쳤다"가 아니라
**"이 패턴을 쓰는 모든 자리"** 를 찾아야 끝난다. `grep -n "\.scan()\|\.query(" ` 한 번이면 3주가 안 걸렸다.

**에러를 안 내는 API 가 가장 위험하다.** 예외를 던졌으면 첫날 알았다.
DynamoDB 는 "여기까지가 1페이지"라고 성실하게 알려 주는데, **그걸 안 읽으면 알려 준 적이 없는 것과 같다.**

**틀린 숫자를 저장하면 그게 사실이 된다.** 앞의 두 건은 다음 사이클에 복구되지만
리포트는 S3 에 남는다. **집계 결과를 영구 저장하는 경로는 검증을 한 단계 더** 걸어야 한다.
