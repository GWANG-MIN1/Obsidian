# Troubleshooting

serverless-uptime-monitor 에서 실제로 막혔던 것들.
형식과 원칙은 [`../../../infra-lab/troubleshooting/README.md`](../../../infra-lab/troubleshooting/README.md) 와 같다.

```
## 현상       무엇이 어떻게 안 됐는가 (에러 메시지 원문 포함)
## 환경       재현에 필요한 최소 정보
## 진단       가설 → 검증 → 반증의 과정 (막다른 길도 남긴다)
## 원인       왜 그랬는가 (확인한 근거로)
## 해결       실제로 통한 명령·설정
## 재발 방지   다음에 안 겪으려면 무엇을 바꿔야 하는가
## 배운 점
```

## 이 프로젝트에서 특히 남길 만한 것

- **01** 이 이 저장소의 중심이다. **에러 없이 시스템이 멈췄고, 테스트 78개가 그걸 못 잡았고,
  잡은 것은 운영 중인 시스템이 스스로 보낸 알림**이었다.
- **02** 는 같은 버그를 **세 곳에서 세 번** 고친 기록이다. 한 번 고친 버그를 "고쳤다"고
  생각하는 것이 왜 위험한지에 대한 사례.
- **05** 는 밟기 전에 문서에 먼저 적어 둔 함정이다. 다른 노트들과 성격이 다르니 그렇게 표시해 뒀다.

## 이 저장소의 기록 방식

`docs/upgrades/` 에 개선 계획이 남아 있어서 **"무엇을 하려 했는가"는 되짚을 필요가 없었다.**
반면 **실패는 거의 안 적혀 있다** — 커밋 메시지에만 있고, 그중 상세한 것은 `5fd2795` 하나다.
그래서 아래 노트 대부분은 커밋 diff 와 코드에서 복원한 것이다.
→ [결정 10](../decisions/10-스켈레톤을-먼저-커밋하고-구현은-다음-날.md)

## 아직 안 쓴 소재

- `visibility_timeout 35초` 를 어떻게 정했나 — HTTP 타임아웃 10초와의 관계, 그리고 재배달
- `maxReceiveCount` 를 체크 큐 2 / 알림 큐 3 으로 다르게 준 것의 실제 효과 (아직 DLQ 가 빈 채)
- ruff 게이트를 켜면서 정리한 E501 과 import 순서 — 무엇이 걸렸는지 커밋에만 있음
