# 01. 헬스체크가 조용히 멈췄는데 DOWN 알림은 한 건도 없었다

- **발생**: 2026-08-01 (요약 알림 배포 직후 발견) · 커밋 `5fd2795`
- **증상 한 줄**: 엔드포인트 3개가 전부 `status: UP` 인데 체크가 며칠째 안 돌고 있었다

---

## 현상

[요약 알림](../decisions/05-요약-알림을-기존-알림-큐에-얹기.md)을 배포하고 첫 발송을 받았는데,
정상(`[OK]`)이 아니라 **경고**였다.

```
[WARN] Check Summary: 3/3 UP, 3 stale
```

`3/3 UP` 인데 `3 stale`. 전부 정상인데 전부 오래됐다.

- DynamoDB `endpoints` 의 `status` 는 세 건 다 `UP`
- `last_checked_at` 은 **며칠 전에 멈춰 있음**
- **DOWN 알림은 그동안 한 건도 안 왔다**
- CloudWatch 알람 `health_check_not_invoked` 는 **울지 않았다** — 호출은 되고 있었으니까

## 환경

- Lambda(Python 3.12) 6개, EventBridge `rate(1 minute)` → `health_check`(enumerator) → SQS → worker
- 테스트 78개가 전부 통과하는 상태
- 문제 구간: `health_check` 가 엔드포인트를 SQS 로 넘기는 부분

## 진단

### 1) DOWN 알림이 없다는 게 정상이 아니다

`status` 가 `UP` 이니 알림이 없는 건 코드상 맞다. 그런데 **`last_checked_at` 이 안 움직인다**는 건
worker 가 안 돈다는 뜻이고, 그러면 `status` 를 갱신하는 주체가 없다.

```
체크가 안 돈다
  → status 를 아무도 안 바꾼다
    → 마지막 성공값 UP 에 얼어붙는다
      → "전부 UP" 으로 보인다
        → 알림 로직은 전환이 없으니 아무것도 안 보낸다
```

**정상으로 보이는 것 자체가 증상**이었다.

### 2) worker 가 아니라 enumerator 다

`check_queue` 에 메시지가 안 들어오고 있었다. worker 는 받을 게 없어서 안 돈 것뿐이다.
→ 범인은 `health_check`.

### 3) enumerator 가 죽는 지점

```python
for endpoint in endpoints:
    sqs.send_message(
        QueueUrl=CHECK_QUEUE_URL,
        MessageBody=json.dumps(endpoint),      # ← 여기
    )
```

`endpoint` 는 **DynamoDB 에서 읽은 항목**이다. boto3 의 DynamoDB 리소스 인터페이스는
**숫자를 `Decimal` 로 돌려준다.** `json.dumps` 는 `Decimal` 을 직렬화하지 못한다.

```
TypeError: Object of type Decimal is not JSON serializable
```

### 4) 왜 처음부터 안 터졌나 — 이게 핵심이다

등록 직후의 엔드포인트에는 **숫자 필드가 하나도 없다.**

```python
item = {
    "id": ..., "url": ..., "name": ...,     # 전부 문자열
    "status": "UNKNOWN",
    "created_at": ...,
}
```

그래서 **첫 사이클은 성공한다.** 그런데 worker 가 한 번 돌면 숫자가 생긴다.

```python
":l": latency_ms,                # int → Decimal 로 저장
":cf": consecutive_failures,     # int → Decimal 로 저장
```

**다음 사이클부터 enumerator 가 전멸한다.** 정확히 첫 체크 이후부터.

### 5) 같은 파일에 정답이 이미 있었다

```python
def log_event(event, **fields):
    logger.info(json.dumps({"event": event, **fields}, default=str))   # ← 있다
...
        MessageBody=json.dumps(endpoint),                              # ← 없다
```

**같은 파일, 같은 함수 이름, 한쪽에만 `default=str`.**

## 원인

`json.dumps(endpoint)` 에 `default=str` 이 빠져서, DynamoDB 가 돌려준 `Decimal` 을
직렬화하지 못하고 enumerator 가 매 호출마다 예외로 죽었다.

**worker 를 분리한 것**([결정 01](../decisions/01-헬스체크를-enumerator와-worker로-분리.md))이
장애를 격리해 줄 거라 생각했는데, **enumerator 는 여전히 단일 장애점**이었다.
거기서 죽으니 전체가 멈췄고, 알림 경로는 "전환이 있을 때만" 동작하므로 **아무 소리도 안 났다.**

## 해결

```python
for endpoint in endpoints:
    # DynamoDB 는 숫자를 Decimal 로 돌려주고 json.dumps 는 이걸 직렬화하지 못한다.
    # default=str 이 없으면 첫 체크 이후(last_latency_ms / consecutive_failures 가
    # 생긴 뒤) 이 람다가 통째로 죽어 헬스체크 전체가 조용히 멈춘다.
    sqs.send_message(
        QueueUrl=CHECK_QUEUE_URL,
        MessageBody=json.dumps(endpoint, default=str),
    )
```

함께 넣은 테스트 2종 (`5fd2795`)

- **회귀 테스트** — `Decimal` 이 든 엔드포인트를 dispatch. 기존 테스트는 **문자열만 넣어** 검증해서
  이 경로를 한 번도 안 지나갔다.
- **계약 테스트** — `default=str` 을 쓰면 숫자가 **문자열로** worker 에 도착한다.
  worker 가 `int(endpoint.get("consecutive_failures") or 0)` 로 받는지 고정.

두 번째가 중요하다. **고친 방식이 다운스트림의 입력 타입을 바꾼다.**

## 재발 방지

- **테스트 픽스처를 실제 저장 형태로 만든다.** DynamoDB 를 흉내 내려면 숫자는 `Decimal` 이어야 한다.
  moto 통합테스트는 실제로 DynamoDB 를 거치므로 이 타입이 자연히 나온다 —
  단위 테스트의 손으로 만든 dict 가 문제였다.
- **`json.dumps` 로 DynamoDB 항목을 다룰 때는 `default=str` 을 기본으로.**
  지금 저장소의 모든 `json.dumps` 에 들어 있다.
- **"아무 일도 안 일어남"을 감지하는 층을 유지한다.** 이걸 잡은 건 알람이 아니라 요약 알림이었다.
  → [결정 06](../decisions/06-살아있음을-status-대신-신선도로.md)

## 아직 안 한 것

**enumerator 실패를 그 자체로 알리지 않는다.** `health_check_errors` 알람이 걸려 있어서
CloudWatch 는 감지했을 것이다. 그런데 그 알람 메일에서 *"람다 오류 1건"* 을 읽는 것과
*"지금 아무것도 감시되고 있지 않다"* 를 아는 것 사이에는 **사람의 해석 한 단계**가 있다.
그 해석을 시스템이 대신해 준 것이 `stale` 한 줄이었다.

**얼마나 오래 멈춰 있었는지 정확히 모른다.** `last_checked_at` 으로 며칠이라는 건 알지만,
CloudWatch 로그 보존이 14일이라 정확한 시작 시점을 확인하지 않았다.

## 배운 점

**모니터링 시스템의 최악은 장애를 놓치는 게 아니라, 장애를 못 보는 상태를 모르는 것이다.**
`status` 가 `UP` 인 것은 "지금 정상"이 아니라 **"마지막으로 확인했을 때 정상"** 이다.
그 "마지막"이 언제인지를 같이 보지 않으면 값이 거짓말을 한다.

**테스트는 내가 상상한 입력만 검증한다.** 테스트 78개가 전부 통과하는 상태에서 터졌다.
픽스처를 문자열로 만든 것은 편해서였고, 그 편의가 **실제 데이터 타입을 검증 범위 밖으로**
밀어냈다. [aws-serverless-agent 트러블 12](../../aws-serverless-agent/troubleshooting/12-재배포하니-전-요청이-500.md) 가
*"환경이 바뀌면 재현되지 않는다"* 였다면, 이건 **환경은 그대로인데 데이터가 자라서** 터졌다.

**같은 파일 안의 일관성은 검사되지 않는다.** `log_event` 에는 `default=str` 이 있고
바로 아래 줄에는 없었다. 사람 눈으로는 "같은 파일이니 같겠지"로 넘어간다.
