## 1단계 · 2026-05-14 ~ 05-16 — 뼈대와 데모 (커밋 9개)

이틀 만에 **서비스 전체가 한 번에** 올라간다. Terraform · Lambda 4개 · API Gateway ·
DynamoDB 2 테이블 · SQS · SNS · EventBridge.

```
EventBridge (1분)
      ↓
health_check ── 전 엔드포인트 순차 HTTP GET → history put → status update
      ↓  SQS alert_queue (UP→DOWN 전환 시)
alert ── Slack + SNS 이메일
```

- **5/14** 초기 구조, Terraform 백엔드 S3 버킷, 아키텍처 SVG
- **5/16** 헬스체크 에러 메시지 분기 → [트러블 03](troubleshooting/03-DNS-실패와-타임아웃이-같은-메시지.md),
  데모 스크린샷, 엔드포인트 현황 SVG

이 단계의 특징은 **테스트가 한 개도 없다는 것**이다. 그리고 이때 만든 `health_check` 가
"엔드포인트 N개를 하나의 Lambda 가 순차로" 도는 구조라 다음 단계에서 통째로 갈린다.

## 2단계 · 2026-06-20 ~ 06-27 — 입력검증·테스트, 그리고 fan-out 재설계 (커밋 14개)

5주 만에 돌아와서 두 가지를 한다. **둘 다 브랜치를 따로 파서 병합했다** — 이 저장소의 병합 커밋은 이 두 개가 전부고,
나머지 구간은 전부 `main` 에 직접 쌓였다.

**6/20 (커밋 6개, 브랜치 병합)** — 주니어 레벨 보강

- `POST /endpoints` 입력 검증 강화 (스킴 검사, 잘못된 JSON → 400, `name` 100자 제한)
- 리포트 통계 계산을 **순수 함수**(`compute_stats`)로 분리 → 테스트 가능한 형태로
- pytest 단위 테스트 도입, CI 에 `test` 잡 추가

순수 함수로 먼저 떼어낸 다음 테스트를 붙인 순서가 중요하다. 이 `compute_stats` 는
나중에 `heartbeat` 에도 그대로 쓰인다(복제해서).

**6/27 (커밋 8개, 브랜치 병합)** — 아키텍처 재설계

```
health_check (enumerator)  ── scan + SQS fan-out
      ↓  SQS check_queue
health_check_worker        ── 엔드포인트 1개씩 병렬 체크
      ↓  SQS alert_queue
alert
```

엔드포인트 N개 × 타임아웃 10초가 Lambda 하나의 실행시간에 그대로 쌓이는 문제를,
**시간을 늘리는 대신 일감을 쪼개는 쪽**으로 풀었다. → [결정 01](decisions/01-헬스체크를-enumerator와-worker로-분리.md)

같은 날 함께 한 것

- `scan` 페이지네이션 누락 수정 **2건** (`health_check`, `register`)
  → [트러블 02](troubleshooting/02-같은-페이지네이션-버그를-세-번.md)
- 테스트 확대 (health_check / worker / alert)
- CloudWatch 알람 5개 — DLQ 2, Lambda 오류 2, **"10분 이상 호출되지 않음" 1**
- 전 리소스 공통 태그

마지막 알람이 이 프로젝트의 주제를 미리 건드린다. **"에러가 났다"가 아니라 "아무 일도
안 일어났다"를 알람으로 잡으려는 시도**다 (`treat_missing_data = "breaching"`).
그런데 4단계에서 실제로 터진 조용한 실패는 이 알람이 아니라 요약 알림이 잡았다.
→ [결정 06](decisions/06-살아있음을-status-대신-신선도로.md)

## 4단계 · 2026-07-30 ~ 08-01 — 요약 알림, 그리고 그것이 실제 버그를 잡았다 (커밋 12개)

**7/30 (커밋 4개)** — upgrade-09, `heartbeat` 람다

*"슬랙이 조용할 때 그게 다 정상인지, 모니터가 죽은 건지 알 수 없다."*

새 람다 하나를 EventBridge 로 돌려 하루 1회 "N개 전부 UP" 요약을 **기존 알림 큐에 그대로**
흘려보낸다. SNS·Slack·IAM 은 손대지 않았다. → [결정 05](decisions/05-요약-알림을-기존-알림-큐에-얹기.md)

이때 넣은 것이 `stale` 판정이다. 엔드포인트가 전부 `UP` 으로 보여도 그건 **마지막으로 성공한
체크의 값**일 뿐이라, `last_checked_at` 신선도를 따로 본다.
→ [결정 06](decisions/06-살아있음을-status-대신-신선도로.md)

**7/31 (커밋 1개)** — README 에 `-> 검증 필요` 한 줄

이 커밋은 코드가 아니라 **"아직 확인 안 했다"는 메모**다. 실제 발송을 못 본 상태로
문서에 스크린샷을 넣지 않기 위해 남긴 표시고, 8/1에 확인한 뒤 지운다.
→ [트러블 06](troubleshooting/06-데모-이미지가-실물이-아니었다.md)

**8/1 (커밋 7개)** — 배포하고 봤더니

요약 알림이 `stale` 경고를 띄웠다. 엔드포인트 `status` 는 전부 `UP` 인데 체크가 안 돌고 있었다.

```
health_check 가 endpoints 를 json.dumps(endpoint) 로 SQS 에 넣는데
  → DynamoDB 숫자는 Decimal 로 돌아온다
    → TypeError 로 enumerator 가 통째로 죽는다
      → 체크가 안 도니 DOWN 알림도 안 나간다
        → status 는 마지막 성공값 UP 에 얼어붙어 있다
```

**DOWN 알림은 한 건도 발생하지 않았다.** 같은 파일의 `log_event` 에는 `default=str` 이
있는데 그 한 줄에만 빠져 있었다. → [트러블 01](troubleshooting/01-헬스체크가-조용히-멈췄다.md) ⭐

나머지 커밋은 그 결과를 문서에 반영한 것이다 — 목업 SVG 를 실제 스크린샷으로 교체,
옛 API 주소 갱신, `-> 검증 필요` 제거. → [트러블 06](troubleshooting/06-데모-이미지가-실물이-아니었다.md)
