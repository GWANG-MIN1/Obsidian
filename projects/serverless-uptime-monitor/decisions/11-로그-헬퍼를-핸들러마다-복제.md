# 11. 로그 헬퍼를 공용 모듈 대신 핸들러마다 복제

> 메모: 람다 6개가 **똑같은 6줄짜리 `log_event`** 를 각자 들고 있다.
> 의도한 중복이다. upgrade-08, 2026-07-10 커밋 `4a7afd8`

---

## 상황

이때까지 로그가 이랬다.

```python
print("Report saved: ...")
print("Slack notification failed: ...")
```

자유 문자열이라 CloudWatch 에서 **필터링·집계가 안 된다.**
"지난 1시간 동안 DOWN 이 몇 번이었나"를 물으려면 문자열 파싱을 해야 한다.

한 줄 JSON 으로 바꾸면 Logs Insights 로 바로 질의된다.

```
fields @timestamp, endpoint_id, status, latency_ms
| filter event = "check_result" and status = "DOWN"
| sort @timestamp desc
```

그런데 이 헬퍼를 **어디에 둘 것인가**가 문제였다.

## 결정

**각 핸들러 파일에 똑같은 헬퍼를 복사해 넣는다.**

```python
logger = logging.getLogger()
logger.setLevel(logging.INFO)


def log_event(event, **fields):
    """CloudWatch Logs Insights 로 질의하기 쉬운 한 줄 JSON 로그를 남긴다."""
    logger.info(json.dumps({"event": event, **fields}, default=str))
```

이 6줄이 `register` · `health_check` · `health_check_worker` · `alert` · `report` ·
`heartbeat` 에 **각각 들어 있다.**

남기는 이벤트는 문서에 표로 고정했다.

| 핸들러 | event | 주요 필드 |
|---|---|---|
| health_check | `dispatch` | dispatched |
| health_check_worker | `check_result` | endpoint_id, status, status_code, latency_ms |
| health_check_worker | `alert_dispatched` | endpoint_id, event_type, failure_count / downtime_seconds |
| alert | `sns_published` / `slack_sent` / `slack_failed` | endpoint_id, event_type, error |
| register | `endpoint_created` / `register_blocked` | endpoint_id, url, reason |
| report | `report_saved` | bucket, key, month, endpoint_count |
| heartbeat | `summary_dispatched` | total, up, down, stale, uptime_pct |

## 왜

- **람다가 디렉터리별로 따로 zip 된다.** `terraform/lambda.tf` 가 `lambda/<name>/` 을 각각
  아카이브한다. 공용 모듈을 `lambda/common/` 에 두면 **각 zip 에 넣는 배선을 추가로** 짜야 한다.
- **6줄이다.** 중복 제거의 이득보다 배선의 비용이 크다.
  DRY 를 지키는 비용이 위반하는 비용보다 크면 위반하는 쪽이 맞다.
- **핸들러 파일 하나가 자기 완결적이다.** `conftest.py` 가 `handler.py` 를 경로로 직접 로드하는
  테스트 구조와도 맞는다 → [트러블 05](../troubleshooting/05-moto-테스트가-테이블을-못-찾는다.md)
- **`default=str` 이 여기 들어 있다.** 이게 나중에 결정적이 된다 —
  같은 파일의 `json.dumps` 다른 한 줄에는 이게 **없어서** 헬스체크가 통째로 멈췄다.
  → [트러블 01](../troubleshooting/01-헬스체크가-조용히-멈췄다.md)

## 왜 다른 건 안 썼나

**Lambda Layer 에 공용 모듈**

정석이다. 그런데 Layer 하나를 만들고, 6개 람다에 붙이고, 버전을 관리해야 한다.
**6줄을 위해 배포 단위를 하나 더 만드는 것**이 이 규모에서 맞지 않았다.

**`lambda/common/` 을 각 zip 에 포함**

`archive_file` 의 `source_dir` 을 바꾸거나 빌드 스텝을 넣어야 한다.
빌드 스텝이 생기면 **로컬 배포와 CI 배포가 갈라진다** — 지금은 둘 다 `terraform apply` 하나다.

**`aws-lambda-powertools` 같은 라이브러리**

구조적 로깅·메트릭·트레이싱을 다 준다. 대신 **의존성 설치와 패키징**이 붙는다.
지금 6개 람다 전부 **표준 라이브러리 + boto3(런타임 제공)** 만 쓰고 있어서
`pip install` 이 들어가는 빌드가 아예 없다. 그 상태를 유지하는 게 더 값졌다.

## 이 결정의 대가

**복제된 것이 `log_event` 만이 아니다.**

`compute_stats` 가 `report` 와 `heartbeat` 양쪽에 **거의 같은 코드로** 들어 있다.
같은 `scan` 페이지네이션이 **네 곳**에 있다 — `report` 와 `heartbeat` 는 `_scan_all` 이라는
이름으로, `health_check` 와 `register` 는 이름 없는 인라인 `while` 루프로.
`_parse_iso` 는 `worker` 와 `heartbeat` 에 있고 **구현이 서로 다르다** —
`heartbeat` 쪽만 tz-naive 를 UTC 로 보정한다.

6줄짜리 헬퍼를 복제하는 것과 **집계 로직을 복제하는 것은 다른 판단이어야 했다.**
`incidents` 를 전환 기준으로 고치려면 지금 두 곳을 같이 고쳐야 한다
(→ [README 아직 안 한 것](../README.md#아직-안-한-것과-이유)).

## 배운 점

**"공유하지 않는다"는 결정에도 범위가 있다.**
배선 비용 때문에 복제를 고른 것은 맞지만, 그 판단을 **파일 안의 모든 중복에 자동으로
확장**해 버렸다. 복제해도 되는 것(포맷 헬퍼)과 복제하면 안 되는 것(집계 규칙)은 다르다.
