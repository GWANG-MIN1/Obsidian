# 06. 살아있음 판정을 status 대신 last_checked_at 신선도로

> 메모: 전부 `UP` 인데 체크가 안 돌고 있을 수 있다. `status` 는 **마지막으로 성공한
> 체크의 값**이지 지금의 값이 아니다. upgrade-09, 2026-07-30

---

## 상황

[결정 05](05-요약-알림을-기존-알림-큐에-얹기.md) 의 요약 알림을 만들면서, "전부 정상"을
무엇으로 판정할지 정해야 했다. 가장 자연스러운 답은 테이블에 이미 있는 값이다.

```python
healthy = all(e["status"] == "UP" for e in endpoints)
```

여기에 함정이 있다. **`status` 는 마지막으로 기록에 성공한 체크의 결과다.**
체크가 아예 안 돌면 이 값은 **갱신되지 않고 그대로 있는다.**

```
헬스체크 파이프라인 정지
  → status 를 아무도 안 바꾼다
    → 마지막 성공값 "UP" 에 얼어붙는다
      → "전부 UP" 이라고 보고한다     ← 최악
```

**모니터가 죽으면 모니터가 "다 정상"이라고 말한다.**

## 결정

`status` 를 믿지 않고 **`last_checked_at` 의 나이**를 따로 검사한다.

```python
STALE_AFTER_MINUTES = max(int(os.environ.get("STALE_AFTER_MINUTES", "10")), 1)

def is_stale(last_checked_at, now):
    """마지막 체크가 임계시간을 넘겼는지. 값이 없거나 깨졌으면 stale 로 본다."""
    checked = _parse_iso(last_checked_at)
    if checked is None:
        return True
    return (now - checked).total_seconds() > STALE_AFTER_MINUTES * 60
```

그리고 정상 판정에 **and 조건으로 넣는다.**

```python
healthy = down == 0 and stale == 0 and up == total
```

- 임계값은 **체크 주기 × 10** (1분 주기 → 10분). 한두 번 밀린 것은 stale 이 아니다.
- **파싱 실패도 stale 로 본다.** 값이 없거나 깨졌다는 것은 "확인할 수 없다"이지 "정상"이 아니다.
- stale 은 **DOWN 과 따로 센다.** 메시지에 `2/3 UP, 1 stale` 처럼 나온다 —
  엔드포인트가 죽은 것과 모니터가 죽은 것은 대응이 다르기 때문이다.

## 왜

- **`status` 는 상태가 아니라 관측 기록이다.** 마지막 관측이 언제였는지를 같이 보지 않으면
  그 값이 지금도 유효한지 알 수 없다. 이건 모니터링 전반에 걸린 이야기다 —
  Prometheus 의 `up` 과 스크레이프 시각을 같이 보는 것과 같은 구조다.
- **없는 값을 정상으로 치면 안 된다.** `last_checked_at` 이 없는 상태(등록 직후, 혹은
  체크가 한 번도 성공 못 함)를 "아직 모름"으로 넘기면 **새로 등록한 엔드포인트가
  영원히 정상으로 보고**된다. 그래서 `None → stale = True` 다.
- **모르는 것을 모른다고 말하는 쪽이 안전하다.** 오탐(정상인데 stale) 의 대가는
  "확인해 봤더니 괜찮더라"이고, 미탐의 대가는 [트러블 01](../troubleshooting/01-헬스체크가-조용히-멈췄다.md) 이다.

## 왜 다른 건 안 썼나

**CloudWatch `Invocations < 1` 알람만으로**

이미 있다 (`health_check_not_invoked`, `treat_missing_data = "breaching"`).
하지만 **호출됐는지만 본다.** 호출된 뒤 안에서 예외로 죽는 경우는 못 잡는다.
2026-08-01에 실제로 터진 것이 정확히 그 경우였고, 이 알람은 **울지 않았다** —
enumerator 는 1분마다 정상적으로 호출되고 있었다.

**`Errors` 알람만으로**

이건 울었을 것이다. 하지만 CloudWatch 알람 메일에서 *"람다에 오류가 있다"* 를 읽는 것과,
*"헬스체크가 통째로 멈춰서 지금 아무것도 감시되고 있지 않다"* 를 아는 것 사이에는
**사람의 해석 한 단계**가 있다. 요약 알림의 `stale` 은 그 해석을 미리 해서 문장으로 준다.

**히스토리 테이블의 최신 행 시각을 쓴다**

더 정확하다 — `last_checked_at` 은 `endpoints` 테이블 갱신이 성공해야 찍히는데,
히스토리 put 은 성공하고 update 만 실패하는 경우를 잡을 수 있다.
대신 **엔드포인트마다 query 가 한 번 더** 늘고, 요약 람다는 이미 기간 내 이력을 다 읽고 있다.
지금 구조에서 그 정도 정밀도는 과했다.

## 결과

**배포 첫날 이걸로 실제 장애를 잡았다.** 엔드포인트 3개가 전부 `status: UP` 인데
`last_checked_at` 이 며칠 전에 멈춰 있었다. DOWN 알림은 한 건도 없었다.
→ [트러블 01](../troubleshooting/01-헬스체크가-조용히-멈췄다.md)

## 배운 점

**"괜찮아 보인다"와 "확인했다"는 다르다.**
값이 정상 범위에 있는 것과, 그 값이 방금 갱신된 것은 별개의 사실이고
**둘 다 확인해야 정상이라고 말할 수 있다.**

이 원칙은 코드 밖에도 적용된다. [gym-management-db 트러블 03](../../gym-management-db/troubleshooting/03-GET-members-p95-2초.md) 의
*"그럴듯한 원인을 검증 없이 적으면 그게 기록으로 남는다"* 와 같은 종류의 실수를,
여기선 **시스템이 스스로 하지 않게** 만든 것이다.
