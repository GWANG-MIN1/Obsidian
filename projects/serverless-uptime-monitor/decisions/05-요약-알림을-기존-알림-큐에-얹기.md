# 05. 요약 알림을 새 배선 대신 기존 알림 큐에 얹기

> 메모: "슬랙이 조용한 게 정상인지 모니터가 죽은 건지 모르겠다"에서 시작.
> upgrade-09, 2026-07-30 커밋 `3ae869d` · `681c353`

---

## 상황

이 시점까지 알림은 **`DOWN` 과 `RECOVERED` 때만** 나갔다. 사고 없이 며칠이 지나면
슬랙 채널이 조용하다. 그런데 그 조용함이 두 가지를 동시에 뜻한다.

```
채널이 조용하다
  ├─ 다 정상이다                        (좋다)
  └─ 모니터가 죽어서 아무것도 못 보낸다    (최악)
```

**둘을 구분할 방법이 없다.** 모니터링 시스템에서 가장 위험한 실패 모드다.
그리고 이건 가정이 아니라 **일주일 뒤 실제로 일어났다**
→ [트러블 01](../troubleshooting/01-헬스체크가-조용히-멈췄다.md)

## 결정

주기적으로 **"지금 N개 전부 UP"** 요약을 보내 **정상임을 능동적으로 증명**한다
(dead man's switch — 올 시간에 안 오면 그 자체가 이상 신호).

구현은 **새 배선을 하나도 안 만드는 쪽**으로 했다.

```
EventBridge cron(0 23 * * ? *)   ← KST 08:00
      ↓
heartbeat Lambda ── endpoints scan + 기간 내 history query
      ↓  SQS alert_queue   (event_type: "SUMMARY")
alert Lambda ── Slack / SNS      ← 기존 그대로
```

- **SNS Topic · Slack Webhook · IAM 정책을 하나도 안 건드렸다.**
  `alert` 람다에 `SUMMARY` 포맷 분기만 추가.
- 판정: 정상(`good`/`[OK]`)은 `down == 0` **and** `stale == 0` **and** `up == total` 일 때만.
  하나라도 어긋나면 주의(`warning`/`[WARN]`).
- **엔드포인트가 0개여도 요약을 보낸다.** 목적이 엔드포인트 보고가 아니라
  **파이프라인 생존 신호**이기 때문이다.

## 왜

- **[결정 02](02-알림을-SQS-큐-경유로.md) 가 여기서 값을 치렀다.** 알림을 큐 뒤에 둔 덕분에
  새 알림 종류가 **메시지 타입 하나**로 들어왔다. `terraform/sns.tf` 는 9줄이고 안 바뀌었다.
- **집계 기간과 발송 주기를 변수로 묶었다.** `SUMMARY_PERIOD_HOURS`(기본 24)와
  `summary_schedule_expression`(기본 일 1회)을 맞춰야 한다는 것을 변수 설명에 적어 뒀다.
  6시간마다 보내려면 둘 다 바꾼다.
- **읽기를 아꼈다.** 통계에 쓰는 두 필드만 `ProjectionExpression` 으로 투영한다.

  ```python
  "ProjectionExpression": "#s, latency_ms",
  "ExpressionAttributeNames": {"#s": "status"},
  ```

  1분 주기 × 24시간 = 엔드포인트당 1,440건이라 `query` 한 페이지(1MB)를 넘을 수 있어
  **여기도 페이지네이션을 처음부터 넣었다** → [트러블 02](../troubleshooting/02-같은-페이지네이션-버그를-세-번.md)

## 왜 다른 건 안 썼나

**매 체크마다 UP 알림을 보낸다**

가장 확실한 생존 신호다. 그리고 **못 쓴다** — 1분 주기 × 엔드포인트 3개면 하루 4,320건이다.
알림 피로로 정작 중요한 DOWN 을 놓친다. [결정 04](04-알림-상태를-raw-status와-분리.md) 에서
flap 을 막은 것과 **완전히 같은 이유**다. 요약은 반드시 **낮은 빈도 + 집계** 형태여야 한다.

**요약용 SNS Topic / Slack 채널을 따로 판다**

장애 알림과 요약이 섞이지 않아 깔끔해 보인다. 그런데 **채널이 나뉘면 요약 채널을 안 보게 된다.**
"안 온 것을 알아채는" 것이 목적인데, 안 보는 채널에서는 안 온 것을 못 알아챈다.
같은 채널에 있어야 매일 아침 한 줄이 눈에 밟힌다.

**CloudWatch 알람만으로 (Invocations < 1)**

이미 있다 — `health_check_not_invoked` 알람이 `treat_missing_data = "breaching"` 으로
10분간 호출이 없으면 운다 ([타임라인 2단계](../타임라인.md)). 이것도 dead man's switch 다.

그런데 **한 층 얕다.** 이 알람은 *"람다가 호출됐는가"* 만 본다.
호출됐는데 **안에서 죽는 경우는 못 잡는다.** 실제로 터진 것이 정확히 그거였다 —
enumerator 는 EventBridge 에 의해 1분마다 정상 호출됐고, 그때마다 예외로 죽었다.
`Errors` 알람도 걸려 있었지만 **알람이 SNS 로 보낸 메일과 "체크가 멈췄다"를 잇는 것은
결국 사람이 하는 일**이었고, 그 연결을 해 준 것이 요약 알림의 `stale` 한 줄이었다.
→ [결정 06](06-살아있음을-status-대신-신선도로.md)

**외부 dead man's switch 서비스 (healthchecks.io 등)**

정석이다. **"모니터를 모니터하는 것이 같은 계정 안에 있으면 같이 죽는다"**는 문제를
실제로 푸는 유일한 방법이기도 하다. 학습 프로젝트 범위에서 외부 SaaS 의존을 안 넣었다.
**이건 남은 구멍이다** — AWS 계정 전체나 리전이 죽으면 요약 알림도 같이 안 온다.
그때 "안 왔다"를 알아챌 사람이 있어야 한다는 것에 여전히 기대고 있다.

## 결과

헬스체크 전면 중단**을 드러냈다. → [트러블 01](../troubleshooting/01-헬스체크가-조용히-멈췄다.md)
