# 03. 체크 이력을 배치 삭제 대신 DynamoDB TTL 30일로

> 메모: 1분 주기 × 엔드포인트 N개 = 하루 1,440 × N 건. 지우지 않으면 무한히 쌓인다.
> `expires_at` 속성 + `ttl { enabled = true }`. 1단계(2026-05-14)부터.

---

## 상황

`check-history` 테이블은 **엔드포인트 하나당 하루 1,440건**이 쌓인다.
`PAY_PER_REQUEST` 라 쓰기 요금은 건당이지만, **저장 용량은 지운 만큼만 줄어든다.**
그리고 이 데이터는 오래될수록 쓸모가 급격히 준다 — 3개월 전 응답시간을 볼 일이 없다.

## 결정

put 할 때 **행마다 만료 시각을 같이 넣는다.** 삭제는 DynamoDB 가 한다.

```python
TTL_DAYS = 30
expires_at = int((now + timedelta(days=TTL_DAYS)).timestamp())

history_table.put_item(Item={
    "endpoint_id": endpoint_id,
    "checked_at": now.isoformat(),
    ...
    "expires_at": expires_at,      # ← epoch 초. 이 필드가 TTL 속성
})
```

```hcl
ttl {
  attribute_name = "expires_at"
  enabled        = true
}
```

## 왜

- **삭제 비용이 0이다.** TTL 삭제는 쓰기 용량을 소비하지 않는다.
  배치 삭제 람다를 돌리면 그 삭제가 전부 과금되는 쓰기다.
- **지울 코드가 없다.** 삭제 람다, 그 람다의 스케줄, 그 람다의 IAM, 그 람다의 실패 알람이
  전부 안 생긴다. 대신 **put 하는 쪽에서 한 줄** 늘어난다.
- **행마다 수명을 따로 줄 수 있다.** 지금은 전부 30일이지만, 나중에 DOWN 기록만 더 오래
  남기고 싶으면 `expires_at` 계산만 바꾸면 된다. 배치 삭제였다면 쿼리 조건이 복잡해진다.
- **월별 리포트가 S3 에 남는다.** 원본 이력이 사라져도 집계 결과(`reports/YYYY-MM.json`)는
  S3 에 영구히 있다. 오래된 데이터를 "요약해서 옮기고 원본은 버린다"는 형태다.

## 왜 다른 건 안 썼나

**EventBridge + 삭제 람다로 배치 삭제**

지워야 할 행을 먼저 **찾아야** 한다. `checked_at` 은 정렬키지만 파티션키가 `endpoint_id` 라
"전체에서 30일 지난 것"을 뽑으려면 엔드포인트를 순회해야 한다. 그리고 삭제가 전부 과금된다.

**S3 로 내보내고 테이블은 비우기**

이 규모에서 과하다. 그리고 리포트가 이미 그 역할을 한다.

**아예 안 지운다**

`PAY_PER_REQUEST` 라 쓰기 비용은 같지만 저장 용량이 계속 늘고, 무엇보다
**`query` 범위가 넓어지면 리포트가 느려진다.** 리포트는 이미 페이지네이션으로
수만 건을 훑는다 → [트러블 02](../troubleshooting/02-같은-페이지네이션-버그를-세-번.md)

## 이 결정이 남긴 구멍 *(이 노트를 쓰며 코드에서 찾은 것 — 아직 안 고침)*

**월별 리포트와 30일이 안 맞는다.**

리포트는 `cron(0 0 1 * ? *)` — 매달 1일 00:00 UTC 에 돌면서 **전월 1일 ~ 당월 1일**을 집계한다.

```
7월 1일 00:05 의 체크  →  expires_at = 7월 31일 00:05
리포트 실행           →  8월 1일 00:00
                          ↑ 이미 만료 시각을 지났다
```

31일인 달(1·3·5·7·8·10·12월)은 **월초 이력이 리포트가 도는 시점에 이미 만료 대상**이다.
DynamoDB TTL 삭제는 만료 후 보통 48시간 이내에 일어나므로 **운이 좋으면 남아 있고 아니면 없다.**
남아 있어도 그건 우연이지 보장이 아니다.

지금까지 티가 안 난 이유는 단순하다 — **한 달을 꽉 채워 돌려 본 적이 없다.**
그리고 이 버그도 [트러블 02](../troubleshooting/02-같은-페이지네이션-버그를-세-번.md) 처럼
**에러 없이 숫자만 틀리는** 종류다.

고치는 방법은 둘 중 하나.

- `TTL_DAYS` 를 35로 (리포트 실행까지의 여유를 준다)
- 리포트를 매달 1일이 아니라 2~3일에 (TTL 삭제 지연에 기대게 되므로 위쪽이 낫다)

## 배운 점

**TTL 은 "이 시각에 사라진다"가 아니라 "이 시각 이후 언젠가 사라진다"다.**
삭제 지연을 관대함으로 받아들이면 이번처럼 **경계를 우연에 맡기게** 된다.
데이터 수명과 그 데이터를 읽는 배치의 주기는 **같이 설계해야 한다.**
